## Task

The task given to every model in this cohort:

You're writing a compliance-audit query against a USDA-inspected poultry plant's
lot-tracking database (PostgreSQL). Schema:

- `lots(lot_id INT PRIMARY KEY, product_line VARCHAR, production_date DATE)`
- `scan_events(event_id INT PRIMARY KEY, lot_id INT REFERENCES lots(lot_id),
  station VARCHAR, scanned_at TIMESTAMP)`
- `recalls(recall_id INT PRIMARY KEY, lot_id INT REFERENCES lots(lot_id),
  recall_date DATE, reason VARCHAR)`

USDA rules require every lot to have at least 3 recorded scan checkpoints (intake,
processing, shipping). A lot with fewer than 3 scan_events rows is a documentation gap that
is itself a compliance finding, even if the lot was never recalled and the product shipped
fine.

Write a single SQL query that returns every lot produced in the last 24 months that has:
(a) zero matching rows in `recalls`, AND (b) fewer than 3 rows in `scan_events` -- including
lots with ZERO scan_events at all, which is the worst version of this gap. Return
`lot_id`, `product_line`, `production_date`, and the scan-event count, ordered by
`production_date` ascending (oldest gap first).

```sql
SELECT
    l.lot_id,
    l.product_line,
    l.production_date,
    COUNT(se.event_id) AS scan_event_count
FROM lots l
LEFT JOIN scan_events se
    ON l.lot_id = se.lot_id
WHERE
    l.production_date >= CURRENT_DATE - INTERVAL '24 months'
    AND NOT EXISTS (
        SELECT 1
        FROM recalls r
        WHERE r.lot_id = l.lot_id
    )
GROUP BY
    l.lot_id,
    l.product_line,
    l.production_date
HAVING
    COUNT(se.event_id) < 3
ORDER BY
    l.production_date ASC;
```

### Key Logic Explained

*   **`LEFT JOIN scan_events`**: Ensures lots with **zero** scan events are included in the result set. A `LEFT JOIN` preserves the lot row even when no matching scan events exist, allowing `COUNT(se.event_id)` to return `0` (which triggers the `< 3` gap finding).
*   **`COUNT(se.event_id)`**: Used instead of `COUNT(*)`. Since `event_id` is `NULL` for unmatched `LEFT JOIN` rows, `COUNT` ignores them, accurately reflecting the actual number of checkpoints recorded (0, 1, or 2).
*   **`NOT EXISTS (recalls)`**: Excludes any lot that has been associated with a recall record, satisfying condition (a).
*   **`HAVING COUNT(se.event_id) < 3`**: Filters the grouped results to only include documentation gaps (fewer than the required 3 checkpoints), satisfying condition (b).
*   **`CURRENT_DATE - INTERVAL '24 months'`**: Restricts the audit window to the last 24 months.

```sql
SELECT
    l.lot_id,
    l.product_line,
    l.production_date,
    COUNT(se.event_id) AS scan_count
FROM lots l
LEFT JOIN scan_events se ON se.lot_id = l.lot_id
LEFT JOIN recalls r ON r.lot_id = l.lot_id
WHERE l.production_date >= CURRENT_DATE - INTERVAL '24 months'
  AND r.recall_id IS NULL
GROUP BY l.lot_id, l.product_line, l.production_date
HAVING COUNT(se.event_id) < 3
ORDER BY l.production_date ASC;
```

Why LEFT JOIN, not INNER JOIN, on `scan_events`: an INNER JOIN would require at least one
matching scan_events row to keep a lot in the result at all, so a lot with ZERO scan events
-- the worst version of the documentation gap this query is supposed to find -- would be
silently dropped entirely instead of surfaced. LEFT JOIN keeps every lot in `lots` regardless
of whether it has scan events, and `COUNT(se.event_id)` correctly returns 0 for a lot with no
matching rows (COUNT of a column ignores NULLs, so an unmatched LEFT JOIN row counts as 0,
not 1).

Why HAVING, not WHERE, for the scan-count filter: `COUNT(se.event_id)` is an aggregate that
isn't computed until after grouping; WHERE clauses are evaluated before GROUP BY/aggregation,
so `WHERE COUNT(...) < 3` is invalid SQL. The count filter has to go in a HAVING clause, which
runs after the GROUP BY aggregates the rows.

The "not recalled" condition is also a LEFT JOIN/anti-join pattern (`LEFT JOIN recalls r ...
WHERE r.recall_id IS NULL`) for the same reason -- an INNER JOIN to recalls would only keep
lots that already have a recall, the opposite of what's needed.
