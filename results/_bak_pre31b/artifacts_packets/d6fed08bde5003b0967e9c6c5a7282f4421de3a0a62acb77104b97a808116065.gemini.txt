## 10 -- Frontier
Triage priority matches the actual business impact described, and the response tone is consistent with the urgency that priority implies. Troubleshooting steps are ordered from least to most disruptive, a clear escalation path is given for when the fix is out of the agent's scope, and the answer is calibrated about what genuinely needs remote hands or an on-site visit.
Example character: a triage call that matches the stated impact, a non-disruptive-first troubleshooting sequence, and a named escalation trigger.

## 7 -- Strong
The troubleshooting sequence is usable and the priority call is correct, but the escalation path or SLA framing is a light miss -- present but not fully specified. Nothing here jumps to a disruptive step too early.
Example character: a correct non-disruptive troubleshooting sequence with no stated escalation trigger if it fails.

## 5 -- Adequate
The response is a generic troubleshooting checklist (restart, check cables, reinstall) not tied to the specific symptom or business impact described in the ticket.
Example character: standard first-line steps offered without adapting to the reported symptom.

## 3 -- Weak
The priority or severity call is wrong relative to the stated impact, or the response skips straight to a disruptive fix (reimage, factory reset) without trying non-disruptive steps first, with no escalation path given.
Example character: recommends reimaging a device as the first step for a minor, non-blocking symptom.

## 0 -- Unusable
Recommends a data-destructive action (wipe, reformat, delete profile) with no backup step or warning, or fabricates vendor or product behavior presented as known fact. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Destructive troubleshooting step (reimage, factory reset, delete profile) recommended before non-disruptive steps, or with no backup warning.
- Priority/SLA call that does not match the stated business impact.
- No escalation path given when the issue is clearly out of scope.
- Fabricated product or vendor behavior presented as known fact.

## Unit-specific excellence markers
- Triage priority matches the stated business impact.
- Troubleshooting steps ordered least-to-most disruptive.
- Explicit escalation trigger and path given.
- SLA/urgency framing consistent with the ticket's actual severity.

*   **Action:** The IT Support team initiates a voice call to the drilling rig using the site's dedicated landline or satellite voice phone.
*   **Rationale:** Voice traffic is significantly lower bandwidth than data/telemetry and is often prioritized or independent of SCADA congestion. This ensures the call connects despite the VSAT saturation.
*   **Mutual Identification:** The IT agent confirms their identity using a known number, and the technician confirms their identity by verifying the agent's call reason and agent ID.

#### 2. Identity Verification (Out-of-Band)
Since standard factors are unavailable, verification relies on **Challenge-Response** and **Contextual Knowledge-Based Authentication (KBA)** over the voice channel. This prevents social engineering and verifies the user is physically at the site.

*   **Step A: Contextual Verification:**
    *   The IT agent asks specific questions that only the authenticated technician would know, tied to the specific rig and current operation.
    *   *Examples:* "State the name of the active well and the shift supervisor," "Recite the unique serial number of the rig's primary telemetry antenna," or "Describe the specific drill bit configuration currently in use."
    *   *Goal:* Proves the caller has access to the specific environment and role.
*   **Step B: Challenge-Response Protocol:**
    *   The IT agent generates a random alphanumeric code (e.g., `X7-9K-P2`) and reads it to the technician.
    *   The technician must immediately repeat the code back to the agent.
    *   *Goal:* Verifies the technician is actively listening, is in real-time, and controls the communication channel. This mitigates risks of a compromised rig phone or an impersonator.
*   **Step C: Physical Artifact Check (Optional but Recommended):**
    *   If the rig phone supports video or the agent requests, the technician may be asked to display a physical item visible only to the rig staff, such as the unique rig ID plaque or a specific regulatory placard, to confirm physical location.

#### 3. Account Recovery Execution
Once identity is verified, the IT agent performs the recovery using the **Support Administrator** portal. This does not disable MFA; it utilizes a temporary, high-assurance fallback factor.

*   **Action:** The agent generates a **One-Time Password (OTP)** specific to the user's account.
*   **Delivery:** The agent reads the OTP over the voice channel to the technician.
*   **Usage:** The technician logs into their corporate laptop, enters the MFA challenge, and inputs the OTP provided by support.
*   **Constraints Check:**
    *   *MFA is not disabled:* The account remains protected; the OTP is a single-use exception that does not alter MFA policy.
    *   *No generic credentials:* The OTP is cryptographically bound to the specific user account.

## 2.  Identity‑verification & recovery flow that meets the constraints  

Below is a step‑by‑step “break‑glass” path that:

* **Never disables MFA** for the account.  
* **Never issues a generic password**.  
* **Uses only out‑of‑band, non‑SMS, non‑push factors** that are already registered for the user.  
* Leaves a **full audit trail** for later review.

### 2.1  Preconditions (already in place for every field technician)

| Item | How it is provisioned | Why it helps here |
|------|----------------------|-------------------|
| **Hardware security key (e.g., YubiKey 5 Series)** | Issued during onboarding; registered to the corporate Azure AD / Okta account as a **FIDO2 security key**. | The key can generate a **cryptographic signature** locally; no network is required. |
| **Recovery‑code list (10 one‑time use codes)** | Printed on a secure, tamper‑evident card and stored in the technician’s personal “field‑kit” (the same kit that contains the hardware key). | Each code is single‑use and can be entered manually when the normal MFA path is unavailable. |
| **Pre‑shared “security‑question seed”** | A unique, user‑specific phrase (e.g., “The name of the first well you spudded in West Texas”) that was set up in the IAM system and stored in a secure vault. | Provides a knowledge‑factor that can be verified over a voice call. |
| **Designated “break‑glass” secure voice channel** | A satellite phone number (or a satellite‑enabled radio) that dials a **SOC “Identity‑Verification Hotline”** (the number is stored in the corporate emergency‑contact list). | Allows a human analyst to confirm identity without any data connection. |
| **Audit‑ticketing system** (e.g., ServiceNow, JIRA) | All break‑glass events must be recorded in a **“MFA‑Recovery”** issue type with mandatory fields. | Guarantees documentation. |

> **Note:** All of the above must already be registered *before* the incident. The recovery procedure never creates new credentials on the spot; it only **activates** something that was pre‑registered.

### 2.2  The actual recovery steps (executed on‑site)

| Step | Action | What it proves | How it is done without SMS/push |
|------|--------|----------------|--------------------------------|
| **1 – Initiate a secure voice call** | Technician picks up the satellite phone and dials the SOC “Identity‑Verification Hotline” (the number is stored on the field‑kit). | *Possession of a known, secure voice channel* and *knowledge of the correct dial‑in number*. | No data connection required; the call is routed over the satellite voice link. |
| **2 – Human verification** | SOC analyst asks the **seed‑question** (e.g., “What was the name of the first well you spudded in West Texas?”). The technician answers correctly. | *Knowledge factor* – only the legitimate user should know the exact seed phrase. | This step is performed entirely over voice; no network payload. |
| **3 – Challenge with a one‑time “recovery code”** | Analyst reads back a **pre‑generated, single‑use recovery code** that was previously stored in the IAM vault for that user (e.g., “Code 7F9B‑3C2E”). The technician enters that code on the corporate laptop’s MFA prompt (the prompt now accepts a *manual* OTP). | *Possession of a recovery code that was issued only to that account*. | The code is typed on the laptop’s local keyboard; it does **not** require network connectivity to validate because the SOC analyst has already verified the user’s identity and will manually approve the login in the backend. |
| **4 – Insert hardware security key** | Technician plugs the registered YubiKey into the laptop’s USB port and touches the gold contact. The laptop presents a **FIDO2 assertion** to the authentication service. | *Possession of the registered hardware token* that can produce a cryptographic signature. | No network traffic is needed from the device; the key signs a challenge that the authentication service can verify offline (the signature is validated by the IAM service when the device later contacts the server via satellite). |
| **5 – Successful login** | After the FIDO2 assertion is accepted **and** the recovery code has been recorded as “used”, the user is logged into the corporate laptop. | *Two‑factor proof*: **something you have** (the hardware key) + **something you know** (the seed phrase) + **something you possess** (the recovery code). | The login is now possible even though the satellite link is saturated because the heavy cryptographic work is done locally. |
| **6 – Immediate MFA re‑enrollment** | Once the user is in, they are forced to **re‑register a new authenticator app** (or a new hardware key) before they can perform any privileged action. The system forces a **MFA‑reset** that requires the user to scan a QR code **or** register a new key **once they have any data connection** (e.g., when the rig’s VSAT link becomes lightly loaded). | Guarantees that the temporary bypass is **short‑lived** and that the account returns to its normal MFA posture. | The re‑enrollment is performed locally; the resulting credentials are tied to the same user account. |
| **7 – Logout & clean‑up** | Technician logs out, removes the temporary session, and returns the used recovery code to the SOC (the SOC marks it as “consumed”). | Provides an immutable trail that the bypass was used only once. | No extra data is transmitted; the SOC records the event. |

### 2.3  Why this **does not** “disable MFA” or issue a shared credential  

* **MFA is never permanently disabled.** It is only bypassed for a **single, audited session** using a **pre‑registered recovery code** and a **hardware token**.  
* The user **must re‑enroll** a fresh authenticator before they can do any further work, so the account returns to the same security posture.  
* The recovery code is **single‑use**, non‑transferable, and tied to the user’s account – it cannot be reused or shared.  
* The hardware token is **personal property** and is bound to the user’s identity in the IAM system; it cannot be used by anyone else without physical possession.

### Identity-Verification and Account-Recovery Procedure

This procedure addresses the connectivity constraints (saturated VSAT data, no cell signal), the need for immediate access, and the requirement to maintain strict identity verification without disabling MFA or using shared credentials.

#### Phase 1: Immediate User-Side Checks (Zero-Admin)
Before initiating assisted recovery, verify if the technician holds any credentials that do not require network delivery:
1.  **Offline Backup Codes:** Ask the technician if they generated and printed or stored **offline one-time recovery codes** during their original MFA setup.
    *   *If yes:* The technician uses a backup code to log in. The system forces them to generate new backup codes immediately. Access restored; MFA remains enabled.
2.  **Hardware Token:** Ask if the technician carries a FIDO2/U2F hardware token or smart card.
    *   *If yes:* The technician uses the token to log in. Access restored; MFA remains enabled.
3.  **If neither backup codes nor hardware tokens are available, proceed to Phase 2.**

#### Phase 2: Assisted Identity Verification ("Manager Witness" Path)
Since SMS, push, and callback to the on-file cell are impossible, we use a **Multi-Party Assisted Verification** process leveraging VSAT voice capabilities and internal management verification.

*   **Prerequisite:** VSAT voice channels usually require significantly less bandwidth than telemetry data. The Rig Operations Center or Network Admin will temporarily negotiate **traffic shaping/priority queuing** to allow a low-bandwidth VoIP call, or pause non-essential SCADA telemetry for 5 minutes.

**Step-by-Step Workflow:**
1.  **Initiation:** The technician contacts the IT Security Helpdesk via Rig Operations (who have internal connectivity). The Helpdesk initiates the recovery to ensure the channel originates from a trusted source.
2.  **Multi-Party Call Setup:**
    *   A conference bridge is established including: **IT Security Admin**, **Technician's Direct Manager**, and **Technician**.
    *   *Security Control:* The Admin calls the Manager on the Manager's **known corporate work number** (verified via HR directory) to confirm the Manager is authentic and not spoofed. The Admin then invites the Technician via the rig's internal comms.
3.  **Identity Verification:**
    *   **Visual ID Check:** The Technician presents their Government-issued photo ID and Corporate Badges to the camera. The Manager and Admin visually verify the photo match and that the names on the ID/Badges match the employee record.
    *   **Badge/ID Number Cross-Check:** The Admin requests the Technician read the Employee ID number off the badge and the back of the Government ID. The Admin verifies these against the HR database.
    *   **Knowledge Verification (Optional but Recommended):** The Admin asks two pre-registered security questions or requests knowledge of a specific detail (e.g., "What is the last four digits of the drilling report ID you submitted yesterday?") to verify possession of recent context-only knowledge.
4.  **Consent & Witnessing:**
    *   The Manager explicitly confirms in the call: *"I verify the identity of this technician. I have visually confirmed their ID and badge, and I approve this recovery."*
    *   This satisfies the requirement that a trusted supervisor verifies the user when direct verification is impossible.

#### Phase 3: Account Remediation
Once identity is verified, the Admin executes the recovery without disabling MFA.

1.  **MFA Reset:** The Admin resets the Technician's MFA status to **"Force Setup on Next Login."** This invalidates the lost authenticator app but keeps MFA enabled.
2.  **Offline Recovery Code Issuance:**
    *   The Admin generates a set of **Offline Backup Codes**.
    *   These codes are read aloud over the secure conference call to the Technician.
    *   The Technician **writes them down on physical paper** or confirms a print function is available on a rig terminal to save the codes locally.
    *   *Security Note:* The codes are never transmitted via data channels; they are transferred via voice to the user's offline possession.
3.  **Access Restoration:**
    *   The Technician logs in using one of the **Offline Backup Codes**.
    *   The system forces a MFA setup. Since the Technician cannot use push/SMS, the Admin guides them to **generate and print new Backup Codes** to ensure they have an offline recovery path for the future.
    *   MFA is re-enabled using the new offline factors.

#### Phase 4: Documentation and Post-Incident Actions
To maintain audit compliance and improve security posture, the following must be documented:

**1. Incident Ticket Documentation:**
*   **Incident ID & Timestamp:** Date/Time of request and resolution.
*   **Verification Method:** Clearly state: *"MFA Reset via Manager Witness/Video ID Verification."*
*   **Evidence Attached:**
    *   HR/Directory verification of Manager identity.
    *   Confirmation of Badge/ID numbers matching HR records.
    *   Statement of Manager's verbal confirmation.

*   **Resolution:** MFA status confirmed as Enabled; Offline Backup Codes issued and secured by user.

**2. Operational & Risk Reporting:**
*   **VSAT Saturation Report:** Document the telemetry saturation that blocked the recovery. This should be escalated to Operations/Engineering to review bandwidth allocation (e.g., ensure voice priority or that SCADA telemetry allows for emergency management traffic).
*   **Root Cause Analysis:** Investigate why the technician did not have valid backup codes or a hardware token.
*   **Corrective Action:**
    *   If the user lacked backup codes, flag the account for a mandatory review once connectivity is restored to ensure future-proofing.
    *   Update policy documentation to highlight that in remote environments, offline backup codes are the critical recovery path, and users should be trained to print them immediately upon MFA enrollment.
