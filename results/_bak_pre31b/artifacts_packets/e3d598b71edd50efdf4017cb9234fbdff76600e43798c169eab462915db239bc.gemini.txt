## 7 -- Strong

Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate

Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak

Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Task

The task given to every model in this cohort:

A regional bank is acquiring an 18-branch community bank. The community bank runs 340
mailboxes on an on-prem Exchange Server 2016 environment, which is already past Microsoft's
end of extended support. The plan is to migrate those mailboxes into the acquiring bank's
Microsoft 365 tenant. Regulatory constraint: the bank's retention obligations require every
mailbox's content and metadata (including original delivery timestamps) to survive the
migration intact, with a documented chain of custody. Operational constraint: branches are
open 9 AM-5 PM across two time zones, so there is no single company-wide after-hours window,
and mailbox access cannot be interrupted during any branch's business hours. Timeline
constraint: the core-banking system conversion (a separate workstream) is cutting over in 45
days, and email migration must NOT be scheduled during that same week, because branch staff
need working email to field cutover-related questions and both teams cannot be in a change
freeze at the same time. Write a phased Microsoft 365 migration plan: the cutover approach
given Exchange 2016 is already unsupported, a rollback plan if a mailbox batch migration fails
partway, and the sequencing relative to the 45-day core-banking cutover with the blast radius
of getting that sequencing wrong.

This migration plan is designed to address the high-stakes regulatory requirements of a financial institution while navigating the technical debt of an unsupported Exchange environment and the extreme operational sensitivity of a core-banking conversion.

### 1. Migration Strategy: Third-Party Tool-Led "Minimal Hybrid"
Because the source Exchange 2016 environment is past end-of-support, a traditional, deep Microsoft Hybrid configuration is risky; any failure in the underlying Exchange services could jeopardize the migration.

**The Approach:** We will utilize a professional third-party migration tool (e.g., **BitTitan MigrationWiz** or **Quest On Demand**). 

*   **Why this approach?**
    *   **Metadata Integrity:** These tools are designed specifically to preserve `OriginalReceivedDate`, `InternetMessageID`, and folder hierarchies, satisfying the regulatory requirement for metadata survival.
    *   **Chain of Custody:** These tools generate granular, item-level migration logs. These logs serve as the "documented chain of custody," proving that every item in the source was successfully verified in the destination.
    *   **Bypassing Unsupported Risks:** Unlike a native hybrid setup, a third-party tool interacts with the Exchange API/MAPI, reducing the need to perform complex configuration changes on the aging, unsupported local server.

---

### 2. Phased Migration Plan

#### Phase 1: Discovery & Remediation (Days 1–10)
*   **Identity Alignment:** Ensure UPNs (User Principal Names) in the local Active Directory match the target email addresses in Microsoft 365.
*   **Health Check:** Run a deep scan of the Exchange 2016 environment to identify any corrupted mailboxes or "orphaned" objects that might break the migration.
*   **Regulatory Audit Prep:** Configure the migration tool to generate "Pre-Migration" and "Post-Migration" checksum reports for compliance.

#### Phase 2: Pilot & Tool Validation (Days 11–15)
*   **The Pilot:** Migrate 5-10 non-critical IT mailboxes.
*   **Validation:** Perform a "Metadata Audit" where a compliance officer compares a source mailbox item's properties (Timestamp, Sender, Subject) against the M365 copy to ensure zero degradation.

#### Phase 3: Pre-Staging/Bulk Migration (Days 16–30)
*   **The "Heavy Lift":** Initiate the bulk migration of all 340 mailboxes. 
*   **The Strategy:** This is a "Pre-Stage" migration. The tool copies all email data from Exchange 2016 to M365 in the background. 
*   **Operational Impact:** **Zero.** Users continue to work on the Exchange 2016 server. The only impact is a slight increase in network bandwidth. This allows us to move 95% of the data *before* the cutover window.

#### Phase 4: The Cutover (Days 31–40)
*   **Batching by Branch:** To respect the 9 AM–5 PM/Two Time Zone constraint, we will not perform a "big bang" cutover. Instead, we use **"Sliding Window Batching."**
*   **Execution:**
    1.  **Batch 1 (Branch A):** Perform the "Final Delta Sync" and update the user's Outlook profile/DNS during the specific gap between the end of Branch A's day and the start of Branch B's day.
    2.  **Batch 2 (Branch B):** Repeat for the next set of branches.
*   **Minimal Downtime:** Since 95% of data is already in M365, the "cutover" is merely a final sync of the last few hours of mail and a profile switch. The actual "blackout" per user is reduced to minutes.

---

### 3. Rollback Plan (The "Safety Net")

If a mailbox batch migration fails (e.g., sync error or profile corruption), the following protocol is triggered:

1.  **Immediate Divergence:** Do **not** attempt to "fix" the M365 mailbox while the user is live. 
2.  **Revert Profile:** The technician will immediately revert the user’s Outlook profile to point back to the local Exchange 2016 server (which remains online and untouched).
3.  **Root Cause Analysis (RCA):** The migration team identifies if the error was due to item corruption (Source) or connectivity (Network).
4.  **Retry Logic:** Only after the RCA is completed is the specific mailbox re-queued for a "Delta Sync." 
5.  **Continuity:** Because the local Exchange server was never decommissioned, no data is lost during the rollback; the user simply continues working as if the migration never started.
