### **Detailed Technical Breakdown & Implementation Guide**

#### **1. Duplicate Title Tags**
*   **The Issue:** Search engines cannot differentiate between individual project pages because the `<title>` tag is identical across all 34 pages (e.g., "Our Projects | Firm Name"). This causes "Keyword Cannibalization," where [model] doesn't know which page to rank for a specific project name.
*   **The Fix (WordPress/Yoast):**
    1.  Navigate to **Yoast SEO > Search Appearance > Content Types**.
    2.  Locate the **Projects** post type (or the custom post type used for portfolios).
    3.  In the **SEO Title** field, replace the static text with the Yoast variable: `%%title%% %%sep%% %%sitename%%`.
    4.  This forces WordPress to pull the specific post title into the HTML `<title>` tag for every unique project.

#### **2. Broken Internal Links (404s)**
*   **The Issue:** The main navigation menu is attempting to send users and crawlers to pages that no longer exist. This creates "crawl waste" and damages user experience (UX).
*   **The Fix (WordPress/Yoast):**
    1.  **Identify:** Use the 404 list to see which projects were removed.
    2.  **Redirect:** If you have **Yoast SEO Premium**, use the built-in **Redirect Manager**. If using the free version, install the **"Redirection"** plugin.
    3.  **Action:** Implement **301 Redirects** for each of the 18 URLs. Redirect them to the most relevant "Parent" page (e.g., `/portfolio/` or `/projects/`) rather than the homepage, to maintain topical relevance.
    4.  **Cleanup:** Manually update the WordPress Menu (`Appearance > Menus`) to remove the dead links to prevent "ghost" clicks.

#### **3. Largest Contentful Paint (LCP) Optimization**
*   **The Issue:** Architecture sites are visually driven. A 4.8s LCP suggests that the "hero" images on the homepage are likely high-resolution, uncompressed JPEGs being loaded with low priority, delaying the visual rendering of the page.
*   **The Fix:**
    1.  **Image Compression:** Use a plugin like *Smush* or *ShortPixel* to compress all existing images.
    2.  **Next-Gen Formats:** Convert all homepage hero images to **WebP** format, which provides superior compression at similar quality.
    3.  **Fetch Priority:** For the specific hero image that triggers the LCP, add the `fetchpriority="high"` attribute to the `<img>` tag. This tells the browser to prioritize this image over everything else.
    4.  **CDN:** Implement a Content Delivery Network (like Cloudflare) to serve assets from a server closer to the user's physical location.

#### **4. Pagination & Duplicate Content (Blog Series)**
*   **The Issue:** [model] sees `/blog/`, `/blog/page/2/`, and `/blog/page/3/` as highly similar content. Without proper signals, [model] may struggle to decide which page is the "master" copy, potentially leading to the exclusion of your older blog posts from the index.
*   **The Fix (WordPress/Yoast):**
    1.  **Canonical Tags:** Ensure that each paginated page has a **self-referencing canonical tag**. (e.g., Page 2's canonical should point to Page 2, not the homepage). Yoast usually handles this automatically, so if it is failing, it is likely due to a custom theme template overriding the header.
    2.  **Check Theme Logic:** If the canonicals are incorrect, check the `header.php` of your theme to ensure `wp_head()` is present, which allows Yoast to inject the correct tags.
    3.  **Rel="next/prev":** Note that [model] officially stopped using `rel=next/prev` for indexing in 2019, but other search engines and browsers still use them for pagination UI. Ensure your theme/plugin is correctly outputting these in the `<head>`.

## 2. Duplicate Title Tags on 34 Project Pages *(P2 – High Impact / Medium Effort)*  

### **Cause**  
- The **project‑page template** (likely `single‑project.php` or a page template used for all portfolio items) uses a **static title** in the `<title>` tag (e.g., “Project – Architecture Firm”) instead of injecting the project’s actual name (`post_title` or custom field).  
- Yoast SEO’s **title template** for the “Post Type: Project” is left at the default (`%title% | %sitename%`) **but the theme overrides** it with hard‑coded text, or the template never calls `wp_title()` / `yoast_output_title_parts()`.

### **Fix (WordPress + Yoast)**  

| Step | Action | Yoast‑specific notes |
|------|--------|----------------------|
| **1️⃣ Locate the title generation** | Open the theme’s template file that renders project pages (e.g., `single‑project.php`, `page‑template‑project.php`). Search for `<title>` or `wp_title()`. | If the theme uses **`wp_head()`** correctly, Yoast will inject its own title via the `wpseo_title` filter. If the theme echoes a static string **before** `wp_head()`, Yoast’s title never appears. |
| **2️⃣ Ensure Yoast’s title is used** | Replace any hard‑coded `<title>` blocks with `<?php wp_head(); ?>` **and** make sure the theme **does not** echo a title outside that call. | In Yoast → **SEO → Search Appearance → Titles & Metas → Post Types → “Project”**, set the **Title SEO template** to something like: <br>`%title% | %sitename%` **or** `%wpseo_title%` (the latter pulls Yoast’s computed title). |
| **3️⃣ Add dynamic project name** | If the project name lives in a **custom field** (e.g., `project_name`), edit the title template to include it: <br>`%wpseo_title% %custom_field:project_name% | %sitename%` <br>or use a PHP snippet: <br>`echo get_post_meta($post->ID, 'project_name', true);` inside the title tag. | Yoast allows **“%custom_field:FIELD_NAME%”** placeholder only when the **Yoast SEO Premium** “Custom fields” add‑on is enabled. Otherwise, use a small filter: <br>`add_filter('wpseo_title', function($title, $sep) { global $post; $proj = get_post_meta($post->ID, 'project_name', true); return $proj . $sep . $title; }, 10, 2);` |
| **4️⃣ Test each project page** | Use **[model] Search Console → URL Inspection** or a crawler (Screaming Frog, Sitebulb) to verify titles now contain unique project names. | Yoast’s **SEO analysis** on each post will change from “Duplicate title” → “OK” once the template is dynamic. |
| **5️⃣ (Optional) Bulk update existing pages** | If many pages already indexed with duplicate titles, consider a **301 redirect** from the old URL to a new slug that includes the project name, *or* submit a **URL Parameters** change in GSC to re‑crawl. | Yoast’s **XML sitemap** will automatically reflect the new titles on the next regeneration (`wpseo_sitemap->regenerate()`). |

### **Why P2?**  
- **Impact:** Duplicate titles dilute ranking potential, cause [model] to choose a “best” version arbitrarily, and can hide important project keywords.  
- **Effort:** Requires code edits (theme template + possibly a small PHP snippet) and a review of ~34 pages, but once fixed the template scales automatically for future projects.

## 3. Missing Canonical / rel=next/prev on 12‑page Paginated Blog Series *(P3 – Medium Impact / Low‑Medium Effort)*  

### **Cause**  
- The blog series uses **`page/2`**, **`page/3`**, … pagination but the theme or pagination logic does **not** insert **canonical** URLs (pointing to the first page) nor **`rel="next"` / `rel="prev"`** link attributes.  
- Yoast SEO *does* automatically add canonical tags for paginated archives **if** the pagination is generated via WordPress’s built‑in `paginate_links()` or the default `WP_Query` with `paged`. However, many custom pagination setups bypass Yoast’s filters.

### **Fix (WordPress + Yoast)**  

| Step | Action | Yoast‑specific notes |
|------|--------|----------------------|
| **1️⃣ Verify pagination method** | Check the theme’s loop for the blog series. Is it using `wp_link_pages()`, custom `while (have_posts())` with manual page handling, or a plugin (e.g., **Infinite Scroll**, **Envato Pagination**)? | If using **WordPress native pagination** (`the_posts_pagination()` or `paginate_links()`), Yoast already injects canonical & rel attributes via `wpseo_linkattributes` filter. |
| **2️⃣ Enable Yoast’s pagination handling** | In **Yoast SEO → Search Appearance → Blog page**, ensure **“Show pagination for the blog pages”** is **ON**. This forces Yoast to add `<link rel="canonical">` on each paginated page pointing to the base URL (e.g., `/blog/`). | Yoast also adds `rel="next"`/`rel="prev"` automatically when pagination is recognized. |
| **3️⃣ If using a custom pagination loop** | Add the following code to `functions.php` (or a site‑specific plugin) to let Yoast know the pagination context: <br>```php<br>add_filter('wpseo_prev_url', function($url, $post) {<br>    if (is_archive() && get_query_var('paged')) {<br>        $prev = get_permalink( $post ) . '&page=' . (get_query_var('paged') - 1);<br>        return $prev;<br>    }<br>    return $url;<br>}, 10, 2);<br>add_filter('wpseo_next_url', function($url, $post) {<br>    if (is_archive() && get_query_var('paged')) {<br>        $next = get_permalink( $post ) . '&page=' . (get_query_var('paged') + 1);<br>        return $next;<br>    }<br>    return $url;<br>}, 10, 2);<br>``` | This tells Yoast where the “next” and “prev” URLs are, prompting it to emit the proper `<link>` tags. |
| **4️⃣ Manually add canonical (fallback)** | If the above still fails, insert a canonical tag directly in the theme header: <br>`<link rel="canonical" href="<?php echo esc_url(home_url(add_query_arg(array(), false))); ?>" />` for all paginated pages (replace with the base URL of the series). | Yoast will respect a manually added canonical *only* if it sees it **before** its own output; otherwise, its filter may overwrite it. Best practice: let Yoast handle it. |
| **5️⃣ Test** | Use **[model] Search Console → URL Inspection** on page 2, 3, etc., to confirm the presence of `<link rel="canonical">` and `<link rel="prev/next">`. Also run a quick crawl in **Screaming Frog** with “Canonical” column enabled. | Yoast’s **SEO analysis** on each paginated page should now show “✓ Canonical URL set” and “✓ Pagination links set”. |

### **Why P3?**  
- **Impact:** Without canonical/next‑prev, search engines may treat each pagination page as a separate, duplicate piece of content, potentially diluting authority and causing indexing bloat.  
- **Effort:** Usually a few lines of code or toggling a Yoast setting—low effort, but the fix is essential for a clean index.

## 4. Homepage Largest Contentful Paint (LCP) = 4.8 s ([model] “good” threshold < 2.5 s) *(P2 – Medium‑High Impact / Medium Effort)*  

### **Cause**  
- **LCP** measures the render time of the largest visible element (often an above‑the‑fold hero image, background video, or large banner). A 4.8 s result indicates one or more of the following typical culprits on a WordPress site:  
  1. **Unoptimized images** (large file size, wrong dimensions).  
  2. **Render‑blocking JavaScript/CSS** (theme scripts loaded in `<head>`).  
  3. **Server response time** (slow host, lack of caching).  
  4. **Above‑the‑fold content relies on external assets** (e.g., [model] Fonts loaded async but still delaying paint).  

### **Fix (WordPress + Yoast)**  

| Step | Action | Yoast‑specific notes |
|------|--------|----------------------|
| **1️⃣ Diagnose with LCP‑focused tools** | Run **[model] PageSpeed Insights**, **WebPageTest**, and **GTmetrix** on the homepage. Note the “LCP element” (e.g., a 1920×1080 hero JPG). | Yoast does not affect LCP directly, but its **SEO analysis** may flag “Page speed” if you enable the **Yoast SEO Premium “Page speed”** module (which pulls data from PageSpeed Insights). |
| **2️⃣ Optimize the hero image** | - **Resize** to the exact display dimensions (e.g., 1200×800 for a 1200‑px wide viewport).<br>- **Compress** using **ShortPixel**, **EWWW Image Optimizer**, or **TinyPNG** (lossless or balanced).<br>- **Serve next‑gen formats**: convert to **WebP** (most modern browsers) via the same plugin or manually (`<picture>` with `srcset`). | Yoast’s **Image SEO** add‑on can auto‑add `alt` tags, but image size is a performance issue handled by a separate plugin. |
| **3️⃣ Leverage browser caching & CDN** | - Enable **browser caching** headers (`.htaccess` `Expires`/`Cache‑Control`).<br>- Deploy a **CDN** (Cloudflare, KeyCDN) for static assets (images, JS, CSS). | Yoast does not manage caching; use a caching plugin like **W3 Total Cache** or **WP Rocket** (premium) that integrates well with Yoast. |
| **4️⃣ Defer/async non‑critical JS & inline critical CSS** | - Move **render‑blocking CSS** to `<style>` in the `<head>` (critical CSS). Tools: **Critical** (via Webpack) or **Autoptimize** (critical‑CSS feature).<br>- Add `async` or `defer` to theme’s JS enqueues: <br>`wp_enqueue_script('theme-js', '...js', array(), '1.0', true);` (the last param = `true` loads in footer). | Yoast SEO itself loads a small `yoastseo.js` in the footer by default; ensure it’s not blocking. |
| **5️⃣ Optimize web fonts** | - If using **[model] Fonts**, add `?display=swap&` and load **asynchronously** (`<link rel="preload" as="style" onload="this.onload=null;this.rel='stylesheet'">`).<br>- Consider **self‑hosting** the font files for faster delivery. | No direct Yoast involvement, but self‑hosting can be done via **Use Any Font** plugin or by uploading .woff2 files to your server and enqueuing them. |
| **6️⃣ Test & iterate** | Re‑run PageSpeed Insights after each change. Aim to drop LCP under **2.5 s** (target < 2 s for best user experience). | Yoast’s **SEO → Dashboard → Performance** tab (Premium) will surface any remaining “Page speed” warnings once the underlying metrics improve. |

### **Why P2?**  
- **Impact:** Core Web Vitals (including LCP) are now a **ranking factor** (2021+). A 4.8 s LCP places the site in the “needs improvement” bucket, potentially lowering organic visibility.  
- **Effort:** Requires image optimization, caching/CDN setup, and possibly code changes (deferring scripts, generating critical CSS). While more involved than fixing a 404, the payoff in rankings and user retention justifies the medium effort.
