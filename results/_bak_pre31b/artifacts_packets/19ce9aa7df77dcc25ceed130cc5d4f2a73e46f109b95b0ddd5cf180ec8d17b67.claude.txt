Example character: recommends reimaging a device as the first step for a minor, non-blocking symptom.

### Identity-Verification and Account-Recovery Path

Given the constraints (no push delivery, no SMS/cell signal, saturated VSAT data, regulatory deadline, and prohibition against disabling MFA or using shared credentials), the solution must leverage **offline MFA capabilities**, a **manager-proxy verification workflow**, and **low-bandwidth voice channels** (which typically survive data saturation via QoS prioritization in satellite links).

#### 1. Establish a Voice Communication Bridge
*   **Assumption:** While VSAT data is saturated by SCADA, remote drilling operations typically maintain voice connectivity via **VoIP with QoS prioritization**, a dedicated **satellite phone**, or a **rig landline**. These channels use minimal bandwidth and often bypass data saturation rules.
*   **Action:** The technician initiates a voice call to their direct supervisor/manager using the lowest-bandwidth available channel (e.g., rig landline or compressed VoIP).
*   *Note:* If no voice channel exists, this situation requires a "Break Glass" physical escalation, but standard rig infrastructure almost invariably supports voice even when data is saturated.

#### 2. Multi-Point Identity Verification (Manager Proxy)
Since the IT team cannot call the technician, identity verification is delegated to the Manager via a structured proxy protocol. The Manager must verify the technician using **three independent factors**:

1.  **Manager Vouching:** The Manager confirms they are speaking to the correct technician and that the technician has a critical business need.
2.  **Knowledge-Based Authentication (KBA):** The Technician answers security questions known only to the user (e.g., specific employee ID, last successful login timestamp, or a secret phrase established during onboarding).
3.  **Physical ID Verification:**
    *   The Technician presents their physical corporate badge, passport, or ID to a camera on the laptop.
    *   If the VSAT can transmit even a single low-resolution image or text, the Technician sends a photo of the ID to the Manager.
    *   *Fallback:* If no image can be sent, the Technician reads the ID number, name, and expiration date aloud, which the Manager manually verifies against the HR system.

#### 3. Account Recovery via TOTP Switchover
*   **Technical Enabler:** Authenticator apps generate **Time-based One-Time Passwords (TOTP)** locally and offline. The failure is only in the *push notification delivery*, not the app itself.
*   **Action:** Upon successful verification, the Manager contacts IT/SOC. The IT administrator performs an emergency MFA reset with specific constraints:
    *   **Reset MFA Factor:** Switch the account from "Push Notification" to **"TOTP Only"** (or enable TOTP if it exists but was not previously set up).
    *   **No MFA Disablement:** MFA remains enabled; only the delivery method is changed to one that functions offline.
    *   **Temporary Access:** The technician can now log in immediately by entering the 6-digit code generated by their authenticator app, which does not require any network connectivity.

#### 4. Post-Recovery Hardening
*   Once logged in, the technician is required to set up a secondary MFA method that does not rely on real-time push/SMS (e.g., hardware token or backup codes) to prevent recurrence.
*   The account is flagged for review to ensure the MFA preference is locked to TOTP/Hardware for this user until connectivity is restored.

**Identity‑verification & MFA‑reset flow that does NOT rely on SMS, push‑notifications or a callback to a cell‑phone**

Below is a concrete, auditable path that can be run from the rig with only an **offline authenticator** (or a pre‑issued hardware token) and a **satellite voice channel** (or any other out‑of‑band voice link that the site does have).  The steps keep the principle of “something you *have* + something you *know* + something you *are*” intact, and they never issue a shared or generic credential or permanently disable MFA.

---

## 1.  Gather the offline proof‑of‑possession factors that are already on the technician’s kit  

| What the technician has (and can use without any network) | Why it works for verification |
|------------------------------------------------------------|------------------------------|
| **YubiKey / FIDO2 security key** (programmed with a static *HMAC‑SHA1* OTP or with a FIDO2 resident key) | The secret key never leaves the device; a simple touch produces a 6‑digit code that can be read aloud or entered on a local console. |
| **Printed recovery code** (single‑use, 8‑digit code that was generated when the account was first enrolled) | It is stored in a sealed envelope in the rig’s “Emergency Access Kit”.  It can be used only once and is tied to that user. |
| **Offline TOTP app** (e.g., [model] Authenticator, Authy “offline” mode, or a custom app that stores the secret locally) | The app can generate the 30‑second TOTP without any data connection. |

*If any of the above is present, the technician can prove “possession” without needing the satellite data link.*

---

## 2.  Out‑of‑band voice verification (the “something you *are*” factor)

1. **Open a satellite voice channel** (e.g., Iridium 9603, Inmarsat, or a hardened radio‑to‑satellite phone that the rig already has for emergency communications).  
2. The technician calls the **pre‑registered “MFA‑reset hotline”** (a dedicated DID that routes to the corporate security operations center).  
3. The caller is asked to state:
   - Full name and employee ID.
   - The **employee‑ID‑linked secret phrase** that was set in HR onboarding (e.g., “The first color of the rig’s safety flag is ___”).  
   - A **one‑time challenge** generated by the security team (e.g., “What is the last 4 digits of the serial number on your badge?”).  

   Because the challenge phrase lives only in the HR database and is known to the employee, answering it correctly demonstrates **knowledge** that an attacker could not guess.

4. The security analyst on the other end **verifies** the answers against the employee’s HR record (which is stored offline in the corporate IAM admin console).  No cell‑phone network is required; only the voice link.

*Result:* The analyst now has high‑confidence assurance that the caller is the legitimate account owner.

---

## 3.  Prove “possession” with an offline factor

While still on the voice call (or after the call ends if the technician can’t stay on the line), the technician does one of the following:

| Option | How it is performed | What the analyst receives |
|--------|-------------------|---------------------------|
| **YubiKey OTP** | Touch the key, read the 6‑digit OTP aloud, and the analyst types it into the admin console’s “MFA‑reset verification” field. | The OTP is checked against the pre‑registered secret stored for that user. |
| **Printed recovery code** | Read the 8‑digit code from the envelope and whisper it to the analyst. | The code is a one‑time use token that the admin can consume to unlock the reset workflow. |
| **Offline TOTP** | Open the authenticator app on the personal phone (which works without data), read the 6‑digit code, and give it to the analyst. | Same verification as above. |

*If none of these physical factors are available, the technician can skip to step 4 only after a **second independent voice verification** (e.g., a manager on a different satellite channel repeats the challenge and confirms the answer).*

---

## 4.  Reset the MFA factor (without disabling MFA)

1. **Admin console action** – Once the analyst has received a valid OTP/recovery‑code/TOTP **and** the voice‑challenge verification, they open the IAM “MFA Management” screen for that user.  
2. **Delete only the *push‑notification* factor** (or any factor that is known to be non‑functional on the rig).  
3. **Force a “re‑enrollment”** – The console automatically prompts the user to set up a new MFA method on next login.  
4. **Provide a temporary, single‑use “re‑enrollment link”** (a URL that is valid for 15 minutes and can be opened on any device with a browser).  The link is delivered **via the satellite voice channel as a spoken URL** (the analyst reads it out loud) or via a **QR code printed on a paper slip** that the technician can scan with the offline authenticator app.  
5. **Technician logs in** using their existing password *plus* one of the offline verification codes (OTP/recovery code) they just proved possession of.  On first successful login they are forced to **re‑register a new MFA factor** (e.g., push, authenticator app, or a new YubiKey).  

*Result:* MFA is **restored** for the account, not disabled, and the technician must enroll a working factor before they can complete the drill‑report submission.
