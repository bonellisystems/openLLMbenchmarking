## Anchors

# SEO -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Technical recommendations are correct for the stated platform (canonical tags, redirects, schema, robots directives used properly), keyword strategy is matched to actual search intent, and every recommendation is prioritized by expected impact versus effort. No black-hat tactic is suggested, and the answer is calibrated about ranking-factor uncertainty rather than asserting exact algorithm weights as fact.
Example character: a prioritized fix list starting with the highest-impact technical issue, each item tied to a specific, correctly-described mechanism.

## 7 -- Strong
The technical guidance is sound and usable for the stated platform, and keyword direction matches intent. It is missing an explicit effort-versus-impact prioritization, or one recommendation is generic rather than platform-specific, but nothing here is technically wrong.
Example character: correct on-page and technical fixes listed without ranking them by which matters most.

## 5 -- Adequate
The advice is SEO-fundamentals-correct (use target keywords, build backlinks, improve page speed) but reads as a generic checklist not tied to the specifics of the site or platform given.
Example character: a standard keyword-and-backlink checklist with no reference to the site's actual issues.

## 3 -- Weak
Contains outdated or incorrect technical claims (keyword stuffing helps rankings, more backlinks always help regardless of quality), or recommends tactics unrelated to the actual ask.
Example character: advice built around an outdated ranking factor treated as still authoritative.

## 0 -- Unusable
Recommends black-hat or manipulative tactics (cloaking, link farms, hidden text, doorway pages) as safe practice with no penalty-risk warning, or fabricates specific ranking-factor claims as verified fact. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Black-hat tactics (cloaking, PBNs, hidden text, keyword stuffing) recommended without a penalty-risk warning.
- Fabricated or overconfident claims about exact Google ranking-factor weights.
- Technical errors in canonical, redirect, or robots guidance that would deindex pages.
- Ignoring a stated platform or CMS constraint.

## Unit-specific excellence markers
- Recommendations prioritized by effort versus expected impact.
- Correct technical implementation detail for the stated platform (canonical, redirects, schema, robots).
- Keyword strategy matched to actual search intent, not just volume.
- Honest flag of algorithm-update or ranking-factor uncertainty.

## ⚙️ TECHNICAL HANDLING (NEW DOMAIN FOCUS)

### Canonical Tags
- All new pages must include a **self-referencing** `<link rel="canonical" href="https://newdomain.com/...">`
- **Never** point canonicals to old-domain URLs; this signals search engines to crawl/serve the deprecated domain and wastes crawl budget
- For migrated whitepapers/case-study PDFs: host an HTML landing page, 301-redirect old PDF URLs to the new landing, and place the self-referencing canonical on the HTML page
- Disable any CMS plugin or theme that auto-appends old-domain canonicals

### robots.txt (New Domain)
- Ensure `User-agent: *` **allows** crawling of all new content paths (whitepapers, case studies, service pages, blog)
- Remove any legacy `Disallow` rules inherited from the old CMS that may inadvertently block priority content
- **Old domain (post-launch):** Add `Disallow: /` to the old domain’s `robots.txt` to prevent search engines from crawling redirect-only pages; the 301s will still pass equity, but crawl budget is preserved
- Never use `robots.txt` to hide pages or block redirects; redirects must remain fully accessible to crawlers

### XML Sitemap (New Domain)
- Generate a fresh sitemap containing **only** published new-domain URLs (target: 340)
- **Exclude:** Redirect-only URLs, draft pages, admin paths, parameter/trackable URLs, and any old-domain URLs
- Validate in GSC: Submit new sitemap, remove old sitemap reference, monitor `Crawled – currently not indexed` and `Submitted – not indexed` reports
- Ensure sitemap is publicly accessible at `https://newdomain.com/sitemap.xml` (not behind auth, login wall, or JS render)
- If using a sitemap index, update it to reference the new-domain sitemaps and notify crawlers via GSC `Sitemap` test tool

## QUICK “DO / DON’T” CHEAT SHEET  

| ✅ Do | ❌ Don’t |
|------|----------|
| **Map every old URL → its exact new‑page equivalent** (1:1 301). | Redirect *any* old URL to the homepage or a generic landing page. |
| Use **permanent 301 redirects** (server‑level, not meta refresh or JavaScript). | Use 302 (temporary) redirects or client‑side redirects. |
| Keep **redirect chain length = 1** (no old → intermediate → final). | Create multiple hops (old → old‑v2 → new) – wastes crawl budget. |
| Update **canonical tags** on all new pages to point to themselves (or the chosen canonical if content merged). | Leave old canonicals pointing to the old domain or omit canonicals entirely. |
| Submit a **clean XML sitemap** (only live URLs) and remove any redirected or 404 URLs. | Submit a sitemap that still contains old URLs or redirects. |
| **Allow** crawling of the new site in `robots.txt` (except staging/admin sections). | Disallow the entire site or key sections by mistake. |
| Perform **full QA testing** before DNS switch. | Assume redirects work because they “look right” without testing. |
| **Monitor** Search Console & Analytics daily for the first 2 weeks. | Wait weeks before checking for errors. |
| Keep a **record of the redirect map** (CSV/SQL) for future reference. | Lose the mapping and rely on memory. |
