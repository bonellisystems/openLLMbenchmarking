### 🔍 What Goes Wrong: The Cartesian Product (Fan-Out) Trap

If you join `projects` directly to both child tables in one query and `SUM` the amounts, you create an implicit cross-join between the two child tables on the shared parent key. For project 101:

- `change_orders` has **3 rows**
- `invoices` has **4 rows**
- The join produces `3 × 4 = 12` intermediate rows per project.

**Numerical impact for Project 101:**
- Each change order is duplicated **4 times** (once per invoice).  
  `$50k + $30k + $20k = $100k` → `$100k × 4 = **$400,000**` (❌ Wrong)
- Each invoice is duplicated **3 times** (once per change order).  
  `$500k + $500k + $500k + $300k = $1,800,000` → `$1.8M × 3 = **$5,400,000**` (❌ Wrong)

`SUM()` operates on the duplicated intermediate rows, inflating both totals by the row count of the opposite child table. This is the classic **fan-out / cross-join aggregation problem**.

---

### ✅ Correct Query (ANSI-Standard / PostgreSQL-Compatible)

Aggregate each child table independently first, then join the single-row-per-project results to the parent. Common Table Expressions (CTEs) are ANSI-92+ and fully supported in PostgreSQL:

```sql
WITH change_totals AS (
    SELECT project_id, SUM(co_amount) AS total_co_amount
    FROM change_orders
    GROUP BY project_id
),
invoice_totals AS (
    SELECT project_id, SUM(invoice_amount) AS total_invoice_amount
    FROM invoices
    GROUP BY project_id
)
SELECT 
    p.project_id,
    p.project_name,
    COALESCE(ct.total_co_amount, 0) AS total_change_orders,
    COALESCE(it.total_invoice_amount, 0) AS total_invoices
FROM projects p
LEFT JOIN change_totals ct  ON p.project_id = ct.project_id
LEFT JOIN invoice_totals it ON p.project_id = it.project_id
ORDER BY p.project_id;
```

**Output for Project 101:**
| project_id | project_name         | total_change_orders | total_invoices |
|------------|----------------------|---------------------|----------------|
| 101        | Riverside Office Park| 100000.00          | 1800000.00    |

*(Note: `COALESCE(..., 0)` ensures projects with zero change orders or invoices still appear with a clean `0` rather than `NULL`. Replace with `NULL` or `INNER JOIN` if your reporting logic dictates.)*

### 📜 General Rule for One-to-One/Many Joins with Two+ Child Tables

> **When two or more child tables share the same parent key (one-to-many off a common parent), you must `GROUP BY` and aggregate each child table independently before joining them to the parent (or to each other).**

**Why this rule exists:**
- Relational algebra treats `JOIN` as a cross-product filtered by equality. Joining two `1:N` children creates an `N₁ × N₂` Cartesian product.
- Aggregate functions (`SUM`, `COUNT`, `AVG`, etc.) operate on the working set. If rows are duplicated by the join, aggregates are multiplied by the fan-out factor.
- Pre-aggregating collapses each child table to **one row per parent key**, neutralizing the cross-product and guaranteeing accurate metrics.

**Alternative valid pattern:** Join the two child tables to each other first, then join to the parent. However, pre-aggregating via CTEs/derived tables is the ANSI-recommended best practice because it's logically explicit, index-friendly, and scales cleanly when adding a third child table.

### General Rule: Aggregation Before Joining

**The Rule:** When a single parent table is joined to two or more child tables that are independently related to it (a "1-to-M-to-1" structure), you **must aggregate the child tables prior to joining**.

If you join the child tables first, the database performs a Cartesian product, multiplying every row from the first child by every row from the second child. Any subsequent `SUM` or `AVG` operations will overstate the value by the product of the row counts ($N \times M$). Pre-aggregation reduces each child to exactly one row per parent, ensuring that the join remains one-to-one and the totals remain mathematically correct.

**3.  General rule**

> **When a parent table has two (or more) one‑to‑many child tables, you must aggregate each child table **separately** (e.g., in a sub‑query, CTE, or derived table) **before** joining the aggregates together.**

## The Trap: Why a Naive Join Produces Wrong Numbers

If you write a query that joins `projects`, `change_orders`, and `invoices` in a single pass and sums the amount columns together, you will get a **Cartesian product** (cross-product) between the two child tables.

Every row in `change_orders` will be paired with every row in `invoices` for the same project. When you then apply `SUM()`, it aggregates over that inflated row count, multiplying both totals.

### The Wrong Query

```sql
SELECT
    p.project_id,
    SUM(co.co_amount) AS total_change_order_amount,
    SUM(inv.invoice_amount) AS total_invoiced_amount
FROM projects p
JOIN change_orders co ON p.project_id = co.project_id
JOIN invoices inv ON p.project_id = inv.project_id
GROUP BY p.project_id;
```

### The Numerical Failure for Project 101

For Project 101, the join produces **12 rows** ($3 \text{ change orders} \times 4 \text{ invoices}$). Here is exactly what the database calculates:

1.  **Change Order Total:** Each of the 3 CO rows is repeated 4 times (once for every invoice row).
    *   Calculation: $(50,000 + 30,000 + 20,000) \times 4 = 100,000 \times 4$
    *   **Wrong Result: $400,000** (True value: $100,000)
2.  **Invoice Total:** Each of the 4 Invoice rows is repeated 3 times (once for every CO row).
    *   Calculation: $(500,000 + 500,000 + 500,000 + 300,000) \times 3 = 1,800,000 \times 3$
    *   **Wrong Result: $5,400,000** (True value: $1,800,000)

This error compounds with larger projects. A project with 10 COs and 20 invoices would produce 200 rows before summing, inflating totals by a factor of 200x relative to the unique combinations.

## The Correct Query

To fix this, we must **aggregate each one-to-many relationship independently** in separate CTEs (Common Table Expressions) *before* joining them to the `projects` table. This ensures each sum runs over the correct number of rows.

```sql
WITH change_order_totals AS (
    SELECT
        project_id,
        SUM(co_amount) AS total_co_amount
    FROM change_orders
    GROUP BY project_id
),
invoice_totals AS (
    SELECT
        project_id,
        SUM(invoice_amount) AS total_invoice_amount
    FROM invoices
    GROUP BY project_id
)
SELECT
    p.project_id,
    co.total_co_amount,
    inv.total_invoice_amount
FROM projects p
LEFT JOIN change_order_totals co ON p.project_id = co.project_id
LEFT JOIN invoice_totals inv ON p.project_id = inv.project_id;
```

### Why This Works
1.  **`change_order_totals`**: Aggregates `change_orders` into a single row per project ($3$ rows $\to$ $1$ row).
2.  **`invoice_totals`**: Aggregates `invoices` into a single row per project ($4$ rows $\to$ $1$ row).
3.  **Final Join**: The two CTEs join on `project_id` to produce exactly **one output row per project**. No cross-product occurs because each child table has already been collapsed to a single summary row.

| project_id | total_co_amount | total_invoice_amount |
| :--- | :--- | :--- |
| 101 | 100,000 | 1,800,000 |

## The General Rule

**Rule:** When a parent table has two or more independent one-to-many child tables that must be aggregated together in a result set, **never join the child tables to the parent in a single query and then aggregate across them.**

Instead, always follow this pattern:
1.  **Aggregate independently:** Run separate `GROUP BY` queries (or CTEs/subqueries) for each child table to produce a summary row per parent key.
2.  **Join the summaries:** Join the resulting summary tables back to the parent (or to each other) using the common key.

**Why:** If you join un-aggregated one-to-many tables directly, the database performs a cross-product multiplication of row counts before aggregation. The resulting sums are inflated by the product of the cardinality of the child tables ($M \times N$). Pre-aggregation eliminates the multiplication factor, preserving the true total for each dimension.

- Table `A` has a one-to-many relationship with `B`
- Table `A` has a one-to-many relationship with `C`

```sql
  p.project_name,
  COALESCE(co.total_co_amount, 0) AS total_co_amount,
  COALESCE(inv.total_invoiced, 0) AS total_invoiced
FROM projects p
LEFT JOIN (
  SELECT project_id, SUM(co_amount) AS total_co_amount
  FROM change_orders
  GROUP BY project_id
) co ON co.project_id = p.project_id
LEFT JOIN (
  SELECT project_id, SUM(invoice_amount) AS total_invoiced
  FROM invoices
  GROUP BY project_id
) inv ON inv.project_id = p.project_id;
```

For project 101 this returns total_co_amount = $100,000 and total_invoiced = $1,800,000, both
correct.

General rule: whenever you need totals from TWO different one-to-many child tables hanging off
the same parent, and the children have no relationship to each other, aggregate each child
independently (a GROUP BY in a subquery or CTE) before joining the aggregates back to the
parent. Joining both children directly to the parent in the same query and summing afterward
will silently double-count (fan out) whenever either child has more than one row per parent.
