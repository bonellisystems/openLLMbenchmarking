# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

### 2. Rollback Plan (Batch Failure Scenario)

**Scenario:** A migration batch fails partway (e.g., sync error, permission issue, or metadata corruption detected).

1.  **Immediate Action:**
    *   Pause the migration batch (`Update-MigrationBatch`).
    *   If failure is during final cutover, the batch rolls back to a "Syncing" state automatically or can be forced back. The mailbox remains on Exchange 2016.
2.  **Diagnosis & Remediation:**
    *   Check `Get-MoveRequestStatistics` for error codes.
    *   **Unsupported Server Constraint:** Since MS support is unavailable, reliance is on internal Exchange expertise. If the source server is the cause (e.g., I/O error, DB corruption), remediation may require a restore from backup.
3.  **Rollback Execution:**
    *   **Partial Rollback:** If only specific mailboxes failed, retry those individually.
    *   **Full Batch Rollback:** If the batch is tainted, abort the batch. Mailboxes revert to Exchange 2016. Users experience no change; they were likely already using on-prem during the sync phase.
    *   **Data Integrity:** If M365 created a partial mailbox, delete the cloud object. The source of truth remains Exchange 2016 until a successful move.
4.  **Chain of Custody Update:** Document the failure, root cause, rollback action, and re-validation steps. This is critical for regulatory audits.
5.  **Constraint Check:** Rollback does not impact other batches or branches. The unsupported server remains the fallback, ensuring business continuity.

### 4. Rollback Plan

**Scenario A: Sync Failure Partway**
*   **Action:** MRS will mark the move as "Failed." Data remains intact on Exchange 2016.
*   **Impact:** No user impact. No data loss.
*   **Resolution:** Troubleshoot error (e.g., connectivity, quota). Fix issue and restart the move. Data resyncs from the point of failure.

**Scenario B: Cutover Failure (e.g., Autodiscover routing error or user complaints)**
*   **Action:** Immediately revert Autodiscover DNS/CNAME records to point back to Exchange 2016.
*   **Impact:** Users revert to on-prem within minutes of profile refresh.
*   **Data Safety:** Since the cutover is a routing switch, no data was moved permanently. Mailboxes remain fully intact on Exchange.
*   **Chain of Custody:** The batch is marked "Failed/Reverted" in the audit log. The "As-Is" state is preserved.
*   **Resolution:** Analyze root cause. Fix configuration. Resume cutover at the next available off-hours window.

**Scenario C: Exchange Server Crash (EOL Risk)**
*   **Risk:** Exchange 2016 may become unresponsive.
*   **Mitigation:**
    *   If server fails before sync: No data loss. Resume from backup or re-image.
    *   If server fails during sync: Sync pauses. Data remains on source. Resume sync once Exchange is restored.
    *   *Contingency:* If Exchange cannot be restored, initiate **Emergency PST Export/Import** procedure. This preserves chain of custody via hash verification of PSTs, though it requires user re-configuration. This is a last resort.

### Executive Summary & Migration Approach

3.  **Metadata Preservation:** Mover copies items with full properties, including original delivery timestamps, senders, and hierarchy, satisfying the retention audit requirements.
4.  **Chain of Custody:** Mover provides granular job logs, and the architecture allows for a pre-migration cryptographic archive to establish the baseline chain of custody.

### 1. The Migration Approach: Hybrid Modernization
Because the source Exchange 2016 environment is unsupported, a standard "Cutover Migration" is too risky (it is "all or nothing" and can be unstable on aged hardware). An **Exchange Hybrid Migration** is the only viable path.

*   **Addressing the "Unsupported" Status:** To protect the production environment, we will not run the heavy migration load directly on the existing, fragile Exchange 2016 server. This offloads the heavy I/O and prevents a crash of the primary mail server.
*   **Chain of Custody (CoC):** We will utilize the Microsoft 365 Migration Reporting tool and enable "Detailed Logging" on the migration server. ### 2. Phased Implementation Timeline

The 45-day window is the "Danger Zone." To mitigate risk, we will split the migration into **Data Synchronization** (Low Risk) and **Mailbox Switching** (High Risk).

## 3. Phase‑2 – Staggered Production Migration  

### 3.1 Core Design Principles  

| Principle | How it is realized |
|-----------|-------------------|
| **No branch‑impact during business hours** | Each batch is scheduled **only during the 1‑hour “quiet window”** that each branch *does not* use for customer‑facing activity. Because branches span two time‑zones, we can always find a 1‑hour slot somewhere in the day (e.g., 10 AM‑11 AM EST overlaps with 7 AM‑8 AM PST, when the West‑Coast branch is still closed). |
| **Incremental, reversible batches** | Migrate **≤ 20 mailboxes per batch** (max 15 GB each). If any batch fails, only that batch is rolled back; the rest of the migration continues. |
| **Preserve original timestamps at import** | Use the `PreserveTimestamp` flag and store original metadata in extended properties that are never overwritten. |
| **Immutable audit trail** | Every export, import, and verification step writes a **signed hash** to a **WORM‑enabled SharePoint library**. This satisfies chain‑of‑custody. |
| **Staggered cut‑over to DNS** | DNS MX changes are performed **only after the final batch is verified**; they are rolled out in a rolling‑forward fashion (one region at a time) to minimize blast radius. |
| **Parallel but non‑overlapping with core‑banking** | Migration **must be fully completed at least 7 days before** the core‑banking cut‑over week. This provides a safety buffer for any unexpected issue. |

### 3.2 Batch Scheduling Matrix  

| Week | Branch(es) Affected (Time‑Zone) | Quiet‑Window (local) | Mailboxes in Batch | Target Cut‑over Date |
|------|-------------------------------|----------------------|--------------------|----------------------|
| 6 | East‑Coast Branch #1 (EST) | 10:00‑11:00 AM EST (07:00‑08:00 PST) | 15 | 2025‑10‑30 |
| 6 | West‑Coast Branch #2 (PST) | 10:00‑11:00 AM PST (13:00‑14:00 EST) | 15 | 2025‑11‑01 |
| 7 | East‑Coast Branch #3 | 10:00‑11:00 AM EST | 15 | 2025‑11‑07 |
| 7 | West‑Coast Branch #4 | 10:00‑11:00 AM PST | 15 | 2025‑11‑08 |
| … | … | … | … | … |
| 18 | Final batch (last 10 mailboxes) | 10:00‑11:00 AM (whichever zone still open) | 10 | 2025‑12‑15 (final verification) |

*Each week we migrate **two batches** (one per coast) – never more than one batch per branch in a given calendar day.*  

### 3.3 Detailed Migration Workflow per Batch  

1. **Pre‑Batch Preparation (Day ‑1)**  
   * Verify source mailbox health (`Get‑MailboxStatistics`).  
   * Confirm no active litigation hold or compliance hold that would block export.  
   * Reserve the quiet‑window in the regional ops schedule ( communicated to branch manager).  

2. **Export & Hash (During Quiet‑Window)**  
   * Run `New‑ExportRequest` → PST → Azure Blob (encrypted, WORM‑locked).  
   * Capture SHA‑256 of the PST, timestamp, source GUID, and store in immutable audit log.  

3. **Import into Exchange Online**  
   * Use `New‑ImportRequest` with `-PreserveTimestamp:$true`.  
   * Set `TargetRootFolder:"Inbox"` (or appropriate custom folder).  
   * Monitor import job; capture job‑ID and final status.  

4. **Post‑Import Validation**  
   * Run a **Message‑Trace** for a random sample (5 % of messages) to ensure delivery timestamps match source.  
   * Run a **Compliance Search** for a set of known compliance‑critical messages (e.g., “Reg‑2023‑01”) to confirm they are present and retain original `SentDate`.  
   * Compare exported hash with imported hash; any mismatch triggers rollback.  

5. **Rollback (if needed)**  
   * If any validation fails, **immediately** stop further batches, execute the **Rollback Playbook** (see Section 4).  
   * Re‑apply the original PST to the source Exchange 2016 (if still reachable).  
   * Document failure, root cause, and corrective action; obtain sign‑off before proceeding.  

6. **Batch Sign‑off**  
   * Compliance officer signs the **Batch Completion Certificate** (includes hash, timestamps, validation results).  

### 3.4 Batch Size Rationale  

| Factor | Impact on Batch Size |
|--------|----------------------|
| **Regulatory integrity** | Smaller batches reduce the amount of data at risk; easier to trace. |
| **Operational bandwidth** | 20 mailboxes ≈ 2 hours of export + import + validation within a single quiet‑window. |
| **Network constraints** | Each branch’s internet uplink is limited; 20 mailboxes keep bandwidth < 10 Mbps average. |
| **Human resources** | One migration engineer can comfortably manage 2 concurrent batches (one per coast). |

## 6. Rollback Plan – If a Batch Fails  

### 6.1 Failure Scenarios  

| Scenario | Typical Cause | Immediate Impact |
|----------|---------------|------------------|
| **Export job aborts** | Network glitch, insufficient permissions | No PST created → batch skipped, no migration. |
| **Import job fails** | Corrupt PST, insufficient mailbox quota in target, `PreserveTimestamp` disabled | Mailbox not present in Exchange Online → need to re‑export. |
| **Validation mismatch** | Timestamp alteration, missing messages, hash mismatch | Regulatory breach risk → must roll back. |
| **DNS cut‑over error** (if attempted early) | Wrong TTL, propagation delay | Some users still hit on‑prem server → must revert MX. |

### 6.2 Rollback Steps (per batch)  

1. **Abort further processing** – stop any scheduled export for the next batch.  
2. **Re‑apply source mailbox** – if the source Exchange 2016 server is still reachable, **re‑import the original PST** (`New‑ImportRequest -IsArchive:$false -SourceHealthCheck:$true`).  
3. **Validate source integrity** – run `Get‑MailboxStatistics` to ensure mailbox size and item count match pre‑migration.  
4. **Document failure** – capture the immutable audit log entry, note the exact failure point, and capture screenshots of error messages.  
5. **Escalate** – notify the Governance Board within **30 minutes**; initiate **Root‑Cause Analysis** within 4 hours.  
6. **Resume** – once a fix (e.g., adjust throttling, correct permission set) is applied, **re‑schedule the batch** in the next available quiet‑window.  

> **Key point:** Because each batch is **self‑contained**, a rollback only affects that batch, leaving all previously migrated mailboxes untouched. This minimizes blast radius.

### 6.3 Escalation Matrix  

| Severity | Action | Escalated To |
|----------|--------|--------------|
| **Low** (e.g., export took longer than expected) | Adjust window, retry next day | Migration Lead |
| **Medium** (import failed, but source intact) | Rollback, fix config, re‑run batch | Governance Board + IT Service Manager |
| **High** (timestamp loss, compliance breach) | Immediate suspension of all batches, legal review | CRO / Chief Compliance Officer + Board |

|------------------|-----------------------|---------------|

## Microsoft 365 Migration Plan: Community Bank Acquisition

### Executive Summary

This plan addresses the migration of 340 mailboxes from an unsupported, on-premises Exchange Server 2016 environment to Microsoft 365. The strategy relies on **Shadow Migration** to ensure zero operational interruption during business hours (9 AM–5 PM, two time zones), **MAPI-based tooling** to preserve regulatory metadata/timestamps, and strict **sequencing** to avoid conflict with the 45-day core-banking cutover.

---

### 1. Cutover Approach: Shadow Migration via MAPI Tooling

**Why not Hybrid Deployment?**
Although Hybrid Deployment is the standard for on-prem-to-M365 migration, Microsoft has ended support for Exchange 2016 Hybrid Connectivity. Attempting to establish a hybrid connection to an EOL server creates a regulatory risk (unsupported infrastructure) and a security risk (no security patches for the EOL server).

**Why Shadow Migration over Direct Cutover?**
Direct Cutover (`New-MigrationBatch`) requires a full switch. Shadow Migration allows us to replicate content to M365 while users remain connected to the legacy Exchange 2016 server. This satisfies the "no interruption during business hours" constraint.

**Tool Selection:**
We will use a certified, MAPI-based migration tool (e.g., **BitTitan MigrationWiz**). This is critical because:
*   It connects directly to the Exchange 2016 MAPI layer without requiring a Hybrid connector.
*   It preserves MAPI properties, headers, and delivery timestamps natively.
*   It maintains a detailed audit log (Chain of Custody) for regulatory compliance.
*   It operates independently of the EOL server's Microsoft support status.

**Phased Execution:**

*   **Phase 0: Discovery & Compliance Baseline (Days 1–7)**
    *   **Inventory:** Enumerate all 340 mailboxes. Record current content volume, folder structures, and known critical items.
    *   **Security Scan:** Perform a full vulnerability scan on the Exchange 2016 server. Isolate the server on its network segment to prevent lateral movement while connecting to M365.
    *   **Baseline Hashing:** Generate cryptographic hashes of mailbox content for the first 10 pilot mailboxes to establish a "Chain of Custody" baseline.
    *   **Compliance Log:** Initiate the Chain of Custody ledger in the acquiring bank's GRC system.

*   **Phase 1: Shadow Migration & Validation (Days 8–21)**
    *   **Tooling:** Deploy the migration tool to create shadow mailboxes in M365.
    *   **Pilot (10 Mailboxes):** Migrate 10 mailboxes. Verify MAPI headers, timestamps, and content integrity against the baseline hashes.
    *   **Validation:** Regulatory team verifies a sample of migrated mailboxes for timestamp accuracy and metadata retention.
    *   **Scale-Up:** Once validation passes, shadow migration runs for all 340 mailboxes.
    *   **Scheduling:** Migration runs 24/7 in the background. No user interruption occurs.

*   **Phase 2: Incremental User Cutover (Days 22–35)**
    *   **Batching:** Move mailboxes in batches of 20–30 per day during the **overlap window** (9 AM–5 PM in both time zones).
    *   **User Transition:** As each batch is verified, users update their Outlook profile to connect to M365 (Cached Exchange Mode).
    *   **Verification:** For each user, the regulatory team verifies content integrity post-cutover before the legacy mailbox is decommissioned.
    *   **Decommission:** Legacy Exchange 2016 mailboxes are disabled in the source environment only after M365 copy is verified.

*   **Phase 3: Final Decommission (Days 36–38)**
    *   **Source Cleanup:** Remove Exchange 2016 mailboxes from the community bank's on-prem environment.
    *   **Final Audit:** Generate a final Chain of Custody report.
    *   **Decommission Server:** Take the Exchange 2016 server offline for the acquiring bank's disposal/repurposing process.

### 2. Sequencing Relative to the 45-Day Core-Banking Cutover

**The Constraint:**
*   Core-Banking Cutover: **Day 45** (Start of Week 7).
*   Email Migration: **Cannot** occur during the Banking Cutover week.
*   Staff Need Email: During Banking Cutover, branch staff must have working email to field questions.
*   Change Freeze: Both teams cannot be in a freeze simultaneously.

**The Plan:**
*   **Email Migration Window:** Days 1 to **Day 35** (One full week *before* the Banking Cutover).
*   **Banking Cutover Window:** Days 38 to 45.
*   **Buffer:** Days 36–37 (Post-migration verification and legacy server decommissioning).

**Why This Works:**
1.  By Day 35, all 340 mailboxes are live on M365.
2.  Branch staff have been using M365 for one week, ensuring they are comfortable and trained.
3.  During Banking Cutover (Days 38–45), the Email team is *not* in a change freeze. They are free to support the Banking team.
4.  Staff have email (M365) during Banking Cutover to field questions.

### 3. Rollback Plan

**Scenario:** A mailbox batch fails partway through migration (e.g., data corruption detected during sync, or the EOL server becomes unstable).

**Immediate Action:**
1.  **Stop Migration:** Halt the migration tool immediately for the affected batch.
2.  **Isolate:** Quarantine the affected M365 shadow mailboxes to prevent data drift.
3.  **Document:** Log the failure in the Chain of Custody system with the specific mailbox IDs and error codes.

**Recovery Strategy:**
1.  **Revert Shadow:** Delete the failed shadow mailbox in M365.
2.  **Restore Source:** Ensure the mailbox on the Exchange 2016 server remains untouched (intact).
3.  **Resume:** Restart the migration for the specific batch. If the EOL server is unstable, the migration tool may need to be rerun after a server reboot.
4.  **Verify:** Re-run the cryptographic hash comparison against the baseline.

**Worst-Case Rollback (Full Batch Failure):**
If the migration tool fails for an entire week's batch due to server instability:
1.  **Freeze:** Halt migration for the affected batch.
2.  **Legacy Support:** Continue to support affected users via the Exchange 2016 server.
3.  **Recovery:** Schedule a recovery run during the next available window (evening/weekend).
4.  **Regulatory:** Notify the compliance team that the batch is pending recovery. Once recovered, re-verify timestamps and content integrity before cutting over.

### 4. Blast Radius Analysis: Sequencing Errors

**Scenario A: Migration Scheduled During Banking Cutover Week (Days 38–45)**
*   **Blast Radius:** Critical.
*   **Impact:**
    *   **Double Change Freeze:** Both the Email team and Banking team are in freeze. No resources available for either team.
    *   **Email Disruption:** If migration fails during cutover, branch staff lose email access. They cannot field Banking cutover questions.
    *   **Regulatory Violation:** If the Banking cutover is delayed due to email issues, the Banking team may blame the Email team, leading to a breach of the retention obligations if data is lost during emergency manual intervention.
    *   **Financial Loss:** Delayed Banking cutover = delayed revenue/operational changes.

**Scenario B: Migration Started Too Late (After Banking Cutover)**
*   **Blast Radius:** High.
*   **Impact:**
    *   **Staff Frustration:** Branch staff have been on the legacy EOL server during the Banking cutover. If they need to switch to M365 *after* the Banking cutover, they may face training gaps during the transition.
    *   **EOL Risk:** The Exchange 2016 server may fail during the Banking cutover week (unsupported). If it fails, staff have no email at all.
    *   **Compliance Risk:** If the server fails, data integrity may be compromised during emergency recovery.

**Scenario C: Migration Completed Too Early (Before Day 35)**
*   **Blast Radius:** Low (Positive).
*   **Impact:**
    *   **Buffer:** Allows the Email team to test, fix bugs, and train staff *before* the Banking Cutover.
    *   **Risk:** If the migration is completed too early, the EOL server is left running longer than necessary, increasing the risk of a security breach or data loss on the unsupported server.
    *   **Mitigation:** Decommission the EOL server immediately upon successful migration verification.

**Conclusion:**
The **Days 1–35** window for migration is the only safe sequencing. It avoids the Banking Cutover week, provides a buffer for verification, and ensures staff have email during the Banking Cutover. Any deviation from this plan increases the blast radius significantly.

### 5. Chain of Custody & Regulatory Compliance

To satisfy the regulatory constraint that "every mailbox's content and metadata survive migration intact":

1.  **Pre-Migration Hashing:** Generate SHA-256 hashes of mailbox content for a sample of mailboxes before migration.
2.  **Post-Migration Hashing:** Generate SHA-256 hashes of the same mailboxes in M365 after migration.
3.  **Comparison:** Compare hashes. If they match, the data is intact.
4.  **Metadata Preservation:** The migration tool preserves MAPI headers (Received timestamps, Sender, Subject, etc.).
5.  **Logging:** All migration events (start, stop, success, failure) are logged in the migration tool's audit trail.
6.  **Documentation:** A final Chain of Custody report is generated and filed in the acquiring bank's compliance repository.

## 3. Cut‑Over Approach (Given Unsupported Exchange 2016)

1. **Read‑Only Export First** – Because the on‑prem server is past extended support, we **do not attempt a live hybrid sync** that could pull new mail after export. Exporting to .pst guarantees a *point‑in‑time snapshot* that can be legally held.
2. **Remote Move‑Request** – Office 365’s **Remote Move** treats the .pst as the source, preserving all Exchange attributes (including `DeliveryTime` from message headers). This method works even when the source server is offline after export.
3. **DNS‑Based Cut‑Over** – The only moment a user’s client points to a different server is the **MX switch**. By scheduling the MX change **outside any branch’s 9 am‑5 pm window**, we honor the “no interruption” rule.
4. **Grace Period** – Keep the on‑prem Exchange **read‑only for 48 h** after the last batch finishes. If a regulatory audit demands a re‑export, the data is still available without having to spin up the server again.

| Failure Point | Detection | Immediate Action | Rollback Scope | Documentation |
|---------------|-----------|------------------|----------------|----------------|

* **Branch‑Level Isolation** – Because each branch’s MX switch is independent, a failure isolates to that branch only, limiting blast radius to ≤ 20 mailboxes at a time.

*If the cut‑over week is in the middle of the migration window, we pause all batches for that week and resume the next week.*

## 5. Rollback Plan (If a Batch Fails)

| Condition | Action | Owner |
|-----------|--------|-------|
| **5.1 Batch Failure** | • Pause batch. <br>• Review error (e.g., “Mailbox size > 50 GB”). <br>• If recoverable, fix and resume. | Migration Engineer |
| **5.2 Critical Failure (> 10 % of mailboxes in batch)** | • Stop all migrations. <br>• Initiate rollback for affected mailboxes. | Migration Lead |
| **5.3 Rollback Steps** | 1. **Backup** – Export affected mailboxes from M365 using *eDiscovery* export (PST). <br>2. **Re‑migration** – Create a *migration endpoint* back to on‑prem (reverse migration). <br>3. **Validate** – Compare PST metadata with on‑prem mailbox. <br>4. **Finalize** – Delete M365 mailbox to avoid duplication. | Migration Engineer |
| **5.4 Backup Strategy (Pre‑Migration)** | • Daily full mailbox backup using a 3rd‑party tool (e.g., Veeam, Altaro). <br>• Store backups in an immutable Azure Blob. | Backup Team |
| **5.5 Documentation** | • Update chain‑of‑custody log with rollback details. <br>• Sign the rollback log. | Compliance Officer |

*Rollback is only performed for **critical** failures; otherwise we resolve issues in‑place.*

3. Export to CSV, sign, and upload.  
4. Verify that every mailbox in the batch appears once with a successful status.

## 7. Risk & Blast‑Radius Mitigation

| Risk | Impact | Mitigation | Owner |
|------|--------|------------|-------|
| **R1 – Migration endpoint failure** | All batches fail | Keep a secondary migration endpoint (using IMAP as fallback, though metadata loss). | Migration Engineer |
| **R2 – Data loss during migration** | Regulatory breach | Daily mailbox backups; audit logs; *Litigation Hold* active. | Backup Team |
| **R3 – Mis‑scheduling causing cut‑over conflict** | Business disruption | Shared calendar, automated blackout week detection, change‑freeze approvals. | Project Manager |
| **R4 – Network congestion during overnight migration** | Slow migration, time‑outs | Use *Quality of Service* (QoS) on branch routers; schedule high‑priority traffic for migration. | Network Ops |
| **R5 – User confusion post‑migration** | Productivity loss | Pre‑migration training, FAQ, dedicated support line. | User Experience Lead |
| **R6 – Regulatory audit during migration** | Legal exposure | Keep all audit logs, chain‑of‑custody signed, and ready for review. | Compliance Officer |

## 10. Summary

By leveraging **Exchange Online mailbox‑move** with a migration endpoint, we preserve every piece of mailbox data—including timestamps, metadata, and retention tags—while keeping user access uninterrupted. The overnight, per‑branch batch strategy respects operational constraints across two time zones. The 45‑day timeline is deliberately structured to avoid any overlap with the core‑banking cut‑over week, thereby eliminating the blast‑radius risk. The robust chain‑of‑custody process, daily backups, and a clear rollback path ensure regulatory compliance and provide a safety net for any unforeseen failures. This phased plan gives the acquiring bank confidence that the migration will be seamless, compliant, and fully auditable.
