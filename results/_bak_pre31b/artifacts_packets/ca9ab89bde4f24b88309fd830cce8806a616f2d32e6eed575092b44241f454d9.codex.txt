# Cybersecurity -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Severity is triaged correctly against the actual impact described, response actions follow containment before eradication before recovery, and any CVE, CWE, or ATT&CK reference used is real and correctly applied (never invented). Evidence-preservation is called out before disruptive remediation, and breach-notification or compliance timelines are flagged when the scenario implies regulated or sensitive data. The answer is calibrated about what needs live forensics versus what can be assessed from the facts given.
Example character: a triaged action list that isolates the affected system first, preserves logs, then patches, with the real CVE cited only where it is genuinely relevant.

## 7 -- Strong
The response plan is sound and correctly ordered (containment before eradication), and is directly usable by a responder. References to standards or CVEs are generic rather than specific, or evidence-preservation/notification timing gets only a light mention. Severity is judged reasonably even if not formally scored.
Example character: a correct incident-response sequence that never names a specific CVE or ATT&CK technique even where the prompt supports one.

## 5 -- Adequate
The advice reads as a generic security checklist (patch systems, enable MFA, monitor logs) that is directionally correct but not prioritized by the actual severity or tailored to the specific incident described.
Example character: a list of general hardening steps with no sense of which one matters most given the described exposure.

## 3 -- Weak
The response gets the ordering wrong (patches or removes an attacker's access before containing them), misjudges severity, or pads the answer with boilerplate ("enable a firewall") that does not engage the specific scenario.
Example character: jumps straight to "eradicate the malware" on an active intrusion without isolating the host first.

## 0 -- Unusable
Cites a fabricated CVE, CWE, or CVSS score as if verified, or recommends actively dangerous steps (disable logging, do not isolate an active breach) as sound practice. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Fabricated CVE, CWE, or CVSS identifiers presented as real.
- Eradication or patching recommended before containment on an active incident.
- Recommending disabling logging or otherwise destroying evidence.
- Ignoring implied breach-notification or regulatory timelines when sensitive data is involved.
- Treating every finding as equally critical with no severity differentiation.

## Unit-specific excellence markers
- Severity correctly triaged and prioritized against the described impact.
- Containment-before-eradication-before-recovery ordering respected.
- Real, correctly-applied CVE/CWE/ATT&CK references where relevant.
- Evidence-preservation explicitly called out.
- Notification or compliance timeline awareness when data exposure is implied.

# Phishing‑Response Run‑Book – Level‑1 Helpdesk  
*(Designed for a 60‑person MSP client with no dedicated security staff)*  

> **Goal:**  Stop the attack, recover the compromised accounts, and make sure no hidden back‑doors remain – **in the order that matters most.**  

---  

## 1️⃣  PRIORITY 1 – Contain the Breach (Stop the attacker from using the stolen credentials)

| Step | What to Do | Why it Matters |
|------|------------|----------------|
| **1‑A** | **Force an immediate password reset for each of the 6 compromised accounts.**  <br>• Open the M365 admin portal → Users → Active users → Select the account → *Reset password*.<br>• Choose **“Force password change at next sign‑in.”** | Guarantees the attacker can no longer use the password that was harvested. |
| **1‑B** | **Require MFA enrollment for every affected user.**  <br>• In the same user pane, enable **“Multi‑Factor Authentication.”**<br>• Send the user a short “Set up MFA now” link (or direct them to https://mysignins.microsoft.com). | MFA blocks the same password from being used again, even if the attacker still has it. |
| **1‑C** | **Terminate all active sessions** for the six accounts.  <br>• In the admin portal, **Sign‑ins** → select the user → **“Sign out”** (or “Sign out all”).<br>• Or run `Clear‑SignInSessions -UserPrincipalName <user>` via PowerShell if needed. | Cuts off any session the attacker may already have open (e.g., the “ASN‑X” sign‑in you saw). |
| **1‑D** | **Block sign‑ins from the suspicious ASN** (if you can identify it).  <br>• In the Conditional Access policy, add a **“Block”** rule for the offending IP range or ASN.<br>• If you’re not comfortable editing policies, ask a senior admin to add a temporary block. | Prevents any further log‑ins from that location while you investigate. |
| **1‑E** | **Check for “App passwords” or “Exchange‑online PowerShell” tokens** that may have been created.  <br>• In the admin portal → Users → Multi‑factor authentication → *App passwords*.<br>• Revoke any you find. | Attackers can bypass MFA with an app password; revoking removes that back‑door. |

> **Result of Priority 1:** The attacker can no longer authenticate with the stolen password, all active sessions are killed, and you’ve added a barrier (MFA) that blocks future misuse.

## 2️⃣  PRIORITY 2 – Verify the Account is Clean & Re‑Enable Normal Access

| Step | Action | Reason |
|------|--------|--------|
| **2‑A** | **Ask the user to sign in again** (on a trusted device) and confirm they can now **receive an MFA challenge**. | Confirms that the password reset + MFA enforcement worked. |
| **2‑B** | **Confirm the user can access Outlook/Teams without prompts** (e.g., open mailbox, read a recent message). | Ensures normal service is restored before you move on to deeper checks. |
| **2‑C** | **Document the outcome** (reset time, MFA enrollment status, any error messages). | Provides a clear audit trail for later review and for any escalation. |

## 3️⃣  PRIORITY 3 – Investigate the Compromised Mailboxes (What to look for beyond the obvious inbox rule)

> The attacker didn’t just steal a password; they also **created hidden forwarding rules** and likely performed other actions that a simple password reset will not fix.  

| Step | What to Check | How to Do It (Level‑1 Friendly) |
|------|---------------|---------------------------------|
| **3‑A** | **All inbox rules** (including hidden ones). | In Outlook Web → Settings (gear) → **“View all Outlook settings.”** → **Mail → Rules**. Export or screenshot the list. |
| **3‑B** | **Forwarding to external addresses** (e.g., rules that forward “any mail” or “mail with subject containing …”). | In the same **Rules** view, look for any rule that ends with **“Redirect to people outside the organization.”** If found, delete it immediately. |
| **3‑C** | **Inbox “Redirect” vs. “Forward”** – Redirect shows the original message in the recipient’s inbox; Forward adds a copy to the original sender. | Confirm the rule type; if it’s a **Redirect**, it may have been used to send copies to an external mailbox that the attacker controls. Delete it. |
| **3‑D** | **Delegate access / sharing permissions** (e.g., “Editor” on Calendar, “Send As” rights). | Outlook → **File → Account Settings → Delegates** (or in the admin portal → **Permissions** → **Mailbox permissions**). Remove any unknown users. |
| **3‑E** | **Hidden mailbox folders** (e.g., “Dumpster,” “Recoverable Items,” or custom folders used to hide malicious messages). | In Outlook Web → **Mail** → **More** → **Deleted Items** → **Recover items** → scan for suspicious emails. |
| **3‑F** | **Message trace / audit logs** for sent items. | In the admin portal → **Exchange admin center** → **Mail flow > Message trace**. Search for any outbound email from the compromised accounts in the last 48 h. Look for recipients you don’t recognize. |
| **3‑G** | **Deleted or sent‑mail items that match the phishing template**. | Search the **Sent Items** and **Deleted Items** folders for any messages with the same subject line (“invoice”) or attachment name. If found, delete them permanently. |
| **3‑H** | **External mail‑forwarding aliases** attached to the mailbox (e.g., an extra SMTP address that forwards mail to a personal domain). | In Exchange admin center → **Recipients → Mailboxes** → select the account → **Email aliases**. Remove any you do not recognize. |
| **3‑I** | **Mailbox auditing / retention policies** that may have been altered. | Verify the **Retention** settings are still the default corporate policy; if they were changed to “Never delete,” revert them. |
| **3‑J** | **Check for malicious attachments or links still saved in the mailbox** (e.g., the original Word file that delivered the Follina exploit). | Use Outlook’s **Search** box with keywords like “*Follina*”, “*CVE‑2022‑30190*”, or the attachment name. If any are found, delete them and run a quick **Endpoint AV scan** on the user’s device (if you have that capability). |

> **Why each check matters:**  
> *Forwarding rules* can silently exfiltrate data even after you change the password. *Delegate permissions* can let the attacker act as the victim without needing credentials. *Sent‑mail* or *message‑trace* evidence shows whether the attacker already used the compromised account to send phishing or malicious emails to others. *Retention / audit* changes may hide the attacker’s tracks.

| **4‑B** | **Check for similar inbox rules** on any other mailboxes that contain the word “invoice” or “payment.” | Attackers often copy successful tactics to other targets. |
| **4‑C** | **Refresh the user’s device compliance** (if you manage endpoints). Ensure the user’s laptop/phone is up‑to‑date and has the latest security patches. | Reduces the chance the same vulnerability (e.g., a macro‑less Office exploit) is re‑used. |
| **4‑D** | **Send a short “Security awareness” reminder** to all staff, highlighting the specific phishing technique (Word doc with external link that triggers Follina). | Helps prevent repeat clicks. |

| **5‑C** | **Update the client’s incident‑response checklist** with the steps you just performed. | This makes future incidents faster to handle. |

## 📌  Why a Password Reset Alone Is **Not** Enough  

1. **The attacker already used the stolen credentials** to sign in from an unknown ASN and **bypassed MFA** (no challenge was triggered). That means the attacker still had an active session when you reset the password.  
2. **Inbox rules were created that silently forward and delete** copies of messages containing “invoice.” Deleting the password does **not** automatically delete those rules; they remain active and will continue to exfiltrate data.  
3. **The attacker may have added forwarding to external mailboxes** or delegated themselves to other users. Those permissions survive a password change.  
4. **Session tokens, app passwords, or OAuth grants** could still be valid, allowing the attacker to stay connected even after the password is changed.  
5. **The malicious Word document may still reside** in the user’s mailbox or on the endpoint, ready to be re‑used if the user opens another similar attachment.  

**Bottom line:** Resetting the password stops *future* misuse of that credential, but it does **not** remove the *back‑doors* (rules, permissions, sessions) that the attacker already installed. That’s why the run‑book above checks every rule, permission, and log entry before declaring the incident “closed.”

# Phishing‑Response Runbook  
**Audience:** Level‑1 Help‑Desk Technician (no prior security experience)  
**Environment:** 60‑employee MSP client, Microsoft 365 (Exchange Online, Azure AD) – no dedicated security staff  

---

## 1.  WHY A SIMPLE PASSWORD RESET IS NOT ENOUGH  

| Observation | What it means | Why a password reset alone does **not** solve it |
|-------------|---------------|---------------------------------------------------|
| Successful sign‑ins from an unfamiliar ASN (different country) within 48 h of the phishing email. | Attackers already have a valid authentication **session** (access token) for the compromised accounts. | Resetting the password does not immediately invalidate existing access tokens, OAuth app grants, or “remembered” devices. The attacker can continue to act until those tokens are revoked. |
| No MFA challenge was presented. | The attacker bypassed MFA (either because MFA was not enabled, or they used a “remembered” device / “app password”). | Even after a password reset, the attacker can reuse the same “remembered” device or app password unless MFA is enforced and existing device registrations are cleared. |
| New inbox rules that silently forward/delete messages containing “invoice”. | Persistence mechanism – the attacker can keep receiving copies of new invoices even after the password is changed. | Resetting the password does not delete the malicious inbox rule. The forward will continue until the rule is removed. |
| Potential other artifacts (delegations, connected apps, mailbox‑export‑permissions, etc.) that are not visible in the UI. | Attackers often add **additional** back‑doors (e.g., grant an OAuth app, add a delegate, enable “auto‑reply”, create a hidden rule). | A password change does not automatically remove these back‑doors. They must be discovered and cleared. |

**Bottom line:** To fully remediate you must **(a) terminate all existing sessions**, **(b) enforce MFA**, **(c) revoke any persistent tokens or app grants**, and **(d) remove all malicious mailbox configurations** (rules, delegates, apps, etc.).

## 3.  DETAILED STEP‑BY‑STEP PROCEDURES  

> **Tip:** If you ever feel unsure, stop and ask your supervisor or the MSP security lead. Do not skip any step.

### 3.1  Prerequisites (what you need)

| Item | Where to find it | How to access |
|------|------------------|---------------|
| **Microsoft 365 admin credentials** (global admin) | Provided by MSP manager | Sign‑in to <https://admin.microsoft.com> |
| **Azure AD portal** | <https://aad.portal.azure.com> | Same global admin |
| **PowerShell (AzureAD / MSOnline)** | Installed on your admin workstation | Run `Connect-AzureAD` (or `Connect-MsolService`) |
| **Microsoft 365 Defender portal** | <https://security.microsoft.com> | Global admin or Security admin |
| **List of the six compromised user UPNs** | From the ticket or sign‑in log | e.g., `jane.doe@client.com` |
| **Two compromised mailboxes** | `accountspayable@client.com`, `controller@client.com` | Use Exchange admin center (EAC) or Outlook Web App (OWA) |

---

### 3.2  Priority 1 – Isolate & Reset

1. **Block sign‑in for each compromised user**  
   - In the **Azure AD portal**, go to **Users > Select user > Sign‑in blocked** → **Yes**.  
   - *(Why?)* This prevents any further login while you work.

2. **Force sign‑out of all active sessions**  
   - Still in the user profile → **Devices > Sign‑out all sessions** (or **Revoke sessions**).  
   - Alternatively, run PowerShell:  

     ```powershell
     # Replace USER@domain.com with the actual UPN
     Revoke-AzureADUserAllRefreshToken -ObjectId (Get-AzureADUser -ObjectId USER@domain.com).ObjectId
     ```

3. **Reset the password**  
   - In **Microsoft 365 admin center** → **Active users** → select user → **Reset password**.  
   - Use a **strong, unique** temporary password (the system will generate one).  
   - Record the new password in the ticket (encrypted or in the MSP password vault).

4. **Enforce MFA immediately**  
   - In **Azure AD > Users > Multi‑Factor Authentication** → **Enable** for the user.  
   - If the tenant uses Conditional Access, add a temporary policy:  

     - **Assignments:** All users (or just the six).  
     - **Grant:** Require multi‑factor authentication.  
     - **Enable** the policy.

5. **Unblock sign‑in** (once MFA is enforced)  
   - Return to the user profile → **Sign‑in blocked** → **No**.

**Result:** The attacker can no longer use the old password, cannot log in without MFA, and any existing session tokens are revoked.

---

### 3.3  Priority 2 – Revoke All Tokens & App Grants

1. **Revoke OAuth refresh tokens** (covers third‑party apps, Outlook mobile, etc.)  

   ```powershell
   # For each compromised user
   $user = Get-AzureADUser -ObjectId USER@domain.com
   Revoke-AzureADUserAllRefreshToken -ObjectId $user.ObjectId
   ```

2. **Remove “remembered” devices** (if any)  

   - In Azure AD portal → **Devices > All devices** → filter by **Owner** = user → **Delete** each device.  
   - Or run:  

     ```powershell
     Get-AzureADUserDevice -ObjectId $user.ObjectId | foreach { Remove-AzureADDevice -ObjectId $_.ObjectId }
     ```

3. **Delete any App Passwords** (if the tenant allows legacy auth)  

   - In **My Account > Security info** (user can do this after password reset) or via PowerShell:  

     ```powershell
     Get-MsolUser -UserPrincipalName USER@domain.com | Select-Object -ExpandProperty StrongAuthenticationMethods
     # Then remove any listed app passwords
     ```

**Result:** No lingering tokens or app passwords can be used to bypass the new password/MFA.

---

### 3.4  Priority 3 – Remove Malicious Inbox Rules (visible)

Do **this for each of the two compromised mailboxes** (`accountspayable@`, `controller@`).

1. **Log into Outlook on the Web (OWA) as the affected user** (you can use the temporary password).  
2. Click the **gear icon** → **View all Outlook settings** → **Mail > Rules**.  
3. Locate any rule that:  

   - Has **“Forward to”** an external address.  
   - Has **“Delete”** or **“Move to Deleted Items”**.  
   - Contains the word **“invoice”** in the subject condition.  

4. Click the **trash can** icon to **delete** the rule.  
5. **Save** changes.

*If you cannot log in as the user (e.g., mailbox is locked), use PowerShell:*

```powershell
# Connect to Exchange Online first
Import-Module ExchangeOnlineManagement
Connect-ExchangeOnline -UserPrincipalName admin@client.com

# List all inbox rules for the mailbox
Get-InboxRule -Mailbox accountspayable@client.com

# Delete the suspicious rule (replace "InvoiceForward")
Remove-InboxRule -Identity "InvoiceForward" -Mailbox accountspayable@client.com -Confirm:$false
```

**Result:** No more automatic forwarding or deletion of invoices.

---

### 3.5  Priority 4 – Deep Mailbox Audit (what else to look for)

> **Goal:** Find any hidden persistence the attacker may have added.

| Check | Where to look | How to do it (step‑by‑step) |
|-------|---------------|-----------------------------|
| **Other inbox rules** (including hidden ones) | Exchange Online PowerShell: `Get-InboxRule` | Run `Get-InboxRule -Mailbox <mailbox>` and scan the full list for anything suspicious (e.g., forwarding to external addresses, “Mark as read”, “Delete”, “Move to folder”). |
| **Mailbox delegation** (FullAccess, SendAs, SendOnBehalf) | Azure AD / Exchange: `Get-MailboxPermission`, `Get-RecipientPermission` | ```powershell Get-MailboxPermission -Identity accountspayable@client.com | Where {$_.AccessRights -ne "None"} ``` Look for unfamiliar users or service accounts. |
| **Connected OAuth apps** (grant permissions to the mailbox) | Microsoft 365 Defender > **Identity > Applications** or PowerShell `Get-MgUserOAuth2PermissionGrant` | ```powershell Connect-MgGraph -Scopes "User.Read.All","Directory.Read.All" Get-MgUserOAuth2PermissionGrant -UserId <UPN>``` Review any app that has **Mail.Read**, **Mail.ReadWrite**, **Mail.Send** scopes. |
| **Automatic Replies / Vacation messages** | OWA > Settings > Automatic replies, or PowerShell `Get-MailboxAutoReplyConfiguration` | ```powershell Get-MailboxAutoReplyConfiguration -Identity accountspayable@client.com``` |
| **Inbox export / eDiscovery permissions** | Security & Compliance Center > **eDiscovery** > **Permissions** | Verify that the compromised user does not have eDiscovery manager rights (unlikely, but check). |
| **Mailbox audit log** (who accessed, when) | In Defender > **Search** > **Audit log** or PowerShell `Search-UnifiedAuditLog` | ```powershell Search-UnifiedAuditLog -StartDate (Get-Date).AddDays(-7) -EndDate (Get-Date) -UserIds accountspayable@client.com -Operations MailItemsAccessed, MailItemsExported``` |
| **Hidden “Inbox rules” stored in the mailbox (client‑side)** | Outlook client > Rules & Alerts → “Run Rules Now” (rare) | If the user uses Outlook desktop, ask them to open **Rules & Alerts** and click **Options → Export Rules** – look for any rule file that may have been imported. |

**What to do with findings:**  

- **Delete** any rule, delegate, or app that is not part of normal business operation.  
- **Document** the name, type, and who created it (the audit log often shows the creator).  

**Result:** All persistence mechanisms are removed.

### 3.6  Priority 5 – Scan for Additional Compromised Accounts

1. **Sign‑in risk report**  
   - In **Microsoft 365 Defender** → **Identity** → **Sign‑in risk**.  
   - Filter: **Risk level = High / Medium** and **Date = last 7‑14 days**.

# 📌 WHY A PASSWORD RESET ALONE WILL NOT FULLY REMEDIATE THIS INCIDENT
*(Given the sign-in logs showing successful logins from an unfamiliar ASN with NO MFA challenge)*

A password reset **does not** address the actual attack vector or the attacker’s existing access. Here’s why:

1. **Active sessions persist after a password change.**  
   Microsoft 365 does NOT automatically terminate logged-in sessions when a password is reset. The attacker’s browser, Outlook, or mobile device remains authenticated until sessions are explicitly revoked.

2. **MFA was never challenged → the attacker likely didn’t use a password at all.**  
   The sign-in logs show successful logins without an MFA prompt. This strongly indicates one of:
   - **Session token/cookie theft:** The Follina exploit or phishing page captured an existing browser session token, which the attacker replayed without re-authenticating.
   - **Conditional Access misconfiguration:** A policy allowed sign-ins from untrusted locations without requiring MFA.
   - **Legacy authentication enabled:** Protocols like IMAP/POP3/ActiveSync do not trigger MFA. The attacker authenticated using username + captured password via a non-interactive protocol.
   Password reset does not invalidate OAuth tokens, refresh tokens, or legacy auth sessions.

3. **Attacker-created access mechanisms survive password changes.**  
   Once inside, the attacker can create inbox rules, mailbox forwarding, delegated access, and OAuth app registrations. None of these are tied to the user’s password. Resetting the password leaves all of these intact.

4. **OAuth & refresh tokens are independent of passwords.**  
   If the phishing page tricked the user into granting consent to a malicious app, or if the attacker registered a service principal, those tokens persist regardless of password changes until explicitly revoked by an admin.

**Bottom line:** You must (a) revoke all active sessions, (b) force MFA re-enrollment, (c) disable legacy auth, (d) clean mailbox artifacts, and (e) audit OAuth/app access. A password reset only handles step 1 of a multi-layer compromise.

## Part 1: The "Why" (Read Before Starting)

**Why isn't a Password Reset alone enough to fix this?**

You might be tempted to just tell the 6 affected users to change their passwords. **Do not do this.** Here is why:

1.  **Active Sessions:** Even after you reset the password, the attacker is *already logged in*. Microsoft 365 sessions persist for a long time. The attacker will stay in until you force them to sign out.
2.  **MFA Bypass:** Your sign-in logs show the attacker logged in **without triggering Multi-Factor Authentication (MFA)**. This means the attacker likely has a device registered to the account that Microsoft trusts, or the MFA policy is not enforced for this type of login. If you reset the password but don't force them to use MFA, the attacker can simply log back in with the new password and keep going.
3.  **Shared Accounts:** Two of the compromised accounts (`accountspayable@` and `controller@`) are likely shared mailboxes used by multiple people. A password reset changes the credential, but it doesn't remove the malicious rules or permissions the attacker created.

**The Goal:** We need to **lock them out** (Contain), then **reset credentials and enable MFA** (Recover), and finally **remove the attacker's access** (Eradicate).

---

## Part 2: Immediate Containment (Do Immediately)

**Objective:** Stop the attacker from reading, deleting, or forwarding emails.

### Step 1: Force Sign-Out for All 6 Accounts
*   **Action:** Go to the Microsoft 365 Admin Center > **Users** > **Active Users**. Find the 6 affected email addresses. Click on each and select **Sign out**.
*   **Why:** This forces the attacker off the account immediately. It does not reset the password, but it stops them from reading emails while you fix the other issues.
*   **Note:** If you cannot find all 6 accounts easily, ask your MSP Manager to run a PowerShell command to force sign-out for all 6 addresses at once.

### Step 2: Disable the 2 Most Critical Accounts
*   **Action:** For `accountspayable@` and `controller@`, click **Disable** in the Admin Center.
*   **Why:** These accounts are forwarding emails to an external address. If we don't disable them, the attacker might re-activate them or continue deleting invoices. We will re-enable them in Step 5 after cleaning.

## Part 3: Credential Recovery & MFA Enforcement

**Objective:** Ensure the attacker cannot log back in.

### Step 3: Reset Passwords for All 6 Accounts
*   **Action:** In the Admin Center > **Users** > **Active Users**, find the 6 accounts. Click on each and select **Reset Password**. Send them a notification (password reset email).
*   **Why:** This invalidates the stolen password.

### Step 4: Force MFA Enrollment
*   **Action:** In the Admin Center > **Users** > **Active Users**, find the 6 accounts. Click on each and select **Manage Multi-Factor Auth**. If MFA is not enabled, **Enable it** and force them to register a device immediately.
*   **Why:** The logs showed the attacker logged in *without* MFA. This is the biggest risk. If MFA is not enforced, the attacker can log in with the new password and take over again.
*   **Note:** If MFA is technically broken for these users, escalate to your MSP Manager immediately. Do not try to bypass it.

## Part 4: Mailbox Forensics (Beyond Inbox Rules)

**Objective:** Find everything the attacker has done *other* than the known inbox rules.

The inbox rules forwarding "invoice" emails are just the tip of the iceberg. The attacker may have done other things. Check the following in each affected mailbox:

### Step 5: Check Delegate Permissions (Critical)
*   **Action:** In the Admin Center > **Mail** > **Mail flow** > **Mailboxes**. Select the affected mailbox. Look for **Mailbox Delegation**.
*   **What to look for:** Did the attacker add themselves as a "delegate" for **other mailboxes**?
*   **Why:** Attackers often add themselves as delegates to *other* employees' mailboxes to harvest more credentials. If they have delegate access to `hr@`, `sales@`, or `ceo@`, they can read those emails too.

### Step 6: Check for Admin Roles
*   **Action:** In the Admin Center > **Users** > **Active Users**. Select the affected mailbox. Look for **Roles** or **Permissions**.
*   **What to look for:** Did the attacker add themselves to the **Exchange Admin role** or **Global Admin role**?
*   **Why:** If they have admin access, they can lock out real employees, change security policies, or access *every* mailbox in the company, not just these two.

### Step 7: Check for Additional Transport Rules
*   **Action:** In the Admin Center > **Mail** > **Mail flow** > **Rules**.
*   **What to look for:** Are there **other rules** that forward or delete emails? Look for rules that match keywords like "payment," "wire," "transfer," "vendor," or "expense."
*   **Why:** The attacker might have more rules than just the "invoice" one. They may be sending sensitive financial data to an external email address under a different keyword.

### Step 8: Check Calendar, Contacts, and OneDrive
*   **Action:** Log into the affected mailbox via Outlook Web App (OWA) with a **newly created test account** (or use the Admin Center > **Mail** > **Mailboxes** > **Inspect mailbox**).
*   **What to look for:**
    *   **Calendar:** Is the attacker viewing sensitive meeting invites (e.g., "Board of Directors Meeting")?
    *   **Contacts:** Is the attacker syncing the contact list to their personal phone or email?
    *   **OneDrive/SharePoint:** Is the attacker sharing files externally? Look for "Shared with people outside your organization" in the sharing settings.
*   **Why:** Data exfiltration often happens through files, not just emails. The attacker may be downloading client lists or financial documents to a cloud drive.

### Step 9: Check for Malicious Outlook Profiles
*   **Action:** Ask the affected users to open Outlook desktop app. Go to **File** > **Account Settings** > **Account Settings**.
*   **What to look for:** Are there **extra email accounts** listed? (e.g., a personal Gmail or Yahoo account added to Outlook).
*   **Why:** The Follina vulnerability runs code on the user's computer. The attacker may have installed a profile to redirect emails from the corporate account to their personal account.

# Incident Response Runbook: Phishing & Account Compromise

**Incident Overview:** Users clicked a malicious Word document (CVE-2022-30190). Attackers successfully stole Microsoft 365 credentials and have bypassed MFA to maintain access. They are currently monitoring financial emails (invoices).

### ⚠️ CRITICAL: WHY A PASSWORD RESET IS NOT ENOUGH
**Do not simply reset the passwords and stop.** 
The sign-in logs show successful logins from an unfamiliar country *without* an MFA challenge. This indicates the attacker likely performed a **Session Hijack (Cookie Theft)**. 

When a user logs in, Microsoft issues a "Session Token" (a digital key) so the user doesn't have to type their password every time they click a new email. The attacker has stolen this "key." **Even if you change the password, that "key" remains valid, and the attacker will remain logged in until that specific session is forcefully killed.**

---

## Phase 1: Immediate Containment (Stop the Bleed)
*Perform these steps in order for all 6 compromised accounts.*

1.  **Revoke All Active Sessions:**
    *   Go to the **Microsoft 365 Admin Center** $\rightarrow$ **Active Users**.
    *   Select the affected user $\rightarrow$ **Sign-out all sessions**.
    *   *Goal:* This invalidates the stolen "Session Tokens" and forces the attacker out.
2.  **Reset Passwords:**
    *   Perform a password reset for all 6 users. 
    *   **Requirement:** The new password must be unique and not used by the user previously.
3.  **Re-Enroll/Verify MFA:**
    *   Check the user's MFA settings. Ensure no new, unrecognized phone numbers or "Authenticator Apps" were added by the attacker to maintain access.

---

## Phase 2: Eradication (Deep Clean)
*The attacker may have left "backdoors" to get back in later.*

1.  **Audit Mailbox Rules (Done by Lead, but verify):**
    *   Check for the "Invoice" rules mentioned in the briefing.
    *   **Check for other rules:** Look for rules that move mail to "RSS Feeds," "Deleted Items," or "Archive" folders (attackers use these to hide their activity).
2.  **Check Mailbox Forwarding Settings:**
    *   In the Exchange Admin Center, ensure **External Forwarding** is disabled for these users. Attackers often set up "Global Forwarding" which is separate from "Inbox Rules."
3.  **Check OAuth App Permissions:**
    *   In the M365 Admin Center, check if any "Third-Party Apps" or "Permissions" were granted to these mailboxes. 
    *   *Goal:* Attackers often authorize a malicious app to "Read Mail" so they can access data even after you change the password. **Delete any suspicious/unrecognized apps.**

---

## Phase 3: Investigation (Damage Assessment)
*Check these specific areas in the 6 compromised mailboxes to see what was stolen or changed.*

1.  **Sent Items Folder:**
    *   Check if the attacker sent any emails to clients, vendors, or internal staff (e.g., asking for gift cards or wire transfers).
2.  **Deleted Items / Archive Folders:**
    *   Look for emails that were deleted shortly after the compromise. Attackers often delete their "footprints" or the original phishing email.
3.  **Calendar Entries:**
    *   Check if the attacker added new meetings or changed meeting links. They may try to join future calls to gather more intelligence.
4.  **Contact List:**
    *   Verify that the user's contact list hasn't been altered to redirect communication to an attacker-controlled email address.

---

## Phase 4: Device Remediation (Local Security)
*Because the attack used "Follina" (a document-based exploit), the physical computer might be compromised.*

1.  **Identify the Machines:** Identify which 6 physical computers were used to open the malicious Word document.
2.  **Isolate the Machines:** Disconnect these computers from the Wi-Fi/Network immediately.
3.  **Full Malware Scan:** Run a full system deep scan using the company’s Endpoint Detection and Response (EDR) or Antivirus tool.
4.  **Escalate to Security Tier 2:** Notify the senior security team that potential "Remote Code Execution" occurred on these specific workstations.

---

## Phase 5: Reporting
1.  Document the time each account was secured.
2.  List the specific "Sent Items" or "Rules" found to help the client understand the scope of the data breach (important for their legal/compliance needs).

## 3. Reset Passwords **AND** Enforce MFA for All Accounts  
**Why a password reset alone is NOT enough**

| Reason | Explanation |
|--------|-------------|
| **Session persistence** | Once the attacker logs in, they can generate session tokens that stay valid for days. Resetting the password does **not** invalidate those tokens. |
| **MFA not triggered** | The sign‑in logs show *no* MFA challenge for the 6 accounts. If MFA is disabled or bypassed, the attacker can use the stolen credentials without additional verification. |
| **New rules/permissions** | The attacker may have already added forwarding rules, mail‑flow rules, or delegated permissions. Resetting the password won’t remove those changes. |
| **Other accounts** | The attacker could have used the credentials to create new privileged accounts. Resetting only the 6 users leaves a door open. |

| Step | Action | Tool |
|------|--------|------|

| 3.4 | Repeat steps 3.1–3.3 for **all other users** in the company (to be safe). |
| 3.5 | Record the **“MFA Enabled”** status in the ticket. | |

> **Note:** If you can’t enable MFA for all users immediately, at least enable it for the 6 compromised accounts and set a reminder.
