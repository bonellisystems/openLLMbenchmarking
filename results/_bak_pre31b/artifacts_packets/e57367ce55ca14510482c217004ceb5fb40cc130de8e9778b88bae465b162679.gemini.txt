## Role

You are one of three independent judges (Claude, Codex, Gemini) scoring a set
of blinded answers to a single MSP-realistic business task. You do not know
which model produced which answer -- every answer below is labeled only by a
letter. Do not try to guess model identity from writing style. Score only
what is on the page against the anchors below.

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

# Microsoft 365 / Active Directory Tenant Consolidation Plan

## Executive Summary
This plan addresses the migration of Firm B (45 users) into Firm A's (120 users) Microsoft 365/Active Directory environment while preserving critical AutoCAD Xref links for two projects with imminent permit submission deadlines.

## Migration Timeline
**Total Duration: 20 business days**
- **Phase 1:** Preparation and low-risk migrations (Days 1-10)
- **Phase 2:** Critical system migrations (Days 11-20)

## Migration Sequence

### Phase 1: Preparatory Work (Days 1-10)

#### Day 1-3: Infrastructure Preparation
- **File Share Preparation:**
  - Create new folder structure on Firm A's file share (\\FIRM-A-FS01\Projects\B-Users\)
  - Copy existing Firm B project files to new location
  - Update all Xref paths in Firm B projects to use new UNC paths
  - Document original Xref paths and new paths for rollback
  - Test AutoCAD Xref functionality with new paths

#### Day 4-7: User Account Preparation
- **Mailbox Preparation:**
  - Create placeholder mailboxes in Firm A tenant for all Firm B users
  - Configure mailbox retention policies
  - Test mailbox migration tools (Exchange Online PowerShell)
  - Prepare batch migration schedule
  - Create backup copies of Firm B users' mailboxes

#### Day 8-10: Testing and Validation
- **Testing:**
  - Perform test migration of 5 Firm B users
  - Validate mailbox functionality
  - Test email flow and calendar synchronization
  - Verify file access permissions
  - Document any issues

### Phase 2: Migration Execution (Days 11-20)

#### Days 11-15: Mailbox Migration
- **Batch 1:** 15 users (30% of Firm B)
  - Start migration during off-peak hours (midnight)
  - Monitor migration progress
  - Validate mailbox functionality
  - Update DNS records if necessary

#### Days 16-20: Final Migrations
- **Batch 2:** 30 users (remaining Firm B users)
  - Complete remaining user migrations
  - Verify all mailboxes are accessible
  - Update email routing rules
  - Final testing of shared mailboxes if applicable

## Critical Timing Requirements

### Before Permit Deadlines Pass (Days 1-20)
- **File share paths:** Must remain unchanged during permit deadlines
- **Mailbox UPNs:** Must remain unchanged during permit deadlines
- **AutoCAD Xref links:** Must remain functional for all active projects

### After Both Permit Deadlines Pass (Day 21+)
- **File share renaming:** Can proceed safely
- **Mailbox UPN changes:** Can be implemented
- **Final cleanup:** Remove old resources

## Risk Mitigation Strategies

### Xref Link Protection
1. **Pre-migration:** All Xref paths in active projects must be updated to new UNC paths
2. **During migration:** No file share movement or renaming occurs
3. **Post-migration:** Verify all Xref links function properly

### Mailbox Migration Failures
#### Rollback Plan:
1. **Immediate Action (Within 2 hours):**
   - Stop migration process
   - Revert user accounts to original state
   - Restore original UPNs
   - Reactivate Firm A's Exchange Online migration

2. **Recovery Steps:**
   - Identify failed batch
   - Restore mailboxes from backup
   - Re-enable original email routing
   - Restart migration for failed batch
   - Document rollback steps

3. **Alternative Recovery:**
   - Create new mailbox for failed user
   - Manually copy email content from original mailbox
   - Update user contact information
   - Update email routing

## Required Actions After Permit Deadlines

### Must Wait Until Both Deadlines Pass:
1. **File Share Renaming:**
   - Rename \\FIRMB-FS01 to \\FIRM-A-FS01
   - Update all AutoCAD project files with new paths

2. **User UPN Changes:**
   - Change Firm B user UPNs to match Firm A naming convention

3. **Final Cleanup:**
   - Decommission old Firm B mailboxes

# M365/AD Tenant Consolidation Change Plan: Firm A (Absorbing Firm B)

## 1. Executive Summary & Critical Constraints
*   **Objective:** Consolidate Firm B (45 users) into Firm A (120 users) M365/AD Tenant.
*   **Critical Risk:** Firm B’s AutoCAD drawings rely on absolute UNC paths (`\\FIRMB-FS01\Projects\...`). Changing the file share path or breaking AD trust during work hours will break Xrefs, halting engineering work.
*   **Business Constraint:** Two permit submissions are due in **10 business days**. No infrastructure changes that affect file paths or user access to the project share are permitted during this window.

## 2. Migration Sequence Strategy

### Phase 1: Pre-Migration Stabilization (Days 1–3)
*   **Goal:** Secure data and establish Hybrid Identity without disrupting access.
*   **Action:**
    1.  **Backup:** Perform full backup of Firm B’s on-prem file share (`FIRMB-FS01`) and local workstations.
    2.  **Hybrid Identity Setup:** Configure Azure AD Connect between Firm B’s on-prem AD and Firm A’s M365 tenant.
        *   *Constraint:* Do **not** change Firm B’s UPN prefix or domain name yet. Keep `user@firmb.local` synced to M365 temporarily to maintain access to the on-prem file share.
    3.  **Network Validation:** Ensure Firm A’s network has DNS routes to `FIRMB-FS01`.
    4.  **Communication:** Inform Firm B engineers that the file server will remain unchanged; no workarounds required yet.

### Phase 2: Mailbox Migration (Days 4–6)
*   **Goal:** Move email data and users to Firm A’s M365 Tenant.
*   **Action:**
    1.  **Batch Migration:** Use the M365 Admin Center to migrate Firm B mailboxes in batches (e.g., 10 users per batch).
    2.  **File Access Preservation:** As mailboxes move, users retain access to `\\FIRMB-FS01` because the on-prem AD trust is active via Hybrid Identity.
    3.  **Xref Verification:** Randomly check 5 engineers’ drawings to confirm Xrefs resolve to `FIRMB-FS01`.
    4.  **No File Share Changes:** The file server remains on-prem with the exact UNC path `\\FIRMB-FS01`.

### Phase 3: Permit Deadline Lock (Days 7–10)
*   **Goal:** Permit Submission.
*   **Action:**
    *   **STOP ALL MIGRATION.** Do not touch the file share, AD domain, or UNC paths.
    *   Engineers continue work using the existing UNC paths.
    *   Permit files are submitted to the building department.
    *   **Rollback Readiness:** If a mailbox batch fails during Phase 2, the rollback (see Section 4) must be executed *before* Day 10.

### Phase 4: Post-Permit Consolidation (Day 11+)
*   **Goal:** Full architectural merger and modernization.
*   **Action:**
    1.  **File Share Migration:** Move project data from on-prem `FIRMB-FS01` to Firm A’s M365 File Storage (SharePoint/OneDrive or Azure File Share).
    2.  **Path Update:** Change the UNC path from `\\FIRMB-FS01` to `\\FIRMA-Share\Projects`.
    3.  **Xref Repair:** Run a PowerShell script across all Firm B drawings to update external references to the new path.
    4.  **UPN Change:** Switch Firm B users’ UPNs to `@firma.com` and decommission the on-prem `FIRMB-FS01` server.

---

## 3. Changes Required ONLY AFTER Permit Deadlines Pass

The following actions **cannot** occur until **Day 11** (after the 10-day deadline window is closed) to prevent Xref breakage:

1.  **UNC Path Change:** Moving files from `\\FIRMB-FS01` to a new server name or path (e.g., `\\FIRMA-FS01`).
2.  **AD Domain Termination:** Removing Firm B’s on-prem domain controller or breaking the trust relationship with Firm A’s tenant, as this would invalidate the credentials needed to access the on-prem share during the hybrid phase.
3.  **AutoCAD Xref Updates:** Any script or manual action that rewrites the `\\FIRMB-FS01` strings in the `.dwg` files.
4.  **Share Permissions Reset:** Removing the old ACLs on the file share that allow Firm B users to access the data.

---

## 4. Mailbox Migration Rollback Plan

If a batch fails partway during Phase 2 (Days 4–6), execute this rollback to prevent data loss and ensure engineers can still access the file share.

### Scenario A: Single Batch Failure (e.g., 5 users fail)
1.  **Pause:** Stop the migration job immediately in the M365 Admin Center.
2.  **Isolate:** Do not migrate subsequent batches.
3.  **Verify Access:** Confirm the affected 5 users can still access `\\FIRMB-FS01` via their on-prem credentials.
4.  **Un-Move:** Use the M365 Admin Center "Move to other tenant" or "Cancel Migration" feature for the specific users.
5.  **Investigate:** Check logs for sync errors (e.g., password hash mismatch, license conflicts).
6.  **Retry:** Re-attempt the migration for those specific users using a smaller batch size.

### Scenario B: Systemic Failure (e.g., All Mailbox Migrations fail)
1.  **Halt:** Stop all migration jobs.
2.  **Revert Identity:** If Azure AD Connect has already changed the `targetDir` for users, use the **"Reverse Sync"** option (if available) or restore the last known working configuration from the AD Connect backup.
3.  **Keep On-Prem Active:** Ensure Firm B’s on-prem domain controllers remain online to manage access to `FIRMB-FS01`.
4.  **Communicate:** Inform Firm B that the migration is paused; they continue using original credentials for email (cached) and file access.
5.  **Plan B:** Schedule a new migration window for Week 2, ensuring the File Share remains untouched until permits are submitted.

| Control | Configuration |

## 4. Rollback Strategy for Mailbox Migration  

Because mailbox moves are **asynchronous** and can be partially completed, a clear rollback path is essential.

### 4.1 Pre‑Migration Safeguards  

1. **Full backup** of each source mailbox (export to PST or use native Exchange **Mailbox Export/Import**). Store PSTs in a secure location (e.g., Azure Blob with immutable storage).  
2. **Snapshot** of the on‑prem Exchange database (if using Exchange Server) taken **just before** the first move request.  
3. **Document** every `New-MoveRequest` command with its **RequestGuid** and the **batch number** (e.g., Batch‑01‑A, Batch‑01‑B …).  

### 4.2 Detection of a Failed Batch  

- **Monitoring**: Use **Exchange Admin Center** alerts + **PowerShell** `Get-MoveRequestStatistics` filtered by `Status -eq "Failed"` or `Status -eq "InTrouble"`.  
- **Threshold**: If **any** user in a batch reports failure (e.g., missing items, size mismatch, or error code `ErrorPermanentFailure`), treat the whole batch as **failed**.  

### 4.3 Immediate Rollback Steps  

| Step | Action | Command / Tool |
|------|--------|----------------|
| **4.3.1** | **Cancel** the pending move requests for the failing batch. | `Get-MoveRequest -BatchId <BatchGUID> | Remove-MoveRequest` |
| **4.3.2** | **Re‑enable** the original on‑prem mailbox (if it was placed in **RetentionHold** or **Disabled** state). | `Set-Mailbox -Identity <user>@firmB.local -IsArchive $false -ArchiveStatus None` |
| **4.3.3** | **Restore** from the PST backup (if any data was partially migrated). | `New-MailboxImportRequest -Mailbox <user>@firmB.local -FilePath \\BackupShare\pst\<user>.pst` |
| **4.3.4** | **Notify** the user and the project lead that the mailbox is back to the original state and that mail will continue to flow from the on‑prem server. | Email template (pre‑written). |
| **4.3.5** | **Investigate** root cause (e.g., corrupt PST, network latency, permission issue) and **fix** before re‑attempting. | Review Exchange logs, run `Get-MessageTrackingLog`. |

### 4.4 Post‑Rollback Validation  

1. **Send/Receive test** from the user’s workstation.  
2. **Run** `Get-MailboxStatistics -Identity <user>` to confirm **ItemCount** matches the pre‑migration snapshot.  
3. **Confirm** that the user’s **UPN** is still the old one (`@firmB.com`) – **do not** change it until after the permit deadlines.  

### 4.5 Re‑Attempt Strategy  

- After fixing the identified issue, **re‑run** the move request for the *same* batch (or split into smaller sub‑batches of 5 users).  
- Keep the **same monitoring** window; if the second attempt succeeds, proceed to the next batch.  

### 4.6 Full‑Project Rollback (worst‑case)  

If **multiple batches** fail and a decision is made to **abort the entire mailbox migration**, execute:

1. **Cancel all pending move requests** (`Get-MoveRequest | Remove-MoveRequest`).  
2. **Re‑enable** every on‑prem mailbox that was placed in a hold.  
3. **Re‑apply** the original DNS MX records to point back to Firm B’s mail servers (if they were switched).  
4. **Communicate** to all stakeholders that the migration is paused; schedule a new window after the permit deadlines.

### M365/AD Tenant Consolidation Change Plan: Firm A Absorbs Firm B

**Objective:** Consolidate Firm B into Firm A's Microsoft 365/Active Directory tenant while preserving AutoCAD Xref integrity and meeting two permit deadlines in 10 business days.
**Constraint:** Xref links rely on absolute UNC paths (`\\FIRMB-FS01\Projects\...`). Changing file share paths or UPNs during active work risks breaking links. **Stability is paramount until permits are submitted.**

---

### 1. Risk Assessment & Strategy
*   **Xref Dependency:** AutoCAD Xrefs resolve based on the UNC path. Any change to the DNS name `FIRMB-FS01`, the share name, or the underlying server IP/DNS record will break links for all open drawings.
*   **UPN/Mailbox Dependency:** The prompt indicates moving mailboxes/UPNs risks breaking Xref links (likely due to authentication mapping, SID history issues, or dependency on legacy AD trusts for file share auth).
*   **Permit Deadline:** 10 Business Days (BBD). No changes that risk Xref integrity or file access may occur during the window leading to submission.
*   **Strategy:** **Freeze** all identity and path changes until post-deadline. Use a staged migration where preparation occurs, but cutover and path changes happen after the deadline. Use a rollback-capable batch migration process.

---

### 2. Migration Sequence

#### Phase 1: Freeze & Preparation (Days 1–9 BBD)
*Goal: Stabilize environment, prepare M365 objects, ensure data integrity, without touching active paths or user identities.*

1.  **Environmental Freeze:**
    *   Announce a **Change Freeze** to Firm B drafters. No changes to file shares, DNS, or AD identities for the next 10 BBD.
    *   Verify `FIRMB-FS01` DNS A-record and NetBIOS name are static.
    *   Ensure `\\FIRMB-FS01\Projects\...` accessibility is validated for all Firm B users.

2.  **M365/AD Preparation:**
    *   Create Firm B user accounts in Firm A's tenant with a **temporary/staging UPN** (e.g., `user@firmb-temp.onmicrosoft.com` or a synced on-prem UPN if hybrid) that does **not** change the user's primary UPN or SID yet.
    *   *Note:* If hybrid, ensure sync is paused or filtered so the live UPN does not change. If cloud-only, keep users in a "disabled" state or with placeholder credentials to avoid license conflicts until migration.
    *   Perform a full backup of `FIRMB-FS01` and AD objects.
    *   Deploy any pending AutoCAD updates or patches to Firm B workstations (non-disruptive).

3.  **Migration Readiness:**
    *   Create a **Pilot Migration Batch** for 3-5 non-critical users to test the mailbox migration flow.
    *   Verify rollback procedures (see Section 4).
    *   *Result:* Data is backed up, M365 targets exist, but no user has moved, and paths are untouched.

#### Phase 2: Permit Deadline Window (Day 10 BBD)
*Goal: Submit permits with zero risk.*

*   **Action:** Firm B continues work on-prem. `FIRMB-FS01` remains active. Mailboxes remain on-prem (or staged). UPNs remain unchanged.
*   **Outcome:** Permits submitted. Xref links remain valid.

#### Phase 3: Post-Deadline Consolidation (Day 11+ BBD)
*Goal: Execute migration with Xref preservation measures.*

**Changes that MUST happen ONLY AFTER permit deadlines pass:**

1.  **File Share Migration & Path Preservation:**
    *   *Option A (Recommended for CAD):* Migrate files to a new location (e.g., Firm A's consolidated share or SharePoint) but maintain the UNC path via **DFS (Distributed File System) or DNS CNAME**.
        *   Create a DFS Namespace or DNS Alias `\\FIRMB-FS01` that points to the new location.
        *   *Result:* Xref paths remain `\\FIRMB-FS01\...`, but files now live in the merged environment.
    *   *Option B (SharePoint Migration):* If migrating to SharePoint, you must use a **Path Mapping tool** in AutoCAD post-migration to update Xrefs, or keep a "Bridge" file server running DFS aliases for 2 weeks.
    *   *Decision:* Implement DFS Alias to ensure zero Xref breakage during cutover.

2.  **Mailbox Migration (Batch Cutover):**
    *   Execute Migration Batches for Firm B users.
    *   Since Xref risks are linked to UPN/Identity moves, ensure the migration preserves **Security Identifiers (SIDs)** or use **SID History** to maintain access to the file share (if the share remains on-prem or relies on AD auth).
    *   Monitor `MoveRequest` status.

3.  **UPN Change & Cutover:**
    *   After file share DFS alias is verified, cutover users to Firm A's UPN (`user@firmA.com`).
    *   Update DNS records for `FIRMB-FS01` if the server was decommissioned.
    *   Disable old on-prem AD accounts for Firm B users.

---

### 3. Rollback Approach for Mailbox Migration
*Scenario: A migration batch fails partway (e.g., connectivity issue, corrupted item, auth error). The batch must be rolled back to restore users to their original state before retrying.*

**Rollback Procedure (PowerShell/M365):**

1.  **Stop the Batch:**
    ```powershell
    Stop-MigrationBatch -Identity "FirmB_Migration_Batch_01"
    ```

2.  **Remove Pending Move Requests:**
    *   Identify failed/pending moves and remove them.
    ```powershell
    Get-MoveRequest -BatchName "FirmB_Migration_Batch_01" | Where-Object {$_.Status -in ("Failed","Queued")} | Remove-MoveRequest -Confirm:$false
    ```

3.  **Delete Provisioned Cloud Mailboxes:**
    *   If the migration provisioned mailboxes in the target tenant, remove them to avoid duplicate objects or license waste.
    ```powershell
    Get-Mailbox -ResultSize Unlimited | Where-Object {$_.PrimarySmtpAddress -like "*@firmB-users*" -and $_.RecipientTypeDetails -eq "UserMailbox"} | Remove-Mailbox -Confirm:$false
    ```
    *   *Note:* Adjust the filter based on your specific provisioning naming convention.

4.  **Re-add Users to Batch:**
    *   Review logs, resolve the root cause (e.g., network, permission, item count), and re-add the users to a fresh batch.
    *   Create new batch:
    ```powershell
    New-MigrationBatch -Name "FirmB_Migration_Batch_01_Retry" -SourceOrganization "ExchangeOnPrem" -CSVData (Import-Csv "C:\Migration\Users.csv") -TargetDeliveryDomain "firmA.com"
    ```

5.  **Verify Rollback:**
    *   Confirm users are back in on-prem (or source) state.
    *   Ensure `FIRMB-FS01` access is unaffected (users never left AD/FQDN, so access should be intact).
