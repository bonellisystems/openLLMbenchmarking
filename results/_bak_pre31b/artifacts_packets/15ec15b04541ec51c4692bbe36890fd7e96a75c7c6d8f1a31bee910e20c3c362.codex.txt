## 1. Capacity & Performance Analysis

### 1.1 CPU Spike at Shift‑Change
* **Observed pattern:** 91 % CPU for ~20 min, three times per day, when all handheld scanners re‑sync.
* **Implication:** The current 8‑vCPU configuration is running at the edge of its capacity. A 10 % safety margin is insufficient when the plant may add a few more scanners or when the sync routine gains extra logic (e.g., new barcode formats).
* **sizing rule of thumb:** *Peak CPU % + 30 % buffer* → 91 % + 30 % ≈ **119 %** → round up to the next whole‑core count → **12 vCPU** (or 2 × 8 vCPU with hyper‑threading, which gives 16 logical cores but is more expensive; 12 dedicated cores is the cheaper, “right‑sized” choice).

### 1.2 RAM
* The sync service, Windows OS, anti‑virus, and the file‑share services all compete for memory.  
* When the CPU is saturated, the system also begins to page if RAM is exhausted, which would further aggravate the spike.
* **Rule of thumb:** *Current usage + 100 % head‑room* → 32 GB + 32 GB ≈ **64 GB**.

### 1.3 Storage Growth & Retention
* **Growth rate:** 23 GB / week → 23 GB × 52 ≈ 1 196 GB / year.  
* **Two‑year USDA requirement:** 2 × 1 196 ≈ 2 392 GB (≈ 2.4 TB).  
* **Current usage:** 82 % of 500 GB = **410 GB** used, **90 GB** free.  
* **Head‑room for safety:** +20 % → ≈ 2.9 TB total needed.  
* **Solution:** Move the hot‑access logs to a **2 TB SSD** (covers the most recent ~6‑9 months) and archive anything older than 6 months to a **2 TB HDD** (or a second SSD tier) that can be expanded later. This keeps the active log folder on fast storage for the scanners while still meeting the 2‑year legal window.

## 3. Storage Plan that Honors the 2‑Year Retention Rule

### 3.1 Tier‑ed Architecture Overview

```
\\PM-FILES\LotTracking      ← 2 TB SSD (hot tier) – active logs (last ~6 months)
\\PM-FILES\Archive           ← 2 TB HDD  (cold tier) – logs older than 6 months
```

*The share `\\PM-FILES\LotTracking` is the **only** path exposed to the handheld scanners.  
*Inside that share we create two sub‑folders: `Hot` (points to the SSD volume) and `Archive` (points to the HDD volume).  
*The scanner software is configured to write to `\\PM-FILES\LotTracking\Hot`.  
* A scheduled PowerShell script (run nightly at 02:30 AM) moves any file older than **180 days** from `Hot` to `Archive` and updates the NTFS junction so the path remains transparent to the scanners.

### 3.2 How It Meets USDA Requirements

| Requirement | How the design satisfies it |
|-------------|------------------------------|
| **2‑year retention** | All logs are kept for **≥ 730 days**. The hot tier holds only the most recent ~180 days; the cold tier holds the remainder, still accessible via the same UNC path. |
| **No deletion** | The script *moves* files; it never deletes them. The archival location retains them indefinitely (or until a separate archival policy is enacted). |
| **Continuous availability** | The share stays online during the move (the script works on files older than 180 days; new files are always written to `Hot`). The move operation is I/O‑light because it’s just a rename + copy; the scanner never sees a “missing” folder. |
| **Auditability** | All move operations are logged (`Move-LotLogs.ps1` writes to an event log entry). This satisfies USDA audit trails. |

## 2. Storage Architecture that Honors the 2‑Year Retention Requirement  

### 2.1 Tiered Storage Layout  

| Tier | Technology | Size (initial) | Data Held | Access Pattern | Management |
|------|------------|----------------|-----------|----------------|------------|
| **Tier 1 – Hot Cache** | Hyper‑V host‑local NVMe (or high‑performance SSD) | **1 TB** (as part of the VM’s C: volume) | Scans from the **last 7–14 days** (the period scanners may request for “recent” lot‑tracking queries) | Direct block‑level reads/writes, sub‑ms latency | Automatic file‑age sweep (scheduled PowerShell/Robocopy) moves files older than 14 days to Tier 2. |
| **Tier 2 – Warm Nearline** | Dedicated NAS or iSCSI appliance with 10 TB spinning‑disk (e.g., SATA 7.2 K RPM) + Erasure‑Coding/Parity for resilience | **10 TB** (expandable) | Scans **15 days → 180 days** (≈ 6 months) | Sequential bulk reads; occasional random reads for audit | Retention policy enforced by the NAS (e.g., Synology/NetApp “Retention” feature) plus a weekly integrity checksum. |
| **Tier 3 – Cold Archive** | Object‑storage solution (e.g., Wasabi, Amazon S3 Glacier Deep Archive, or an on‑prem tape‑library with robotic indexing) | **≈ 30 TB** projected for 2 years (23 GB/week × 104 weeks ≈ 2.4 TB raw; after compression/dedup ≈ 1.2 TB, plus safety margin) | Scans **181 days → 730 days** (2 years) | Infrequent access (primarily for USDA audits). Retrieval latency acceptable if < 24 h. | Immutable write‑once‑read‑many (WORM) bucket with legal hold; periodic (quarterly) integrity verification. |

### 2.2 Data‑Flow & Automation  

1. **Ingestion** – Handheld scanners write directly to the VM’s *hot* volume (Tier 1).  
2. **Nightly Migration Job** (00:30 – 01:00) – A PowerShell script runs on the Hyper‑V host:  
   ```powershell
   $src = "C:\ScanData\"
   $dstWarm = "\\NAS-Scans\Warm\"
   $dstCold = "s3://usda‑scan‑archive/"   # via AWS CLI or Wasabi SDK

   # 1️⃣ Move 14‑day‑old files to Warm tier
   Get-ChildItem $src -Recurse | Where-Object {$_.LastWriteTime -lt (Get-Date).AddDays(-14)} |
       Move-Item -Destination $dstWarm

   # 2️⃣ Move 180‑day‑old files to Cold tier (using AWS CLI / Wasabi)
   Get-ChildItem $src -Recurse | Where-Object {$_.LastWriteTime -lt (Get-Date).AddDays(-180)} |
       % { aws s3 cp $_.FullName $dstCold --storage-class DEEP_ARCHIVE }
   ```
3. **Retention Enforcement** – The NAS and object‑storage services are configured with *immutable retention* (e.g., 730‑day WORM) so that accidental deletion is prevented.  
4. **Compression / Deduplication** – Enable inline deduplication on the NAS (many vendors support it) and consider compressing the logs (e.g., `gzip` or `7z`) before sending to Glacier‑style storage.
