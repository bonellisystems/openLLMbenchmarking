# Network Segmentation Review for Multi-Provider Outpatient Clinic

## Executive Summary
The current flat network architecture (all devices on VLAN 10.10.0.0/22) violates HIPAA Security Rule access-control obligations by allowing guest WiFi users to reach the EHR application server via RDP. This review proposes a segmented VLAN structure, identifies the specific control that will close the guest-to-EHR RDP path, and outlines a detailed change implementation plan with a rollback procedure, all respecting the clinic's no-downtime window (8:00 AM - 6:00 PM).

---

## 1. Proposed VLAN Structure

| VLAN ID | Network Range      | Purpose                                   | Security Zone            |
|---------|--------------------|-------------------------------------------|--------------------------|
| 10      | 10.10.0.0/24       | **EHR Workstations & Application Server** | **High-Security (PHI)**  |
| 11      | 10.10.1.0/24       | Medical IoT Devices (infusion pumps, monitors) | **Medium-Security (Device)** |
| 12      | 10.10.2.0/24       | Back‑Office/Administrative Systems        | **Medium-Security (Admin)** |
| 13      | 10.10.3.0/24       | Guest WiFi Access                         | **Public/Low‑Security**  |

### Rationale
- **Strict Separation**: Each functional area now resides in its own broadcast domain, preventing lateral movement.
- **Access Control Lists (ACLs)** can be applied at the VLAN interfaces or via a core L3 switch/router to enforce **least‑privilege** traffic flows.
- **Scalability**: /24 subnets provide ample address space for growth while simplifying management.
- **Compliance**: Aligns with HIPAA by isolating ePHI systems (VLAN 10) from untrusted guest traffic (VLAN 13).

---

## 2. What Specifically Closes the Guest‑to‑EHR RDP Path?

1. **VLAN Isolation**: By moving the EHR workstations and application server to VLAN 10, they are no longer in the same broadcast domain as the guest WiFi (VLAN 13).  
2. **Layer‑3 Routing Controls**: Implement **explicit deny** ACL rules on the core router/layer‑3 switch:
   - **Deny** any IP traffic from VLAN 13 (Guest) to VLAN 10 (EHR) on TCP port **3389** (RDP) **and** any other ePHI‑related ports.
   - **Permit** only required inter‑VLAN traffic (e.g., IoT devices (VLAN 11) → EHR (VLAN 10) for clinically necessary data, admin systems (VLAN 12) → EHR (VLAN 12) for management, etc.).
3. **Stateful Firewall/Next‑Gen Firewall (NGFW)**: Deploy an NGFW in the data path that enforces the above ACLs and provides application‑level inspection, ensuring that even if a malicious actor attempts to tunnel RDP over another port, it will be blocked.

**Result**: Even if a guest laptop retains an IP in the old /22 range, it will be reassigned to VLAN 13 during the switchover, and the routing/firewall rules will immediately prevent any RDP packets from reaching the EHR server.

## Network Segmentation Review & Remediation Plan

**Client:** Multi-Provider Outpatient Clinic  
**Scope:** HIPAA Access Control Remediation / Flat Network Segmentation

### 1. Proposed VLAN Structure

The current flat `10.10.0.0/22` network must be decomposed into functionally isolated subnets. We recommend a `/24` schema to limit broadcast domains and simplify ACL management.

| VLAN ID | Subnet | Scope | Purpose |
|:---:|:---|:---|:---|
| **10** | `10.10.10.0/24` | EHR Workstations, EHR App Server, EHR DB | **Restricted.** Only EHR traffic + Authorized Admin. |
| **20** | `10.10.20.0/24` | Infusion Pumps, Patient Monitors, Med IoT | **Quarantined.** IoT-only. Allowed to speak *to* EHR only on required ports; cannot initiate to anything else. |
| **30** | `10.10.30.0/24` | Guest WiFi | **Isolated.** Internet only. **No internal access.** |
| **40** | `10.10.40.0/24` | Back-office Admin, Printers, Servers | **Standard.** Standard user traffic. |
| **50** | `10.10.50.0/24` | Network Mgmt, Switch/FW Management | **Secure.** IT management only. |

**Addressing Note:** Since the clinic currently uses `10.10.0.0/22`, migrating to new subnets requires re-IP or DHCP scope changes. To minimize disruption to IoT and EHR, we will use a **phased approach**:
1.  **Immediate ACL** (see below) to close the gap without moving devices.
2.  **VLAN Migration** performed exclusively in the overnight window.

---

### 2. What Closes the Guest-to-EHR RDP Gap

The specific gap (Guest WiFi → EHR App Server RDP) is closed by a **defense-in-depth** combination of Layer 2 separation and explicit ACLs.

**A. Layer 2 Segmentation (Primary Control)**
*   Moving Guest WiFi to **VLAN 30** severs the L2 path to the EHR server on **VLAN 10**.
*   Without a router/FW allowing inter-VLAN traffic, the packet cannot leave the Guest subnet.

**B. Inter-VLAN ACLs (Secondary Control)**
Even with VLANs, if the core router permits transit, we must enforce strict allow-lists:
*   **Guest VLAN 30:** Default policy **DENY ALL** internal traffic. Only allow `TCP/443` and `TCP/80` outbound to Internet (NAT). **No destination IPs in `10.10.x.0/24` ranges are reachable.**
*   **EHR VLAN 10:** Inbound ACL permits:
    *   `10.10.10.0/24` → `10.10.10.x` (App Server) on `TCP/3389` (EHR Workstations).
    *   `10.10.20.0/24` → `10.10.10.x` (App Server) on specific IoT telemetry ports (e.g., `TCP/514`, `TCP/18125`).
    *   `10.10.50.0/24` → EHR VLAN (Management).
    *   **All other sources denied.**

**C. Immediate Remediation (Zero-Migration Fix)**
To close the HIPAA gap **immediately during business hours** without touching VLANs:
*   Deploy an ACL on the core switch or firewall:
    ```text
    DENY TCP 10.10.30.0/24 -> <EHR_APP_SERVER_IP> TCP 3389
    ```
*   *Result:* Guest traffic is blocked at the RDP vector instantly. The flat network remains until the overnight migration.

### **Executive Summary**

A recent internal security review has identified a critical network segmentation flaw: guest WiFi users can directly access the EHR application server via RDP (port 3389), violating HIPAA Security Rule requirements for access control and data confidentiality. This exposure creates an unacceptable risk to electronic protected health information (ePHI).

The current network is effectively flat, with all systems — including EHR workstations, medical IoT devices, guest WiFi, and back-office systems — residing on a single VLAN (10.10.0.0/22). This design lacks appropriate segmentation and access controls, enabling lateral movement from low-trust zones (guest network) to high-trust systems (EHR).

This document proposes a secure, compliant VLAN segmentation architecture, details how it closes the guest-to-EHR RDP exposure, and outlines a change management plan that eliminates the risk **without disrupting clinic operations** during business hours (8:00 AM – 6:00 PM).

---

### **Proposed VLAN Segmentation Architecture**

| VLAN ID | Subnet | Purpose | Security Zone | Access Requirements |
|--------|--------|-------|---------------|---------------------|
| VLAN 10 | 10.10.10.0/24 | EHR Workstations & Application Server | **Protected (High Trust)** | Isolated; no inbound access from guest or IoT |
| VLAN 20 | 10.10.20.0/24 | Medical IoT (Infusion Pumps, Monitors) | **IoT (Medium Trust)** | Restricted to EHR VLAN for telemetry only; no RDP |
| VLAN 30 | 10.10.30.0/24 | Back-Office Admin Systems | **Internal (Medium Trust)** | Access to EHR via secure protocols only (e.g., EHR client, no direct RDP) |
| VLAN 40 | 10.10.40.0/24 | Guest WiFi | **Untrusted (Low Trust)** | Internet-only; no access to internal subnets |
| VLAN 99 | 10.10.99.0/24 | Management/Network Infrastructure | **Management (High Trust)** | Restricted to authorized IT personnel only |

> **Router/Firewall**: A Layer 3 switch or next-generation firewall (NGFW) will enforce inter-VLAN routing with stateful firewall rules.

---

### **How This Closes the Guest-to-EHR RDP Path**

1. **Guest Traffic Isolated to VLAN 40**  
   Guest WiFi clients are confined to VLAN 40 (10.10.40.0/24). They receive DHCP from this subnet and are routed only to the internet via NAT.

2. **No Inter-VLAN Routing from Guest to EHR by Default**  
   The firewall/router will block all traffic from VLAN 40 (Guest) to any internal VLAN (including VLAN 10), **by default**.

3. **Explicit Deny Rule for RDP (TCP 3389)**  
   A firewall rule will **explicitly deny** any traffic from VLAN 40 to VLAN 10 on port 3389 (RDP), with logging enabled for audit purposes.

4. **EHR Server Not Directly Accessible via RDP from Anywhere Except Trusted Admin Network**  
   RDP access to the EHR application server will be restricted to:
   - The management VLAN (VLAN 99), or
   - Back-office VLAN (VLAN 30) **only if required and secured via jump host or MFA-protected access**

   Direct RDP from guest or IoT VLANs is **prohibited**.

> ✅ **Result**: Guest users **cannot** reach the EHR server on port 3389 or any internal resource. The path is closed via **network segmentation + firewall policy enforcement**.

Specifically, it fails to implement "appropriate technical measures to prevent, to the extent possible, unauthorized access."

A guest WiFi connection (untrusted, unauthenticated) has direct Layer 2 reach to the EHR application server. If a guest device is compromised (malware, phishing, brute-force), it can pivot directly to ePHI systems via RDP (TCP/3389).

**Objective:** Segment the network to isolate Guest traffic from Clinical/Production traffic.
**Hard Constraint:** Zero EHR downtime between **8:00 AM and 6:00 PM**.

### 2. Proposed VLAN Architecture

We will split the current 10.10.0.0/22 into four logical sub-VLANs. The EHR subnet remains the same to avoid re-IPing provider workstations during clinic hours.

| VLAN ID | Name | Subnet | Scope |
| :--- | :--- | :--- | :--- |
| **VLAN 10** | `MSP-PROD-EHR` | 10.10.0.0/24 | EHR Servers, EHR Workstations, Critical Printers |
| **VLAN 20** | `MSP-IOT` | 10.10.1.0/24 | Infusion Pumps, Patient Monitors, Medical IoT |
| **VLAN 30** | `MSP-ADMIN` | 10.10.2.0/24 | Back-office, Billing, HR, Accounting |
| **VLAN 40** | `MSP-GUEST` | 10.10.3.0/24 | Guest WiFi APs, Guest Devices, Social Media |

**Intended Traffic Flow:**
*   **Guest VLAN (40) → EHR VLAN (10):** **DENIED** (All traffic, specifically TCP 3389).
*   **Guest VLAN (40) → Admin VLAN (30):** **DENIED** (No ePHI or billing access).
*   **EHR VLAN (10) ↔ IoT VLAN (20):** **RESTRICTED** (IoT devices must not initiate outbound traffic; allow only specific API endpoints if required by the EHR).
*   **EHR VLAN (10) ↔ Admin VLAN (30):** **ALLOWED** (Admins need to manage EHR settings).

### 3. Closing the Guest-to-EHR RDP Path

The specific gap—Guest Laptop $\rightarrow$ EHR Server on Port 3389—is closed by **Layer 3 Access Control Lists (ACLs)** applied on the core switch and the perimeter firewall (if applicable).

**The Control Mechanism:**
1.  **ACL on Core Switch (VLAN 40 Interface):**
    *   Deny all IP traffic from `10.10.3.0/24` (Guest) to `10.10.0.0/24` (EHR).
    *   **Explicitly block TCP port 3389** to ensure no RDP tunneling attempts succeed.
2.  **Perimeter Firewall (Default Rule):**
    *   Ensure the firewall rule base has an explicit **`deny ip any any`** between the Guest zone and the Production zone.
3.  **Guest SSID Configuration:**
    *   The Guest SSID will be associated with VLAN 40. The Access Points (APs) will be tagged with VLAN 40.
    *   Guest devices are assigned DHCP leases in the `10.10.3.0/24` range.

**Result:** Even if a guest device is on the same physical network, the ACL prevents any packet from being routed to the EHR server. The RDP path is physically broken at the routing layer.

### 3. Specific Remediation: Closing the Guest-to-EHR RDP Path
VLAN separation alone does not close the path if inter-VLAN routing is permitted. The gap is closed by the combination of **Layer 2 Segmentation** and **Inter-VLAN Access Control Lists (ACLs)**.

**Exact Control Implementation:**
1.  **VLAN Assignment:** Guest Wireless APs are assigned to **VLAN 99**. EHR systems are moved to **VLAN 20**. This removes broadcast domain overlap.
2.  **Firewall/Router ACL:** An inbound ACL is applied to the **VLAN 99 interface** on the core firewall/router:

    ```text
    DENY IP 10.10.0.0/24 10.10.1.0/24  (Block all traffic to EHR VLAN)
    DENY IP 10.10.0.0/24 10.10.2.0/24  (Block all traffic to Admin VLAN)
    DENY IP 10.10.0.0/24 10.10.3.0/24  (Block all traffic to IoT VLAN)
    PERMIT IP 10.10.0.0/24 0.0.0.0/0   (Allow Internet access)
    ```
    *Result:* A guest laptop on 10.10.0.x cannot route to 10.10.1.x (EHR). The RDP attempt is dropped at the first hop by the ACL, regardless of port state on the server.

## 2. Gap Analysis & HIPAA Context
*   **Current State:** A single broadcast domain (`10.10.0.0/22`) allows any connected device to scan and access any other device.
*   **Risk:** If a Guest device is compromised (e.g., via malicious WiFi), an attacker can directly RDP into the EHR Server, potentially stealing ePHI or installing ransomware.
*   **Requirement:** HIPAA requires "reasonable and appropriate" security measures to prevent unauthorized access. Network segmentation is the industry-standard administrative safeguard to enforce this.

## 3. Proposed VLAN Structure
We will partition the existing `10.10.0.0/22` address space into logical `/24` subnets mapped to specific VLANs. This allows us to keep IP addressing familiar while enforcing logical separation.

| VLAN ID | Name | IP Subnet | Purpose | Access Control |
| :--- | :--- | :--- | :--- | :--- |
| **10** | **Clinical-EHR** | `10.10.0.0/24` | EHR Workstations, EHR Server, Clinical Admin PCs. | **Restricted.** Only allow necessary app ports (1433, 443, 8080). |
| **20** | **Guest-WiFi** | `10.10.1.0/24` | Visitor Devices, Staff Personal Devices. | **Isolated.** Internet only. **DENY all access to VLAN 10.** |
| **30** | **Medical-IoT** | `10.10.2.0/24` | Infusion Pumps, Patient Monitors. | **Restricted.** Only allow traffic to VLAN 10 (EHR) for data ingestion. Deny internet access. |
| **40** | **Management** | `10.10.3.0/24` | Network Devices (Switches, Firewalls), Backup Servers. | **High Security.** Out-of-band management access only. |

**Why this structure closes the gap:**
By placing Guest WiFi on **VLAN 20** and the EHR Server on **VLAN 10**, the traffic must pass through a Layer 3 boundary (Core Switch or Firewall). The physical separation prevents Layer 2 attacks, while Layer 3 ACLs will explicitly block the RDP path.

## 4. Security Control Implementation: Closing the RDP Path
To permanently close the Guest-to-EHR RDP gap, we will implement **Inter-VLAN Access Control Lists (ACLs)** on the Core Firewall.

**The Rule Set:**
1.  **Block:** `Source: 10.10.1.0/24` -> `Destination: 10.10.0.0/24` -> `Protocol: TCP` -> `Port: 3389 (RDP)`. **Action: DENY.**
2.  **Block:** `Source: 10.10.1.0/24` -> `Destination: 10.10.0.0/24` -> `Protocol: TCP` -> `Port: 135, 445, 139`. **Action: DENY.** (Block SMB/RPC to prevent lateral movement).
3.  **Allow:** `Source: 10.10.1.0/24` -> `Destination: 0.0.0.0/0` (Internet). **Action: PERMIT.** (Guests must still have internet).
4.  **Allow:** `Source: 10.10.0.0/24` -> `Destination: 10.10.1.0/24`. **Action: PERMIT.** (Optional: Allows EHR workstations to print to guest printers if needed, but usually restricted).

**Verification Step:**
Before going live, a simulated attack scan will be run from a Guest VLAN device to verify Port 3389 on the EHR server is filtered (State: *Closed/Filtered*).

## 1. Executive Summary  

A flat‑VLAN design (10.10.0.0/22) allows any device on the guest Wi‑Fi to reach the EHR application server on TCP 3389 (RDP). ## 2. Proposed VLAN Architecture  

| VLAN ID | Subnet (CIDR)      | Description                              | Key Devices / Services                         |
|---------|-------------------|------------------------------------------|------------------------------------------------|
| 10      | 10.10.0.0/24      | **EHR Clinical VLAN** – Core EHR servers, workstations, medical IoT | EHR app servers, RDP, SQL, PACS, Infusion pumps |
| 20      | 10.10.1.0/24      | **Back‑Office VLAN** – Billing, HR, admin systems | Finance, HR, Scheduling, AD/DC                 |
| 30      | 10.10.2.0/24      | **Medical‑IoT VLAN** – Patient monitors, infusion pumps, vitals routers | Devices that need low‑latency local traffic    |
| 40      | 10.10.3.0/24      | **Guest Wi‑Fi VLAN** – Public wireless access | Guest APs, captive‑portal, Internet uplink      |
| 50      | 10.10.4.0/24      | **Management VLAN** – NMS, Syslog, Patch servers, console access | NOC, remote‑admin consoles, monitoring tools   |

*All subnets remain within the original /22 block, preserving the address plan while providing clear broadcast domains.*  

### 2.1. Inter‑VLAN Routing Controls  

All routing between VLANs will be forced through a **dedicated Layer‑3 firewall (or firewall‑capable core switch)**. No “router‑on‑a‑stick” or implicit L2 forwarding will be allowed. The firewall will enforce a **white‑list ACL** that only permits explicitly required traffic.

#### 2.1.1. Guest‑VLAN (40) ACL – “GUEST‑TO‑INTERNET ONLY”

| Source VLAN | Destination VLAN | Protocol / Port | Action |
|-------------|------------------|-----------------|--------|
| 40 (Guest)  | Any (Internet)   | IP any          | Permit |
| 40 (Guest)  | 10 (EHR)          | TCP 3389 (RDP)  | **Deny** |
| 40 (Guest)  | 10 (EHR)          | IP any          | **Deny** |
| 40 (Guest)  | 20 (Back‑Office) | IP any          | **Deny** |
| 40 (Guest)  | 30 (IoT)         | IP any          | **Deny** |
| 40 (Guest)  | 50 (Mgmt)        | IP any          | **Deny** |
| 40 (Guest)  | 40 (Self)        | IP any          | Permit (intra‑guest for captive‑portal) |
| *Default*   | *Any*            | *Any*           | Deny |

> **Result:** The only path out of VLAN 40 is to the Internet (via the upstream ISP). All internal subnets, including the EHR VLAN, are blocked at L3. No RDP or any other protocol can traverse.

#### 2.1.2. Clinical & IoT VLANs (10/30) – “Least‑Privileged Access”

| Source | Destination | Protocol / Port | Reason |
|--------|------------|-----------------|--------|
| 10 (EHR) | 30 (IoT) | TCP 443, UDP 161/162 (SNMP) | Device monitoring |
| 10 (EHR) | 20 (Back‑Office) | TCP 445 (SMB), TCP 389/636 (LDAP) | File share & auth |
| 10 (EHR) | 50 (Mgmt) | TCP 22, TCP 443, UDP 514 | Admin/monitoring |
| 20 (Back‑Office) | 10 (EHR) | TCP 1433 (SQL) | Billing integration |
| 30 (IoT) | 10 (EHR) | TCP 443 | Secure telemetry |
| *All other* | *All* | – | Deny (implicit) |

#### 2.1.3. Management VLAN (50)

Only privileged admin hosts (jump‑servers, NOC workstations) are allowed to originate traffic to any other VLAN. All inbound traffic to VLAN 50 is denied except from the core firewall for health‑checks.

## 3. What Exactly Closes the Guest‑to‑EHR RDP Path?  

1. **Physical Separation:** Guest APs are moved to switch ports assigned to VLAN 40 (tagged/untagged as appropriate). No trunk ports connect VLAN 40 to the core switch that also carries VLAN 10.  
2. **Layer‑3 Enforcement:** The firewall’s ACL **explicitly denies** any source IP in 10.10.3.0/24 (Guest) destined for 10.10.0.0/24 (EHR) on **all ports**, with a specific “deny tcp any any eq 3389” entry to satisfy the audit finding.  
3. **Removal of Implicit L2 Flooding:** By eliminating a flat VLAN, broadcast traffic (including ARP) from Guest cannot reach the EHR subnet, preventing “stealth” reachability.  

> **Bottom line:** Guest devices can no longer resolve or forward packets to the EHR network because the *only* route out of VLAN 40 passes through a firewall rule that blocks every internal destination, including the previously open RDP port.

### Addressing the Guest‑to‑EHR RDP Gap  

1. **Logical segregation** – Guest Wi‑Fi lives in **VLAN 40**. The EHR servers reside in **VLAN 20**.  
2. **Stateful firewall rule** – The perimeter firewall (or an inline L3 switch with ACLs) will have a **default‑deny** posture. The only allowed flow is:  

   - **VLAN 30 → VLAN 20** (RDP/HTTPS) for clinician workstations.  
   - **VLAN 50 → VLAN 20** (RDP/HTTPS) for admin workstations (restricted to specific admin hosts).  

   **All traffic from VLAN 40 to VLAN 20 is explicitly denied**, which immediately cuts the RDP path.  

3. **RDP exposure limited to management VLAN** – RDP is moved to a **management‑only** interface (VLAN 10 or a dedicated “Admin‑RDP” VLAN) that is not routable from VLAN 40. If RDP must remain on VLAN 20 for clinician workstations, it will be **source‑restricted** to the **Clinician‑Workstation VLAN (30)** only.

### 2. Closure of the Guest-to-EHR RDP Gap

```text
ACTION: DENY
PROTOCOL: TCP
SOURCE: 10.10.40.0/24 (Guest VLAN)
DESTINATION: 10.10.10.0/24 (EHR VLAN)
PORT: 3389 (RDP)
DESCRIPTION: Block Guest RDP to EHR
```

*Security Best Practice Addition:* While the rule above explicitly closes the RDP gap, the policy should enforce a default deny for the Guest VLAN to all internal subnets.
```text
ACTION: DENY
SOURCE: 10.10.40.0/24
DESTINATION: 10.10.10.0/24, 10.10.20.0/24, 10.10.30.0/24
SCOPE: ALL
```

# Network Segmentation Review: Closing the EHR Access Gap

## Executive Summary

The current flat network architecture creates a critical security vulnerability where guest WiFi traffic can directly access EHR systems over RDP, violating HIPAA Security Rule access control requirements. This review proposes a segmented network architecture that isolates sensitive EHR systems while maintaining 24/7 clinic operations.

## Current Architecture Analysis

**Current State:**
- Single VLAN (10.10.0.0/22) hosts all systems
- Guest WiFi, EHR workstations, medical IoT devices, and admin systems share the same broadcast domain
- RDP port 3389 is accessible from guest VLAN to EHR server
- No ACLs or firewalls restrict inter-VLAN communication

## Proposed VLAN Structure

### Network Segmentation Plan

**VLAN 10 - Guest WiFi Network**
- IP Range: 10.10.0.0/24
- Purpose: Public guest access only
- Security: No access to internal systems

**VLAN 20 - Clinical Workstations**
- IP Range: 10.10.1.0/24
- Purpose: EHR workstations, clinical staff devices
- Security: Limited to EHR and clinical applications

**VLAN 30 - Medical IoT Devices**
- IP Range: 10.10.2.0/24
- Purpose: Infusion pumps, patient monitors, medical devices
- Security: Isolated from general network traffic

**VLAN 40 - Administrative Systems**
- IP Range: 10.10.3.0/24
- Purpose: Back-office systems, non-clinical applications
- Security: Isolated from clinical systems

**VLAN 50 - EHR Application Servers**
- IP Range: 10.10.4.0/24
- Purpose: EHR application servers, database servers
- Security: Highest security level, restricted access

## Security Controls Implementation

### Key Security Controls

1. **VLAN Isolation**: Each VLAN operates on separate broadcast domains
2. **Inter-VLAN Routing**: Only permitted through controlled routing points
3. **Firewall Rules**: Apply strict ACLs between VLANs
4. **Access Control Lists**: Block all traffic except explicitly permitted flows

### What Closes the Guest-to-EHR RDP Path

**Primary Solution**: 
- Remove direct VLAN access to EHR VLAN (VLAN 50)
- Implement inter-VLAN routing with strict ACLs
- Block all traffic from VLAN 10 (Guest) to VLAN 50 (EHR) except:
  - Legitimate administrative access (via secure jump server)
  - Pre-approved monitoring services (if required)

**Secondary Solution**: 
- Implement firewall rules between VLANs to prevent any unauthorized access paths
- Ensure all servers on VLAN 50 (EHR) have minimal exposed services
