It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 4. Storage Plan – Keeping 2‑Year Retention While Avoiding Full Volumes

### 4.1. Live‑Working Volume (Performance Tier)

| Tier | Size | Purpose | Retention |
|------|------|---------|-----------|
| **Live‑Log Volume** (the folder that scanners write to) | 1.8 TB (or 2.7 TB with a 3‑disk pool) | Real‑time scan logs – **must stay on fast SSD** for immediate scanner access. | **Keep only the most recent 90 days** (≈ 30 GB / week × 13 weeks = 390 GB). | **Archive Tier** | 2 TB (or 3 TB) **cold‑storage SSD/HDD** or **Azure Blob/On‑Premises Tape** | Holds immutable logs for the **full 2‑year window** (≈ 2.4 TB). | 2‑year immutable, **write‑once‑read‑many (WORM)** compliance. Accessible only via a **read‑only share** for auditors. |

### 4.2. Archival Strategy

1. **Automated Age‑Based Migration** – A scheduled PowerShell script (run hourly) checks file age. When a log file reaches **90 days**, it is:
   - **Copied** to the Archive share (using `robocopy /MT /Z /R:2 /W:5` to preserve timestamps).  
   - **Marked** with the `USDA-Archived` attribute.  
   - **Deleted** from the live folder **after verification of successful copy** (the script logs the operation; a checksum is stored for audit).  

2. **Compression & Deduplication** – Enable **Data Deduplication** on the Archive volume (Windows Server 2016+). Typical compression ratio for sequential scan logs is **3:1–4:1**, reducing the 2‑year archive from ~2.4 TB to **≈ 600 GB** on disk.  

3. **Immutable/WORM Layer** – Turn on **Windows “Object Lock”** (if using SMB 3.1.4+ on a Storage Spaces Direct target) or **Azure Blob immutable storage** if you decide to off‑load the archive to the cloud for extra compliance protection.  

4. **Retention Policy Enforcement** – After **730 days** the archived file is **moved to a “deep‑archive” tier** (e.g., Azure Glacier Deep Archive or on‑premise LTO‑9 tape). This tier is still **read‑only**, but it can be deleted after the statutory 2‑year period (documented in the compliance SOP).  

5. **Audit Trail** – Every migration step writes an entry to a **SQL‑based audit log** (or a simple CSV) that records:
   - Source path & filename  
   - Destination path & timestamp  
   - Checksum (SHA‑256)  
   - Operator/account that performed the move  
   This satisfies USDA audit requirements for traceability.

### 1. Right-Sized VM Specification
The current CPU spikes indicate "CPU contention" or "Ready Time" issues during the burst synchronization period. To ensure the system handles the burst without latency (which could cause scanner timeouts and compliance gaps), we must increase the headroom.

*   **Recommended vCPU:** **12 to 16 vCPUs.** 
    *   *Rationale:* Doubling the vCPU count allows the OS to handle the massive I/O interrupts and concurrent write requests from all handhelds simultaneously during the sync window. 
*   **Recommended RAM:** **64GB.** 
    *   *Rationale:* Increasing RAM allows for a larger File System Cache. Since these are log files (small, frequent writes), a larger cache will allow the OS to buffer the "burst" in memory and commit it to the disk more efficiently, smoothing out the I/O spike.

### 2. Storage Plan (Tiered Lifecycle Management)
The current storage will be exhausted in approximately **4 weeks**. To meet the 2-year (104-week) retention requirement without overspending on expensive SSD space, we will implement a tiered approach.

*   **Tier 1 (Hot Data - SSD):** 
    *   **Size:** 1TB SSD Volume.
    *   **Purpose:** Hosts the OS, the Shared Folder for "Active" logs, and the last 6 months of scan data.
    *   **Benefit:** Ensures the high-speed I/O required by the handheld scanners during the shift-change bursts.
