Example character: a paragraph explaining how the process generally works, without numbered, followable steps.

Proposed Naming/Taxonomy Convention -- Lot-Tracking Scan Logs (3-Line Plant)

New filename format: `<LineCode>-<Year>Q<Quarter>-<4-digit-lot-seq>_<ProductionDate
YYYYMMDD>.csv`, e.g. `L1-2026Q3-0047_20260715.csv`. LineCode is a fixed 2-character
identifier per production line (L1, L2, L3), assigned once and never reused. This makes every
filename unique and self-describing without opening the file: which line, which quarter,
which sequence number within that quarter/line, and the production date are all visible from
the name alone.

Lot-ID taxonomy: change the lot ID itself (not just the filename) to embed the line code as a
prefix -- `L1-0047`, `L2-0047`, etc. -- instead of a bare 4-digit counter shared across all
three lines. Because each line's counter now has its own namespace (L1's 0047 and L2's 0047
are different, distinguishable IDs), two lines can never again produce an identical lot ID in
the same quarter, even though each line's counter still independently resets to 0001 every
quarter.

Handling the existing collision (this quarter's already-shipped, ambiguous dual-use lot
number): do NOT rename the historical records -- the product has already shipped under that
bare number, and renaming after the fact would break traceability to shipping/customer
records rather than fix it. Instead: (1) identify both original scan-event sets that share
the collided number, (2) create a compensating cross-reference record explicitly documenting
"lot #XXXX refers to two distinct physical lots: Line A's run on [date] and Line B's run on
[date], disambiguated here because retroactive renaming is not possible," and (3) file that
cross-reference alongside the original records so a future USDA audit finds the disambiguation
immediately rather than discovering the collision cold.

Here is a complete, audit-defensible taxonomy designed for your MSP environment. It separates the **operational lot identifier** (which stays printed on product/packaging) from the **system-level unique key** (which lives in the filename and filesystem).

---
### 1. New File/Folder & Naming Taxonomy

**Directory Structure:**
```
/{FacilityCode}/
  /{LineID}/
    /{LotNum}/
      {LineID}_{LotNum}_{YYYYMMDD}_{HHMMSS}_{Seq03}.csv
```

**Concrete Example:**
`/PLANT_A/L2/0087/L2_0087_20240715_143022_001.csv`

**Filename Component Rules:**
| Segment | Format | Meaning | Why It's Required |
|---------|--------|---------|-------------------|
| `LineID` | 2-char prefix (e.g., `L1`, `L2`, `L3`) | Production line that generated the scan batch | Resolves cross-line ambiguity without opening file |
| `LotNum` | 4-digit plant counter (e.g., `0087`) | Original USDA lot number as printed on product | Preserves chain-of-custody alignment with shipped product |
| `YYYYMMDD` | ISO date | Date scan batch began | Prevents cross-day collisions |
| `HHMMSS` | 24h timestamp | First scan timestamp in this file | Prevents same-second collisions |
| `Seq03` | 3-digit zero-padded | Sequential batch number | Prevents collisions when multiple scan runs occur in the same second |

**Why this is self-describing:** An auditor can read any filename and immediately reconstruct: *Which line? Which lot? When did recording start? Is this the first or subsequent scan batch?* No file introspection required.

---
### 2. How This Eliminates Collisions Going Forward

The plant's 4-digit quarterly counter remains the **operational ID** (tied to packaging, labeling, and shipping systems). It is *not* changed. However, the **system-level uniqueness** is enforced by the compound filename key:

```
UNIQUE_KEY = LineID + LotNum + YYYYMMDD + HHMMSS + Seq03
```

- Two different lines running lot `0087` in the same quarter now write to `/L1/0087/` and `/L2/0087/` with timestamped, sequenced filenames. The system will never overwrite, and two records can never share the same filesystem path.
- If the same lot repeats on the same line later in the quarter, the new filename's timestamp + sequence increments automatically.
- Scanner software must be reconfigured to:
  1. Write only to its assigned `/{LineID}/` directory tree
  2. Auto-generate the filename using the format above
  3. Refuse writes that would overwrite an existing file (hardened write guard)
  4. Log the write event to a separate audit trail (not the lot log itself)

**Core Principle:** Historical records are **untouched, unrenamed, and immutable**. Product has shipped under those numbers; altering filenames or contents would break chain-of-custody and violate USDA retention expectations (9 CFR § 381.100 / FSIS Policy Guide 2019-1).

**Implementation Steps:**

1. **Lockbox Archive:** Move all current-quarter files to an immutable archive path:

2. **Collision Manifest (`collision_manifest.json`):** Place this in the archive root. It documents the known ambiguity transparently:
   ```json
   {
     "archive": "Q3_2024",
     "collision_flag": true,
     "records": [
       {
         "original_path": "lot_log.csv",
         "system_key": "ARC-2024Q3-L1-0087-001",
         "reconstructed_line": "L1",
         "scan_date": "2024-07-12",
         "note": "Lot 0087 assigned on L1 and L2 within same quarter. Physical lots distinct. Records preserved without alteration per USDA retention policy."

       {
         "original_path": "lot_log.csv",
         "system_key": "ARC-2024Q3-L2-0087-001",
         "reconstructed_line": "L2",
         "scan_date": "2024-07-13",
         "note": "Same lot number used on L2. Physical lots distinct. Records preserved without alteration."
       }
     ]
   }
   ```
   The `reconstructed_line` is filled in from scanner logs, shift records, or line-specific timestamps. If the original file lacks line context, the manifest explicitly notes: `"Line attribution unverifiable from file metadata alone."`

3. **Master Registry (`file_index.csv`):** A single lookup table that maps every retained file (historical and current) to:
   - System Key (UUID or sequential)
   - Original filename
   - Line ID
   - Lot Num
   - Archive path

## 1. New Lot-ID Taxonomy

## 2. File & Folder Naming Convention

To ensure every retained scan-log file is unique without opening it, we will enforce a **date-partitioned folder structure** with **compound filenames**.

**Server Path:** `\\fileserver\production\scan_logs\YYYY\MM\DD\`

**Filename Format:** `[LineID]_Lot[YYYYMMDD-NNNN].csv`

**Example Path & Filename:**
`\\fileserver\production\scan_logs\2023\10\04\L2_Lot20231004-0042.csv`

### Why this structure works:
1.  **Folder Partitioning (`YYYY/MM/DD`):** Limits file growth per directory, makes it trivial to archive or purge old logs (e.g., only 12 folders per year), and prevents a flat folder from becoming unreadable.
2.  **Compound Filename:** The filename contains the Line ID and the Lot ID. An auditor can open a folder and immediately see which line produced which lot without reading the CSV header.
3.  **Prevention of Overwrite:** Because the timestamp is baked into the name, two files can never have the same name, even if a scanner error occurs.

## 3. Implementation Strategy (Scanner Configuration)

The current scanners are writing generic filenames. The MSP must update the scanner driver/software configuration to enforce the new naming convention at the point of ingestion:

1.  **Dynamic Variable Injection:** Configure the scanner software to auto-populate `[LineID]` based on the physical port or IP address of the scanner, and `[LotNumber]` based on the barcode value scanned.
2.  **Auto-Prepend Date:** Configure the server-side write script (or scanner local driver) to auto-prepend the current date into the folder path (`YYYY/MM/DD`) and the filename.
3.  **Write Validation:** Implement a file-server-side validation script (e.g., a PowerShell or Python watcher) that triggers if a new file in the `scan_logs` root folder does not match the `[LineID]_Lot[YYYYMMDD-NNNN].csv` pattern, alerting the plant manager immediately.
4.  **Retention Policy:** Configure the file server to retain logs for 7 years (per FSIS recommendation) and auto-archive older folders to cold storage or a historical share.

### File/Folder Naming and Lot-ID Taxonomy Proposal

This proposal addresses the audit findings by ensuring **filename uniqueness**, **self-describing metadata**, **collision-free lot identification**, and **integrity of historical data**. The solution requires minimal changes to scanner firmware (only filename formatting) and relies on folder structure and lot-ID scoping to eliminate ambiguity.

---

### 1. Filename Taxonomy
**Rule:** No file shall ever be overwritten. Every filename must be unique and contain sufficient context to identify the origin and contents without opening the file.

**Format:**
```text
[LIN]_[YYYYMMDD]_[LOTSEQ]_scanlog.csv
```

**Field Definitions:**
*   **`[LIN]`**: Two-character Line Identifier (e.g., `L1`, `L2`, `L3`).
*   **`[YYYYMMDD]`**: Date the lot was initiated (ISO 8601 format).
*   **`[LOTSEQ]`**: The lot sequence number for that specific line on that day (see Lot-ID Taxonomy below).
*   **`_scanlog.csv`**: Static suffix indicating file type.

**Example:**
*   `L1_20231025_0042_scanlog.csv`
    *   *Interpretation:* Line 1, Lot started Oct 25, 2023, 42nd lot on Line 1 that day.
    *   *Uniqueness:* No other file can have this exact string.
    *   *Self-Describing:* Line, Date, and Lot Sequence are immediately visible.

---

### 2. Lot-ID Taxonomy
**Rule:** To eliminate collisions, lot counters must be **scoped per line** rather than shared globally across the plant. This ensures that `LOTSEQ` is only unique within the context of its `[LIN]` and date.

**Configuration:**
*   **Counter Scope:** Each scanner maintains its own independent counter.
*   **Counter Reset:** The counter resets daily (recommended) or quarterly. A daily reset is preferred to keep sequence numbers short and reduce collision risk, but if quarterly is required for plant policy, the daily date in the filename still guarantees uniqueness.
*   **Format:** 4-digit zero-padded integer (`0001`–`9999`).

**Why this eliminates collision:**
*   *Current Failure:* `L1` and `L2` both generate lot `0500` in Q3. Ambiguity exists.
*   *New Success:* `L1` generates `0500`; `L2` generates `0500`.
    *   File on L1: `L1_20230915_0500_scanlog.csv`
    *   File on L2: `L2_20230915_0500_scanlog.csv`
    *   **Result:** Files are unique. Lot `0500` is distinct per line. No physical lots share an identical identifier in the retained records.

---

### 3. Folder Structure
**Rule:** Organize by Line and Date to enforce separation of concerns and prevent cross-line file overwrites.

**Hierarchy:**
```text
/PoultryScanLogs/
└── Active/
    ├── L1/
    │   ├── 2023/
    │   │   └── 10/
    │   │       ├── L1_20231001_0001_scanlog.csv
    │   │       └── L1_20231001_0002_scanlog.csv
    │   └── 2024/
    │       └── 01/
    │           └── L1_20240102_0001_scanlog.csv
    ├── L2/
    └── L3/
```

**Benefits:**
*   **Isolation:** Scanners write only to their own `[LIN]/` subfolder.
*   **Scalability:** Date-based subfolders keep file counts manageable.
*   **Auditability:** USDA auditors can navigate `Line -> Year -> Month -> File` instantly.

* **Legacy (already‑recorded) ambiguous lot numbers** – **do not rename** the files on disk. Instead, move them into a *read‑only* “legacy‑ambiguous” sub‑tree and annotate the filename with a *suffix that preserves the original lot‑number* while also providing a unique qualifier.  The suffix is added **only at the file‑system level**; the logical lot number that the business continues to use on the product label stays unchanged.

  Example legacy file moved to:  

  ```
  /LotLogs/legacy‑ambiguous/2025/Q2/ambiguous_LOT0047_line1_20250415T091234.csv
  ```

  The suffix `_20250415T091234` is the UTC timestamp of the *first* scan that created the ambiguous file, guaranteeing uniqueness while still making the file discoverable via a simple directory scan.

## 1.  Why the Current Scheme Fails

| Problem | Current Implementation | Why it Breaks USDA Lot‑Tracking |
|---------|------------------------|---------------------------------|
| **Single shared folder** | All three lines drop `lot_log.csv` into `\\fileserver\LotLogs` | Overwrites happen the moment any line starts a new lot. |
| **Generic filename** | `lot_log.csv` | No intrinsic identifier → cannot be distinguished without opening the file. |
| **Quarter‑reset 4‑digit lot counter** | Global counter 0001‑9999 that resets each quarter | Same numeric value can be generated on different lines → two physically different lots share a lot‑number. |
| **Audit requirement** | Needs “self‑describing, unique filename” and “no collisions across lines” | USDA wants to verify lot provenance by *filename alone*. |

The solution must **replace the single generic name with a name that is globally unique, contains all the information needed to trace the lot, and can be read by a script or a human without opening the file**.

## 2.  Taxonomy – From “lot number” to “lot identifier”

### 2.1  Core Elements of the New Identifier

| Element | Symbol | Description | How it is generated |
|---------|--------|-------------|---------------------|
| **Plant‑wide timestamp** | `TS` | UTC date‑time down to seconds (`YYYYMMDDTHHMMSS`). | Auto‑generated by the scanner at the moment the first barcode for a new lot is read. |
| **Line code** | `L#` | One‑character or two‑character identifier for the production line (e.g., `L01`, `L02`, `L03`). | Configured per scanner; never changes. |
| **Line‑local lot sequence** | `LOT<NNNN>` | 4‑digit sequential counter **per line per quarter** (0001‑9999). | Incremented each time a new lot starts on that line; resets to 0001 at the first lot of the quarter. |
| **Product‑type code (optional)** | `P#` | Short code for product family (e.g., `P01` = whole‑bird, `P02` = parts). | Fixed per product family, optional. |
| **Checksum / hash (optional)** | `H` | 2‑digit CRC or short hash for extra safety (e.g., `H01`). | Calculated over the filename components; not required for uniqueness but helpful for audit trails. |

### 2.2  Full Filename Pattern

```
<TS>_L<LineID>_LOT<LLNN>[_P<PP>][_H<HH>].csv
```

*All components are concatenated with underscores; no spaces or special characters other than the underscore and the leading “T” in the timestamp.*

#### Example (real‑world)

```
20251103T143210_L02_LOT0047_P01.csv
```

*Interpretation*  

* `20251103T143210` – the exact UTC time the lot was opened on line 2.  
* `L02` – the line that generated the file.  
* `LOT0047` – the 47th lot opened on line 2 in the current quarter.  
* `P01` – product family “whole bird” (optional).  

If you need a checksum:  

```
20251103T143210_L02_LOT0047_P01_H01.csv
```

### 2.3  Folder Layout (optional but highly recommended)

```
<RootFolder>/
   └─ <Year>/                     ← Year folder (e.g., 2025)
        └─ <Year>-<Quarter>/      ← Quarter folder (e.g., 2025-Q2)
             └─ L<LineID>/          ← Line sub‑folder (e.g., L02)
                  └─ <TS>_L<LineID>_LOT<LLNN>[_P<PP>][_H<HH>].csv
```

*Why this layout?*  

* **Human‑readable navigation** – a quick “ls” shows the year → quarter → line → file path.  
* **No name collisions** – even if two files are created in the same second on different lines, the full timestamp (including milliseconds if you want to add them) stays unique.  
* **Audit‑ready** – the folder depth mirrors the data elements required for USDA traceability (Year, Quarter, Line, Lot‑Sequence, Timestamp).

## 3.  Enforcing Uniqueness at the Application Level

1. **Scanner firmware / driver** – add a small script that, when a new lot is detected, does the following:  

   a. Capture the **UTC timestamp** (e.g., using `datetime.utcnow().strftime("%Y%m%dT%H%M%S")`).  
   b. Increment the **line‑local lot counter** (persisted in a tiny SQLite DB per line).  
   c. Build the filename using the pattern above.  
   d. Write the file directly to the appropriate folder (`<Root>/<Year>/<Year>-<Quarter>/L<LineID>/`).  

2. **Collision guard** – before creating the file, the script checks for an existing file with the same constructed name. If one exists (extremely unlikely but possible if two scanners race), the script appends a **millisecond suffix** (`_<ms>`) and retries. Because the timestamp includes seconds, the probability of a clash is < 1 in 10⁶ per line per day.

3. **Immutable file name** – Once the file is closed, the name is never changed. This satisfies the “self‑describing” requirement: a user can look at `20251103T143210_L02_LOT0047_P01.csv` and instantly know *when*, *where*, *which lot* (by sequence), and *what product family* it belongs to.

## 4.  Handling the Already‑Recorded Ambiguous Lot Numbers

The audit discovered that **some lots already share the same numeric lot‑counter** (e.g., “LOT0047”) on different lines within the same quarter. Because those files already exist on the shared drive and product has shipped under those numbers, **renaming them in‑place would break downstream references (ERP, shipping manifests, etc.)**.  

### 4.1  What We Do **NOT** Do  

* **Never rename** the original files on the live share.  
* **Never delete** them without a documented migration plan.  

### 4.2  What We **DO** Do  

1. **Create a “legacy‑ambiguous” archive tree** that mirrors the new taxonomy but **adds a disambiguating suffix** that is *derived from the original file’s creation timestamp* (or another unique attribute).  

   ```
   /LotLogs/legacy-ambiguous/<Year>/<Year>-<Quarter>/ambiguous_LOT<NNNN>_<LineID>_<OriginalTS>.csv
   ```

   *Example*  

   ```
   /LotLogs/legacy-ambiguous/2025/Q2/ambiguous_LOT0047_L01_20250415T091234.csv
   ```

   *Why this works*  

   * The suffix (`_20250415T091234`) is the **exact UTC timestamp** when the original ambiguous file was first created. Because timestamps are unique to the second, the full path becomes unique even though the logical lot number (`LOT0047`) is duplicated.  
   * The prefix `ambiguous_` flags the file as a *historical artifact* that must be reviewed for audit compliance.  

2. **Update the inventory/ERP mapping** – add a column that points from the **physical file path** in the legacy‑ambiguous folder to the **new, unambiguous filename** that will be used for any *future* references to that lot. This can be a simple CSV mapping file:

   ```
   old_path,new_path,original_lot_number,line_id,quarter
   \\fileserver\LotLogs\2025\Q2\L01\lot_log.csv,\\LotLogs\legacy-ambiguous\2025\Q2\ambiguous_LOT0047_L01_20250415T091234.csv,0047,L01,Q2
   ```

   This mapping can be used by downstream reporting tools to translate legacy references without needing to rename anything on disk.

3. **Mark the legacy files as read‑only** (Windows ACL “Read” only, or Linux `chmod 444`). This prevents accidental overwrites while still allowing auditors to browse them.

4. **Communicate** – Issue an internal SOP that says:  

   *“All new lot‑tracking scans must use the new filename pattern under the active folder hierarchy. Legacy ambiguous files remain in *LotLogs\legacy‑ambiguous* and must never be moved, renamed, or deleted. When a legacy file is needed for a traceability query, the mapping table should be consulted to retrieve the associated new‑style identifier.”*

| Element | What it is | Example | Why it matters |

### How the Lot‑Sequence is generated

- **Global counter per quarter**: The first lot that line 1 starts in 2024Q1 is `000001`, line 2’s first lot is `000002`, etc.  
- **Reset policy**: Reset to `000001` at the *beginning of each quarter*.  
- **Why not per line?** Because that would re‑introduce collisions.  
- **Implementation**: The scanning software queries a small “Lot‑Counter” database (or a lock file) each time a new lot starts; the counter is atomically incremented and returned.  

This guarantees that *no two lot‑sequence numbers are identical in a given quarter*, even across lines.

## 6. Sample code snippets

### 6.1 Python function to build the new filename

```python
from datetime import datetime

def build_lot_log_name(plant, line, quarter, lot_seq, first_scan_ts):
    """
    plant: str, e.g., "P123"
    line: str, e.g., "L1"
    quarter: str, e.g., "2024Q1"
    lot_seq: int, e.g., 12
    first_scan_ts: datetime object
    """
    seq_str = f"{lot_seq:06d}"
    ts_str = first_scan_ts.strftime("%Y%m%dT%H%M")
    return f"lot_log_{plant}-{line}-{quarter}-{seq_str}_{ts_str}.csv"
```

### 6.2 SQL schema for the Lot‑Counter

```sql
CREATE TABLE lot_counter (
    plant_code   VARCHAR(10) NOT NULL,
    quarter      VARCHAR(6)  NOT NULL,   -- e.g., 2024Q1
    next_seq     INT          NOT NULL,   -- next sequence to allocate
    PRIMARY KEY (plant_code, quarter)
);

-- Initialize for the current quarter
INSERT INTO lot_counter (plant_code, quarter, next_seq)
VALUES ('P123', '2024Q1', 1)
ON CONFLICT DO NOTHING;
```

When a new lot starts:

```sql
UPDATE lot_counter
SET next_seq = next_seq + 1
WHERE plant_code = 'P123' AND quarter = '2024Q1'
RETURNING next_seq - 1 AS allocated_seq;
```

This ensures atomic allocation.

## 1. New Lot‑ID Taxonomy

### 1.1. Structure of a Lot Identifier

```
<LineID>-<QuarterSuffix>-<QuarterCounter>
```

| Component | Description | Example |
|-----------|-------------|---------|
| **LineID** | Two‑character code for each production line (e.g., `A`, `B`, `C` or `L1`, `L2`, `L3`). | `A` |

*Why this works:*  
- The **LineID** differentiates lots that otherwise share the same quarter counter.  
- The **QuarterSuffix** ensures that a counter value from one quarter can never be mistaken for the same value in another quarter (useful for cross‑quarter queries).  
- The **four‑digit counter** retains the plant’s familiar 4‑digit format while providing 10,000 unique IDs per line per quarter—far more than any realistic production volume.

### 1.2. Why Reset Per Line, Not Globally?

The audit revealed that a **global** 4‑digit counter (`0001`‑`9999`) reset each quarter caused collisions when two lines independently generated the same number. By **partitioning the counter per line**, each line can independently cycle through `0001`‑`9999` without interference, eliminating the collision entirely.

## 4. Handling Already‑Recorded Ambiguous Lots (Current Quarter)

Because the lots have already shipped, we **cannot simply rename the files** (that would break traceability). Instead, adopt a **metadata‑augmentation** strategy:

1. **Identify Ambiguous Lot Numbers**  
   - Run a scan of all `lot_log.csv` files from the current quarter.  
   - Group by the *raw* 4‑digit lot number (e.g., `0123`).  
   - Flag any group that appears under **more than one LineID** (derived from the date‑folder or from embedded scanner metadata if available).

2. **Create a “Collision Resolution” Record** for each ambiguous lot:  

   **File:** `/ScanLogs/2025/B/CollisionResolution/<AmbiguousLot>_<LineID>.json`

   **Example JSON (`0123_A.json`):**
   ```json
   {
     "ambiguousLotNumber": "0123",
     "linesAffected": ["A", "B"],
     "startDate": "2025-04-01",
     "endDate": "2025-06-30",
     "notes": "Both lines generated lot 0123 in Q2 2025. Product shipped under these numbers; USDA audit will reference this resolution file."
   }
   ```

3. **Tag the Original Log Files** (without renaming) by adding a **header line** at the top of each CSV (if the format permits) or by appending a **side‑car** CSV with the same name but a `_meta.csv` suffix:

   - **Header approach (if CSV parser ignores a comment line):**  
     `# LotID=A-B-0123; Line=A; Quarter=B; OriginalLot=0123`

   - **Side‑car approach:**  
     Create `A-B-0123_2025-04-15.csv_meta.csv` containing:
     ```
     OriginalLotNumber,LineID,ResolvedLotID
     0123,A,A-B-0123
     ```

   This **preserves the original file name** (so any downstream systems that already reference it continue to work) while providing a clear mapping to the *resolved* LotID.

4. **Update Internal Reporting & Audits**  
   - When generating lot‑track reports, the system should **join** the original log file with its corresponding side‑car/metadata to present the **resolved LotID** (`A-B-0123`, `B-B-0123`, …).  
   - Include a **footnote** in USDA‑required documentation stating: “Lot numbers 0123 (Q2 2025) were generated on both Line A and Line B. They have been disambiguated by appending the line identifier as shown above. No product was re‑labeled; the mapping is for record‑keeping only.”

5. **Long‑Term Archival**  
   - After the quarter closes, **archive** the collision‑resolution folder alongside the regular logs.  
   - Keep the original ambiguous files **read‑only** in a dedicated “LegacyAmbiguous” sub‑folder for historical completeness, but **do not** expose them as active lot identifiers.

**Result:** The USDA audit will see a clean, unambiguous lot‑tracking dataset moving forward, while the plant retains a transparent, auditable record of the legacy collision.

### TL;DR

- **New Lot ID:** `Line‑QuarterLetter‑QuarterCounter` (e.g., `A‑B‑0123`). Counters reset **per line** each quarter → no more cross‑line collisions.  
- **File storage:** ` /ScanLogs/<Year>/<Quarter>/<Line>/<LotID>_<ISODate>[_<Seq>].csv ` – fully self‑describing.  
- **Legacy ambiguous lots:** Keep original files, attach side‑car metadata or header rows that map the old 4‑digit number to the resolved LotID, and store a dedicated collision‑resolution record.  
- **Implementation:** Update scanner config, deploy a tiny counter service, restructure folders, add metadata, train staff – all achievable within a 6‑8‑week window with zero disruption to shipped product.

This taxonomy satisfies USDA lot‑tracking requirements, provides an audit‑ready, human‑readable file system, and cleanly resolves the current numbering ambiguity without re‑labeling shipped product.
