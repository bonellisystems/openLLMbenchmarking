### 3. SQL Semantics: Why Issue 3 is Silently Excluded

The `WHERE rate_type = 'standard'` clause excludes the 460 NULL rows because of **SQL's Three-Valued Logic (3VL)**.

In SQL, `NULL` does not represent "empty" or "zero"; it represents **"Unknown."**
*   When the database engine evaluates the comparison `NULL = 'standard'`, the result is not `TRUE` and not `FALSE`; the result is `UNKNOWN`.
*   The `WHERE` clause functions as a filter that retains rows **only if the condition evaluates to `TRUE`**.
*   Rows where the condition is `FALSE` or `UNKNOWN` are discarded.
*   Therefore, 460 rows with a `NULL` `rate_type` fail the filter because `UNKNOWN` is treated as `FALSE` for the purpose of row selection. The engine does not raise an error because comparing a NULL to a value is a valid operation in SQL; it simply returns `UNKNOWN`.

### 3. Why NULL `rate_type` rows are silently excluded

The reporting query most likely looks like:

```sql
SELECT … 
FROM time_entries_fact
WHERE rate_type = 'standard';
```

**SQL semantics of `=` with NULL**

* In SQL, any comparison (`=`, `<>`, `>`, etc.) that involves a `NULL` value yields **`UNKNOWN`**, not `TRUE` or `FALSE`.
* The `WHERE` clause keeps only rows for which the predicate evaluates to `TRUE`.  
* Because `rate_type = 'standard'` is `UNKNOWN` when `rate_type` is `NULL`, those rows are **filtered out** without any error or warning.  
* No exception is raised because the engine treats `UNKNOWN` as “do not include” – this is the defined behavior for three‑valued logic (TRUE / FALSE / UNKNOWN) in ANSI‑SQL.

Thus the query **silently drops** the 460 NULL rows; the data pipeline never sees an error, and the report simply reports a smaller total.

## 4.  Why NULL `rate_type` rows are silently excluded (SQL semantics)

The report uses the predicate:

```sql

```

* In SQL a comparison with `NULL` does **not** return `TRUE` or `FALSE`; it returns **`UNKNOWN`**.
* The `WHERE` clause **keeps only rows where the predicate evaluates to TRUE**.  
  Rows where the predicate is `FALSE` **or** `UNKNOWN` are filtered out.
* Therefore, any row where `rate_type` is `NULL` evaluates to `UNKNOWN` for the expression
  `rate_type = 'standard'` and is dropped from the result set without raising an error
  or a warning.

The engine is doing exactly what the SQL standard prescribes; the problem is the
assumption that “missing = not‑standard” rather than “missing = unknown”.

## 🔍 **Issue 3: Why NULL `rate_type` Rows Are Silently Excluded**

> **Question**: Why are the 460 rows with `rate_type = NULL` silently excluded instead of causing an error?

### ✅ **Answer: SQL Three-Valued Logic (3VL) and Predicate Evaluation**

In standard SQL, comparisons involving `NULL` do **not** return `TRUE` or `FALSE` — they return **`UNKNOWN`**.

When a query uses:
```sql
WHERE rate_type = 'standard'
```

- For a row where `rate_type = 'standard'` → `TRUE` → **included**
- For a row where `rate_type = 'contingency'` → `FALSE` → excluded
- For a row where `rate_type IS NULL` → `UNKNOWN` → **excluded**

Because `WHERE` clauses only return rows where the condition evaluates to `TRUE`, any row with `rate_type IS NULL` fails the filter **silently** — no error, no warning.

Furthermore:
- `NULL = 'standard'` → `UNKNOWN`
- `NULL != 'standard'` → also `UNKNOWN`
- You must explicitly handle `NULL`s using:
  ```sql
  WHERE rate_type = 'standard' OR rate_type IS NULL
  ```
  or use `COALESCE(rate_type, 'standard')`.

> ❗ There is **no error raised** because `NULL` filtering is standard SQL behavior — it's expected, not exceptional.

## 4.  Why NULL `rate_type` rows are silently excluded (SQL semantics)

The typical filtering clause in the reporting query looks like:

```sql
SELECT …
FROM   time_entries_fact f
WHERE  f.rate_type = 'standard'      -- only standard‑type rates are kept
  AND  …   -- other filters
```

**SQL three‑valued logic (3VL)** treats `NULL` as *unknown*.  The predicate `f.rate_type = 'standard'` evaluates to:

| `f.rate_type` | Result of `= 'standard'` |
|---------------|--------------------------|
| `'standard'`  | **TRUE** (row passes)   |
| `'contingency'`| **FALSE** (row filtered out) |
| **NULL**      | **UNKNOWN** (the predicate is *not true*) |

Because the predicate is **not true**, the row does **not satisfy the `WHERE` clause** and is therefore omitted from the result set.  It does **not raise an error** – the engine simply treats the comparison as “false” and continues processing.  Consequently, a row with `rate_type IS NULL` is invisible to any downstream aggregation that relies on the `WHERE` filter, even though the row physically exists in the fact table.

*In short:*  Equality comparison with `NULL` never returns *true*, so those rows are filtered out silently.

### 🔍 Why NULL `rate_type` Rows Are Silently Excluded (SQL Semantics)

4. To explicitly match or handle `NULL` values, you must use `IS NULL`/`IS NOT NULL` or `COALESCE()`, as equality operators never match `NULL`.

    SHA256(CONCAT(attorney_id, '|', matter_id, '|', start_time, '|', duration, '|', description)) AS src_fingerprint
  FROM raw_time_entries

  SELECT *, ROW_NUMBER() OVER (
    PARTITION BY src_fingerprint 
    ORDER BY ingestion_timestamp DESC
  ) AS rn
  FROM staged

USING deduped d ON f.src_fingerprint = d.src_fingerprint
  AND f.ingestion_timestamp = (SELECT MAX(ingestion_timestamp) FROM time_entries_fact WHERE src_fingerprint = d.src_fingerprint)
WHEN MATCHED THEN UPDATE SET ...  -- or IGNORE for strict dedupe
WHEN NOT MATCHED THEN INSERT (...) VALUES (...);

### 3. Why NULL `rate_type` Rows Are Silently Excluded (SQL Semantics)

The exclusion is not an error; it is the default behavior of **SQL Three-Valued Logic (3VL)**.

Standard SQL does not treat `NULL` as "zero" or "false." It treats `NULL` as **UNKNOWN**. When the query engine evaluates the `WHERE` clause `rate_type = 'standard'`, it produces the following truth table for the 460 NULL rows:

| `rate_type` | `rate_type = 'standard'` | `WHERE` Filter Result |
| :--- | :--- | :--- |
| `'standard'` | TRUE | **Return** |
| `'contingency'` | FALSE | **Discard** |
| `NULL` | **UNKNOWN** | **Discard** |

Because `UNKNOWN` is logically distinct from `TRUE`, the `WHERE` clause filters it out without raising an exception or error. The engine simply treats these rows as "not matching the condition." To catch them, the query would need an explicit check like `WHERE rate_type = 'standard' OR rate_type IS NULL`.

**Issue 1: Duplicate Ingestion**

**4.  Why `NULL rate_type` rows are silently excluded**

In SQL, comparison operators treat `NULL` as **UNKNOWN** rather than **FALSE**.  
The predicate

```sql

```

returns **TRUE** only for rows where `rate_type` is *exactly* `'standard'`.  
Rows where `rate_type` is `NULL` produce an **UNKNOWN** result, which the `WHERE` clause discards because it keeps only rows where the predicate is **TRUE**.  

- No error is raised because the column is allowed to contain `NULL`s (there is no `NOT NULL` or domain constraint).
- The filter simply excludes those rows; SQL semantics do not consider a comparison with `NULL` a violation.
