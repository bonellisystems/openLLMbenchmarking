## Priority 2: Core Web Vitals & Performance

### Issue 3: Homepage Largest Contentful Paint (LCP) = 4.8 Seconds
*   **Cause:** Architecture firms rely on high-resolution hero imagery and detailed blueprints. **Root Cause**

### 2. 34 Duplicate Title Tags on Project Pages
**Root Cause**  
Yoast title templates are using the global default rather than a post-type-specific template. The project Custom Post Type (CPT) template likely doesn't inject dynamic variables (`{post_title}`, `{post_excerpt}`), so every project page renders the same static title. This causes duplicate `<title>` tags in the `<head>`, hurting indexing and CTR.

**WordPress + Yoast Fix**
1. **Yoast Title Template:** 
   - `SEO > Search Appearance > Custom Content Types` → select your Projects CPT.
   - Set **Title template** to: `{post_title} | {site_title}`
   - Set **Meta description template** to: `{post_excerpt} | {site_title}`
   - Save. Yoast will now dynamically generate unique titles per project.
2. **Theme Template Check:** 
   - Inspect `single-projects.php` (or your project single template). Ensure it isn't hardcoding `<title>` or outputting a custom `<h1>` that overrides Yoast.
   - Confirm the theme calls `wp_head()` in `<head>` and doesn't duplicate or strip Yoast's title output. If the theme uses a custom title function, add: 
     ```php
     add_filter('pre_get_document_title', 'my_theme_project_title');
     ```
     or simply let Yoast handle it by removing theme overrides.
3. **Validation:** Use Yoast's page preview or crawl 5–10 project URLs to confirm unique titles. Check Search Console > Pages for duplicate title warnings.

**Priority & Rationale**  
- **Impact: 4** – Removes duplicate titles, improves indexing clarity, boosts project-page CTR.
- **Effort: 2** – Yoast config = 15 mins. Theme verification = 1–2 hrs if developer needed.
- **Verdict:** P2. Quick Win. Architecture firms rely on project visibility; unique titles directly support organic discovery.

### 3. Paginated Blog Series (Missing Canonical/rel=next/prev)
**Root Cause**  
WordPress pagination doesn't automatically emit `rel=next`/`rel=prev` or per-page self-referencing canonicals for custom query loops. Yoast handles standard archive pagination, but if this series uses a custom loop or the theme overrides canonical output, each page may inherit page 1's canonical or have none at all. **Note:** [model] officially deprecated `rel=next`/`rel=prev` for pagination in 2019. The current best practice is **self-referencing canonicals** on each paginated page.

**WordPress + Yoast Fix**
1. **Yoast Configuration Check:** 
   - `SEO > Search Appearance > Content Types > Blog` → ensure "Pagination" isn't disabled and that Yoast is allowed to output canonicals.
   - `SEO > Advanced` → verify the series isn't blocked by "Allow search engines to show the Content in [model]".
2. **Implement Self-Referencing Canonicals:** If Yoast isn't generating per-page canonicals (common with custom series), add this to your child theme's `functions.php` or a custom plugin:
   ```php
   add_filter('wpseo_canonical', function($canonical, $meta) {
       if ( is_paged() ) {
           $page = get_query_var('paged') ?: get_query_var('page');
           return trailingslashit(home_url()) . 'page/' . $page . '/';
       }
       return $canonical;
   }, 10, 2);
   ```
3. **Drop `rel=next`/`prev`:** Remove any theme-generated pagination link tags. [model] ignores them for indexing, and they can cause crawl loops.
4. **Validation:** Crawl the 12 series pages. Confirm each has a unique canonical matching its URL. Verify no `rel="next"`/`rel="prev"` tags remain.

**Priority & Rationale**  
- **Impact: 3** – Prevents crawl duplication, reduces index bloat, stops near-duplicate flags.
- **Effort: 2** – Yoast config + code snippet = 2–3 hours.
- **Verdict:** P3. Low risk but important for crawl efficiency. Handle after nav + title fixes.

### 4. Homepage Largest Contentful Paint (LCP) = 4.8s
**Root Cause**  
Architecture firm sites typically feature high-resolution hero imagery, heavy sliders, unoptimized media, render-blocking CSS/JS, or insufficient caching. Yoast does not impact LCP, but the theme, media delivery pipeline, and hosting configuration do. A 4.8s LCP falls firmly in the "needs improvement" CWV band and negatively affects ranking & bounce rate.

**WordPress + Yoast Fix**
1. **LCP Element Optimization (Hero Image):**
   - Convert to **WebP or AVIF** with exact display dimensions.
   - Add `fetchpriority="high"` to the LCP image tag.
   - Remove `loading="lazy"` from the LCP element (lazy loading delays LCP).
   - Use responsive images: `srcset` + `sizes` to serve appropriately sized assets per viewport.
2. **Render-Blocking Resources:**
   - Defer non-critical CSS/JS (`defer` or `async`).
   - Inline critical CSS above the fold.
   - Use a caching/performance plugin: **WP Rocket**, **LiteSpeed Cache**, or **Autoptimize** (disable "Combine CSS/JS" if it causes FOIT).
3. **Hosting & CDN:**
   - Enable object & page caching.
   - Serve assets via CDN (Cloudflare, BunnyCDN, or WP-Admin's built-in CDN).
   - Ensure PHP 8.1+, HTTP/2 or HTTP/3, and a modern web server.
4. **Yoast-Specific Check:** 
   - Yoast is lightweight by default, but verify unused modules aren't loading front-end assets: `SEO > Advanced > Disable features` → turn off `Text link counter`, `Advanced page templates`, or `Related keywords` if not actively used.
5. **Validation:** Run [model] PageSpeed Insights + WebPageTest. Target LCP ≤ 1.5s. Re-audit after each optimization batch.

**Priority & Rationale**  
- **Impact: 4** – LCP is a Core Web Vital ranking signal; 4.8s harms both SEO and conversion.
- **Effort: 4** – Requires media regeneration, caching setup, possible theme refactor, and ongoing monitoring. ~1–2 days of dev work.
- **Verdict:** P4. High impact but high effort. Schedule after P1–P3 are resolved. Consider staging the fixes (image → CSS → caching → CDN) to measure incremental gains.
