Here is a proposal for a file/folder taxonomy and lot-ID scheme that satisfies USDA traceability requirements, eliminates collisions, ensures filename uniqueness, and handles the legacy ambiguity without altering retained records.

## 1. Lot-ID Taxonomy (Prevents Collision, Self-Describing)

**Schema:**
```
{PlantCode}-{LineCode}-{Quarter}-{Counter}
```

**Example:** `USDA-PL01-L2-2024Q3-0042`

**Rules:**
1.  **Line-Prefix:** The Lot ID is anchored by the production line code (`L1`, `L2`, `L3`). This mathematically eliminates collision. If Line 2 and Line 3 both reach counter `0042`, the Lot IDs are `L2-...` and `L3-...`. They are distinct.
2.  **Quarter in ID:** Including the quarter (`2024Q3`) prevents confusion as counters reset; the quarter is part of the identity, not just a folder context.
3.  **Counter Scope:** The counter may reset per-line per-quarter (e.g., `0001` on Line 2 at the start of Q4 is valid) because the Line/Quarter prefix makes the ID globally unique.
4.  **Scanner Action:** The barcode scanner writes the **full** Lot ID to the log. This ensures the log is self-describing.

**Why this works for USDA:**
*   **Uniqueness:** No two physical lots can share the same string.
*   **Traceability:** A USDA auditor reading the Lot ID can immediately identify the line and quarter without opening the file.
*   **Operator Friendly:** The format is short enough for labels but structured enough for automated systems.

---

## 2. Folder Structure (Partitioned by Line and Time)

**Root:** `/MSP-USDA-Scans/Plant01/`

**Hierarchy:**
```
/Plant01/
├── /Scans/
│   ├── /2024/
│   │   ├── /2024-09/
│   │   │   ├── /L1/
│   │   │   │   ├── ScanLog_20240915T143022_L1_USDA-PL01-L1-2024Q3-0042_Scr01_001.csv
│   │   │   │   └── ...
│   │   │   ├── /L2/
│   │   │   └── /L3/
```

**Rationale:**
*   **Parallel Safety:** Each line writes to its own folder. Even if the naming scheme fails, files cannot overwrite each other because the destination path is unique per line.
*   **Retention:** Quarterly/annual retention policies can be enforced on the date folders.
*   **Audit Navigation:** Auditors can navigate directly to the relevant line and date range.

---

## 3. Filename Convention (Unique, Self-Describing, Append-Only)

**Pattern:**
```
ScanLog_{ISODateTime}_{LineID}_{LotID}_{ScannerID}_{SeqNum}.csv
```

**Example:**
```
ScanLog_20240915T143022_L2_USDA-PL01-L2-2024Q3-0042_Scr01_001.csv
```

**Components:**
*   `ISODateTime`: Truncated ISO 8601 (e.g., `20240915T143022`). Guarantees uniqueness per scan event.
*   `LineID`: `L1`, `L2`, `L3`. Self-describing context.
*   `LotID`: The full lot ID from Section 1.
*   `ScannerID`: Hardware identifier of the scanner (`Scr01`, `Scr02`). Disambiguates device swaps and aids root-cause analysis.
*   `SeqNum`: Zero-padded sequence within the lot session.

**File Server Policy:**
*   **No Overwrites:** The MSP must enforce an **append-only** policy on this share. If the scanner attempts to write a file that exists, the write must fail or the system must abort. This prevents the "generic filename" overwriting risk from recurring.
*   **Immutable:** Files should be marked read-only after write to preserve evidence integrity for audit.

## 4. Handling Legacy Ambiguous Lot Numbers

**Constraint:** Records from this quarter contain ambiguous Lot IDs (e.g., both Line 2 and Line 3 used `0001` in the CSV content). These records cannot be renamed or altered because product has shipped under those numbers. The label on the product matches the ambiguous ID in the file.

**Strategy:** Do not alter the records. Instead, create a **Disambiguation Registry** and augment the file references to allow the auditor to resolve the ambiguity using the preserved context.

### 4.1. MSP-Level File Renaming (Safe)
The MSP can rename the **files** to append the unique context, provided the internal CSV content (and thus the shipped Lot ID) remains untouched. This makes the retained files unique and self-describing without changing the data.

*   **Before:** `lot_log.csv` (Overwritten/Lost or Ambiguous)
*   **After:** `Legacy_0001_L2_2024Q3_20240915T1430.csv`

The MSP should recover all retained files from this quarter and apply this naming convention, capturing the Line ID and the timestamp of the first scan (which defines the lot start) in the filename. If files were overwritten and lost, they must be flagged as **MISSING** in the registry, not silently discarded.

### 4.2. Disambiguation Registry (`LotID_Disambig_2024Q3.csv`)
The MSP creates a metadata sidecar file in the root audit folder. This registry bridges the gap for any audit of this quarter.

**Format:**
```csv
LegacyLotID,Quarter,ResolvedLineID,FirstScanTimestamp,RetainedFileName,FileHash
0001,2024Q3,L2,2024-09-15T14:30:22,Legacy_0001_L2_2024Q3_20240915T1430.csv,a3f2b...
0001,2024Q3,L3,2024-09-15T16:10:05,Legacy_0001_L3_2024Q3_20240915T1610.csv,b8c1d...
```

**Rules:**
*   **Authoritative:** Any query for `0001` in Q3 must consult this registry. The registry proves that `0001` is not a single lot but two distinct lots resolved by Line and Time.
*   **Product Alignment:** Since product shipped under `0001`, the registry confirms that for any specific shipment, the auditor can determine which line's record applies based on the production timestamp. If Line 2 produced at 14:30 and Line 3 produced at 16:10, a shipment shipped at 15:00 corresponds to Line 2.
*   **Integrity:** The `FileHash` column ensures the retained file has not been tampered with since the registry was created.

### 4.3. Operational Warning
A prominent notice must be placed on the lot-numbering documentation:
> *"For Q3 2024, Lot IDs `0001` through `N` are ambiguous across lines. All lot identification queries must reference the `LotID_Disambig` registry. Future lots use the new `Line-Prefix` schema which does not require disambiguation."*

## Executive Summary
This situation presents a critical USDA compliance risk. The current file system allows data loss (overwriting), and the lot numbering scheme creates an audit failure (traceability ambiguity). We must implement a **tamper-evident, self-describing file structure** and a **globally unique lot taxonomy** immediately. We cannot alter the physical shipping labels or the content of historical logs (to avoid spoliation of evidence), but we must create a **correlation index** to resolve the historical ambiguity.

Below is the proposed taxonomy and remediation plan.

---

### 1. File & Folder Naming Taxonomy (Prevents Overwrite)
To eliminate the "single shared folder with generic filename" issue, we will enforce a hierarchical structure with unique filenames that contain enough context to be self-describing without opening the file.

**Folder Structure:**
```text
\\USDA-FileServer\Compliance\Traceability\Logs\
    ├── \YYYY\
    │   ├── \MM\
    │   │   ├── \L01\
    │   │   ├── \L02\
    │   │   └── \L03\
    │   └── \Reports\
    └── \Archive\
```
*   **Root:** `\USDA-FileServer\Compliance\Traceability\Logs\`
*   **Year/Month:** Enforces chronological retention policies (e.g., USDA often requires 1-2 years of records).
*   **Line ID:** Isolates data per production line physically on the disk, preventing accidental overwrite.

**Filename Convention:**
`{LineID}_{ISODate}_{LotID}_{Sequence}.csv`

**Example:**
`L01_2023-10-25_2023Q1-0045_A1.csv`

**Why this works:**
*   **Unique:** No two files have the same name.
*   **Self-Describing:** Without opening the file, you know it is **Line 1**, dated **Oct 25, 2023**, for **Lot 2023Q1-0045**.
*   **Audit Trail:** The filename contains the Lot ID, ensuring the file name matches the record content.
*   **Sequence ID:** The `A1` suffix ensures that if two lots start on the same line at the exact same second, they do not overwrite.

---

### 2. Lot ID Taxonomy (Eliminates Collision)
The current 4-digit counter (0001-9999 resetting quarterly) is the root cause of the collision. We must move to a **Composite Identifier** that includes Line, Time, and Sequence.

**Format:** `L{LineID}_{YYYY}{QTR}_{Sequence}`

*   **L{LineID}:** `L01`, `L02`, or `L03`. (Explicitly distinguishes physical origin).
*   **{YYYY}{QTR}:** `2023Q1`, `2023Q2`, etc. (Ensures quarterly resets do not collide across years).
*   **{Sequence}:** A 4 or 5-digit counter (0001-9999) that increments per line, not globally.

**Example:**
*   Line 1, Q1 2023, Lot #45: `L01_2023Q1_0045`
*   Line 2, Q1 2023, Lot #45: `L02_2023Q1_0045`

**Why this works:**
*   **Global Uniqueness:** Even if both lines generate Lot "0045" in the same quarter, the resulting IDs (`L01_2023Q1_0045` vs `L02_2023Q1_0045`) are distinct.
*   **USDA Compliance:** This creates a permanent, unique link between the physical product batch and the digital record.

---

### 3. Remediation of Historical Ambiguity
**Constraint:** We cannot rename the shipping labels on product that has already left the facility. We cannot alter the content of the historical log files (to maintain evidence integrity).

**Solution:** Implement a **Lot Reconciliation Index (LRI)**.

Since the raw data contains two different physical lots labeled with the same internal number (e.g., `1234`), we cannot simply "fix" the database. We must create a secondary metadata layer that tells the auditor how to interpret the ambiguity.

**Step 1: Generate the LRI**
Create a master CSV file (stored in the root `/Reports` folder) that maps the ambiguous records to unique, internal UUIDs.

| Old_Ambiguous_ID | Line_ID | Scan_Date_Time | New_Internal_UUID | Status |
| :--- | :--- | :--- | :--- | :--- |
| 1234 | L01 | 2023-10-01 08:00 | UUID-9928-A1 | Retained |
| 1234 | L02 | 2023-10-01 14:30 | UUID-9928-B2 | Shipped |

**Step 2: Tag Historical Files**
Do **not** rename the raw CSV files (which might be considered tampering). Instead, in the file metadata (where supported) or in a sidecar `.txt` file, note the `New_Internal_UUID`.

**Step 3: Submit to Auditor**
When the USDA auditor questions the "1234" collision, you present the **Lot Reconciliation Index (LRI)**.
*   It proves you are aware of the collision.
*   It proves you have tracked the specific physical instances (Line 1 vs Line 2).
*   It demonstrates that the *new* taxonomy (`L01_2023Q1_...`) prevents this from happening again.

**Action Item for Shipped Product:**
For the product that has already shipped under `1234`, no action is taken on the label. However, the **LRI** allows you to trace those specific items if a recall occurs, based on the Line ID and Ship Date associated with the `1234` number in the historical logs.

## 1.  What a “good” naming / taxonomy looks like  

A **good** file‑name / folder structure must satisfy three things at once  

| Requirement | How we satisfy it | Example (real‑world) |
|-------------|------------------|----------------------|
| **Globally unique** – no two files can ever have the same name on the same share. | Include **all** of the attributes that together make a lot unique **and** add a millisecond‑resolution timestamp (or a GUID) as a final safety net. | `LOT_2024Q2_20240514_03_001_L01_S2_141527_123.csv` |
| **Self‑describing** – a user can tell what the file contains without opening it. | Encode **Plant‑ID, Year‑Quarter, Calendar date, Production line, Shift, Lot‑sequence‑within‑line, and a time stamp** in the name. | `LOT_2024Q2_20240514_03_L01_S2_001_141527.csv` |
| **Future‑proof** – the scheme can keep working when the plant adds lines, changes shift schedules, or moves to a new lot‑numbering scheme. | Use **fixed‑length fields** and a **separator** (underscore) so a parsing script never breaks.  The lot‑sequence is **line‑scoped**, not plant‑wide, eliminating the “same number on two lines” problem. | `LOT_<YY>Q<q>_<YYYYMMDD>_<Line>_<Shift>_<LotSeq>_<HHMMSS>.csv` |

### 1.1  The taxonomy (field list)

| Field | Format | Meaning | Why it matters |
|-------|--------|---------|----------------|
| **Prefix** | `LOT` | Fixed literal – instantly tells the user this is a lot‑tracking file. | Human recognisable. |
| **Year‑Quarter** | `YYYYQX` (e.g. `2024Q2`) | Plant‑wide fiscal period – useful for archiving and audit‑by‑quarter. | Matches USDA quarter‑reset rule. |
| **Date** | `YYYYMMDD` | Calendar day the lot started. | Allows chronological browsing. |
| **Line ID** | `Lnn` where `nn` = two‑digit line number (`L01`, `L02`, `L03`). | Identifies which production line generated the lot. | Solves the duplicate‑lot‑number issue. |
| **Shift** | `Sx` where `x` = shift number (`S1`, `S2`, `S3`). | Some plants run 2‑3 shifts; shift is part of the “when”. | Helps locate the original scanner log if needed. |
| **Lot‑Seq** | `nnn` – a **line‑scoped** sequential counter that **resets each quarter** (000‑999). | The plant’s existing 4‑digit lot number is still used, but now it is **qualified** by line. | Keeps the legacy numbering that customers already see on labels. |
| **Time‑Stamp** | `HHMMSS` (24‑hr) or optionally `HHMMSSmmm` for millisecond precision. | Guarantees uniqueness when two lots on the same line start in the same minute (rare, but possible). | Provides a “last‑ditch” uniqueness guarantee. |
| **Extension** | `.csv` (or `.txt` etc.) | File type. | Standard. |

**Full example**  

```
LOT_2024Q2_20240514_L01_S2_007_141527.csv
```

*Interpretation*:  

* Q2‑2024, started 14 May 2024, produced on line 01, shift 2, the **7th** lot that line 01 has recorded this quarter, scan log started at 14:15:27.

## 3.  How the new scheme eliminates the lot‑number collision

| Old problem | New rule that prevents it |
|-------------|--------------------------|
| The 4‑digit lot counter is **plant‑wide** and resets each quarter, so line 1 and line 2 can both issue “001”. | The **Lot‑Seq** field is **line‑scoped**. Each line maintains its own counter that also resets each quarter. The full identifier is `LineID + Lot‑Seq`. Therefore “L01‑001” and “L02‑001” are distinct. |
| The scanner writes to a **single generic filename** (`lot_log.csv`). | Scanner software is re‑configured to **inject the full taxonomy** into the filename at creation time (see section 4). No two scans can write to the same name because the timestamp (or GUID) part is always different. |

If the plant prefers to keep the **legacy “4‑digit” lot number on the external label**, simply expose only the `Lot‑Seq` part on the label. Internally all downstream systems use the **full composite ID** (e.g., `L02‑001‑20240514‑141527`). This satisfies USDA because the audit trail shows a unique identifier for every lot, while the customer‑facing label remains unchanged.

## 4.  Implementation steps – making the change live

1. **Update scanner firmware / PC‑side capture software**  
   * Add a routine that, **when a new lot starts**, reads:  
     * Current date & time (system clock)  
     * Plant ID (hard‑coded)  
     * Production line ID (hard‑coded per scanner)  
     * Shift number (derived from clock or entered by operator)  
   * Pull the **line‑scoped lot counter** from a tiny local text file (or a central DB) that is reset each quarter. Increment it and write it back.  
   * Build the filename using the taxonomy above and open the CSV with that name.  
   * Example pseudo‑code (PowerShell, Python, etc.)  

   ```python
   from datetime import datetime
   plant = "PlantA"
   line = "L02"
   shift = f"S{current_shift()}"
   quarter = f"{now.year}Q{((now.month-1)//3)+1}"
   date = now.strftime("%Y%m%d")
   time = now.strftime("%H%M%S")
   seq = get_and_increment_line_seq(line, quarter)   # 001‑999
   filename = f"LOT_{quarter}_{date}_{line}_{shift}_{seq:03}_{time}.csv"
   open(os.path.join(root, plant, str(now.year), f"Q{quarter[-1]}", line, date, filename), "w")
   ```

2. **Create a “Lot‑ID Service”** (lightweight REST or SMB‑share file) that stores the **current line‑scoped sequence** and can be queried by any scanner. This guarantees that two scanners on the same line cannot hand out the same sequence number if they ever run in parallel (unlikely, but safe).

3. **Deploy a folder‑structure script** that automatically creates the required sub‑folders on the file server the first time a line writes a file for a new date/quarter.

4. **Add a daily/weekly validation job** that scans the share for duplicate names (should never happen) and logs any anomalies to a “Lot‑Integrity” report.

5. **Train operators** to verify that the new filename appears on the scanner’s screen before they start a lot.

6. **Update all downstream applications** (MES, ERP, USDA reporting scripts) to read the **full composite ID** from the filename instead of relying on a single 4‑digit number.

## 5.  What to do with the **already‑recorded, ambiguous lot numbers** from this quarter

The audit constraint is:  

*The product has already shipped under those numbers – you cannot retroactively change the lot numbers on the labels or in the shipping manifests.*  

Therefore we must **preserve the legacy numbers** for external reference **but** create an **internal, unambiguous mapping** that can be used for any future USDA audit, trace‑back, or quality‑investigation request.

### 5.1  Create a “Lot‑Reconciliation Table”

| Column | Content | Source |
|--------|---------|--------|
| `LegacyLotNumber` | The 4‑digit number that appears on the label (e.g., `0012`). | Existing records. |
| `LineID` | `L01`, `L02`, `L03`. | Derivable from the **scan‑log header** (first few rows normally contain line ID) or from the **operator‑entered shift log**. |
| `StartDateTime` | Timestamp of the **first scan** in the file (read from the CSV). | Inside the CSV. |
| `EndDateTime` | Timestamp of the **last scan** in the file. | Inside the CSV. |
| `GeneratedUniqueID` | New composite ID built from the taxonomy (e.g., `LOT_2024Q2_20240503_L02_S1_012_083015`). | Constructed by the reconciliation script. |
| `FilePath` | Full UNC path to the original file (`\\fileserver\LotLogs\...`). | Known. |
| `AuditStatus` | `OK`, `CONFLICT`, `MANUAL_REVIEW`. | Determined by script. |

**Steps to populate it**

1. **Run a one‑off script** that walks every CSV in the current quarter’s folder.  
2. For each file, read the first line (or a dedicated “LotHeader” row) to capture the **line ID** and the **timestamp** of the first scan.  
3. Extract the **legacy lot number** (the plant’s original 4‑digit counter) – it is usually stored in a column called `LotNumber` in the CSV.  
4. Build the **GeneratedUniqueID** using the taxonomy (line‑ID + timestamp).  
5. Insert the row into a **SQL Server / PostgreSQL** table called `LotReconciliation`.  

### 5.2  Resolve the collisions

*If the script finds two rows with the **same** `LegacyLotNumber` *and* the **same** `LineID`* → that is a true duplicate (should never happen). Flag for manual review.  

*If the script finds two rows with the same `LegacyLotNumber` *but different* `LineID`* → this is the exact problem you described. The table now holds **both** rows, each with a distinct `GeneratedUniqueID`.  

**Result:**  

* **External world** (customers, shipping documents) still sees “Lot 0012”.  
* **Internal world** (USDA audit, recall, QC) can refer to “Lot 0012‑L01‑20240503‑083015” **or** “Lot 0012‑L03‑20240504‑091230”.

## 1. High‑level naming philosophy  

| Element | What it tells you | How it is generated | Example value |
|--------|-------------------|---------------------|---------------|
| **Plant‑ID** | The USDA establishment number or internal plant code | Fixed 3‑digit code | `001` |
| **Line‑ID** | Production line identifier (1‑3 digits) | Fixed per line | `L01` |
| **Year** | Calendar year of the lot | 4‑digit year | `2025` |
| **Quarter** | USDA quarter (Q1‑Q4) | `Q01`‑`Q04` | `Q02` |
| **Lot‑Seq** | *Line‑local* sequential counter that **never resets within a quarter** (starts at 0001 each quarter and increments monotonically) | Incremented each time a new lot is started on that line | `L001` |
| **Date‑Stamp** | ISO‑8601 date the lot started (YYYYMMDD) | Extracted from the first scan record | `20250415` |
| **Shift‑ID** | Optional – “D” (day), “N” (night), “M” (mid) | Fixed per shift schedule | `D` |
| **Collision‑Suffix** | A 2‑character hash derived from the *global* unique lot identifier (see §4) – used only when the same lot‑number would otherwise repeat on a *different* line within the same quarter | Computed from a deterministic hash of Plant‑ID+Line‑ID+Lot‑Seq+Date‑Stamp | `H7` |

The final filename is built as:

```
<PlantID>_<LineID>_<Year>_<Quarter>_<LotSeq>_<DateStamp>_<Shift>_<CollisionSuffix>.csv
```

**Full concrete example**

```
001_L01_2025_Q02_001_20250415_D_H7.csv
```

*If the same lot‑number were generated on another line during the same quarter, the Collision‑Suffix would be different, guaranteeing a unique filename.*

## 2. Why this naming scheme eliminates collisions

* **Lot‑Seq is *line‑local*.** Each line starts its own counter at `001` each quarter and never re‑uses a number that has already been used on that line.  
* **The quarter is part of the filename.** Because the quarter string (`Q01`‑`Q04`) is baked into the name, a lot‑number that was `001` in Q1 can be reused as `001` in Q2 without any conflict.  
* **The Collision‑Suffix ties the filename to the *global* lot identifier.** Even if two lines accidentally start a lot with the same `LotSeq` on the same day, the suffix will differ because it incorporates the line identifier and the hash of the unique lot sequence number (see §4).  
* **The filename is self‑describing.** Anyone glancing at `001_L01_2025_Q02_001_20250415_D_H7.csv` knows:  
  * Plant 001  
  * Line 01  
  * Year 2025, Quarter 2  
  * This is the first lot on that line in the quarter (`001`)  
  * It started on 2025‑04‑15  
  * It was generated during the Day shift (`D`)  
  * The suffix `H7` guarantees uniqueness.

No need to open the file to know what it contains.
