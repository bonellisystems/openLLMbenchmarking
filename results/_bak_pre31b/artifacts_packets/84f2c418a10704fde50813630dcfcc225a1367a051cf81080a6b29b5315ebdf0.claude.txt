# IT Infrastructure -- scoring anchors (0-10)

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.

### Executive Summary
This plan outlines a **Staged Migration** strategy to move 340 mailboxes from an unsupported Exchange 2016 environment to the acquiring bank's Microsoft 365 tenant. Due to the unsupported source server, strict regulatory metadata requirements, and the absence of a unified after-hours window, this plan prioritizes **per-branch incremental cutover**, **third-party migration tooling** for chain-of-custody assurance, and **completion well ahead of the core-banking cutover**.

**Critical Recommendation:** Given Exchange 2016 is past extended support, native Hybrid configuration carries security and stability risks. A specialized third-party migration tool (e.g., BitTitan, Quest, or SkyKick) is recommended over native Staged/Cutover methods. These tools provide granular metadata preservation, immutable audit logs for chain of custody, and the ability to migrate without exposing the unsupported on-prem server to broad M365 hybrid protocols.

### 1. Migration Approach & Technical Strategy

#### A. Cutover Method: Staged Per-Branch Migration
*   **Why Staged:** Cutover migration locks source mailboxes during the final sync and lacks incremental sync capabilities, posing too high a risk for metadata integrity and operational disruption. Staged migration allows incremental syncs, reducing the final cutover window to minutes.
*   **Execution:** Migration is executed **per branch**, not globally. This accommodates the two time zones and eliminates the need for a company-wide maintenance window.
*   **Batch Size:** ~19 users per branch. This small batch size ensures the final cutover (mail flow switch and user testing) can be completed within a 60-minute window, easily fitting into local off-hours.

#### B. Regulatory Compliance: Metadata & Chain of Custody
*   **Metadata Preservation:**
    *   Migration tool must be configured to map and preserve EWS/MAPI properties, specifically `PR_MESSAGE_DELIVERY_TIME` and `PR_CLIENT_SUBMIT_TIME`.
    *   **Validation:** Post-migration, run automated PowerShell validation scripts to compare a sampling of items between source and target, verifying that `Received` headers and delivery timestamps remain identical.
    *   **Legal Hold:** Ensure M365 Compliance Manager Legal Holds are applied to target mailboxes *before* migration begins to satisfy retention obligations during the transition.
*   **Chain of Custody:**
    *   **Audit Trails:** The migration tool must generate immutable logs detailing: Source/Target IDs, User performing migration, Start/End timestamps, Checksums of data blocks, and Transfer Status.
    *   **Encryption:** Enforce TLS 1.2 for all data in transit. Verify Exchange 2016 TLS settings; if the unsupported server has expired certs or weak ciphers, remediate or use a local relay agent immediately.
    *   **Documentation Package:** Create a "Migration Certification" document signed by IT and Compliance, including the validation report and audit logs, to be retained per bank policy.

### 3. Operational Execution & Constraints

#### Handling Two Time Zones & No Global Window
*   **Scheduling:** Migration jobs are scheduled based on **local branch close time**.
    *   *Example:* If Branch A (EST) and Branch B (CST) are scheduled for the same night:
        *   Branch B cutover runs at 5:30 PM CST.
        *   Branch A cutover runs at 5:30 PM EST (6:30 PM CST).
        *   Support team follows the sun or covers the 5:30 PM EST to 9:00 AM EST window.
*   **User Notification:** Send branch-specific notices 3 days prior: *"Your email will be migrated on [Date] after close. You will receive instructions to log in to M365 before opening the next morning."*

#### Exchange 2016 Unsupported Status Risks
*   **Mitigation:** Since the server is unsupported, it may lack critical security patches required for modern M365 connectivity.
    *   *Action:* Isolate the migration network path. Use a dedicated migration proxy if possible. Do not expose the Exchange server to the internet; route traffic through a secure DMZ or internal proxy.
    *   *Contingency:* If Exchange 2016 crashes or becomes unstable during migration, the staged approach ensures only the current branch batch is affected. The source data remains intact on disk.

### 4. Rollback Plan

**Trigger:** A mailbox batch migration fails partway through, or post-cutover validation reveals critical data loss/corruption for a branch.

**Scope:** Rollback is performed at the **Branch Batch level**. Other migrated branches are unaffected.

**Procedure:**
1.  **Halt:** Stop the migration job for the affected batch.
2.  **Verify:** Confirm data integrity in M365. If data is partial/corrupt, do not allow user login.
3.  **Mail Flow Reversal:**
    *   Update M365 Connectors/Receive Connectors to exclude the affected branch users.
    *   Update On-Prem Send Connectors to route mail for these users back to the local Exchange Server.
    *   *Note:* In a Staged migration, users typically have mailboxes in both environments until cutover. Reverting mail flow is the primary technical step.
4.  **User Communication:** Notify branch staff immediately: *"Email service is temporarily reverted to the previous system while we resolve a technical issue. Access will remain available on-prem."*
5.  **Remediation:** Troubleshoot source/target issues. Re-run validation.
6.  **Retry:** Resume migration in the next available local off-hours window.
7.  **Final Cutover:** Once validated, perform the final sync and switch mail flow to M365.

### **2. Regulatory & Metadata Preservation Strategy**

*   **Timestamp Integrity:** Exchange 2016 and M365 handle `ReceivedTime` and `CreatedTime` differently. M365 may update timestamps upon ingestion.
    *   *Mitigation:* Use **Microsoft 365 Migration Tool (MMT)** with the `PreserveTimestamps` flag enabled (if supported by tenant policy) or PowerShell migration with explicit `Set-Mailbox -CreatedTime` preservation. Post-migration, a script will audit a statistical sample to verify `ReceivedTime` delta < 1 second.
    *   *Warning:* Built-in Exchange Forwarding is **PROHIBITED**. Forwarding resets timestamps and duplicates headers, violating regulatory constraints.
*   **Chain of Custody:**
    *   **Immutability:** Generate cryptographic SHA-256 hashes of the migration configuration and pre-migration mailbox sizes. Store in immutable storage.
    *   **Logging:** Enable M365 Audit Logs (Sign-in, Mailbox Access, Mailbox Change) and Migration Tool logs. Logs must be forwarded to the Acquiring Bank's SIEM/Compliance repo immediately.
    *   **Sign-off:** A "Migration Manifest" containing user IDs, hash values, timestamp validation results, and administrative signatures will be generated and signed by both the Acquiring Bank and the Community Bank IT leads.

### **3. Phased Migration Plan**

#### **Phase 1: Discovery, Security, & Prep (Days 1–5)**
*   **Security Isolation:** Since Exchange 2016 is unsupported, isolate the Exchange server in a restricted VLAN to prevent lateral movement or ransomware while migration tools access it.
*   **Inventory & Retention Mapping:**
    *   Export all mailbox metadata, retention policies, and quota sizes.
    *   Map Exchange retention policies to M365 retention policies to ensure content survival.
    *   Identify "Hot" mailboxes vs. "Archive" mailboxes.
*   **Tooling Validation:** Validate M365 tenant structure, DNS MX records, and client configurations (Outlook/OST/Autodiscover). Ensure Autodiscover resolution points to the Acquiring Bank's M365 environment.

#### **Phase 2: Staging & Validation (Days 6–10)**
*   **Pilot Group:** Select 10 mailboxes representing different sizes and configurations.
*   **Test Migration:** Run migration to a sandbox M365 tenant.
*   **Timestamp Verification:** Verify original delivery timestamps are preserved. If drift occurs, adjust migration parameters.
*   **Chain of Custody Run:** Test log capture and hash generation.

#### **Phase 3: Incremental Migration (Days 11–24)**
*   *Approach:* **Batch-by-Batch Migration without Cutover.**
*   *Rationale:* 340 mailboxes across two time zones with no after-hours window requires a "Set-and-Forget" approach. We move the data but keep the source mailbox active until the final switch.
*   *Execution Strategy:*
    *   **Wave 1 (Zone A):** Migrate Mailboxes 1–170 to M365. Leave Exchange mailbox active. Update M365 mailbox attributes.
    *   **Wave 2 (Zone B):** Migrate Mailboxes 171–340 to M365. Leave Exchange mailbox active.
    *   *Continuous Sync:* Run MMT "Delta Sync" every 4 hours during business hours to capture new items. *Note: Delta sync preserves timestamps for new items.*
    *   *Result:* M365 contains a complete, timestamped replica of all mail. Exchange remains the receiver. No user disruption.

#### **Phase 4: Zero-Downtime Cutover (Day 30)**
*   *Timing:* Scheduled during a low-traffic window (e.g., 10:00 AM - 10:15 AM), but acceptable in either zone due to instantaneous nature.
*   *Sequence:*
    1.  **Final Delta Sync:** Run final sync to minimize drift.
    2.  **Client Update:** Push Autodiscover updates or GPO updates to all branch clients to point to M365.
    3.  **DNS MX Switch:** Update MX records to point exclusively to M365. *Critical: Ensure TTL is low (<1 hour) to minimize stale routing.*
    4.  **Exchange Decommission:** Disable Exchange mailbox receive queues.
    5.  **Validation:** Verify new mail arrives in M365 with correct timestamps. Verify clients can access history.
    6.  **Chain of Custody Finalization:** Sign off on migration manifest. Archive logs.
*   *Rollback Trigger:* If validation fails, MX is reverted to Exchange immediately. Clients are instructed to reconnect to Exchange.

#### **Phase 5: Decommission & Cleanup (Days 31–32)**
*   Remove Exchange 2016 server.
*   Archive Exchange backups (retained per legal hold).
*   Update documentation and access rights.

### **4. Rollback Plan**

**Trigger Conditions:**
*   Migration tool failure on a batch exceeding 5% of mailboxes.
*   Timestamp validation failure on pilot or full migration.
*   Data loss or corruption detected.
*   Security incident on Exchange 2016 before cutover.

**Rollback Procedures:**
1.  **Stop Migration:** Halt MMT and Delta Sync.
2.  **Assess State:**
    *   *If Wave 1 Failed:* M365 mailboxes may be partially populated. Delete failed M365 mailboxes. Restore Exchange state (already active).
    *   *If Wave 2 Failed:* Delete failed M365 mailboxes. Wave 1 remains intact. Decide: Pause migration or Abort? If Abort, revert Wave 1.
3.  **Revert Wave 1 (Complex Rollback):**
    *   Since data moved to M365 cannot be instantly moved back without risk, and Exchange 2016 is unsupported:
    *   *Option A (Preferred):* Restore Exchange 2016 from the **Pre-Migration Backup** taken on Day 5. This reverts the source of truth to Exchange. *Note: This requires a restoration window and temporary data loss for items created after the backup, though unlikely during the isolated migration phase.*
    *   *Option B:* If M365 data is pristine, perform a "Reverse Migration" using M365 tools to restore data to Exchange. *High Risk:* Restoring to unsupported server is risky.
4.  **Restore Clients:** Ensure DNS MX and Clients point back to Exchange 2016.
5.  **Root Cause Analysis:** Investigate failure. Fix. Re-evaluate plan.

# 1 Executive Summary  

* **Goal** – Migrate 340 mailboxes from an unsupported Exchange 2016 farm into the acquiring bank’s Microsoft 365 tenant while **preserving all content, metadata (including original delivery timestamps), and maintaining a documented chain of custody**.  
* **Constraints** –  
  * **Operational** – No mailbox downtime during any branch’s 9 AM‑5 PM business window in either of the two time‑zones.  
  * **Regulatory** – Full retention of content and metadata; audit‑ready chain of custody.  
  * **Timeline** – The core‑banking conversion cuts over in 45 days; **email migration must not run in that same week**.  

**High‑level solution** – A **zero‑downtime, batch‑by‑batch migration** driven by a third‑party tool (e.g., BitTitan MigrationWiz or Quest On-Premises Migration Suite) that can:

* Connect directly to Exchange 2016 over IMAP/Exchange Web Services (EWS).  
* Preserve original timestamps, delivery headers, and all message metadata.  
* Provide per‑mailbox audit logs and signed migration receipts for chain‑of‑custody.  

The migration is staged in three 60‑day phases (Planning, Pilot, Production) with a rollback strategy that relies on a full on‑prem backup of each mailbox. The migration schedule is *branch‑specific* – each branch’s mailbox batch runs during its local after‑hours, ensuring no overlap with any branch’s business hours.

# Microsoft 365 Migration Plan  
**Project:** Migration of 340 mailboxes from an on‑premises Exchange Server 2016 (EOL) to the acquiring bank’s Microsoft 365 tenant  
**Stakeholders:** IT Integration Lead (Acquirer), Compliance Officer (Regulatory), Branch Operations Manager (Two time‑zones), Core‑Banking Workstream Lead, External Migration Vendor (if used)  

---

## 1. Executive Summary  

| Goal | Deliverable |
|------|-------------|
| **Regulatory** | Every message – content **and** metadata (original Received‑date, Message‑ID, folder hierarchy) must survive migration unchanged and be auditable. |
| **Operational** | No mailbox downtime for any branch during **9 am‑5 pm** local business hours. Migration must happen within normal working windows (or a “quiet‑hour” that does **not** fall outside 9‑5 for any site). |
| **Timeline** | Migration must be **completed before** the week the core‑banking system cut‑over occurs (day 45 ± 3). No migration activity may be scheduled **during** that week. |
| **Risk** | If a batch fails, the source mailbox must remain fully functional, and the rollback must be documented for chain‑of‑custody. |

Because Exchange 2016 is already out of Microsoft support, we will **avoid a classic “cut‑over” migration** that shuts down the on‑prem server. Instead we will implement a **Hybrid‑Staged migration** with *incremental sync* and *final “cut‑over” per batch* while keeping the source mailbox online until the batch is verified.  

---

## 2. High‑Level Migration Strategy  

| Phase | Description | Key Technologies | Why it meets constraints |
|-------|-------------|------------------|--------------------------|
| **0 – Environment Prep** | Build a **Hybrid Exchange** trust, Azure AD Connect sync, and mail‑flow connectors. | Exchange Hybrid Configuration Wizard (HCW), Azure AD Connect, DNS (MX, Autodiscover) | Provides seamless coexistence; source mailboxes stay online. |
| **1 – Pilot (5 % of mailboxes)** | Move a single low‑risk branch (≈ 15 mailboxes) through the full flow. | New‑MoveRequest (MRS), Staged Migration Batch, ‑SuspendWhenReadyToComplete | Validates metadata preservation, chain‑of‑custody logging, and performance. |
| **2 – Bulk Staged Migration** | Move **10‑15 mailboxes per branch per day** (≈ 2 % of total) in overlapping “quiet‑hour” windows that still fall within 9‑5 for every site. | Staged Migration Batches, ‑TargetDeliveryDomain, ‑RemoteHostName, ‑AutoCompleteAfterSync, ‑SuspendWhenReadyToComplete | Keeps mailbox access live; each batch is small enough to stay under bandwidth caps and to be rolled back quickly. |
| **3 – Final Cut‑over & Decommission** | After the last successful batch, switch mail flow permanently to Microsoft 365, remove Hybrid connectors, decommission Exchange 2016. | Set‑Default‑Routing‑Connector, Remove‑Hybrid‑Configuration, Archive old server logs | Completes migration **before** the core‑banking week and provides a clean hand‑off. |

**Why not a classic “Cut‑over” migration?**  
*Cut‑over* requires the source server to be taken offline for the entire tenant – impossible with 9‑5 availability and regulatory audit needs. A *Hybrid‑Staged* approach lets us **preserve original timestamps** (the MRS copies the message “as‑is”), provides **per‑batch rollback**, and satisfies the “no‑downtime” rule.

### Phase 2 – Bulk Staged Migration (Days 21‑44)

#### 2.1 Batch Design  

| Parameter | Value |
|-----------|-------|
| **Batch Size** | 10‑15 mailboxes per branch per day (≈ 30 MB – 150 MB per mailbox, average 70 MB → ~ 1 GB/day per branch) |
| **Time‑zone alignment** | Each branch runs its batch **starting at 9 am local time**. The migration engine works in the background; users continue to read/write. |
| **Batch window** | 9 am‑12 pm local (first pass). **Delta sync** runs automatically until 4 pm. |
| **SuspendWhenReadyToComplete** | **Enabled** for every batch. The batch is **not** completed until the PM signs off after validation. |
| **Validation checklist per batch** | 1) Message‑Trace shows original Received‑date unchanged (sample 5 % of messages). 2) Folder hierarchy matches source (export‑import via `Export-Mailbox`). 3) Audit log entries captured. 4) End‑user confirms mailbox accessible. |
| **Rollback window** | If any validation step fails, the batch is **suspended** and rolled back within the same day (no impact on other branches). |

#### 2.2 Daily Execution Flow (example for a single branch)

1. **08:45** – Ops confirms branch is open, network capacity OK.  
2. **09:00** – Run `New-MigrationBatch` for that branch’s CSV list (10‑15 users).  
3. **09:05‑11:30** – Initial sync copies all items (MRS runs in parallel).  
4. **11:30‑12:00** – Pause batch (`Suspend-MigrationBatch`) – this forces MRS to finish any in‑flight items and lock the source mailbox for delta capture.  
5. **12:00‑13:00** – **Business lunch** – no user impact; delta sync runs automatically.  
6. **13:00‑14:30** – Ops performs **validation script** (PowerShell + Graph API) and records results in the audit SharePoint list.  
7. **14:30‑15:00** – If validation **PASS**, PM issues `Set-MigrationBatch -Complete`. If **FAIL**, run `Stop-MigrationBatch -Cancel` → rollback.  
8. **15:00‑16:30** – End‑user acceptance testing (send/receive test mail).  
9. **16:30‑17:00** – Update migration dashboard, log timestamps, sign‑off.

#### 2.3 Parallelism & Bandwidth  

* Use **Microsoft’s “Network throttling”** (`Set-MigrationEndpoint -MaxConcurrentMigrations 5`) to keep total outbound traffic < 2 Gbps per data‑center (well within the bank’s WAN contracts).  
* Enable **Compression** (`-UseCompression $true`) on the Migration Endpoint.

# Microsoft 365 Migration Plan: Community Bank Acquisition

## 1. Executive Summary
This plan addresses the migration of 340 mailboxes from an unsupported, on-premises Exchange Server 2016 environment into the acquiring bank's Microsoft 365 tenant. It is designed to satisfy strict regulatory retention requirements, maintain zero user interruption across two time zones during branch business hours, and coordinate safely around the 45-day core-banking system cutover.

The technical approach is a **Hybrid Exchange Pull Migration** using the Microsoft 365 Exchange Online Migration Tool (EOMT). Because the source is unsupported, the on-premises server is treated as a legacy connector and remains fully functional until the final decommissioning step.

---

## 2. Technical Architecture & Cutover Approach

### Why Pull Migration?
*   **Zero Downtime:** A "Push" or Cutover migration requires mailbox disconnection. A Pull migration copies data while the user remains connected to their existing Outlook profile on the on-premises server.
*   **Metadata Integrity:** EOMT preserves original message headers, delivery timestamps, and sender information natively, satisfying the regulatory constraint.
*   **EOL Workaround:** Since Exchange 2016 is EOL, we cannot apply patches or upgrade roles. However, it remains capable of acting as an SMTP relay to Exchange Online. We will maintain the hybrid connectivity configuration to allow the migration tool to pull mailboxes without the server going offline.

### The Cutover Sequence
The "Cutover" in this context is not a single event but a final disconnection phase.
1.  **Migration Phase:** All 340 mailboxes are pulled to Exchange Online in batches.
2.  **Validation Phase:** Content and metadata are verified.
3.  **Decommission Phase:** Once validation is signed off, the on-premises Exchange 2016 server is disconnected from the DNS and removed. **This is the only step that interrupts service.** It will be scheduled during the 18-branch overnight window (9 AM - 5 PM constraint applies to *migration*, not necessarily the server shutdown, but we will attempt to do it during the natural overlap gap between time zones if possible).

---

## 3. Phased Migration Plan

### Phase 1: Preparation (Days 1–14)
*   **Tenant Readiness:** Confirm the acquiring bank's M365 tenant has sufficient licenses and mail flow rules configured.
*   **Connectivity Check:** Verify TLS 1.2 compatibility between the EOL Exchange 2016 server and the acquiring bank's Exchange Online endpoint. Apply emergency security patches to the 2016 server if possible, or isolate it via a DMZ network segment to prevent external exploitation while EOL.
*   **Discovery & Audit:** Export a full list of 340 mailboxes, including user roles, shared folders, and calendar permissions.
*   **Compliance Mapping:** Define the "Chain of Custody" document. This will include migration logs, timestamp records, and a sign-off sheet for each batch.

### Phase 2: Pilot Migration (Days 15–21)
*   **Select Pilot Group:** Move 5 mailboxes (1 per branch) representing the two time zones.
*   **Validation:** Verify that delivery timestamps, headers, and shared calendar data are intact in the M365 environment.
*   **User Acceptance:** Have pilot users test sending/receiving to confirm Outlook sync is seamless.
*   **Regulatory Sign-off:** Pilot users and the compliance officer sign off on the "Chain of Custody" template.

### Phase 3: Full Migration (Days 22–34)
*   **Batching Strategy:** Divide the remaining 335 mailboxes into batches of 50. Use parallel batch processing in EOMT to move 2 batches per day.
*   **Time Zone Staggering:**
    *   **Time Zone A (e.g., Eastern):** Migrate Branch A, B, C mailboxes during their 12 PM - 2 PM window (low activity).
    *   **Time Zone B (e.g., Pacific):** Migrate Branch D, E, F mailboxes during their 12 PM - 2 PM window.
    *   This ensures no single branch is in a migration state during their 9 AM - 5 PM peak hours.
*   **Source Server Status:** Keep the Exchange 2016 server running and reachable. Users who prefer on-prem Outlook will continue to function.
*   **User Notification:** Send a brief email 24 hours before each batch move explaining a brief Outlook sync refresh may occur.

### Phase 4: Validation & Decommission (Days 35–38)
*   **Spot Checks:** Randomly sample 10% of migrated mailboxes for timestamp integrity.
*   **Final Cutover:** Once 100% migration is verified, schedule the final disconnection of the on-premises Exchange 2016 server.
*   **Decommission:** Remove the server from the network, back up critical data, and document the retirement.

## 4. Rollback Plan: Batch Failure

### Scenario: A Batch of 50 Mailboxes Fails Midway
*   **Cause:** Network connectivity loss, EOL server instability, or Exchange Online quota issues.
*   **State of Data:** Because Pull Migration preserves the source mailbox on-premises until the move is complete, the mailboxes that *failed* remain fully intact on the Exchange 2016 server. No data is lost.

### Rollback Steps
1.  **Stop Migration:** Halt the EOMT job immediately to prevent further partial state corruption.
2.  **Assess Damage:** Identify which mailboxes are in a "Pending" state (partially in Online, partially on-prem).
3.  **Isolate:** Do not attempt to move the failed mailboxes again until the root cause is resolved.
4.  **Retry:** Resume the batch once the network or server issue is fixed. EOMT supports "Retry" for individual failed mailboxes.
5.  **Compliance Logging:** Document the failure, the root cause, the resolution, and the retry date in the Chain of Custody log.

### Worst Case: Full Migration Failure
If the migration tool itself fails due to the EOL server's instability:
*   **Action:** Keep the Exchange 2016 server online. Do not attempt to migrate.
*   **Impact:** Email service continues via on-premises Exchange.
*   **Regulatory Mitigation:** The bank retains a documented "Hold" status. The compliance officer can issue a temporary variance while the migration is re-attempted.

This plan outlines the migration of 340 on-premises Exchange 2016 mailboxes to the acquiring bank’s Microsoft 365 (M365) tenant. Due to the End-of-Life (EOL) status of Exchange 2016 and strict regulatory requirements, a **Staged Cutover** approach is utilized. This plan prioritizes data integrity, chain of custody, and operational continuity across two time zones while ensuring email migration is completed prior to the critical 45-day core-banking system cutover.

---

## 1. Migration Architecture & Constraints

### 1.1 Cutover Approach (Exchange 2016 EOL)
Since Exchange 2016 is no longer supported by Microsoft, a Hybrid Migration topology is not recommended due to security risks and lack of patching. We will utilize a **Staged Cutover Migration** via the Exchange Online Migration Service.
*   **Mechanism:** Mailboxes are moved from the on-prem 2016 environment to M365 in batches. The on-prem source remains active during the move.
*   **EOL Mitigation:** The on-prem Exchange server will be placed in a **Network Isolated VLAN** accessible only by the migration service. No internet exposure is permitted.

### 1.2 Regulatory Compliance (Retention & Chain of Custody)
*   **Retention:** All M365 mailboxes will be immediately assigned **Retention Policies** matching the on-prem legal hold requirements. **In-Place eDiscovery** and **In-Place Hold** will be active on all mailboxes prior to cutover to ensure content immutability.
*   **Metadata Integrity:** Exchange Online Migration Service preserves message properties (including original `ReceivedTime`, `SentTime`, and `DeliveryTimestamp`) natively.
*   **Chain of Custody:**
    1.  **Pre-Migration:** All 340 mailboxes are identified in a Migration Inventory (Source ID, User, Department).
    2.  **During Migration:** Every batch job is logged via **Unified Audit Logs** in M365.
    3.  **Post-Migration:** An immutable CSV report of the Migration Job ID, Source Mailbox, Target Mailbox, and Completion Timestamp is generated for legal audit.

### 1.3 Operational Constraints (Time Zones & No Interruption)
*   **Constraint:** Branches operate 9 AM–5 PM in EST and CST. There is no company-wide after-hours window. Mailbox access cannot be interrupted during *any* branch’s business hours.
*   **Solution:** **Outlook Cached Exchange Mode**. By default, M365 Outlook clients use Cached Mode.
    *   Users retain a local OST file containing all data.
    *   The "Cutover" is a background server-side switch.
    *   Clients will reconnect to the new tenant (M365) in the background.
    *   **Impact:** A brief "Updating Status" notification (approx. 10–30 seconds) per user. This is not data interruption, satisfying the operational constraint.

## 2. Phased Migration Timeline (45-Day Window)

The 45-day timeline is divided into Migration, Banking Cutover, and Decommission phases. **Email Migration must be fully stabilized before the Core-Banking Cutover Week.**

### Phase 1: Preparation & Compliance (Days 1–10)
*   **Day 1-3:** **Security Hardening.** Isolate the Exchange 2016 server. Validate network connectivity to M365 via Private Express Transit (if available) or secure tunnel.
*   **Day 4-7:** **Regulatory Configuration.** Apply **Retention Policies** and **In-Place Holds** to the M365 tenant *before* any mailboxes are created.
*   **Day 8-10:** **Directory Sync.** Deploy/Verify Azure AD Connect. Ensure all 340 users are synced to M365 with correct attributes.
*   **Deliverable:** Audit-ready list of pre-provisioned users with retention policies applied.

### Phase 2: Pilot & Validation (Days 11–15)
*   **Day 11-13:** **Pilot Batch (10 Mailboxes).** Select 10 critical users (including Compliance/HR).
*   **Day 14:** **Metadata Validation.** Verify `ReceivedTime` and delivery timestamps match on-prem vs. M365.
*   **Day 15:** **Chain of Custody Sign-off.** Confirm audit logs capture the pilot migration.
*   **Decision Point:** If Pilot fails, roll back to Day 1. If passed, proceed to full batch.

### Phase 3: Staged Cutover (Days 16–35)
*   **Batch Size:** 6 Batches of 55–60 mailboxes each.
*   **Scheduling (Time Zone Strategy):**
    *   **Batch 1-3 (EST Branches):** Final Sync performed at **4:00 PM EST** (End of Day for EST). This minimizes the window of potential conflict during active work hours.
    *   **Batch 4-6 (CST Branches):** Final Sync performed at **4:00 PM CST** (End of Day for CST).
    *   **Rationale:** Performing the final sync at the end of the workday ensures that if any client reconnection is visible, it occurs as users are concluding their day, mitigating the risk of interrupting critical transactional activity.
*   **Validation:** Each batch is validated for 24 hours before the next begins.

### Phase 4: Stabilization & Banking Cutover Buffer (Days 36–43)
*   **Day 36-39:** **Final Validation.** Confirm all 340 mailboxes are active in M365.
*   **Day 40-43: CORE-BANKING CUT-OVER WEEK (NO MIGRATION).**
    *   **Status:** Email infrastructure is **frozen and stable**.
    *   **Purpose:** Branch staff require working email to field customer questions regarding the core-banking conversion.
    *   **Constraint Compliance:** Email migration is **NOT** scheduled during this week to ensure zero operational conflict.

### Phase 5: Decommissioning (Days 44–45)
*   **Day 44:** Decommission On-Prem Exchange 2016.
*   **Day 45:** Final Regulatory Audit & Project Closure.

## 3. Rollback Plan (Batch Failure)

If a specific batch migration fails partway (e.g., due to corruption or connectivity):

1.  **Immediate Cancellation:** Pause the Migration Batch in the Exchange Admin Center.
2.  **Preserve Source:** The on-premises mailbox remains **active and untouched**. Users continue using Exchange 2016.
3.  **Investigation:** Review **Unified Audit Logs** and **Exchange Event Viewer** for the specific error.
4.  **Retry Strategy:**
    *   Split the failed batch into two smaller batches (e.g., 30 mailboxes each).
    *   Re-run migration.
    *   Do not proceed to the next batch until this batch is 100% verified.
5.  **Data Integrity Check:** If metadata is found to be corrupted, the batch is rejected, and the data is preserved on-prem until a fix is found.
6.  **Documentation:** The failure and resolution are logged in the Chain of Custody report.

## 4. Sequencing & Blast Radius Analysis

### Correct Sequencing (Recommended)
*   **Order:** Email Migration (Days 1–35) → Core-Banking Cutover (Days 40–43) → Decommission (Days 44–45).
*   **Rationale:** Email is stabilized *before* the high-risk banking cutover. Staff have working email to support the banking transition.

### Blast Radius of Wrong Sequencing
If Email Migration is scheduled **during** the Core-Banking Cutover Week (Days 40–43):
1.  **Operational Failure:** Branch staff cannot send/receive email during their most critical week.
2.  **Customer Impact:** Customers with banking cutover questions cannot be contacted via email.
3.  **Regulatory Breach:** The migration process requires heavy logging and monitoring, which conflicts with the banking cutover change freeze.
4.  **Blast Radius:** **Total.** The entire branch network is impacted, potentially delaying the banking cutover by weeks and causing reputational damage.

### Risk Mitigation
*   **Hard Stop:** A "Migration Freeze" is enforced starting Day 36. No migration activities are permitted in the M365 tenant until after Day 43.
*   **Communication:** Branch staff are informed that email is stable during the banking cutover week to ensure confidence.

This migration plan is designed to balance the technical limitations of an end-of-life (EoL) Exchange environment with the high-stakes regulatory and operational requirements of a banking environment.

### 1. Technical Approach: Hybrid Migration
Because the source is Exchange 2016 and the requirement is to preserve **all metadata and original delivery timestamps**, a **Microsoft Exchange Hybrid Deployment** is the only viable approach.

*   **Why Hybrid?** Unlike a Cutover migration (which is a "big bang" and often loses complex metadata) or an IMAP migration (which loses folders and non-mail items), Hybrid allows for a "Remote Move" migration. This keeps the Outlook profile intact, moves mailbox items in the background while users are working, and uses the Exchange Mailbox Replication service (MRS) to ensure metadata (like `OriginalDeliveryTime`) remains intact.
*   **Addressing the EoL Status:** Since Exchange 2016 is past extended support, the primary risk is security vulnerabilities during the setup of the Hybrid Configuration Wizard (HCW). We will mitigate this by hardening the on-prem server (isolating it from the public internet, limiting management access) and performing the HCW in a controlled, temporary window.

---

### 2. Phased Migration Plan (45-Day Timeline)

To satisfy the constraint of avoiding the core-banking cutover week, we will adopt a **"Front-Loaded Migration"** strategy. We will complete the bulk of the migration *before* the core-banking system cutover to ensure a "stable state" for email before the high-risk core change.

#### **Phase 1: Discovery & Remediation (Days 1–10)**
*   **Audit:** Run PowerShell scripts on Exchange 2016 to identify all mailbox sizes, public folders, and shared mailboxes.
*   **Cleanup:** Address any existing corrupted items or oversized mailboxes that might fail the MRS move.
*   **Compliance Readiness:** Enable "Audit Logging" on the local Exchange server to create the initial "Chain of Custody" record.

#### **Phase 2: Infrastructure & Pilot (Days 11–18)**
*   **Hybrid Setup:** Install the latest available Cumulative Update (CU) for Exchange 2016 to ensure HCW compatibility, then run the Hybrid Configuration Wizard.
*   **Pilot (Batch 0):** Migrate 10 "power users" from both time zones. This validates the metadata preservation and ensures the hybrid connectivity (MRS proxy) is stable.

#### **Phase 3: The "Rolling Wave" Bulk Migration (Days 19–38)**
To respect the "No 9-5 interruption" and "Two time zone" constraints, we will use a **Background Sync + Micro-Cutover** method:
1.  **Background Sync:** We initiate the migration of a batch (e.g., 30 mailboxes) 48 hours before the scheduled switch. The data syncs in the background while staff work.
2.  **The "Micro-Cutover":** The actual "switch" (where the mailbox becomes active in M365) takes seconds. Because the data is already synced, the only downtime is the moment the user re-authenticates.
3.  **Scheduling:** 
    *   **Timezone A (Early):** Migration window at 8:00 AM – 8:30 AM.
    *   **Timezone B (Late):** Migration window at 8:00 AM – 8:30 AM (Local Time).
    *   *Note: This ensures we are not interrupting business hours (9-5) and avoids a "single company-wide window."*

#### **Phase 4: Blackout Period (Days 39–45) — CORE BANKING CUTOVER**
*   **Freeze:** No email migration activities.
*   **Support Readiness:** Email is fully operational in M365 for all migrated users. IT staff are focused entirely on the core-banking system.

---

### 3. Rollback Plan (Batch-Level Failure)
If a mailbox batch fails during the "Micro-Cutover" (e.g., sync error or profile corruption):

1.  **Immediate Reversion:** The migration task is aborted. Since we are in a Hybrid state, the on-premises mailbox remains the "Source of Truth" until the final successful sync.
2.  **DNS/Autodiscover Check:** We verify that Autodiscover is correctly pointing back to the on-prem Exchange server for those specific users.
3.  **Post-Mortem:** The failed batch is analyzed (typically for large attachments or corrupted items) and excluded from the next scheduled wave.
4.  **Integrity Verification:** A checksum/item count report is run on both the on-prem and M365 mailboxes to ensure the "Chain of Custody" and metadata integrity were not compromised by the failed attempt.

---

### 4. Sequencing Risk & Blast Radius Analysis

The most critical decision is whether to migrate **before** or **after** the core-banking cutover.

| Approach | Strategy | Blast Radius / Risk |
| :--- | :--- | :--- |
| **Post-Core (Migrate after)** | Wait for core-banking to stabilize, then migrate email. | **HIGH RISK:** Core-banking cutovers are notoriously unstable. If the core cutover causes network latency, DNS issues, or IP re-addressing, the email migration will fail. Furthermore, if the core cutover causes "Day 1" chaos, the IT team will be too overwhelmed to troubleshoot email issues. |
| **Pre-Core (Migrate before)** | **(Recommended)** Complete email migration before the core cutover. | **LOW RISK:** By completing the email migration in the first 38 days, you ensure that when the core-banking system goes live, the email environment is **already stable and "settled."** Staff will have a reliable communication channel to report core-banking issues. |

**The Blast Radius of getting the sequencing wrong:**
If you attempt to migrate email *during* the core-banking cutover week, you create a **"Double-Fault" scenario.** A network hiccup caused by the core-banking migration could corrupt the email migration process, leading to data loss (violating regulatory requirements) or a total communication blackout at the exact moment the bank needs to communicate critical core-banking changes to customers.
