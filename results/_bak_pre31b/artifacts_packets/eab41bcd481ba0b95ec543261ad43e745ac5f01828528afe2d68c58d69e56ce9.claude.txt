## Task

The task given to every model in this cohort:

A contract research organization's remote clinical research associates (CRAs) upload case
report form data to a sponsor's clinical-trial portal over the company VPN. Over the last 6
weeks, 11 separate tickets from 7 different CRAs all report the same thing: "VPN disconnects
mid-upload, I have to restart the upload." Past fixes, one per ticket, each treated as
unrelated: told a user to reconnect and retry (worked temporarily, every time); once
increased the VPN client's idle-timeout setting for one specific user; once told a different
user to switch from WiFi to a wired connection at home, which seemed to help that one user.
No common cause was ever identified across the 11 tickets. Here is the pattern nobody had
connected yet: in all 11 cases the disconnect happened between 35 and 50 minutes into the VPN
session -- never earlier, never much later. The affected CRAs are on different ISPs,
different home networks, and different laptop hardware. The VPN concentrator's own connection
logs show these sessions ending with a code unrelated to idle-timeout, and the timing lines up
closely with one fact from the concentrator's configuration: its max-session /
re-authentication interval is set to 45 minutes. State the actual root cause (not the
per-ticket fixes already tried), explain why the idle-timeout change and the wired-connection
suggestion each appeared to help their one user even though neither addressed the real cause,
give the actual fix, and say how this should have been caught after the 2nd or 3rd similar
ticket instead of the 11th.

### Root Cause

The root cause is that the **VPN concentrator is configured with a maximum session lifetime / re-authentication interval of 45 minutes.**

When a VPN session reaches this timer, the concentrator terminates the tunnel or requires the client to complete a re-authentication handshake. The CRF upload process (which involves large data transfers and background network traffic) prevents the client from completing this re-authentication handshake reliably within the 45-minute window. Because the affected CRAs are on different ISPs and networks, the failure is consistent with a server-side timer rather than a client-side issue. The "disconnect" is the concentrator enforcing the 45-minute re-auth deadline.

### Why the Two False Fixes "Worked"

Both fixes appeared to resolve the issue for their specific users because they addressed symptoms of the handshake failure, not the server-side timer itself:

1.  **Increasing the VPN Client's Idle-Timeout:** If the client's local idle-timeout (e.g., a Windows VPN setting) was set to a value lower than 45 minutes (e.g., 30 minutes), the client would disconnect the VPN adapter locally due to inactivity (since uploading CRF data does not generate user input/keyboard events). By increasing the idle-timeout, the client remained connected long enough to survive until the concentrator's 45-minute re-auth deadline arrived, giving the user enough time to restart the upload and complete it within the window. It didn't fix the server timer; it just prevented the client from killing the connection prematurely.
2.  **Switching to a Wired Connection:** WiFi connections are susceptible to packet loss, jitter, and latency spikes. If the concentrator sends a re-authentication challenge at the 45-minute mark, a flaky WiFi link might drop the re-auth response packet, causing the handshake to fail and the server to drop the session. A wired connection provided the stable, low-latency network path necessary for the re-authentication handshake to succeed within the 45-minute window.

### The Actual Fix

**Increase the VPN concentrator's re-authentication interval (or max-session lifetime) to a value that accommodates the full expected duration of a CRF upload session** (e.g., 60 to 120 minutes). Alternatively, configure the VPN client to perform transparent re-authentication without dropping the active data session, ensuring that uploads are not interrupted by the re-authentication timer.

1.  **Siloed Ticket Resolution:** Each ticket was treated as an independent, unrelated incident. There was no process for support staff to cross-reference tickets by **timing**, **symptom**, or **session behavior**.

3.  **Missing Infrastructure Monitoring:** If the VPN concentrator logs were monitored via a dashboard or alerting system, a spike in session terminations specifically at the 45-minute mark would have triggered an automated alert, bypassing the need for individual user reports entirely.
4.  **No Root Cause Analysis (RCA) Protocol:** A standard operating procedure should require a quick triage review (e.g., "Are we seeing more than 3 similar tickets in a week?") to trigger a unified investigation rather than creating a separate workaround for every ticket.
