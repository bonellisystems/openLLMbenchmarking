## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this

# Operations -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The process redesign is tied concretely to the specific bottleneck and constraint stated in the prompt, with measurable KPIs that include a baseline and target, not just a goal restated as a metric. Implementation steps are sequenced with a clear first action, change-management or rollout risk is addressed, and resourcing constraints given in the prompt are respected rather than assumed away.
Example character: a redesign that names the actual bottleneck, gives a baseline-to-target KPI, and sequences the first three implementation steps.

## 7 -- Strong
The process improvement is sound and directly usable, correctly targeting the stated bottleneck. The KPI baseline or rollout sequencing is thinner than ideal, but the core recommendation would work as described.
Example character: a correct fix for the stated bottleneck with a named metric but no baseline value given.

## 5 -- Adequate
The advice is generic process-improvement guidance ("streamline the workflow," "reduce handoffs") that is directionally correct but not tied to the specific constraint described in the prompt.
Example character: general efficiency advice that would apply to almost any operational bottleneck.

## 3 -- Weak
The answer misidentifies the bottleneck, or proposes a process that ignores a stated hard constraint (headcount, budget, system limitation), with no measurable KPI anywhere in the response.
Example character: a redesign that requires more staff despite the prompt stating headcount is fixed.

## 0 -- Unusable
Cites fabricated industry-benchmark figures as if real, or recommends a change that outright violates a stated hard constraint with no acknowledgment. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Fabricated industry-benchmark numbers presented as real data.
- Ignoring an explicitly stated resource or system constraint.
- No measurable KPI or success criterion anywhere in the response.
- Steps that restate goals rather than being actually sequenced and actionable.

## Unit-specific excellence markers
- Root cause or bottleneck correctly identified from the details given.
- Measurable KPI with a stated baseline and target.
- Rollout sequenced with a clear, concrete first step.
- Resourcing constraints from the prompt respected in the design.

## 2.  Redesign – “Zero‑Re‑Key, Zone‑Batch, Scan‑Confirm” SOP  

### 2.1  High‑Level Flow (paper‑free as much as possible)

1. **Order Capture** – Orders enter the OMS as usual.  
2. **Auto‑Generate Pick Sheet** – At the end of each hour, the OMS runs a **Pick‑List Report** (built‑in export to CSV/Excel) that groups orders **by warehouse zone** (e.g., Men‑Top, Women‑Bottom, Accessories).  
3. **Print Zone‑Specific Pick Sheets** – Using the existing office printer(s), print **one sheet per zone** that lists **all SKUs** to pick for that zone, *grouped by order* and *ordered by aisle*.  
4. **Zone‑Batch Picking** – Picker(s) assigned to a zone pull the entire sheet, scan each SKU **once** with the handheld scanner, and **physically place the item in a “order‑bin”** that is pre‑labeled with the order number (barcode label printed from the OMS).  
5. **Scan‑Confirm at Pick** – The scanner records **SKU + Order‑Bin barcode**; any mismatch triggers an immediate audible alarm and forces the picker to correct the error before moving on.  
6. **Pack & Verify** – At the packing station, the packer scans the **order‑bin barcode** and then each **SKU barcode** again (second scan). The system confirms that the set of scanned SKUs matches the order’s line‑items.  
7. **Ship** – After successful verification, the order is sealed, labeled, and moved to the shipping dock.  

### 2.2  Key Process Controls (no new software)

| Control | How it works with existing tools | What it eliminates |
|---------|----------------------------------|--------------------|
| **Auto‑Generated, Zone‑Grouped Pick Sheet** | Use the OMS “Export to CSV” + simple Excel macro (already in the office) → print. | Manual re‑keying of each order. |
| **Pre‑Printed Order‑Bin Barcodes** | Use the label printer already used for shipping labels. Print a 2‑inch barcode per order before the shift starts. | Guess‑work when placing items in bins; reduces “which order does this bin belong to?”. |
| **Hand‑Held Scanners (existing)** | Scanners already used for receiving can be repurposed for pick‑confirm and pack‑confirm. | Human visual verification only – prone to transposition. |
| **Zone‑Batch Assignment** | Simple “zone roster” posted on the wall (paper) or a shared spreadsheet. | Random queue where pickers walk the whole warehouse for each order. |
| **Visual “Pick‑Sheet Takedown” Checklist** | At the end of each shift, the picker signs off on a paper checklist that the sheet was fully processed. | Lost or partially‑processed pick sheets. |

### 2. Redesigned SOP: "Direct-Print Zone Picking"

**Phase 1: Order Processing & Batching (Admin/Office)**
1.  **Stop Re-Keying:** Instead of manually typing orders into a document, the admin will use the "Print Pick List" function directly from the existing order management system.
2.  **Digital Sorting:** Before printing, the admin will use the existing system’s "Filter" or "Export to Excel" function to group orders by **Warehouse Zone** (e.g., Aisle A, Aisle B) or **SKU Category**. 
3.  **Batch Printing:** Print one consolidated "Zone Pick Sheet" for each warehouse zone, containing multiple orders at once to minimize walking.

**Phase 2: Execution (Warehouse Floor)**
4.  **Zone-Based Picking:** Pickers are assigned to a specific zone. They move through their assigned zone once per batch, picking all items for all orders in that batch. This prevents "zigzagging" across the warehouse for a single order.
5.  **The "Two-Point Check":** 
    *   **Pick Check:** As the item is placed in the bin, the picker must visually match the SKU on the printed sheet to the physical SKU tag on the apparel.
    *   **Pack Check (The Gatekeeper):** Before sealing the box, the Packer compares the physical items against the *original printed pick sheet* (not a handwritten note) to ensure the quantities and SKUs match perfectly.

**Phase 3: Fulfillment (Packing)**
6.  **Final Audit:** Once the Packer confirms the match, the order is moved to the shipping station.

## 2. First Three Implementation Steps (Process‑Only Fix)

> **All steps use equipment already in the warehouse: barcode scanners, printers, the existing WMS/ERP, and the paper pick sheets that are currently printed. No new software or hardware budget is required.**

### Step 1 – Zone‑Based Order Batching & Pick‑List Generation  
**Goal:** Eliminate the “one unsorted queue” bottleneck; reduce travel time and the number of SKUs a picker must cross‑check per shift.

| Actions | Details |
|---------|---------|
| **Generate zone pick lists** | Use the current WMS/ERP to export orders grouped by the warehouse zone (Zone A, Zone B, …).  Each list is a separate CSV that is printed or displayed on a screen. |
| **Physical zone boards** | Place a large wall‑mounted board in each zone with a real‑time “current batch” column that lists the order IDs to be picked in that zone. |
| **Training** | 15‑min refresher for all pickers: “Pick only the orders listed on your zone board; no cross‑zone picking.”  Highlight that this reduces the number of SKU look‑ups per order. |
| **Measurement** | Track the average travel distance per order (via a simple spreadsheet) before and after implementation. |

> *Result:* Pickers spend 25–30 % less time walking between zones, directly cutting the average handling time.

### Step 2 – Replace Manual Re‑Key with Barcode Scanning at the Pick Station  
**Goal:** Remove the single manual transcription step that is the primary source of SKU transposition.

| Actions | Details |
|---------|---------|
| **Scanner setup** | Use the existing handheld barcode scanners that are already used for receiving.  Configure each scanner to “read the SKU barcode on the pallet/box” and immediately compare it to the next SKU listed on the zone’s pick list. |
| **Immediate feedback** | If a mismatch is detected, the scanner flashes red and a beep alerts the picker.  The picker must correct the item before continuing. |
| **Redundant print** | Keep the paper pick sheet as a backup, but the scanner will be the primary source of truth. |
| **Training** | 30‑min workshop: “Scan‑to‑Validate” protocol, including how to handle scanner glitches and how to pause picking when an error occurs. |
| **Measurement** | Log the number of scanner‑detected mismatches per shift.  This should drop from manual re‑key errors to near‑zero. |

> *Result:* The probability of a SKU transpose falls from ~1.2 % (est. from 4.5 % wrong‑item rate) to < 0.2 % per order.

### Step 3 – Add a “Scan‑to‑Pack” Double‑Check at the Packing Station  
**Goal:** Provide a final safety net that ensures the packed SKU matches the order, catching any slip‑through errors.

| Actions | Details |
|---------|---------|
| **Packing scanner** | At the packing station, the packer scans the same SKU barcode that was scanned at pick.  The scanner queries the order ID and verifies that the SKU is correct. |
| **Visual check** | The packer must also verify the SKU’s packaging label against the item’s visual appearance (color, size).  This is a simple “look‑and‑say” step that takes < 5 s. |
| **Two‑person confirmation** | The second person on the packing team (or a rotating “quality” checker) must scan the order ID and confirm that the scanned SKU and the order line match.  Any discrepancy triggers a stop‑scan protocol. |
| **Training** | 20‑min run‑through with mock orders.  Emphasize the stop‑scan protocol and the importance of not packing until the double‑check passes. |
| **Measurement** | Count “pack‑scan mismatches” and compare to the pre‑implementation baseline.  Track the time added per pack (expect 0.3–0.5 s per item). |

> *Result:* Even if a wrong SKU slips through the picker scanner (rare), it will be caught before shipment, lowering the wrong‑item rate to < 1.5 %.
