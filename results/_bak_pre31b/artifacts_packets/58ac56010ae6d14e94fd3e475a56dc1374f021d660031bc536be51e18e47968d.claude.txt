# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

### **1. Gap Analysis**

The current backup configuration presents an unacceptable level of risk to the firm’s operational continuity, legal compliance, and professional liability.

#### **A. Compliance Gaps (RPO/RTO)**
*   **RPO Gap (Recovery Point Objective):** The firm requires an RPO of **4 hours** (maximum allowable data loss). Your current nightly backup schedule results in an RPO of up to **24 hours**. In a failure scenario occurring at 11:00 PM, you would lose the entire day's case filings, billing entries, and client communications.
*   **RTO Gap (Recovery Time Objective):** The firm requires an RTO of **8 business hours**. Because no restoration testing has been performed in **18 months**, there is no empirical evidence that the firm can meet this window. Without testing, the "estimated" time to restore a SQL database from a NAS is a guess that likely fails to account for hardware failure, data corruption, or network congestion.

#### **B. Ransomware Resilience Gaps**
*   **Single Point of Failure (Co-location):** The backup NAS resides in the same server closet as the production host. A single localized event—fire, flood, theft, or a localized power surge—will destroy both the production data and the backups simultaneously.
*   **Single Point of Failure (Identity/Domain Integration):** The backup NAS is **domain-joined** and uses a **domain service account**. This is a critical vulnerability. If an attacker gains Domain Admin privileges, they inherit the rights to the backup NAS, allowing them to delete or encrypt backups as easily as the production server.
*   **Lateral Movement (Network Topology):** The NAS resides on the same network segment as the production VM. Once ransomware enters the network via a workstation, it can move laterally across the segment to the NAS without encountering any internal barriers.

---

### **2. Quantified Blast Radius**
**If a ransomware attack occurs before remediation:**
*   **Data Loss:** **100% probability of total data loss.** Based on recent industry trends and your peer firm’s experience, the ransomware will traverse the network, compromise the Domain Controller, use the domain service account to access the NAS, and encrypt both the production VM and the backup repository.
*   **Business Impact:** The firm will be unable to meet court filing deadlines, leading to potential malpractice lawsuits, loss of client trust, and significant regulatory scrutiny.
*   **Recovery Prospect:** Near zero. Without an offsite, immutable copy, the firm would be forced to choose between paying a massive ransom (with no guarantee of recovery) or permanent dissolution of the practice.

---

### **3. Remediation Plan (Prioritized)**

**Phase 1: Immediate Risk Mitigation (Ransomware Defense)**
1.  **Implement Immutable Offsite Backup:** Deploy a cloud-based or offsite storage solution that supports **Object Lock (WORM - Write Once, Read Many)**. This ensures that once data is written, it cannot be deleted or encrypted by ransomware for a set period, even with admin credentials.
2.  **Isolate the Backup Repository:** Remove the backup NAS from the Active Directory domain. Transition to using **local, non-domain accounts** with complex, unique passwords for backup authentication.
3.  **Network Segmentation:** Move all backup traffic to a dedicated, non-routable VLAN to prevent lateral movement from the workstation segment.

**Phase 2: Compliance Alignment (RPO/RTO)**
4.  **Increase Backup Frequency:** Transition from nightly full backups to a schedule including **hourly Transaction Log backups** for the SQL Server. This reduces the RPO from 24 hours to <1 hour, exceeding the insurance requirement.
5.  **Implement Automated Testing:** Deploy a solution that performs "Sandbox Restores"—automatically spinning up the VM in an isolated environment to verify bootability and SQL integrity daily.

---

### **4. Mandatory Pre-Change Requirement**

**Before any new backup architecture is implemented, we must perform a full "Verify-and-Validate" restore from the existing NAS.**

We cannot replace the current system until we have successfully restored a copy of the SQL database and case files from the current NAS to a temporary environment. 

**Reasoning:** We must establish a "Known Good" baseline. If we switch to a new system and the firm experiences a failure during the transition, we must be certain that the old backups are actually intact. Without this step, we risk a "double-blind" failure: discovering the current backups are corrupted only *after* we have decommissioned them to make room for the new solution.
