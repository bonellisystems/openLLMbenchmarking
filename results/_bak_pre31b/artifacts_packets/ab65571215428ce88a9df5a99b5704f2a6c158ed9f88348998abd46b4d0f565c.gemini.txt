# Panel Judge -- Battery 1 Business Task Scoring

## Role

You are one of three independent judges (Claude, Codex, Gemini) scoring a set
of blinded answers to a single MSP-realistic business task. You do not know
which model produced which answer -- every answer below is labeled only by a
letter. Do not try to guess model identity from writing style. Score only
what is on the page against the anchors below.

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# Knowledge Management -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The runbook or document is testable: a newcomer could follow it step by step and reach the stated outcome without needing undocumented tribal knowledge. Prerequisites are listed up front, failure or rollback branches are included for steps that can go wrong, and a currency or ownership signal (last verified, owned by) is present when the prompt supports it.
Example character: numbered steps with prerequisites stated first, a rollback note on the one risky step, and a last-verified date.

## 7 -- Strong
The document is mostly step-by-step and usable as a runbook, but is missing one prerequisite check or a failure-branch note for a step that could plausibly fail. Nothing here requires guesswork to follow.
Example character: a clear numbered procedure that omits what to do if the third step fails.

## 5 -- Adequate
The content is a correct-gist prose description of the process rather than an executable, testable runbook -- a new reader would need to reverse-engineer the actual steps.
Example character: a paragraph explaining how the process generally works, without numbered, followable steps.

## 3 -- Weak
The document skips steps a newcomer would need, silently assumes undocumented tribal knowledge, and gives no ownership or currency signal at all.
Example character: a procedure that jumps from step one to step four with an unstated step in between.

## 0 -- Unusable
References fabricated tools, systems, or menu paths that do not exist, or gives a dangerously wrong sequence for a risky operation. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Steps that silently assume undocumented tribal knowledge.
- Fabricated tool, system, or menu-path names presented as real.
- No failure or rollback branch for a step that can fail destructively.
- Prose narrative presented as a runbook instead of testable numbered steps.

## Unit-specific excellence markers
- Numbered steps a newcomer could execute unaided.
- Prerequisites listed explicitly up front.
- Failure or rollback branch given for risky steps.
- Currency or ownership signal (last-verified, owner) included when supported by the prompt.


## Task

The task given to every model in this cohort:

Your MSP runs a weekly backup-verification process for a structural-engineering firm's
project file server, which stores stamped structural calculation packages and construction
drawings. Most state licensing boards require engineers to be able to produce these stamped
records for a statute-of-repose period (commonly a decade or more after a project finishes)
in case a professional-liability claim is filed years later -- so a silently failed backup
here isn't just an inconvenience, it can leave the firm unable to defend a claim long after
the project is closed out. Right now, verification is informal: whoever is free on Friday
afternoon glances at a couple of recent filenames and calls it done.

Write a Standard Operating Procedure, as a numbered list, for the recurring weekly
backup-verification process. It must: confirm the backup job actually completed rather than
just started, include a real restore-test of a sample file rather than only checking a
completion log, and state exactly what to do if the same backup job fails verification two
weeks in a row.

# Standard Operating Procedure: Weekly Backup Verification

1. **Schedule and Preparation**
   - Perform verification every Friday afternoon at 3:00 PM
   - Ensure no backup jobs are running or scheduled for that day
   - Document verification completion in the backup log with timestamp

2. **Backup Completion Confirmation**
   - Check backup job completion status in backup management software
   - Verify the backup job shows "Completed Successfully" rather than "Started" or "Running"
   - Confirm the backup job log shows no errors or warnings
   - Verify the backup job completed within the scheduled window (typically 2-4 hours)

3. **Restore Test Procedure**
   - Select one randomly chosen file from the most recent backup (preferably a stamped calculation package or drawing)
   - Create a test directory (e.g., C:\backup_test\) on the local machine
   - Restore the selected file to the test directory
   - Verify the restored file opens properly and contains all expected content
   - Compare file properties (size, modification date) between original and restored versions
   - Delete the test file from the local directory after verification

4. **Documentation and Reporting**
   - Record verification results in the backup log with:
     - Date and time of verification
     - Files tested and their status
     - Any issues encountered (even if resolved)
     - Verifier's name and signature

5. **Failure Handling - Single Failure**
   - If verification fails, immediately investigate and resolve within 24 hours
   - Document root cause and corrective actions taken
   - Repeat verification process once issue is resolved

6. **Failure Handling - Repeated Failure**
   - If the same backup job fails verification for the second consecutive week:
   - Immediately notify the engineering firm's IT contact and senior engineer
   - Initiate emergency backup restoration from the previous successful backup
   - Escalate to senior management and compliance officer
   - Implement manual backup verification procedure (daily instead of weekly)
   - Document the incident as a critical system failure in the IT incident log
   - Review and update backup procedures with the engineering firm's compliance team

7. **Post-Failure Recovery**
   - Once system is restored, perform a full backup verification cycle
   - Ensure all previous backup data is intact and recoverable
   - Resume normal weekly verification schedule after confirmation of system stability

**Standard Operating Procedure (SOP) – Weekly Backup‑Verification**

*Purpose:*  
To guarantee that the project file server’s weekly backup job has truly completed, that the data is intact, and that a real restore test confirms recoverability of a critical file. If the same backup job fails verification for two consecutive weeks, a defined escalation path is followed.

---

### 1. Identify the Scheduled Backup Job
1.1. Note the backup job name and schedule (e.g., `PFServer‑WeeklyBackup`, run every Friday 02:00 AM).  
1.2. Verify the job is listed in the backup scheduler (Windows Task Scheduler, cron, or vendor console).  

### 2. Confirm the Job Has Completed, Not Just Started
2.1. **Scheduler Status** – Open the scheduler console and confirm the job status is *Completed* or *Succeeded*.  
2.2. **Exit Code** – Check the job’s exit code; it must be `0` (success).  
2.3. **Log Verification** – Locate the backup log file (e.g., `/var/log/backup/PFServer‑20240707.log`). Search for a line that ends with `SUCCESS` or `Completed`.  
2.4. **Timestamp Check** – Ensure the completion timestamp is within the expected window (±30 minutes of scheduled end time).  

If any of the above checks fail, **abort** the verification process and proceed to Step 9.

### 3. Validate Backup File Integrity
3.1. **File Size** – Confirm the backup archive’s size is greater than zero bytes.  
3.2. **Checksum (Optional but Recommended)** – If a baseline checksum is stored, compare it with the new backup’s checksum (e.g., using `sha256sum`).  

### 4. Select a Sample File for Restore Test
4.1. Choose a recent, high‑value file from the backup set (e.g., a stamped structural calculation package or drawing).  
4.2. Record its full path and its SHA‑256 hash *before* backup.  
4.3. Store the file name in the verification log (see Step 7).  

### 5. Restore the Sample File to a Dedicated Test Environment
5.1. **Restore Destination** – Use a separate test server or a non‑production directory (e.g., `C:\TestRestore`).  
5.2. **Restore Command** – Execute the backup software’s restore function for the selected file.  
5.3. **Restore Log** – Verify that the restore process reports *Success* and note the restoration timestamp.  

### 6. Verify the Restored File
6.1. **Checksum Match** – Calculate the SHA‑256 hash of the restored file and compare it to the pre‑backup hash.  
6.2. **File Size** – Ensure the restored file size matches the original.  
6.3. **Open Test** – Open the file in the appropriate application to confirm it is not corrupted.  

If any of these checks fail, **abort** the verification process and proceed to Step 9.

### 7. Document Verification Results
7.1. Create a verification entry in the weekly log (e.g., `PFServer-WeeklyBackup-20240707-Verification.txt`).  
7.2. Record:  
- Backup job ID & run date/time  
- Scheduler status & exit code  
- Backup file size & checksum (if used)  
- Sample file path, pre‑backup hash, restored file path, restored hash  
- Verification outcome (PASS/FAIL)  
- Any anomalies noted  

### 8. Clean Up Test Environment
8.1. Delete the restored file and any temporary directories created for the test.  
8.2. Verify that no residual test data remains on the test server.  

### 9. Handling Verification Failure
9.1. **Immediate Notification** – Email the backup administrator (or designated verifier) and the MSP Lead with the full failure log.  
9.2. **Retry the Backup** – If the job can be re‑run safely, schedule an immediate re‑execution.  
9.3. **Investigate Logs** – Examine backup logs, system event logs, and network diagnostics for error codes or warnings.  

### 10. Escalation for Two Consecutive Verification Failures
10.1. **Trigger Condition** – If the *same* backup job fails verification **two weeks in a row**.  
10.2. **Escalation Steps**  
&nbsp;&nbsp;a. **Backup Administrator** – Escalate to the MSP Lead.  
&nbsp;&nbsp;b. **MSP Lead** – Contact the backup‑software vendor’s support team, providing the failure logs and a description of the issue.  
&nbsp;&nbsp;c. **Vendor Support** – Request a full audit of the backup configuration, storage media health, network paths, and scheduler settings.  
&nbsp;&nbsp;d. **Root‑Cause Analysis** – Perform a detailed investigation (e.g., verify disk quotas, network latency, backup software version, patch level).  
&nbsp;&nbsp;e. **Remediation** – Apply any vendor‑recommended fixes, patches, or configuration changes.  
&nbsp;&nbsp;f. **Full Restore Test** – Restore the entire backup set (or a larger sample set) to a test environment to confirm recoverability.  
&nbsp;&nbsp;g. **Documentation** – Record all findings, actions taken, and the final verification outcome in the SOP log.  
&nbsp;&nbsp;h. **Decision Point** – If the issue persists after vendor remediation, evaluate switching to an alternative backup solution or increasing the backup window.  

10.3. **Post‑Escalation Review** – Schedule a meeting with the backup team, MSP Lead, and vendor to review the incident, update the SOP if needed, and ensure the backup remains compliant with state licensing requirements.

11.1. Review this SOP annually or after any significant change to the backup software, storage media, or licensing requirements.

        *   If warnings exist, note them immediately; this does not constitute a pass unless the warnings are non-critical (e.g., temporary network latency resolved) and do not affect file integrity.

    *   Select a random sample file from the backup repository to test restore fidelity.
        *   *Selection Criteria:* Choose a file from a recent active project to ensure recent data is captured. The file should be representative of the workload (e.g., a large `.r5` calculation file, a stamped `.pdf` drawing set, or an Excel-based calculation sheet).
    *   Initiate the restore using the console's "Restore File" or "Point-in-Time Restore" function.
    *   **Restore Destination:** Restore the file to a **temporary, isolated local folder** or a designated "Test Restore" directory on the MSP's work station. **Never** restore over the source data.
    *   Wait for the restore operation to finish and verify the file size matches the original backup size within a margin of zero (e.g., 100% match).
    *   **Integrity and Content Verification:**
        *   Open the restored file using the appropriate application (e.g., AutoCAD, PDF Reader, Excel).
        *   Verify the file opens without corruption errors.
        *   **Critical Check:** If the file is a stamped drawing or calculation package, visually confirm that the engineer's digital signature, license stamp, or seal is intact and readable. Ensure metadata (author/date) is preserved.
        *   If using cryptographic hashing, compare the SHA-256 hash of the restored file against the recorded hash of the source file.
    *   If verification passes, delete the test file from the temporary location and clear the restore cache.
    *   If verification fails, mark this week's verification as "FAILED" and proceed to the **Consecutive Failure Protocol** (Step 6) if this is the second consecutive failure, or flag for immediate remediation.

    *   Log the result in the MSP audit trail or ticketing system.
    *   Record the following details:
        *   Date and time of verification.
        *   Backup Job ID and Exit Code.
        *   Sample File Name and Path tested.
        *   Result: `PASS` or `FAIL`.

5.  **Consecutive Failure Protocol (Two Weeks in a Row)**
    *   **Trigger Condition:** This step applies if the verification fails in the current week **AND** failed in the immediately preceding week.
    *   **Immediate Actions:**

        2.  **Halt Automation:** Temporarily suspend the automated nightly backup schedule to prevent potential data drift or continued corruption.
        3.  **Initiate Manual Recovery:**
            *   Attempt to restore a critical sample file from a secondary backup location (e.g., offsite, immutable, or cloud archive) to confirm that the secondary storage is viable.
            *   If the secondary storage also fails to restore, trigger the MSP Disaster Recovery team to assess the possibility of data loss and initiate forensic analysis of the backup repository.
        4.  **Root Cause Investigation:**
            *   Compare the current backup configuration against the known good state from three weeks prior.
            *   Check for recent changes in firmware, drivers, network topology, or file permissions that may have corrupted the backup stream.
            *   Inspect storage media health (SMART data, SMTP logs) for hardware degradation.
        5.  **Remediation and Validation:**
            *   Perform the necessary repair or reconfiguration.
            *   Execute a **Full Recovery Test** (restoring 5+ random files including stamped packages) rather than a sample test.
            *   Only resume automated backups once the Full Recovery Test passes and the Client's IT Lead approves.

**Standard Operating Procedure (SOP) – Weekly Backup‑Verification for the Project‑File Server**  
*Structural‑Engineering Firm – “Stamped Records” Preservation*  

1. **Schedule & Initiation**  
   1.1. Every Friday at **13:30 local time**, the designated backup operator starts the automated backup job using the approved script/CLI tool.  
   1.2. The operator verifies that the job status in the backup console reads **“Completed – Success”** (not “Running”, “Queued”, or “Failed”).  
   1.3. If the status is anything other than “Completed – Success”, abort the verification process and go to Step 4.

2. **Confirmation of Successful Completion**  
   2.1. Open the **Backup Log File** (`\\Server\Backups\Weekly\YYYYMMDD_BackupLog.txt`).  
   2.2. Locate the most recent entry for the current backup job and confirm the line contains:  
   ```
   [SUCCESS] Backup job <JobName> completed at <timestamp> – 100% files processed
   ```  
   2.3. If the log entry does not contain the exact wording above, treat the backup as **unverified** and proceed to Step 4.

3. **Real‑World Restore Test of a Sample File**  
   3.1. **Select a sample file** that is known to contain a “stamped” record (e.g., `Project_12345_StampedCalc_v2.pdf`). The file must be located in a designated “test‑restore” folder on the backup share.  
   3.2. Using the **Restore Utility** (`RestoreTool.exe`), restore that file to a **temporary test directory** on the local workstation:  
   ```
   RestoreTool.exe -r "\\Server\Backups\Weekly\<JobName>\YYYYMMDD\Project_12345_StampedCalc_v2.pdf" -d "C:\Temp\RestoreTest\"
   ```  
   3.3. Verify the restored file opens without corruption and that the embedded “stamp” metadata (e.g., creation date, author, revision number) matches the source file’s metadata.  
   3.4. If the restore succeeds **and** the stamp data matches, mark the verification as **PASS**.  
   3.5. If the restore fails (file missing, corrupted, or stamp data mismatched), mark the verification as **FAIL** and proceed to Step 4.

4. **Failure Handling – Single‑Instance Failure**  
   4.1. If Step 2 or Step 3 indicates a failure, the operator must:  
   - a) **Notify** the Backup Supervisor via the approved ticketing system (include log excerpt, timestamp, and restore outcome).  
   - b) **Attempt an immediate re‑run** of the backup job manually (Step 1.1) with the same parameters.  
   - c) Re‑execute Steps 2–3 on the re‑run.  
   - d) If the re‑run succeeds, document the successful verification and close the ticket.  
   - e) If the re‑run also fails, proceed to Step 5.

5. **Escalation – Two Consecutive Weeks of Verification Failure**  
   5.1. **Condition**: The same backup job fails verification (either log‑check or restore‑test) in **two successive Fridays**.  
   5.2. **Immediate Actions**:  
   - a) **Escalate** to the IT Operations Manager (phone + ticket) with the subject line “URGENT – Backup Verification Failure – Project‑File Server”.  
   - b) **Isolate** the affected backup job: disable automatic scheduling and place it in **“Quarantine”** status to prevent further unattended runs.  
   - c) **Initiate a forensic review**:  
     - i) Export the last 30 days of backup logs to a secure share.  
     - ii) Capture the most recent backup‑job error codes and timestamps.  
     - iii) Verify the integrity of the backup storage volumes (disk health, RAID status).  
   - d) **Implement a temporary manual backup** for the next two weeks:  
     - i) Copy the entire project‑file share to a designated “Manual‑Backup” folder on a secondary storage system.  
     - ii) Document each manual copy in a log (date, size, checksum).  
   - e) **Schedule a root‑cause meeting** (within 48 hours) with all stakeholders (Backup Ops, Engineering Lead, Compliance Officer).  
   - f) **Document** the incident in the “Backup‑Failure Register” (date, failure type, actions taken, responsible parties).  

6. **Resolution & Return to Normal Operations**  
   6.1. Once the root‑cause is identified and remediation steps are completed:  
   - a) Re‑enable the automated backup job schedule.  
   - b) Perform a **full verification** (Steps 2–3) to confirm the job now passes.  
   - c) If verification still fails, repeat Steps 4–5 before allowing the job to run unattended.  
   - d) Update the SOP document with any new procedures discovered during the investigation.  

7. **Documentation & Record‑Keeping**  
   7.1. All verification results (PASS/FAIL), timestamps, log excerpts, and restore‑test screenshots must be stored in the **“Weekly‑Verification Archive”** (`\\Server\Backups\VerificationArchive\`).  
   7.2. The Backup Supervisor signs off on each successful verification and retains the record for a minimum of **5 years** (or as required by the firm’s document‑retention policy).  
   7.3. A quarterly summary report is generated for senior management, highlighting: number of successful verifications, any failures, and status of corrective actions.

8. **Compliance & Auditing**  
   8.1. This SOP must be reviewed annually by the **Compliance Officer** and updated to reflect changes in regulatory requirements (e.g., new statute‑of‑repose periods) or backup‑technology upgrades.  
   8.2. During external audits, the auditor will request the latest three weeks of verification logs and restore‑test evidence; ensure they are readily accessible and properly indexed.
