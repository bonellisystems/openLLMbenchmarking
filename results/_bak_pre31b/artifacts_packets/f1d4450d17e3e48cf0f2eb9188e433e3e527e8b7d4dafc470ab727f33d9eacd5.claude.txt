### Why NULL `rate_type` Rows Are Silently Excluded (SQL Semantics)

This is a direct consequence of **SQL three-valued logic (3VL)** and how the `WHERE` clause evaluates predicates:

- In SQL, `NULL` does not represent a value; it represents **absence of a value** (unknown or missing).
- The equality operator `=` follows 3VL: `NULL = 'standard'` evaluates to `UNKNOWN` (not `TRUE` and not `FALSE`).
- The `WHERE` clause acts as a filter that **only retains rows where the predicate evaluates to `TRUE`**. Both `FALSE` and `UNKNOWN` result in row exclusion.
- Crucially, SQL treats `UNKNOWN` as "not qualifying", so the query executes successfully without raising an error. The engine never "sees" a mismatch—it simply can't confirm a match, so the row is dropped silently.

This is by design: SQL avoids assuming missing data equals any concrete value, but the trade-off is that `WHERE col = 'X'` is not a safe filter for data quality—it silently swallows NULLs, COALESCE gaps, and type mismatches.

## 4.  Why the NULL `rate_type` rows are **silently excluded** (SQL semantics)

The report uses:

```sql
SELECT …
FROM time_entries_fact
WHERE rate_type = 'standard';
```

* In SQL, **any comparison with `NULL` yields the three‑valued logic result `UNKNOWN`.  
* The `WHERE` clause keeps rows for which the predicate evaluates to **TRUE**; rows that evaluate to **FALSE** **or** **UNKNOWN** are filtered out.  
* Therefore a row where `rate_type IS NULL` makes the expression `rate_type = 'standard'` evaluate to **UNKNOWN**, and the row is **removed** from the result set without raising an error or warning.

To surface the problem you would need to test for `NULL` explicitly (e.g., `WHERE rate_type = 'standard' OR rate_type IS NULL`) or add a constraint that disallows `NULL`.

### Explanation of NULL rate_type Rows Silently Excluded

The NULL `rate_type` rows are silently excluded from the standard hourly-realization report because of the underlying SQL semantics. Specifically, when filtering on a column with NULL values using a `WHERE` clause, SQL treats NULL as not equal to any value, including itself. In SQL, the following expressions evaluate to:

* `NULL = 'standard'`: FALSE
* `NULL <> 'standard'`: TRUE

As a result, the 460 NULL `rate_type` rows are not included in the report, without raising any error or warning.

### 2. SQL Semantics: Why `NULL` Rows Are Silently Excluded

The `WHERE rate_type = 'standard'` clause excludes NULL rows due to **SQL's Three-Valued Logic (3VL)**.

*   **Unknown Comparison:** In SQL, `NULL` represents an unknown value. Comparing an unknown to a concrete value (`NULL = 'standard'`) does not evaluate to `FALSE`; it evaluates to **`UNKNOWN`**.
*   **WHERE Clause Semantics:** The `WHERE` clause retains only rows where the predicate evaluates to **`TRUE`**. Rows evaluating to `FALSE` or `UNKNOWN` are both filtered out.
*   **No Error:** SQL does not treat `UNKNOWN` as an error state. It is a valid logical outcome. Consequently, the query executes successfully, but the engine silently discards any row where the comparison cannot be confirmed as true. To include NULLs, explicit handling (e.g., `COALESCE` or `IS NULL` checks) is required.

### 4. SQL Semantics: Why NULL `rate_type` Rows Are Silently Excluded

To catch these rows, the query would need to explicitly test for nullity using `IS NULL` (e.g., `WHERE rate_type IS NULL OR rate_type = 'standard'`), or the data would need to be pre-cleaned before loading.

### **3. The "Why" of NULL Exclusion (SQL Semantics)**

The reason the 460 rows are silently excluded is due to **Three-Valued Logic (3VL)** in SQL.

In standard SQL, a boolean expression can evaluate to **TRUE**, **FALSE**, or **UNKNOWN**. When a value is `NULL`, any comparison (e.g., `=`, `<>`, `>`) against that value does not result in TRUE or FALSE; it results in **UNKNOWN**.

When the report executes `WHERE rate_type = 'standard'`, the database engine evaluates each row:
1. If `rate_type` is `'standard'`, the predicate is `TRUE` $\rightarrow$ **Row Included**.
2. If `rate_type` is `'contingency'`, the predicate is `FALSE` $\rightarrow$ **Row Excluded**.
3. If `rate_type` is `NULL`, the predicate is `UNKNOWN` $\rightarrow$ **Row Excluded**.

Because the `WHERE` clause only allows rows through that evaluate strictly to **TRUE**, the `UNKNOWN` (NULL) rows are silently dropped. The database does not consider `NULL` to be "not standard"; it considers the comparison to be "not answerable."

### 2. Why NULL `rate_type` Rows Are Silently Excluded (SQL Semantics)
In standard SQL, `NULL` is not an error or a string; it is a **scalar value representing unknown/missing data**. SQL uses **three-valued logic** (`TRUE`, `FALSE`, `UNKNOWN`). When the pipeline executes:
```sql
WHERE rate_type = 'standard'
```
SQL evaluates `NULL = 'standard'` and returns `UNKNOWN`, not `FALSE` or an error. The `WHERE` clause implicitly filters rows where the condition evaluates to `FALSE` **or** `UNKNOWN`. Because the condition never resolves to `TRUE`, those 460 rows are excluded from the result set. No error is raised because:
- `NULL` is a valid, expected data state (not a constraint violation or syntax error)
- The `=` operator gracefully handles `NULL` without throwing an exception
- SQL's evaluation model treats `UNKNOWN` as a non-matching condition, silently dropping the row during set filtering
