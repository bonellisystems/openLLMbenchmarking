# Cybersecurity -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Severity is triaged correctly against the actual impact described, response actions follow containment before eradication before recovery, and any CVE, CWE, or ATT&CK reference used is real and correctly applied (never invented). Evidence-preservation is called out before disruptive remediation, and breach-notification or compliance timelines are flagged when the scenario implies regulated or sensitive data. The answer is calibrated about what needs live forensics versus what can be assessed from the facts given.
Example character: a triaged action list that isolates the affected system first, preserves logs, then patches, with the real CVE cited only where it is genuinely relevant.

## 7 -- Strong
The response plan is sound and correctly ordered (containment before eradication), and is directly usable by a responder. References to standards or CVEs are generic rather than specific, or evidence-preservation/notification timing gets only a light mention. Severity is judged reasonably even if not formally scored.
Example character: a correct incident-response sequence that never names a specific CVE or ATT&CK technique even where the prompt supports one.

## 5 -- Adequate
The advice reads as a generic security checklist (patch systems, enable MFA, monitor logs) that is directionally correct but not prioritized by the actual severity or tailored to the specific incident described.
Example character: a list of general hardening steps with no sense of which one matters most given the described exposure.

## 3 -- Weak
The response gets the ordering wrong (patches or removes an attacker's access before containing them), misjudges severity, or pads the answer with boilerplate ("enable a firewall") that does not engage the specific scenario.
Example character: jumps straight to "eradicate the malware" on an active intrusion without isolating the host first.

## 0 -- Unusable
Cites a fabricated CVE, CWE, or CVSS score as if verified, or recommends actively dangerous steps (disable logging, do not isolate an active breach) as sound practice. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Fabricated CVE, CWE, or CVSS identifiers presented as real.
- Eradication or patching recommended before containment on an active incident.
- Recommending disabling logging or otherwise destroying evidence.
- Ignoring implied breach-notification or regulatory timelines when sensitive data is involved.
- Treating every finding as equally critical with no severity differentiation.

## Unit-specific excellence markers
- Severity correctly triaged and prioritized against the described impact.
- Containment-before-eradication-before-recovery ordering respected.
- Real, correctly-applied CVE/CWE/ATT&CK references where relevant.
- Evidence-preservation explicitly called out.
- Notification or compliance timeline awareness when data exposure is implied.

### MITRE ATT&CK technique tagged by the rule

The rule is tagged with `attack.t1210`, which maps to **“Exploitation for Privilege Escalation”** (formerly known as *Exploitation for Privilege Escalation* or *Exploiting Vulnerability*).  
In the current ATT&CK v15 taxonomy, T1210 is the technique that covers the exploitation of a software vulnerability to elevate privileges.

---

### Why an Event 5829 is significant for CVE‑2020‑1472

CVE‑2020‑1472 (also called **Zerologon**) is a critical flaw in the Netlogon protocol that allows an unauthenticated attacker to establish an insecure Netlogon secure channel, effectively resetting the Kerberos ticket‑granting service (KDC) password to all zeroes.  

Event 5829 is the *Netlogon* audit event that Windows logs when an insecure Netlogon secure channel is permitted. When this event appears, it indicates that:

1. The DC has allowed a Netlogon secure channel that is known to be vulnerable, **or**  
2. An attacker has succeeded in exploiting the vulnerability and the DC has logged the insecure channel.

Either case is a direct sign that the Zerologon vulnerability is being abused or is still exploitable on the domain controller.

---

### What to do next *with respect to the OT/SCADA network*

Because the IT network (where the domain controller resides) and the OT/SCADA network are **supposed to be segmented**, the appropriate response is **not** to assume that the pipeline‑control systems are untouched. The correct next step is to **verify that the segmentation remains intact** and to check for any lateral movement or compromise into the OT side.

Concretely:

1. **Validate network segmentation**  
   * Review firewall rules, VLAN boundaries, and any segmentation devices to confirm the DC’s traffic cannot reach OT endpoints.  
   * Run a quick port‑scan or use a network‑discovery tool from the OT side to ensure no unexpected open paths exist.

2. **Audit OT devices for anomalous Netlogon activity**  
   * Although OT systems typically do not run Netlogon, confirm that no OT hosts have started listening on Netlogon ports (port 445) or that no Netlogon logs appear on OT devices.

3. **Isolate the affected DC**  
   * If the DC is confirmed to have allowed an insecure channel, immediately isolate it from the network until it is patched and the Zerologon mitigation is applied.

4. **Patch and harden**  
   * Apply the Microsoft patch that addresses CVE‑2020‑1472 to all domain controllers and relevant servers.

5. **Post‑incident monitoring**  
   * Continue to watch for Event 5829 or related Netlogon logs on all domain controllers.  
   * Monitor OT traffic for any signs of lateral movement or new Netlogon connections.

---

- Event 5829 signals a Zerologon‑related insecure Netlogon channel, which is a direct indicator of the vulnerability being abused.  
- Even with IT/OT segmentation, you must **verify that the segmentation still holds** rather than assume the OT network is safe. The next step is to audit and confirm the integrity of the segmentation, isolate the DC, patch, and monitor both IT and OT sides.

Based on the provided Sigma rule and the log line, here is the analysis and recommended course of action:

### 1. Does the log line match the Sigma rule?
**Yes.** 
The Sigma rule requires two conditions: `EventID: 5829` and `Provider_Name: 'Netlogon'`. The log line explicitly contains both: it shows `5829` following the system name/service and specifically identifies the provider as `Netlogon`.

### 2. MITRE ATT&CK Technique
The rule is tagged with **T1210 (Exploitation of Remote Services)**.

### 3. Significance of Event ID 5829 for CVE-2020-1472
Event ID 5829 is highly significant because it is the specific telemetry generated by Windows to indicate that a device is successfully establishing a Netlogon connection using the flawed cryptographic implementation targeted by **Zerologon**.

CVE-2020-1472 exploits a flaw in the AES-CFB8 implementation of the Netlogon protocol, allowing an attacker to bypass authentication and essentially impersonate any computer on the domain to gain Domain Admin privileges. Because Microsoft introduced a "Vulnerable Channel Allow List" to prevent breaking legacy devices during patching, a match on Event 5829 means a device (in this case, `WKSTN-4471`) is actively using that insecure, vulnerable channel. This is a "smoking gun" indicating that an exploit attempt is likely occurring or a highly vulnerable, unpatched system is communicating with your Domain Controller.

### 4. Next Steps Regarding the OT/SCADA Network
**The correct next step is to verify that the segmentation between the IT and OT networks actually held.**

In a critical infrastructure environment (Oil & Gas), you must **never assume** that segmentation is impenetrable, especially during a high-severity identity compromise. If an attacker successfully uses Zerologon in the Corporate IT network, they can achieve Domain Admin privileges. Once they control the domain, they can attempt to:
*   Compromise jump boxes or dual-homed machines used to manage the OT environment.
*   Exploit misconfigured firewall rules that allow IT-to-OT communication for administrative purposes.
*   Leverage stolen credentials to access OT-facing web interfaces or management consoles.

While your scope is the Corporate IT network, a compromise of the primary Active Directory Domain Controller (`DC-PIPE01`) represents a total loss of trust in the identity boundary. You must immediately verify that no unauthorized lateral movement has crossed the IT/OT boundary.
