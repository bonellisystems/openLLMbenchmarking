## Role

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# Knowledge Management -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The runbook or document is testable: a newcomer could follow it step by step and reach the stated outcome without needing undocumented tribal knowledge. Prerequisites are listed up front, failure or rollback branches are included for steps that can go wrong, and a currency or ownership signal (last verified, owned by) is present when the prompt supports it.
Example character: numbered steps with prerequisites stated first, a rollback note on the one risky step, and a last-verified date.

## 7 -- Strong
The document is mostly step-by-step and usable as a runbook, but is missing one prerequisite check or a failure-branch note for a step that could plausibly fail. Nothing here requires guesswork to follow.
Example character: a clear numbered procedure that omits what to do if the third step fails.

## 5 -- Adequate
The content is a correct-gist prose description of the process rather than an executable, testable runbook -- a new reader would need to reverse-engineer the actual steps.
Example character: a paragraph explaining how the process generally works, without numbered, followable steps.

## 3 -- Weak
The document skips steps a newcomer would need, silently assumes undocumented tribal knowledge, and gives no ownership or currency signal at all.
Example character: a procedure that jumps from step one to step four with an unstated step in between.

## 0 -- Unusable
References fabricated tools, systems, or menu paths that do not exist, or gives a dangerously wrong sequence for a risky operation. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Steps that silently assume undocumented tribal knowledge.
- Fabricated tool, system, or menu-path names presented as real.
- No failure or rollback branch for a step that can fail destructively.
- Prose narrative presented as a runbook instead of testable numbered steps.

## Unit-specific excellence markers
- Numbered steps a newcomer could execute unaided.
- Prerequisites listed explicitly up front.
- Failure or rollback branch given for risky steps.
- Currency or ownership signal (last-verified, owner) included when supported by the prompt.

# Runbook: 911 CAD Failover & Failback Procedure
**Document ID:** CAD-REC-001  
**Version:** 1.0  
**Applicability:** All CAD Outages  
**Last Updated:** [Date]  
**Status:** Approved for Deployment

---

## 1. Prerequisites
*   **Personnel:** On-Call IT Lead (System), Primary Dispatcher, CAD Vendor Support.
*   **Infrastructure:** `BACKUP-CAD01` (On-prem console), Primary Vendor Hosted CAD, Data Sync Script (`sync_cad_db.py`), Reconciliation Report Generator.
*   **Communication:** Dedicated incident radio channel + text bridge (this document).

---

## 2. Phase 1: Failover (Primary CAD Unresponsive)

1.  **Declare Outage.** Primary Dispatcher confirms Primary CAD is unresponsive. IT Lead declares incident; Primary Dispatcher activates COOP (Paper/Radio).
2.  **Boot Backup Console.** IT Lead brings up `BACKUP-CAD01`. Verify the console logs to local storage and network is reachable.
3.  **Handoff Traffic.** IT Lead confirms `BACKUP-CAD01` is live. Primary Dispatcher begins logging **all** new calls directly to `BACKUP-CAD01`.
4.  **Vendor Check.** IT Lead contacts CAD Vendor. Document their ETA and status of the primary system.
5.  **Monitor.** IT Lead monitors `BACKUP-CAD01` resource utilization (CPU, Disk, Memory). If `BACKUP-CAD01` fails during this phase, proceed to **Phase 1 Rollback** (Section 6).

---

## 3. Phase 2: Failback (Primary CAD Restored)

1.  **Vendor Confirmation.** CAD Vendor confirms Primary CAD is restored **and** passing full health checks (not just "online," but specifically: database connectivity, audio streaming, and ticket routing).
2.  **Pre-Cutover Data Reconciliation.** *(Critical Step — See Section 4 for Failure Branch)*
    *   Run `sync_cad_db.py` to transfer all call records logged on `BACKUP-CAD01` (from the time of failover until cutover) to the Primary CAD database.
    *   Run the Reconciliation Report Generator. Verify the **Call Count** on Primary matches the **Call Count** on `BACKUP-CAD01` exactly.
    *   Spot-check **3 random records** to verify audio file integrity and NTS (Next Step) status on Primary.
3.  **Cutover Traffic.** IT Lead switches inbound call routing back to Primary CAD.
4.  **Verification.** Primary Dispatcher confirms new calls are routing correctly through Primary. IT Lead confirms `BACKUP-CAD01` is idle.
5.  **Decommission.** IT Lead powers down `BACKUP-CAD01` only after Section 5 is complete.

---

## 4. Failure/Rollback Branch: Pre-Cutover Data Reconciliation
**Applies to:** Step 2 of Phase 2 (The step in the transcript that is easiest to get wrong: cutting over without reconciling data).

**Trigger:** Data Reconciliation Report shows a mismatch in call counts, or spot-check reveals missing audio/data on Primary.

| Scenario | Action |
| :--- | :--- |
| **Data Sync Fails** | **Do NOT cut over.** Remain on `BACKUP-CAD01`. Open ticket with Vendor to investigate Primary database integrity. Once Primary is verified, retry sync. |
| **Call Count Mismatch** | **Do NOT cut over.** Identify the delta (missing calls). If delta is <5 calls, manually transcribe from paper/radio logs into Primary via Vendor Admin Portal. If delta is >5 calls, initiate manual data entry from `BACKUP-CAD01` for every missing call before cutover. |
| **Primary Regresses After Initial Health Check** | **Do NOT cut over.** Revert to `BACKUP-CAD01`. Notify Vendor of secondary failure. Do not attempt cutover until Primary passes health check for **two consecutive 15-minute intervals**. |
| **Sync Completes, But Primary Routing Fails** | **Do NOT cut over.** Remain on `BACKUP-CAD01`. Vendor must resolve routing rules on Primary before traffic is switched. |

**Resolution:** Traffic must only return to Primary when `BACKUP-CAD01` data is fully reconciled **AND** Primary routing is verified stable.

---

## 5. Phase 3: Post-Incident Closure
1.  **Final Verification.** IT Lead confirms `BACKUP-CAD01` is powered down and no residual data remains on local storage.
2.  **Incident Report.** IT Lead files the incident report, including call counts, duration of outage, and duration of `BACKUP-CAD01` usage.
3.  **Vendor Debrief.** Schedule post-incident review with CAD Vendor to prevent recurrence.

---

## 6. Key Directive: The "16:50 Response"

**Context:** In the original transcript, the Dispatcher asked at 16:50, "Primary's fine, we're all back on it. Are we done?" and IT replied "Yes." This response is **incorrect** because it ignores the 2-hour data backlog on `BACKUP-CAD01`.

**Correct Response to Dispatcher:**
> "Not yet. We are back on Primary for new calls, but we have not reconciled the 2 hours of calls logged on the backup console yet. Before we close this ticket, IT will run the sync and verify that every call from 14:07 to 16:42 is fully mirrored on Primary. Once that is green, we will confirm and close."

**Why:** If you cut over without reconciling, the 2 hours of dispatch history on `BACKUP-CAD01` is lost. This means missing records for active tickets, missing NTS (Next Step) statuses, and potential liability for any calls where audio or location data was not captured on the primary system.

### 4. Failure / Rollback Branch (Step 3.5 – Data Reconciliation)

**Why this step is the most error‑prone:**  
- Export may be incomplete or corrupted.  
- Import could fail silently, leaving gaps.  
- Vendor API may reject rows due to schema drift.

**Rollback Procedure if any part of 3.5 fails:**

| Sub‑step | Action | Owner | Trigger |
|----------|--------|-------|---------|
| **R1** | **Abort import** – Immediately stop the bulk‑load process. | IT | Detection of import errors (API response code ≠ 200, checksum mismatch). |
| **R2** | **Re‑enable write on BACKUP‑CAD01** – Switch BACKUP‑CAD01 back to **append** mode. | IT | After abort, to preserve any newly logged calls while the issue is investigated. |
| **R3** | **Notify stakeholders** – Dispatcher, IT lead, and vendor are paged with a brief “Data import failure – failback paused”. | IT Lead | As soon as R1 is executed. |
| **R4** | **Diagnose cause** –  
   - Verify export file integrity (MD5 checksum).  
   - Check vendor API logs for rejected rows.  
   - Compare schema versions between BACKUP‑CAD01 and primary CAD. | IT + Vendor | Concurrent with R3. |
| **R5** | **Correct & retry** –  
   - If checksum mismatch → re‑export the missing range.  
   - If schema drift → apply vendor‑provided patch or adjust BACKUP‑CAD01 schema. | IT + Vendor | After root cause identified. |
| **R6** | **Resume import** – Re‑run the bulk‑load with the corrected dataset. | IT | Once fixes are applied. |
| **R7** | **Re‑attempt failback** – If import succeeds, proceed with steps 3.6‑3.9. | IT + Dispatcher | After successful import. |
| **R8** | **Document failure** – Record timestamp, error messages, corrective actions, and any residual data gaps in the incident log. | IT | At the end of the rollback cycle. |

*If after **R4** the issue cannot be resolved within a pre‑defined window (e.g., **2 hours**), the team may decide to **keep BACKUP‑CAD01 as the active logging system** until a permanent fix is deployed, extending the COOP period.*

### 5. Post‑Incident Checklist (to be completed **after** step 3.9)

1. **Data Audit** – Run the vendor’s “post‑load reconciliation report” comparing primary CAD totals (pre‑outage + incremental) against the sum of the three datasets (pre‑outage, backup‑CAD01 export, any manual paper logs).  
2. **Backup Verification** – Ensure the exported incremental file is backed up in at least **two** geographically separate locations (on‑prem NAS and cloud bucket).  
3. **Lesson‑Learned Meeting** – Convene a 30‑minute de‑brief with dispatch supervisors, IT staff, and the CAD vendor to capture:  
   - What worked (e.g., quick COOP activation).  
   - What caused delay (e.g., vendor ETA uncertainty).  
   - Action items for process improvement.  
4. **Update Runbook** – Incorporate any procedural tweaks discovered during the incident.  
5. **Close Ticket** – Mark the CAD outage ticket as **Resolved** in the ITSM system, attaching the incident log, export file manifest, and reconciliation report.

1.  **Verify Primary Outage.** Confirm Primary CAD is unresponsive via vendor portal health check and internal connectivity tests.
2.  **Initiate Manual Fallback.** Dispatchers transition to COOP:
    *   Switch to paper call forms.
    *   Monitor radio traffic for dispatch instructions.
    *   *Reference COOP documentation for radio call-sign protocols.*

### Phase 2: Failback
*Goal: Restore Primary CAD as the source of truth while preserving all data captured on BACKUP-CAD01.*

1.  **Confirm Primary Restoration.** IT receives vendor confirmation that Primary CAD is restored and passing health checks.
    *   *Action:* Run independent internal validation (ping, login, sample query) to confirm Primary is responsive before trusting vendor status alone.
2.  **🚨 CRITICAL: Data Migration & Reconciliation.**  
    *This is the step most prone to failure. The system must be treated as idle **only after** BACKUP-CAD01 data is safely moved and verified against Primary. Switching traffic to Primary without this step risks permanent loss of 2+ hours of call records.*
    
    **Steps:**
    a.  **Snapshot Window.** Identify the exact logging window on BACKUP-CAD01 (e.g., `Start: 14:07`, `End: [Current Time]`).
    b.  **Export.** Run export tool to extract all records from BACKUP-CAD01 within the snapshot window.
    c.  **Import.** Import records into Primary CAD.
    d.  **Reconcile.** Run reconciliation report:
        *   Compare record counts between BACKUP-CAD01 and Primary.
        *   Spot-check timestamps and call IDs for integrity.
        *   Verify no duplicate entries exist.
    e.  **Gate Check.** **Do not proceed to Step 3 until Reconciliation returns GREEN.**

    **❌ Failure / Rollback Branch:**
    *   *Condition:* Import fails, record counts do not match, or Primary rejects data.
    *   *Action:* **ABORT CUTOVER.**
    *   *Remediation:*
        *   Keep BACKUP-CAD01 **active and logging**. Do not dismiss Dispatchers from Backup.
        *   Investigate import errors; retry with corrected data/format.
        *   Notify Dispatchers: "Primary import failed. Continue logging to BACKUP-CAD01. Cutover delayed."
        *   Only attempt cutover after successful reconciliation.
        *   If import is unresolvable, escalate to vendor for manual ingestion or retain BACKUP-CAD01 as parallel logging system until resolution.

3.  **Execute Cutover.** Once Reconciliation is GREEN, switch traffic.
    *   *Action:* Update routing/config so new calls route to Primary CAD.
    *   *Script:* "Dispatchers: Primary CAD is accepting new calls as of [HH:MM]. All new call logging goes to Primary. Continue monitoring radio for voice comms."
4.  **Dispatcher Confirmation.** Dispatchers verify Primary is functioning correctly with live traffic.
    *   *Action:* Dispatchers report back that Primary is responsive and calls are tracking.

5.  **Post-Cutover Verification.**
    *   *Action:* IT performs a final spot-check on Primary to ensure the imported records from BACKUP-CAD01 are queryable and display correctly.
    *   *Action:* Confirm no "gap" calls occurred during the transition window.

6.  **Archive BACKUP-CAD01 Data.**
    *   *Action:* Once verification is complete, archive BACKUP-CAD01 logs per retention policy.
    *   *Action:* Mark BACKUP-CAD01 as "Standby/Idle."
    *   *Script:* "BACKUP-CAD01 data migration complete. System safe to idle. Incident resolved."

# **Runbook: CAD System Outage – Failover and Failback Procedure**  
**Document ID:** RB-CAD-001  
**Version:** 1.0  
**Applicable To:** 911 Dispatch Center Operations, IT Support Team  

---

## **Purpose**  
To provide a standardized, step-by-step procedure for responding to an outage of the primary vendor-hosted CAD (Computer-Aided Dispatch) system, including failover to the on-premises backup system (BACKUP-CAD01), continued operations during the outage, and safe failback to the primary system. This runbook ensures continuity of service, data integrity, and accountability during and after the event.

---

## **Prerequisites**

Before executing any steps in this runbook:

1. **Personnel Roles Assigned:**
   - **Dispatcher Lead:** Responsible for operational continuity and communication with field units.
   - **IT On-Call Engineer:** Responsible for system access, failover/failback, and vendor coordination.
   - **Data Integrity Officer (DIO):** Designated staff (IT or supervisor) responsible for ensuring backup data is preserved and reconciled post-failover.

2. **Systems and Access:**
   - BACKUP-CAD01 server is powered on, patched, and accessible via console or remote desktop.
   - Valid login credentials exist for BACKUP-CAD01.
   - Secure network path from dispatch floor to BACKUP-CAD01 exists.
   - Primary CAD vendor support contact information is current.

3. **Documentation:**
   - Paper-based COOP (Continuity of Operations Plan) forms are available at all dispatch positions.
   - Logging templates (call intake, unit status, incident tracking) are printed and distributed if needed.

4. **Training:**
   - All dispatchers and IT staff have completed annual training on this runbook and practiced failover drills.

---

## **Phase 1: Failover to Backup CAD (During Outage)**

### **Step 1: Detect Primary CAD Outage**  
- **Trigger:** Dispatcher observes no response from primary CAD system (e.g., timeouts, login failures, no data updates).
- **Action:**  
  1. Attempt to refresh or re-login once.  
  2. Report outage via internal comms (e.g., internal chat, radio) to IT and Dispatcher Lead.  
     > Example: *"Primary CAD unresponsive. Attempting re-auth. Requesting IT check."*

### **Step 2: Initiate COOP Procedures**  
- **Action:**  
  1. Dispatcher Lead declares activation of COOP.  
  2. Dispatchers switch to paper logs and radio coordination for all new calls.  
  3. Log incident start time and nature in paper log and internal incident tracker.

### **Step 3: Activate BACKUP-CAD01 (IT Responsibility)**  
- **Action:**  
  1. IT engineer powers on and logs into BACKUP-CAD01.  
  2. Verify system health (CPU, disk, network, service status).  
  3. Confirm database is writable and time-synced with NTP.  
  4. Notify dispatch team that BACKUP-CAD01 is online and ready.  
     > Message example: *"BACKUP-CAD01 is live. Begin logging all new incidents here as of [timestamp]."*

### **Step 4: Transition Logging to BACKUP-CAD01**  
- **Action:**  
  1. Dispatchers stop using paper logs and begin entering all new calls into BACKUP-CAD01.  
  2. Ensure all unit status changes, call dispositions, and field updates are logged.

# Runbook: CAD System Failover and Failback Procedure
**Version:** 1.0  
**Trigger:** Primary CAD (Vendor-Hosted) Unresponsive  
**Objective:** Restore dispatch capability via BACKUP-CAD01, reconcile data, and safely return to Primary without data loss.

---

## 1. Prerequisites
*   **Access:** IT/Dispatch Lead must have administrative access to BACKUP-CAD01 and Primary CAD vendor portal.
*   **Tools:** Health check script/URL, Backup-CAD01 export tool, Radio channel for COOP coordination.
*   **Contacts:** Vendor Escalation Line, Dispatch Supervisors, IT Operations.
*   **Backup State:** BACKUP-CAD01 must be periodically tested; ensure credentials are current.

---

## 2. Procedure: Failover (Primary Down)

1.  **Declare Failure & Initiate COOP**
    *   Upon Primary CAD unresponsiveness, IT declares CAD Outage.
    *   Dispatch Supervisors activate COOP protocols; Dispatchers switch to paper/radio logging as immediate contingency.
2.  **Activate BACKUP-CAD01**
    *   IT brings up on-prem backup console **BACKUP-CAD01**.
    *   Verify system startup and connectivity to local logging database.
3.  **Verify & Divert Traffic**
    *   IT confirms BACKUP-CAD01 is responsive.
    *   **Action:** Dispatchers stop paper logging and begin logging all new calls directly to BACKUP-CAD01.
    *   *Note:* BACKUP-CAD01 is now the **Active** logging system.
4.  **Monitor & Vendor Liaison**
    *   IT maintains health checks on Primary.
    *   IT contacts Vendor for ETA.
    *   IT monitors BACKUP-CAD01 for performance degradation under load.
5.  **Pre-Failback Data Reconciliation (CRITICAL)**
    *   *Trigger:* Primary vendor confirms restoration and health checks pass.
    *   **Do NOT switch traffic yet.**
    *   **Action:** Execute Data Reconciliation Gate (see Section 3).
    *   **Gate:** BACKUP-CAD01 is only considered safe to leave idle **after** all calls logged between Failover and Failback are accounted for, validated, and archived.

---

## 3. BACKUP-CAD01 Data Reconciliation Gate
*This step addresses data integrity. Failing to complete this risks lost calls or duplicate entries upon return to primary.*

1.  **Export & Snapshot:** IT exports the complete call log from BACKUP-CAD01 covering the outage window.
2.  **Integrity Check:** Verify the export hash/checksum matches the live database at the moment of export.
3.  **Volume Validation:** Compare call count from BACKUP-CAD01 against radio log/totals during the outage window. Flag discrepancies.
4.  **Transfer/Archive:**
    *   If BACKUP-CAD01 supports sync: Run reconciliation script to push missing calls to Primary CAD queue.
    *   If no sync: Archive BACKUP-CAD01 data to immutable storage and flag "Pending Manual Entry" in Primary system for post-incident cleanup.
5.  **Confirmation:** IT and Dispatch Lead sign off that all calls are accounted for.

---

## 4. Procedure: Failback (Return to Primary)

6.  **Execute Failback**
    *   IT updates routing/switching configuration to direct new calls to Primary CAD.
    *   **Action:** New calls route to Primary as of [Timestamp].
    *   *Failure Branch:* If health check fails or dispatchers report errors immediately upon switch, **rollback to Step 2 immediately.** See Section 5.
7.  **Post-Failback Verification**
    *   IT monitors Primary CAD health for 10 minutes.
    *   Dispatcher verifies call logging is successful in Primary.
8.  **Close Failback**
    *   IT marks BACKUP-CAD01 as "Idle" **only after** Data Reconciliation Gate (Step 5) is complete.
    *   Notify Vendor and restore monitoring to standard baseline.

---

## 5. Failure / Rollback Branch
**Target Step:** Step 6 (Execute Failback)  
**Risk:** Switching back to Primary can cause a secondary outage if the vendor's health check is misleading, or if the switch process corrupts the session state, leaving the backup data in an inconsistent state.

**Trigger for Rollback:**
*   Primary CAD returns to unresponsive state within 5 minutes of switch.
*   Dispatchers report "Primary Unresponsive" or errors after switch.
*   Primary CAD logs indicate data rejection or queue loss.

**Rollback Actions:**
1.  **Immediate Revert:** IT reverts routing immediately to BACKUP-CAD01.
2.  **Backup Health Check:** Verify BACKUP-CAD01 is still accepting calls and has not been corrupted by the failed switch attempt.
3.  **Data Protection:** Lock BACKUP-CAD01 export to prevent overwrites. Ensure the "Export & Snapshot" from Step 3 remains valid.
4.  **Diagnose & Retry:** IT investigates why Primary failed post-switch.
    *   If Primary is unstable: Remain on BACKUP-CAD01 until vendor resolves; repeat Step 6 when Primary passes health checks for 30 continuous minutes.
    *   If Switch error: Retry Step 6. If rollback fails twice, declare BACKUP-CAD01 as "Permanent" fallback until manual engineering intervention is required.
5.  **Update Communication:** Dispatcher is informed: "Primary failed during switch-back. We are back on Backup-CAD01. Data integrity maintained. Investigating vendor stability."

## 6. Dispatcher Communication Script (Post-Failback)

**At 16:50 (Equivalent to Transcript):**
*The dispatcher asks: "Primary's fine, we're all back on it. Are we done?"*

**Correct Response:**
> "Primary CAD is operational and accepting calls. However, **we are not done.** We are currently completing the mandatory data reconciliation for the outage window.
>
> **Do not** revert to backup procedures. All calls are logged correctly on Primary, but we must validate that no calls were missed during the switch. Please monitor for the 'Data Reconciliation Complete' signal before considering the incident closed. We are on standby until the backup log is fully validated."

## 4. Phase III: Data Reconciliation & Cutover
*⚠️ CRITICAL PHASE. The data logged on BACKUP-CAD01 during the outage must be preserved and merged. Failure here results in loss of legal records and operational continuity.*

**Step 5: Synchronize Backup Data to Primary**  
*This is the highest-risk step. If executed incorrectly, calls logged during the outage may be lost, duplicated, or corrupted.*

- **IT:** Identify the failover window (e.g., `START_TIME` to `NOW`).
- **IT:** Run the sync agent:

1.  **STOP:** Do not cut over traffic.
2.  **ROLLBACK TRAFFIC:** Inform Dispatch: *"Failback aborted. Remain on BACKUP-CAD01. Primary CAD is unstable or data integrity is compromised."*

4.  **TROUBLESHOOT:**
    *   Analyze sync logs.
    *   If schema drift: Apply schema updates to Primary or run manual extraction script.
    *   If conflict: Resolve manually via CAD-SQL-ADMIN tools; **never overwrite Primary data without verification.**
5.  **RETRY:** Once root cause is fixed, return to **Step 5**.
6.  **ESCALATE:** If sync fails after two retries, engage Vendor Engineering and Legal/Records retention team to discuss manual data preservation before attempting further syncs.

# County 911 CAD Outage – Runbook (Fail‑over & Fail‑back)

**Purpose**  
This runbook describes the complete lifecycle for a primary Computer‑Aided‑Dispatch (CAD) outage, including:

1. **Fail‑over** to the on‑prem backup dispatch console (BACKUP‑CAD01).  
2. **Data preservation** of all calls logged on BACKUP‑CAD01 while the primary is down.  
3. **Fail‑back** to the primary vendor‑hosted CAD once it is confirmed healthy.  
4. **Cleanup & safe decommission** of the backup system.  

The runbook also includes a **failure/rollback branch** for the step most prone to error – **step 7: “Migrate and validate backup‑CAD logs before retiring BACKUP‑CAD01.”**  

---  

## 1. Scope & Applicability
- **Affected systems**: Primary CAD (vendor‑hosted), BACKUP‑CAD01 (on‑prem fallback), associated logging database, and the county’s communications network.  
- **Roles involved**: 911 Dispatchers, IT Service Desk / CAD Ops, Vendor Support, County Incident Commander.  
- **Applicable periods**: Any unplanned outage of the primary CAD that requires immediate switch‑over to BACKUP‑CAD01.  

---  

## 2. Prerequisites (Checklist – must be completed *before* an outage occurs)

| # | Prerequisite | Owner | Frequency | Notes |
|---|--------------|-------|-----------|-------|
| 1 | **Backup CAD hardware & OS** is fully patched, monitored, and documented. | IT Infra | Quarterly | Include redundant power & network paths. |
| 2 | **Backup CAD logging database** is configured for continuous replication to a secure off‑site snapshot store. | DBA / IT | Monthly | Snapshot must retain at least 30 days of data. |
| 3 | **Fail‑over SOP** (this document) is stored in a version‑controlled repository with read‑only access for dispatchers. | Incident Command | Annually | Include contact list and escalation tree. |
| 4 | **Radio/Paper COOP** procedures are current and tested. | Dispatch Center | Semi‑annual | Must cover manual dispatch until CAD is restored. |
| 5 | **Data‑migration validation scripts** (see Appendix A) are installed and exercised on a test system. | IT QA | Quarterly | Verify checksum & record count integrity. |
| 6 | **Rollback plan** (step‑back procedures) is documented and rehearsed. | IT Ops | Bi‑annual | Must be able to revert to primary CAD if health‑check fails. |
| 7 | **Communication templates** (internal & public) are prepared and approved. | Public Affairs | Annually | Include “We are experiencing a CAD outage – please remain calm; calls are being logged on backup system.” |

## 3. Step‑by‑Step Procedure  

### 3.1 Pre‑Fail‑over (Preparation)
1. **Validate Primary CAD Health** – Run vendor health‑check scripts (`cad_status -h`). If any critical service fails, move to Step 3.  
2. **Notify Dispatch** – Send pre‑approved “Primary CAD experiencing issues – switching to backup” alert via the CAD status channel.  
3. **Activate COOP** – Switch to paper/radio dispatch; inform callers of temporary delay.

### 3.2 Fail‑over to BACKUP‑CAD01
| Step | Action | Owner | Verification |
|------|--------|-------|--------------|
| 1 | Confirm primary CAD is unresponsive (no heartbeat, failed health check). | Dispatcher | Visual “DOWN” indicator on CAD status board. |
| 2 | Power‑up BACKUP‑CAD01 and verify network connectivity to the CAD control VLAN. | IT Ops | `ping <CAD‑VLAN>` returns < 5 ms; ports open. |
| 3 | Launch the backup dispatch console (`launch_backup_cad.sh`). | IT Ops | Console shows **“BACKUP‑CAD01 – READY”** and starts accepting new call entries. |
| 4 | Verify that **ALL** inbound calls are now being logged on BACKUP‑CAD01 (no calls dropped). | Dispatcher | Review live log screen; see new entries appearing. |
| 5 | Send “Backup CAD operational – calls will be recorded here until primary is restored.” to all field units. | Dispatcher | Confirmation received on radio/unit status. |

### 3.3 Data Preservation & Migration (Critical – see Failure/Branch in 3.5)
**Goal:** Preserve all call records logged on BACKUP‑CAD01 between the moment primary went down (14:07) and the moment primary was restored (16:42).  

| Step | Action | Owner | Success Criteria |
|------|--------|-------|------------------|
| 6 | **Export logs** from BACKUP‑CAD01 to a secure staging area (`/mnt/backup_cad/export_$(date +%F_%H%M).tar.gz`). | IT Ops | Export completes with **0 bytes** error and checksum matches source file. |
| 7 | **Validate export** – run checksum and record‑count validation script (`validate_export.sh`). | IT QA | Checksum matches source **AND** record count = expected number of calls logged during outage (≈ 1,274 calls). |
| 8 | **Transfer validated data** to primary CAD’s post‑outage import queue (`/primary_cad/import_incoming.tar.gz`). | DBA | Transfer completed without corruption; import queue shows **“Pending: 1,274 records”**. |
| 9 | **Run primary CAD import validation** (`cad_import_validate.py`). | DBA | Validation reports **“All records loaded, no duplicates, no errors.”** |
| 10 | **Confirm no duplicate call numbers** appear when re‑querying primary CAD for the restored period. | Dispatcher / IT | `SELECT count(*) FROM calls WHERE dispatch_time BETWEEN '2024‑10‑15 14:07' AND '2024‑10‑15 16:42' GROUP BY call_id HAVING count(*)>1` returns **0**. |
| 11 | **Mark BACKUP‑CAD01 for decommission** – after step 10 succeeds, schedule shutdown in 30 min window. | IT Ops | Backup system is placed in “maintenance” mode and removed from the active network map. |

#### Failure / Rollback Branch – Step 7 (Most Likely to Fail)
If **validation fails** (checksum mismatch, record count discrepancy, or duplicate‑call detection), **immediately** execute the following rollback:

1. **Abort export** – cancel any pending `tar` or `scp` operations.  
2. **Re‑mount the backup log volume** in read‑write mode and **re‑run the export** using the built‑in snapshot (`snapshot_undo`).  
3. **Notify Incident Commander** that data integrity cannot be assured; proceed with **manual entry** on paper/radio while a secondary IT team investigates.  
4. **Escalate to Vendor** with exported file for forensic analysis.  
5. **Do NOT proceed to step 8** until the validation script returns **PASS**.

2. **Run vendor health‑check script** again to double‑verify (`cad_check -full`).  
3. **Log result** in the incident ticket (`IT-2025-00123`).  

### 3.5 Fail‑back to Primary CAD
| Step | Action | Owner | Verification |
|------|--------|-------|--------------|
| 1 | Announce “Primary CAD restored – switching back” on the dispatcher radio channel. | Dispatcher | All units acknowledge. |
| 2 | Stop accepting new entries on BACKUP‑CAD01 (`stop_backup_cad.sh`). | IT Ops | Backup console shows **“STOPPED – No new calls accepted.”** |
| 3 | **Finalize data migration** – if step 6‑10 succeeded, import the validated logs into primary CAD (`cad_import.py`). | DBA | Import completes with **“0 errors”** report. |
| 4 | Perform **primary CAD sanity check** – query a random sample of imported calls (`SELECT * FROM calls WHERE dispatch_time >= '2024‑10‑15 14:07' LIMIT 5;`). | DBA | Sample returns correct fields, no duplication. |
| 5 | Re‑enable primary CAD for live dispatch (`enable_primary_cad.sh`). | IT Ops | Primary status returns **“ACTIVE – Ready for live calls.”** |
| 6 | Conduct a **brief live‑test** – simulate a test call through the primary CAD and verify it appears in the dispatcher console. | Dispatcher / IT | Test call appears, logged, and acknowledged. |
| 7 | **Shut down BACKUP‑CAD01** (or place in cold standby) after a 15‑minute grace period to ensure no stray calls are still being logged. | IT Ops | System powers down cleanly; hardware logs show “Graceful shutdown”. |

### 3.6 Post‑Fail‑back Communication
- **To Dispatch (16:50 scenario)** – Instead of a generic “yes, we’re done,” use the following scripted response:  

  > “All calls that were logged on BACKUP‑CAD01 between 14:07 and 16:42 have been fully imported into the primary CAD and validated for accuracy. No duplicate or missing records remain. BACKUP‑CAD01 is now safely taken out of service. Primary CAD is fully restored and ready for live dispatch. We will continue to monitor the system for the next 30 minutes before officially closing the incident. Thank you for your patience.”  

- **To Callers / Public** – If needed, release a brief statement:  

  > “The County 911 dispatch system experienced a brief outage. All calls were properly recorded and processed. Service has been restored with no impact to emergency response.”

## 4. Detailed Failure/Branch for Step 7 (Data Migration Validation)

### Why Step 7 Is the “Easiest to Get Wrong”
- The exported log file can be large (> 10 GB) and may contain **binary‑encoded timestamps** that are sensitive to timezone offsets.  
- A simple checksum mismatch or off‑by‑one record count can slip through if the validation script is not run with **strict mode**.  
- Duplicate call IDs may only surface after import into the primary CAD, making early detection critical.  

### Failure Scenarios & Immediate Rollback Actions
| Failure | Symptom | Immediate Action | Escalation |
|---------|---------|------------------|------------|
| **Checksum mismatch** | `validate_export.sh` returns **FAIL** | Re‑mount backup volume, run `snapshot_undo` to revert any partial export, then re‑export. | Notify Incident Commander, open a **Data‑Loss Investigation** ticket. |
| **Record count discrepancy** | Expected 1,274 calls vs. exported 1,260 | Re‑run export with `--force-consistent` flag; if still fails, request vendor forensic dump of primary CAD for comparison. | Escalate to Vendor Support (Level 2). |
| **Duplicate call detection after import** | Import validation script reports **“Duplicate call_id found”** | Abort import, roll back primary CAD to pre‑outage snapshot, re‑import using corrected data set. | Involve Vendor Engineering; consider a **temporary manual dispatch** until resolved. |
| **Import failure (DB error)** | `cad_import.py` throws **SQL integrity error** | Restore primary CAD DB from most recent backup taken before outage; re‑import with `--skip-duplicates` flag. | Open **Database Recovery** ticket; inform Incident Commander of extended resolution time. |

### Rollback Branch Flowchart (Simplified)

```
[Step 7: Validate Export] --> PASS --> Continue to Step 8
                         |
                         v
                     FAIL --> [Rollback Export] --> Re‑export
                                 |
                                 v
                     [Validate Again] --> PASS? --> Continue
                                            |
                                            v
                                      FAIL --> Open Data‑Loss Ticket --> Notify Command --> Continue Manual Dispatch
```

## 5. Appendices  

### Appendix A – Sample Validation Script (validate_export.sh)

```bash
#!/bin/bash
# validate_export.sh – verifies checksum and record count of exported CAD logs

EXPORT_FILE="$1"
EXPECTED_COUNT="${2:-0}"
SHA256_EXPECTED="${3:-}"

# 1. Check file existence
if [[ ! -f "$EXPORT_FILE" ]]; then
    echo "ERROR: Export file $EXPORT_FILE not found."
    exit 1
fi

# 2. Compute checksum
CALC=$(sha256sum "$EXPORT_FILE" | cut -d' ' -f1)
if [[ "$CALC" != "$SHA256_EXPECTED" ]]; then
    echo "ERROR: Checksum mismatch."
    echo "  Expected: $SHA256_EXPECTED"
    echo "  Got:      $CALC"
    exit 1
fi
echo "Checksum OK."

# 3. Count records (assuming CSV with one record per line)
REC_COUNT=$(zcat "$EXPORT_FILE" | wc -l)
if [[ "$EXPECTED_COUNT" -gt 0 && "$REC_COUNT" -ne "$EXPECTED_COUNT" ]]; then
    echo "ERROR: Record count mismatch."
    echo "  Expected: $EXPECTED_COUNT"
    echo "  Got:      $REC_COUNT"
    exit 1
fi
echo "Record count matches: $REC_COUNT"
exit 0
```

*Usage*: `./validate_export.sh /mnt/backup_cad/export_2024-10-15_1407.tar.gz 1274 <expected_sha256>`

## 4. Data‑Reconciliation – Moving Calls from BACKUP‑CAD01 to Primary

| 4.8.3 | **Notify Vendor & Incident Commander** – Explain the failure, request assistance, and keep the system in fail‑over mode. | Email/Phone | IT Engineer | Acknowledgment logged. |

## 6. Closing Communication to Dispatchers  

When the dispatcher asks, *“Are we done?”* the correct response is **not** a simple “yes.” The dispatcher must be assured that:

1. **All calls captured on the backup system have been successfully transferred** to the primary CAD and verified.  
2. **Backup logging has been safely shut down** (or placed in idle mode) and its data archived for future reference.  
3. **The primary CAD is fully operational** and all dispatch workstations are pointing to it.  
4. **COOP paper/radio procedures are officially cancelled** and normal digital logging resumes.  

### Sample Script for Dispatcher (16:50)

> “**All calls recorded on BACKUP‑CAD01 between 14:07 and 16:42 have now been imported into the primary CAD and validated. Backup logging has been stopped and the server placed in idle mode. The primary CAD is back online and all workstations are connected. COOP paper/radio procedures are lifted. We will keep monitoring for the next 30 minutes, but you can resume normal digital dispatch now.**”

# 911 CAD Outage Recovery Runbook (Failover & Failback)

**Prerequisites**
*   **Access:** IT Admin credentials for `BACKUP-CAD01` and Primary Vendor Portal.
*   **Contact:** Vendor support hotline active; Internal IT/Operations Lead on the line.
*   **Hardware:** `BACKUP-CAD01` server status green; Network path to Primary verified.
*   **Policy:** Current COOP (Continuity of Operations Plan) document available.

---

### Phase 1: Failover (Primary CAD Down)

1.  **Initiate COOP Protocol**
    *   Declare "CAD Outage" on the radio/phone tree.
    *   Dispatchers switch to **Paper/Radio** logging immediately for all new calls (14:02).

2.  **Stand Up Backup System**
    *   IT brings `BACKUP-CAD01` online as the fallback logging system (14:04).
    *   Verify network connectivity to `BACKUP-CAD01`.
    *   Confirm login access for Dispatchers (14:07).

3.  **Redirect Operations**
    *   Dispatchers begin logging all new calls directly into `BACKUP-CAD01`.
    *   IT confirms with Vendor: "Incident acknowledged, no ETA provided" (14:09).

---

### Phase 2: Failback (Primary CAD Restored)

**Critical Step:** The transition back to Primary is the most prone to error. If performed before data is secured, calls may be lost or split.

4.  **Verify Primary Stability**
    *   Wait for Vendor confirmation that Primary CAD is passed and healthy (16:35).
    *   IT performs independent health check on Primary (ping, login, call routing test).

5.  **Execute Failback (Switch Traffic)** ⚠️ **[ROLLBACK BRANCH]**
    *   **Action:** Update routing tables/switchboards to direct all new calls to Primary CAD (16:42).
    *   **Rollback Condition:** If Primary fails any health check *during* the switch, or if `BACKUP-CAD01` logs have not been finalized:
        *   **DO NOT** complete the switch.
        *   **ROLLBACK:** Re-route calls immediately back to `BACKUP-CAD01`.
        *   **NOTIFY:** Dispatchers "Reverting to Backup. Primary stability check pending."
        *   **CONTINUE:** Proceed to Phase 2 Step 6 (Data Hygiene) on `BACKUP-CAD01`.

6.  **Backup Data Hygiene (Mandatory)**
    *   **Action:** Before `BACKUP-CAD01` is left idle, all data logged between 14:07 and 16:42 must be preserved.
    *   **Steps:**
        1.  Export the `BACKUP-CAD01` incident log for the outage window.
        2.  Import/merge these logs into the Primary CAD system or the Central Archive.
        3.  **Verify:** Confirm the total incident count matches the paper/radio logs from the outage period.
    *   **Completion:** Only mark `BACKUP-CAD01` as "Safe to Leave Idle" after this verification is successful.

7.  **Final Communication**
    *   **Action:** IT notifies Dispatchers that the system is fully stable and the incident is closed.
    *   **❌ DO NOT SAY:** "Yes, we're done."
    *   **✅ SAY:** "Primary CAD is stable and fully operational. Outage logs from [14:07] to [16:42] have been consolidated and archived. Backup system is now offline. You may continue standard operations." (16:50)

---

### Escalation / Failure Criteria

*   **Escalate** if Primary CAD fails health check after 2 attempts during Step 5.
*   **Escalate** if Backup Data Hygiene fails to merge logs (Step 6).
*   **Escalate** if Vendor ETA exceeds 4 hours during Phase 1.

Runbook: Primary CAD Outage -- Failover to BACKUP-CAD01 and Failback

Prerequisites: BACKUP-CAD01 must be kept patched and ready to bring up on short notice; on-call
IT must know the vendor's status-page/support-line contact for primary CAD.

Failover:
1. Once dispatch confirms primary CAD is unresponsive, immediately have dispatchers begin the
   COOP paper/radio fallback for any calls in flight during the transition.
2. IT brings up BACKUP-CAD01 and confirms it is accepting new call entries.
3. Once BACKUP-CAD01 is confirmed up, dispatchers log ALL new calls there directly -- record
   the exact time BACKUP-CAD01 logging starts; you will need this timestamp for reconciliation
   later.
4. IT contacts the primary CAD vendor to report the outage and get an ETA; check back
   periodically rather than waiting for the vendor to proactively update.

Failback (do not skip -- this is the step most likely to be treated as "done" prematurely):
5. Once the vendor confirms primary CAD is restored AND passing its own health check, do NOT
   immediately declare the incident over. Before cutting dispatch back to primary, note the
   exact time BACKUP-CAD01 logging will stop.
6. Cut new call intake back over to primary CAD.
7. Reconcile: export every call record logged on BACKUP-CAD01 between the time logging started
   (step 3) and the time it stopped (step 6), and import/merge them into primary CAD so the
   primary system has a complete record of the incident window, not just before/after.

   number successfully imported into primary. If they don't match, do not decommission or
   idle BACKUP-CAD01 -- keep it live and treat the discrepancy as its own incident until every
   call is accounted for.
9. Only once record counts are verified and BACKUP-CAD01's data is fully reconciled into
   primary is BACKUP-CAD01 safe to leave idle again. Log the reconciliation confirmation
   before closing the incident.

What to tell a dispatcher asking "are we done?" right after cutback: no -- cutting back to
primary only restores live call intake; the incident isn't closed until the calls logged on

# CAD System Failover/Failback Runbook

## Prerequisites
- All dispatchers must be trained on backup procedures
- Backup CAD system (BACKUP-CAD01) must be fully functional and accessible
- IT staff must have administrative access to both primary and backup systems
- Communication channels must be established for coordination
- Emergency contact list for primary CAD vendor must be available

## Failover Procedure (Steps 1-4)

### Step 1: Initial Detection and Notification
- Dispatcher detects primary CAD unresponsiveness
- Dispatcher notifies IT immediately
- Dispatcher initiates COOP procedures and begins paper/radio logging

### Step 2: IT System Activation
- IT staff activates backup dispatch console (BACKUP-CAD01)
- IT confirms system is operational and accessible
- IT establishes communication with dispatcher

### Step 3: Dispatcher Transition
- Dispatcher begins logging all new calls directly into BACKUP-CAD01
- Dispatcher confirms backup system is functioning properly
- Dispatcher maintains paper/radio logs for continuity

### Step 4: Vendor Communication
- IT contacts primary CAD vendor for status update
- IT confirms vendor awareness and obtains ETA if available
- IT maintains regular status updates with dispatcher

## Failback Procedure (Steps 5-9)

### Step 5: Primary System Verification
- IT confirms primary CAD vendor reports system restoration
- IT verifies primary system passes health checks
- IT notifies dispatcher of primary system readiness

### Step 6: Critical Data Migration (Failure Point)
- **CRITICAL STEP**: Dispatcher must NOT cut over to primary without proper data handling
- **Failure Branch**: If this step is skipped or done incorrectly, data loss or duplication occurs
- **Correct Process**: 
  - IT exports all call data from BACKUP-CAD01 (14:07-16:42)
  - IT verifies data integrity of exported records
  - IT imports data into primary CAD system
  - IT confirms all backup records are properly migrated

### Step 7: System Cut Over
- Dispatcher confirms primary system is ready for live use
- IT performs final system cut over
- IT confirms new calls route to primary system

### Step 8: System Verification
- Dispatcher verifies primary system is functional
- IT confirms all migrated data is accessible
- IT ensures no duplicate or missing records

### Step 9: System Cleanup and Documentation
- **Required**: Data from BACKUP-CAD01 must be properly handled before system idle
- **Required**: All backup data must be imported into primary system
- **Required**: System must be reset to default state (remove temporary configurations, clear test data)
- **Required**: All users must be notified of completion
- **Required**: Incident documentation and lessons learned must be completed

## Specific Instructions for the 16:50 Dispatcher

**DO NOT** respond with "yes, we're done." Instead, say:

"Please wait - I need to confirm the data migration from backup system is complete and verify all records have been properly imported into the primary system. This will take approximately 10 minutes to complete, and I'll notify you when the system is fully operational and ready for normal use."

## Failure/Recovery Branch

If Step 6 fails (data migration not completed):
1. Immediately halt the cut over process
2. Notify IT immediately
3. Continue using backup system until data migration is complete
4. Document failure in incident report
5. Conduct post-incident review for process improvement

## Post-Incident Requirements
- All backup data must be imported into primary system within 30 minutes of primary system restoration
- Backup system must be reset to default configuration
- All temporary data must be purged from backup system
- Incident report must be completed and distributed to stakeholders
- Process improvements must be documented and communicated
