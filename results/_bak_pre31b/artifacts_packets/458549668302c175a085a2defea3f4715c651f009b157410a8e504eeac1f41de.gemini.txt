## Anchors

# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

### M365/AD Tenant Consolidation Change Plan: Firm A + Firm B
**Objective:** Merge Firm B into Firm A's tenant while preserving AutoCAD Xref integrity via absolute UNC paths (`\\FIRMB-FS01\Projects\...`) and maintaining zero disruption to two active permit projects with deadlines in 10 business days.

---

### 1. Core Constraints & Risk Mitigation Strategy
*   **Xref Integrity:** AutoCAD Xrefs using absolute UNC paths will break if the server name, share name, or path structure changes, or if authentication drops during an open session.
*   **UPN/Mailbox Risk:** Changing a drafter's UPN or moving their mailbox during active hours can terminate sessions, drop file handles, or break authentication to the file share, causing Xrefs to fail.
*   **Permit Deadlines:** For the next **10 business days**, the environment for Firm B users and project files must remain immutable. No changes may occur that could interrupt file access or user identity until both deadlines pass.
*   **Mitigation Strategy:** 
    *   **Path Preservation:** The UNC path `\\FIRMB-FS01\Projects\...` must be maintained indefinitely or until Xrefs are manually updated. This is achieved by migrating underlying storage while keeping the network name and share structure identical via SMB redirection or persistent aliases.
    *   **Phased Cutover:** All identity and data changes are deferred until a maintenance window after the permit deadlines.

---

### 2. Pre-Migration Preparation (Days -5 to Day 0)
*Perform all steps below before the 10-day permit window begins. These actions do not impact Firm B users.*

1.  **Target Infrastructure Build:** Provision Firm A M365/AD objects for all 45 Firm B users. Create new Firm A UPNs (e.g., `user@firmA.com`) but **do not assign** them yet.
2.  **File Share Audit:** Document the exact permission matrix on `\\FIRMB-FS01\Projects`. Identify all absolute UNC paths in use.
3.  **Path Preservation Design:** Configure Firm A's file infrastructure to support the legacy path.
    *   *Recommended Method:* Use an SMB Redirector or DNS CNAME/Alias strategy so `\\FIRMB-FS01` resolves to Firm A's new storage, or retain the legacy server name on the migrated VM/container.
    *   *Validation:* Verify from a test workstation that the redirector maintains the exact UNC path and supports reconnection after credential changes.
4.  **Mailbox Migration Prep:** Create migration batches in the M365 migration tool. Map source Firm B mailboxes to target Firm A mailboxes. Leave batches in "New" state.

---

### 3. Changes Strictly Deferred Until After Permit Deadlines
**The following changes are PROHIBITED until both permit-submission deadlines have passed:**

1.  **UPN Modification:** Changing any Firm B user's UPN from `@firmB.com` to `@firmA.com`.
2.  **Mailbox Cutover:** Moving any mailbox or changing the primary SMTP address.
3.  **File Share Path/Name Changes:** Renaming the server `FIRMB-FS01`, renaming the share `Projects`, or altering the directory structure.
4.  **Credential Rotation:** Forcing password resets or session logoffs for Firm B users.
5.  **AD Object Deletion:** Deleting any Firm B AD objects that might be referenced by group policies or local caches.

---

### 4. Post-Deadline Migration Sequence
**Execution Window:** Scheduled maintenance window (e.g., Friday 18:00 to Saturday 06:00) immediately following the final permit deadline.

#### Phase 1: File Share Migration & Path Preservation
*Goal: Move data to Firm A while keeping the UNC path functional and updating permissions for new identities.*

1.  **Quiesce File Share:** Block write access to `\\FIRMB-FS01` via GPO or share permissions. Ensure no users have open handles.
2.  **Data Migration:** Copy data to Firm A storage. Verify integrity (checksums/counts).
3.  **Implement Path Preservation:** Activate the SMB redirector/alias so `\\FIRMB-FS01` now points to Firm A storage.
4.  **Permission Migration:** Update NTFS/Share permissions on the new storage to match Firm A user groups/UPNs. Ensure legacy Firm B permissions are removed.
5.  **Validation:** Test access to `\\FIRMB-FS01` using a Firm A admin account and a Firm A user account. Verify an AutoCAD drawing with an Xref loads successfully.
6.  **Decommission Source:** Shut down old Firm B file server (keep offline for rollback).

#### Phase 2: Mailbox & Identity Migration
*Goal: Move mailboxes and switch UPNs without breaking file access.*

1.  **Submit Migration Batches:** Start Firm B mailbox migration batches to Firm A. Monitor for completion.
2.  **Verify Mailbox Sync:** Confirm all items are synced and target mailboxes are ready.
3.  **UPN Cutover:**
    *   Update UPNs for Firm B users to `@firmA.com`.
    *   Update proxy addresses.
4.  **Client Configuration Push:** Distribute new sign-in instructions. Since the UNC path `\\FIRMB-FS01` is preserved and permissions are updated, users logging in with new UPNs will seamlessly access files. Xrefs will refresh successfully upon re-authentication.
5.  **Communication:** Notify users at window close that they must log off and back in to apply changes.

---

### 5. Rollback Approach for Mailbox Migration Failure
**Scenario:** A migration batch fails partway (e.g., stuck in "Syncing" or error state) or post-migration validation reveals data corruption.

1.  **Isolate Failure:** 
    *   Immediately halt all subsequent batches.
    *   Identify the specific failed batch or users.
2.  **Rollback Execution:**
    *   **Stop Migration:** Run `Stop-MigrationBatch -Identity <BatchID>` (or equivalent tool command).
    *   **Reset State:** Use `Update-MigrationUser` to reset failed users to "Idle" or "New".
    *   **UPN Reversion:** If UPNs were already changed for the batch, revert the UPN suffix to `@firmB.com` for affected users immediately to restore access to Firm B systems.
    *   **Source Integrity Check:** Verify the source mailbox was not modified. Modern migration tools (IMAP/MAPI/Modern) are read-only on source; however, verify no items were inadvertently flagged.
3.  **Recovery Decision:**
    *   *Transient Error:* Retry the batch after the root cause (e.g., connectivity, quota) is resolved.
    *   *Persistent Error:* Roll back the entire batch to Firm B tenant. Isolate affected users for manual migration or separate troubleshooting after hours.
4.  **Validation:** Confirm rolled-back users can authenticate with original UPNs and access `\\FIRMB-FS01` without interruption.

---

### 6. Summary of Critical Success Factors
*   **Immutable UNC:** The absolute priority is that `\\FIRMB-FS01\Projects\...` remains valid. Technical redirection must be used if the underlying storage moves.
*   **Deadlines First:** No work on Firm B identities or files occurs until day 10+ is confirmed.
*   **Out-of-Hours Execution:** All risky changes occur when no users have open drawings.
*   **Path-First Sequence:** Files are migrated and permissions updated *before* UPNs are switched, ensuring that when users log in with new credentials, the file share is already accessible with the correct path and permissions.

### M365/AD Tenant Consolidation Change Plan

#### **Objective**
Merge Firm B (45 users) into Firm A's M365/AD tenant without breaking AutoCAD Xref paths during the 10-day permit-deadline period. Xrefs use absolute UNC paths (e.g., `\\FIRMB-FS01\Projects\...`), and changing file shares or UPNs during active work risks breaking links.

---

### **Sequencing of Migration Activities**
#### **Phase 1: Before Permit Deadlines (Next 10 Business Days)**
**Goal:** Stabilize Firm B’s environment and prepare for minimal-risk changes.  
**Actions:**  
1. **Mailbox Migration (UPN Change) – NOT PERMITTED**  
   - **DO NOT migrate mailboxes or change UPNs** for Firm B users.  
   - **Reason:** Changing UPNs may trigger AutoCAD profile updates (e.g., home drive mappings), risking Xref breaks during active work.  

2. **File Share Migration – NOT PERMITTED**  
   - **DO NOT migrate or alter the file share** (e.g., server name, path, or UNC structure).  
   - **Reason:** Direct UNC path changes will break Xref links immediately.  

3. **Preparation Tasks:**  
   - **AD Integration:**  
     - Create an OU structure in Firm A’s AD for Firm B users (e.g., `OU=FirmB, DC=Firma, DC=com`).  
     - Add Firm B users to this OU with their **existing UPNs** (e.g., `user@firmb.local`).  
   - **M365 Configuration:**  
     - Add Firm B’s domain (e.g., `firmb.local`) as an accepted domain in Firm A’s M365 tenant.  
     - Provision licenses for Firm B users in Firm A’s tenant without assigning mailboxes yet.  
   - **File Share Assessment:**  
     - Inventory all Xref-impacted drawings and confirm they use `\\FIRMB-FS01\...`.  
     - Verify no temporary redirects (e.g., DFS) are in place.  

---

#### **Phase 2: After Permit Deadlines (Post-Day 10)**
**Goal:** Execute migrations once critical work is complete.  
**Actions:**  
1. **File Share Migration (Must Happen AFTER Deadlines)**  
   - **Step 1:** Migrate data from `\\FIRMB-FS01\Projects\...` to a new Firm A file server (e.g., `\\FIRMA-FS01\Projects\...`).  
   - **Step 2:** Update DNS to create a **CNAME alias** `FIRMB-FS01` pointing to `FIRMA-FS01`.  
     - **Result:** UNC paths (e.g., `\\FIRMB-FS01\...\`) resolve to the new server without breaking Xrefs.  
   - **Step 3:** After validation, decommission `FIRMB-FS01`.  

2. **Mailbox Migration (UPN Change) – Must Happen AFTER Deadlines**  
   - **Step 1:** Update UPNs in AD for all Firm B users to Firm A’s domain (e.g., `user@firma.com`).  
   - **Step 2:** Migrate mailboxes to Firm A’s Exchange Online using **batched staged migration** (e.g., 10 users/batch).  
   - **Step 3:** Update user profiles to reflect new UPNs.  
   - **Note:** AutoCAD Xrefs are **not affected** as UNC paths remain unchanged (via CNAME).  

---

### **Critical Changes POST-Deadlines Only**
1. **File Share Migration:**  
   - **MUST WAIT:** Until both permit deadlines pass.  
   - **Reason:** Any path/server change breaks Xrefs immediately.  
   - **Solution:** Use a CNAME alias to preserve UNC paths transparently.  

2. **UPN/Domain Migration:**  
   - **MUST WAIT:** Until deadlines pass.  
   - **Reason:** UPN changes may trigger AutoCAD profile refreshes during open files, risking Xref breaks.  
   - **Solution:** Change UPNs after deadlines to minimize user impact.  

---

### **Mailbox Migration Rollback Plan**
**Scenario:** A mailbox batch fails mid-migration (e.g., 5 of 10 users migrated).  
**Rollback Steps:**  
1. **Halt Migration:** Suspend the batch immediately.  
2. **Isolate Affected Users:**  
   - For **successfully migrated users**:  
     - Disable their Office 365 accounts.  
     - Restore their mailboxes to on-prem Exchange via **backup/restore** (if available) or **re-creation**.  
   - For **failed users**:  
     - Leave them in on-prem Exchange; no action needed.  
3. **Revert AD Changes:**  
   - Reset UPNs for migrated users to their original `@firmb.local` values.  
4. **Verify Connectivity:**  
   - Ensure all Firm B users can access on-prem Exchange with old credentials.  
5. **Retry Later:**  
   - Fix underlying issues (e.g., permissions, licensing).  
   - Re-attempt migration in a new batch.  

**Tools for Rollback:**  
- **Exchange Management Shell:** Use `Disable-Mailbox` and `New-MailboxRestoreRequest`.  
- **AD Users & Computers:** Manually reset UPNs.  
- **Backup Solutions:** Recover user data from on-prem backups.

### 5.  Rollback Approach – If a Batch Fails Mid‑Way  

| Failure Point | Immediate Action | Rollback Procedure | Owner |
|---------------|------------------|-------------------|-------|
| **Mailbox migration batch fails (e.g., 3‑rd user cannot be moved)** | 1. **Stop the migration job** (Exchange admin console → Cancel). <br>2. **Mark the affected user(s) as “staged‑failed”** in the migration report. | - **Restore the source mailbox** from the **exported PST** that was generated during the staging phase (`New‑MigrationUser –Identity <user> –IsStaged $true`). <br>- Re‑import the PST into the original on‑prem mailbox using `Import‑Mailbox`. <br>- Verify mailbox integrity (no missing items). | Exchange Admin |
| **File‑share copy fails (missing files, checksum mismatch)** | 1. **Pause the sync job** (stop the scheduled Robocopy). <br>2. **Re‑run the copy with `/MIR /COPYALL /R:5 /W:5`** to retry only the failed files. | - If the source share becomes unavailable, **re‑mount a read‑only snapshot** of the original volume (VSS snapshot) and copy back the missing files. <br>- Keep the original share online; do **not** delete any files until the migration is fully successful. | File‑Share Admin |
| **AD attribute change breaks login** (e.g., `mail` attribute not updated correctly) | 1. **Re‑apply the original `mail` attribute** from the backup AD export. | - Use `Set-ADUser -Identity <user> -EmailAddress <oldSMTP>` to revert. <br>- Force a replication update (`repadmin /syncall`). | AD Admin |
| **Unexpected Outlook/OneDrive sync error after mailbox move** | 1. **Re‑connect the user to the original on‑prem mailbox** (re‑add the mailbox to Outlook as an additional account, then disable the migrated account). | - Delete the migrated mailbox from Exchange Online (`Remove‑Mailbox`). <br>- Re‑enable the original mailbox (`Enable‑Mailbox`). | Exchange Admin |

**Key rollback principle:** *Everything that has been staged must be reversible.*  
- **Staged mailbox moves** always generate a **PST export** that can be re‑imported.  
- **File‑share copies** are performed *read‑only*; the source remains untouched until a successful commit.  
- **AD changes** are applied in a *test OU* first; any change can be undone by restoring the original `user` object from a backup (e.g., PowerShell `Restore-ADObject`).

## 4.  Roll‑Back Approach (Mailbox Migration)

A rollback may be required **only** if a migration batch fails **mid‑way** (e.g., network outage, corrupted move request). The plan assumes **no data loss** because the source mailboxes remain intact until the batch is *completed*.

### 4.1.  Conditions to Trigger Roll‑Back
- **> 5 %** of users in a batch show status **Failed** for > 30 minutes.  
- **Critical error** logged (e.g., “Mailbox size limit exceeded”, “Authentication failure”).  
- **User impact** confirmed (engineers cannot receive critical project emails).  

### 4.2.  Roll‑Back Steps (Executed within 1 hour)

| Step | Owner | Command / Action | Outcome |
|------|-------|------------------|---------|
| **R1** | Exchange Admin | **Suspend** the batch: `Suspend-MigrationBatch -Identity "B-Merge-<Batch#>"`. | Prevents further moves. |
| **R2** | Exchange Admin | **Remove** all **in‑progress** move requests: `Get-MigrationUser -BatchId "B-Merge-<Batch#>" | Where Status -eq "Syncing" | Remove‑MigrationUser`. | Target mailboxes stay empty. |
| **R3** | Exchange Admin | **Clear** the batch: `Remove-MigrationBatch -Identity "B-Merge-<Batch#>" -Force`. | Batch metadata removed. |
| **R4** | AD Team | **Re‑enable** the source mailboxes (if they were temporarily disabled): `Set-User -Identity user@firmB.com -RemotePowerShellEnabled $true`. | Users can log back into the source tenant. |
| **R5** | IT Support | **Notify** affected users: “Your mailbox move has been cancelled; please continue using your existing mailbox.” | Users aware and can resume work. |
| **R6** | Change Advisory Board | **Root‑cause analysis** (review logs). If fixable (e.g., increase mailbox quota), apply fix and **re‑run** the batch after **30 min**. | Issue resolved, migration proceeds. |

### 4.3.  Full Roll‑Back (Extreme Case)

If a batch completes but later a critical issue emerges (e.g., data corruption), perform a **full mailbox export/import**:

1. **Export** the target mailboxes to PST (`New-MailboxExportRequest`).  
2. **Delete** the corrupted target mailboxes (`Remove-Mailbox`).  
3. **Re‑import** the original PST files into the source mailboxes (`New-MailboxImportRequest`).  
4. **Re‑sync** Azure AD Connect (if needed) to ensure the source UPNs remain active.  

All steps are performed **offline** (no user impact) and validated before returning the mailbox to production.

### **M365/AD Tenant Consolidation Change Plan: Firm A + Firm B**

**Objective:** Absorb Firm B (45 users) into Firm A's Microsoft 365/AD tenant while maintaining uninterrupted access to Firm B's ActiveCAD projects during critical permit submission windows.

**Critical Constraint Analysis:**
*   **Xref Stability:** AutoCAD Xrefs using absolute UNC paths (`\\FIRMB-FS01\...`) will break if the share name, UNC path, IP address, or underlying file server changes.
*   **Deadlines:** Two projects have permit submission deadlines in **10 business days**. Xref integrity is mandatory during this period.
*   **Mailbox/UPN Risk:** While UPN changes do not inherently alter UNC paths, they can disrupt AD authentication sessions. If a drafter's AD object is moved or disabled while they have a file open, the session may drop, potentially causing unsaved file corruption or lock conflicts.

---

### **1. Migration Sequence**

**Strategy:** Mailbox/UPN migration can proceed **before or during** the deadline window (with caution), as it does not impact UNC paths. File share migration is **blocked** until after both permit deadlines pass to protect Xref links.

| Phase | Timing | Action | Impact on Xrefs |
| :--- | :--- | :--- | :--- |
| **Phase 1** | **Days -3 to -1** | **Mailbox & UPN Migration Batch 1 (15 Users)**<br>- Map Firm B AD accounts to Firm A.<br>- Migrate mailboxes using Exchange Online Mailbox Migration Service (EOMS) or approved third-party tool.<br>- Update UPNs (e.g., `u@firmb.com` → `u@firma.com`).<br>- **Verification:** Test login, Outlook sync, and network authentication. | **Safe.** UNC paths remain static. Risk mitigated by keeping old accounts enabled until new sync is verified. |
| **Phase 2** | **Day -1** | **Mailbox & UPN Migration Batch 2 & 3 (Remaining 30 Users)**<br>- Repeat migration steps.<br>- **Checkpoint:** All mailboxes active in Firm A; Firm B mailboxes in "Pause" or disabled state. | **Safe.** |
| **Phase 3** | **Days 1–10** | **PERMIT DEADLINE WINDOW**<br>- **FIRM B SHARE: LOCKED.**<br>- No path changes, no share renaming, no IP changes.<br>- Engineers continue working on active Xrefs. | **Protected.** UNC stability guaranteed. |
| **Phase 4** | **Day 11+** | **File Share Migration & Xref Consolidation**<br>- Execute share migration.<br>- Repair Xrefs.<br>- Decommission legacy assets. | **Post-Critical.** Xref repair required. |

### **3. Rollback Approach: Mailbox Migration**

If a batch of mailbox migrations fails partway through (e.g., sync error, AD corruption, or user impact during the deadline window), execute the rollback immediately to ensure business continuity.

**Prerequisites:**
*   The migration tool must support "Pause" functionality.
*   Firm B AD accounts must remain enabled until rollback or full success is verified.

**Rollback Steps:**
1.  **Stop Migration:** Immediately halt the migration tool to prevent partial states.
2.  **Identify Failed Users:** Generate a report of users whose mailboxes were moved but failed to verify.
3.  **Reverse AD Changes:**
    *   For failed users, revert the UPN change in Active Directory back to the original Firm B UPN.
    *   Re-enable the original Firm B AD account object if it was disabled.
4.  **Restore Mailbox State:**
    *   Using the migration tool, perform a **Reverse Sync** or **Undo** operation to restore the mailbox to the original exchange mailbox in Firm B.
    *   If the tool lacks undo, manually re-provision the old mailbox and disable the new one.
5.  **Verification:**
    *   Confirm the user can log in with the original credentials and UPN.
    *   Verify email flow is restored.
6.  **Root Cause & Resume:**
