# Panel Judge -- Battery 1 Business Task Scoring

## Role

You are one of three independent judges (Claude, Codex, Gemini) scoring a set
of blinded answers to a single MSP-realistic business task. You do not know
which model produced which answer -- every answer below is labeled only by a
letter. Do not try to guess model identity from writing style. Score only
what is on the page against the anchors below.

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# Knowledge Management -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The runbook or document is testable: a newcomer could follow it step by step and reach the stated outcome without needing undocumented tribal knowledge. Prerequisites are listed up front, failure or rollback branches are included for steps that can go wrong, and a currency or ownership signal (last verified, owned by) is present when the prompt supports it.
Example character: numbered steps with prerequisites stated first, a rollback note on the one risky step, and a last-verified date.

## 7 -- Strong
The document is mostly step-by-step and usable as a runbook, but is missing one prerequisite check or a failure-branch note for a step that could plausibly fail. Nothing here requires guesswork to follow.
Example character: a clear numbered procedure that omits what to do if the third step fails.

## 5 -- Adequate
The content is a correct-gist prose description of the process rather than an executable, testable runbook -- a new reader would need to reverse-engineer the actual steps.
Example character: a paragraph explaining how the process generally works, without numbered, followable steps.

## 3 -- Weak
The document skips steps a newcomer would need, silently assumes undocumented tribal knowledge, and gives no ownership or currency signal at all.
Example character: a procedure that jumps from step one to step four with an unstated step in between.

## 0 -- Unusable
References fabricated tools, systems, or menu paths that do not exist, or gives a dangerously wrong sequence for a risky operation. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Steps that silently assume undocumented tribal knowledge.
- Fabricated tool, system, or menu-path names presented as real.
- No failure or rollback branch for a step that can fail destructively.
- Prose narrative presented as a runbook instead of testable numbered steps.

## Unit-specific excellence markers
- Numbered steps a newcomer could execute unaided.
- Prerequisites listed explicitly up front.
- Failure or rollback branch given for risky steps.
- Currency or ownership signal (last-verified, owner) included when supported by the prompt.


## Task

The task given to every model in this cohort:

Your MSP runs a weekly backup-verification process for a structural-engineering firm's
project file server, which stores stamped structural calculation packages and construction
drawings. Most state licensing boards require engineers to be able to produce these stamped
records for a statute-of-repose period (commonly a decade or more after a project finishes)
in case a professional-liability claim is filed years later -- so a silently failed backup
here isn't just an inconvenience, it can leave the firm unable to defend a claim long after
the project is closed out. Right now, verification is informal: whoever is free on Friday
afternoon glances at a couple of recent filenames and calls it done.

Write a Standard Operating Procedure, as a numbered list, for the recurring weekly
backup-verification process. It must: confirm the backup job actually completed rather than
just started, include a real restore-test of a sample file rather than only checking a
completion log, and state exactly what to do if the same backup job fails verification two
weeks in a row.

### Standard Operating Procedure: Weekly Backup Verification  
*For Structural Engineering Firm's Project File Server*  

**Purpose**: To ensure the integrity and recoverability of critical project files (stamped calculations, construction drawings) during the statute-of-repose period.  

---

**Procedure**:  
1. **Verify Backup Completion**  
   - Access the backup system dashboard (e.g., Veeam, Commvault) within 2 hours of the scheduled backup completion (typically Friday 6:00 AM).  
   - Confirm the job status for **all backup jobs** (full/incremental) displays **"Completed Successfully"** with no alerts or errors. Do not accept partial or "started" statuses as verification.  

2. **Select Sample Files**  
   - Choose **three files** modified/created in the past 7 days:  
     - One stamped structural calculation package (e.g., `ProjectA_Calculations_v3.pdf`).  
     - One construction drawing (e.g., `ProjectB_Drawings_Site_Plan.dwg`).  
     - One high-risk file (e.g., recently sealed permit document).  
   - Document filenames and original file sizes/sha256 hashes in the verification log.  

3. **Perform Restore Test**  
   - Initiate a **manual restore** of each sample file to a temporary test directory (e.g., `\\testserver\restore_test`) using the backup software.  
   - Compare restored files to originals using:  
     - **File size verification** (match to original size).  
     - **Checksum validation** (run `certutil -hashfile` on Windows or `sha256sum` on Linux to match original SHA256 hash).  
     - **Content spot-check**: Open 1-2 pages of the PDF/dwg to confirm readability and critical data (e.g., engineer stamp, revision notes).  

4. **Document Results**  
   - Record in the **Weekly Backup Verification Log**:  
     - Date/time of verification.  
     - Backup job IDs and completion status.  
     - Filenames, hashes, and restore test results (pass/fail).  
     - Verifier’s name and timestamp.  
   - If **any step fails**, document the error (e.g., "Restore failed for `ProjectB_Drawings_Site_Plan.dwg`: checksum mismatch").  

5. **Immediate Actions for Failure**  
   - If **backup completion fails** (Step 1) or **restore test fails** (Step 3):  
     - Notify the backup administrator and IT manager within 30 minutes.  
     - Escalate to the structural engineering firm’s lead engineer if files are unrecoverable by end-of-day.  
     - Initiate an ad-hoc backup and restore test within 24 hours.  

6. **Handle Consecutive Failures**  
   - If **the same backup job fails verification for two consecutive weeks**:  
     - **Day 1**: Backup administrator must conduct a **root-cause analysis** and submit a written report to the firm’s IT director within 48 hours.  
     - **Day 3**: MSP must implement a **corrective action plan** (e.g., replace failing storage, reconfigure backup jobs).  
     - **Day 5**: MSP must perform a **full restore test** of all critical files and provide a signed certification of success to the firm.  
     - **Ongoing**: The failing backup job is **temporarily suspended** until the root cause is resolved; alternate backup systems (e.g., cloud) activated.  

7. **Final Verification**  
   - Only sign off on the verification log if **all steps (1–3) pass**.  
   - Retain logs for **10 years** in compliance with statute-of-repose requirements.

**Standard Operating Procedure (SOP) – Weekly Backup‑Verification for Project File Server**  
*Prepared for: Structural‑Engineering Firm – Records Management / IT Services*

### 1. Purpose  
Ensure that the weekly backup of the **Project File Server** (stamped calculation packages, construction drawings, and associated metadata) has **actually completed**, is **intact**, and can be **restored** on demand. This protects the firm’s ability to produce required records for the statutory‑repose period and to defend professional‑liability claims.

### 2. Scope  
Applies to the **weekly incremental backup job** (Job ID BKP‑PROJ‑W‑01) that runs every Friday night at 22:00 UTC and the **full‑weekend restore‑test** performed the following Saturday. The SOP covers all staff designated as **Backup Verification Technicians (BVTs)**.

### 3. Definitions  
| Term | Meaning |
|------|---------|
| **Backup Job Log (BJL)** | The detailed log file generated by the backup engine (e.g., Veeam, NetBackup, Commvault). |
| **Job Completion Flag (JCF)** | A status entry in the BJL indicating “COMPLETED‑SUCCESSFULLY” with a checksum verification. |
| **Sample File Set (SFS)** | A curated list of 10 files representing the diversity of data (large DWG, PDF, Excel, .calc, .zip, etc.) and spanning the last 12 months. |
| **Restore Verification Report (RVR)** | A document that records the restore test results, timestamps, and any anomalies. |
| **BVT** | Backup Verification Technician – employee assigned to perform the SOP steps. |
| **Escalation Lead (EL)** | Senior IT Manager or Records‑Compliance Officer who receives failure escalations. |

### 4. Roles & Responsibilities  

| Role | Responsibility |
|------|----------------|
| **BVT (Primary)** | Execute steps 5‑13, log results, and notify EL of any failures. |
| **BVT (Secondary/Backup)** | Verify the primary BVT’s work by cross‑checking the RVR before signing off. |
| **Backup System Administrator** | Ensure backup schedules, retention policies, and logging are correctly configured; provide log‑access credentials. |
| **Escalation Lead (EL)** | Approve remediation actions, coordinate with legal/compliance if required, and document the incident. |

### 5. Pre‑Verification Checks (Friday 22:30 – 23:00 UTC)  

1. **Confirm Scheduler Execution**  
   - Open the backup console and verify that **Job ID BKP‑PROJ‑W‑01** shows a **Start Time** ≤ 22:15 UTC and **End Time** ≤ 23:00 UTC.  
   - If the job shows “Running” after 23:00 UTC, wait a maximum of 30 minutes; if still active, proceed to **Section 9 – Failure Handling**.

2. **Validate Job Completion Flag (JCF)**  
   - In the **Backup Job Log (BJL)** locate the entry for the current run (date stamp).  
   - Confirm the status line reads **“COMPLETED‑SUCCESSFULLY – Checksum Verified”**.  
   - Record the **checksum hash** (e.g., SHA‑256) displayed for the job summary.

3. **Check Log Integrity**  
   - Verify that the BJL file size is > 1 KB and that the **last line** ends with **“END‑OF‑LOG”** (or the vendor‑specific terminator).  
   - If the log is truncated or missing, treat as a failure (go to Section 9).

4. **Document Preliminary Findings**  
   - Open the **Weekly Backup Verification Sheet (WBVS‑YYYY‑WW)** (shared Excel/[model] Sheet).  
   - Enter: Date, Job ID, Start/End Times, JCF status, checksum, and any notes.  

### 6. Sample File Set Selection (Saturday 08:00 – 08:15 UTC)  

5. **Generate SFS List**  
   - Run the supplied PowerShell script `Select-BackupSample.ps1` which queries the file server and returns a CSV with 10 files meeting the following criteria:  
     - **2** large (> 100 MB) DWG files from the most recent project.  
     - **2** PDF drawings older than 5 years.  
     - **2** Excel calculation sheets (different projects).  
     - **1** compressed archive (.zip) containing a full set of calculations.  
     - **1** a file with special characters in the name.  
     - **1** a file stored on a secondary volume (if applicable).  
     - **1** a file created exactly 10 years ago (to test long‑term retention).  

6. **Record SFS**  
   - Save the CSV as `SFS_YYYYWW.csv` in the verification folder and attach the list to the WBVS entry.

### 7. Restore‑Test Procedure (Saturday 08:30 – 09:30 UTC)  

7. **Create Isolated Restore Destination**  
   - On the **Restore Test Server (RTS)**, create a new empty directory: `C:\RestoreTest\YYYYWW`.  
   - Ensure the RTS is **offline** from production networks to avoid accidental overwrite.

8. **Initiate Restore for Each Sample File**  
   - Using the backup console, select **“Restore → Files”**, point to the **SFS_YYYYWW.csv** list, and choose **“Restore to custom location” → C:\RestoreTest\YYYYWW**.  
   - Enable **“Verify integrity after restore”** (most platforms will recompute checksum against the stored hash).  

9. **Validate Restored Files**  
   - For each file, confirm:  
     - **File exists** in the destination folder.  
     - **File size** matches the original (within 1 KB tolerance).  
     - **Checksum** (run `Get-FileHash -Algorithm SHA256`) equals the backup’s stored hash (recorded in the BJL).  
     - **File opens** with its native application (e.g., AutoCAD for DWG, Adobe Reader for PDF).  
   - Document any discrepancy in the **Restore Verification Report (RVR)** with screenshot evidence.

10. **Clean‑up**  
    - After verification, **securely delete** the restored files from the RTS using `sdelete` (or equivalent) to prevent data leakage.  
    - Archive the RVR (PDF) in the shared folder `\\BackupVerification\Archives\YYYYWW`.

### 8. Sign‑off & Documentation (Saturday 09:45 – 10:00 UTC)  

11. **Primary BVT Sign‑off**  
    - In the WBVS entry, change **“Status”** to **“PASS”** if all 10 files restored correctly, or **“FAIL”** if any file failed.  
    - Attach the RVR PDF.

12. **Secondary BVT Review**  
    - The secondary BVT reviews the WBVS entry, the RVR, and the attached logs.  
    - If they concur, they add their **digital signature** (typed name + timestamp) in the **“Reviewed‑by”** column.  

13. **Notification**  
    - If **PASS**, send an automated email (distribution list: IT‑Ops, Records‑Mgmt, Compliance) with subject: “Weekly Backup Verification – Week WW – PASS”.  
    - If **FAIL**, send an email with subject: “Weekly Backup Verification – Week WW – FAIL – Immediate Action Required” to the same list **and** to the **Escalation Lead (EL)**.

### 9. Failure Handling  

#### 9.1 First‑Week Failure (Week N)  

14. **Immediate Remediation**  
    - EL coordinates with the Backup System Administrator to **re‑run** the failed backup job manually, targeting the same date range.  
    - Perform steps **5‑13** again after the re‑run.  

15. **Root‑Cause Logging**  
    - Document the cause (e.g., network outage, storage full, permission error) in the **Incident Log (IL)** with a unique ID (e.g., **INC‑YYYYWW‑01**).  

#### 9.2 Consecutive Failure (Week N + 1)  

16. **Escalation Protocol**  
    - If the same **Job ID BKP‑PROJ‑W‑01** fails verification **two weeks in a row**, the EL must **escalate** to senior management and the firm’s legal/compliance officer within **2 hours** of the second failure notice.  

17. **Emergency Backup Measures**  
    - Deploy an **alternative backup method** (e.g., manual copy to an external NAS or cloud bucket) for all files modified in the affected week.  
    - Record the alternative backup details in the IL and attach verification evidence (checksum list).  

18. **Comprehensive Investigation**  
    - Initiate a **formal post‑mortem** (minimum 48 hours) covering:  
      - Backup infrastructure health (storage array, network, software version).  
      - Change‑management records for the period.  
      - Security events (e.g., ransomware alerts).  
    - Produce a **Post‑Failure Report (PFR)** and circulate to: CIO, Records‑Compliance Officer, Legal Counsel, and the firm’s Board (if required).  

19. **Remediation Approval & Implementation**  
    - EL presents the PFR and recommended corrective actions (hardware replacement, software patch, configuration change) to senior management.  
    - Upon approval, the Backup System Administrator implements the fix, performs a **full restore test** of a recent project, and documents the outcome.  

20. **Reset Verification Cycle**  
    - After successful remediation, the weekly verification resumes as normal starting the next scheduled Friday.  
    - The IL entry is closed with status **“Resolved – Root Cause Fixed”** and a reference to the PFR.  

### 10. Records Retention  

21. **Retention Period**  
    - All verification artifacts (WBVS, RVR, IL, PFR) must be retained **minimum 7 years** or longer if dictated by state licensing board requirements.  

22. **Secure Storage**  
    - Store records in the firm’s **Records Management System (RMS)** with **read‑only** access for compliance auditors and **encryption at rest** (AES‑256).  

### 11. Audit & Continuous Improvement  

23. **Quarterly Review**  
    - The IT‑Ops Manager conducts a quarterly audit of the verification logs to ensure SOP adherence and to identify trends (e.g., increasing restore times).  

24. **SOP Update**  
    - Any change to backup technology, retention policy, or regulatory requirement triggers an SOP revision, documented with version number and change log.

*Purpose:*

2.2. **Exit Code** – Check the job’s exit code; it must be `0` (success).  
2.3. **Log Verification** – Locate the backup log file (e.g., `/var/log/backup/PFServer‑20240707.log`). Search for a line that ends with `SUCCESS` or `Completed`.  
2.4. **Timestamp Check** – Ensure the completion timestamp is within the expected window (±30 minutes of scheduled end time).  

If any of the above checks fail, **abort** the verification process and proceed to Step 9.

### 3. Validate Backup File Integrity
3.1. **File Size** – Confirm the backup archive’s size is greater than zero bytes.  
3.2. **Checksum (Optional but Recommended)** – If a baseline checksum is stored, compare it with the new backup’s checksum (e.g., using `sha256sum`).  

### 4. Select a Sample File for Restore Test
4.1. Choose a recent, high‑value file from the backup set (e.g., a stamped structural calculation package or drawing).  
4.2. Record its full path and its SHA‑256 hash *before* backup.  
4.3. Store the file name in the verification log (see Step 7).

5.2. **Restore Command** – Execute the backup software’s restore function for the selected file.  
5.3. **Restore Log** – Verify that the restore process reports *Success* and note the restoration timestamp.  

### 6. Verify the Restored File
6.1. **Checksum Match** – Calculate the SHA‑256 hash of the restored file and compare it to the pre‑backup hash.  
6.2. **File Size** – Ensure the restored file size matches the original.  
6.3. **Open Test** – Open the file in the appropriate application to confirm it is not corrupted.  

If any of these checks fail, **abort** the verification process and proceed to Step 9.

### 7. Document Verification Results
7.1. Create a verification entry in the weekly log (e.g., `PFServer-WeeklyBackup-20240707-Verification.txt`).  
7.2. Record:  
- Backup job ID & run date/time  
- Scheduler status & exit code  
- Backup file size & checksum (if used)  
- Sample file path, pre‑backup hash, restored file path, restored hash  
- Verification outcome (PASS/FAIL)  
- Any anomalies noted  

### 8. Clean Up Test Environment
8.1. Delete the restored file and any temporary directories created for the test.  
8.2. Verify that no residual test data remains on the test server.

**SOP-04: Weekly Backup Verification Procedure**
**Client:** Structural Engineering Firm (Project File Server)
**Owner:** MSP Backup Administrator
**Frequency:** Weekly (Friday)

3.  **Execute Real Restore Test.** Select exactly one file from the current week's backup: a stamped structural calculation package or construction drawing created within the last seven days.
