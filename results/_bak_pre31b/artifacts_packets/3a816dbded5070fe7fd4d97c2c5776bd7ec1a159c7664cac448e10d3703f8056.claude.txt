## Role

You are one of three independent judges (Claude, Codex, Gemini) scoring a set
of blinded answers to a single MSP-realistic business task. You do not know
which model produced which answer -- every answer below is labeled only by a
letter. Do not try to guess model identity from writing style. Score only
what is on the page against the anchors below.

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# Cybersecurity -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Severity is triaged correctly against the actual impact described, response actions follow containment before eradication before recovery, and any CVE, CWE, or ATT&CK reference used is real and correctly applied (never invented). Evidence-preservation is called out before disruptive remediation, and breach-notification or compliance timelines are flagged when the scenario implies regulated or sensitive data. The answer is calibrated about what needs live forensics versus what can be assessed from the facts given.
Example character: a triaged action list that isolates the affected system first, preserves logs, then patches, with the real CVE cited only where it is genuinely relevant.

## 7 -- Strong
The response plan is sound and correctly ordered (containment before eradication), and is directly usable by a responder. References to standards or CVEs are generic rather than specific, or evidence-preservation/notification timing gets only a light mention. Severity is judged reasonably even if not formally scored.
Example character: a correct incident-response sequence that never names a specific CVE or ATT&CK technique even where the prompt supports one.

## 5 -- Adequate
The advice reads as a generic security checklist (patch systems, enable MFA, monitor logs) that is directionally correct but not prioritized by the actual severity or tailored to the specific incident described.
Example character: a list of general hardening steps with no sense of which one matters most given the described exposure.

## 3 -- Weak
The response gets the ordering wrong (patches or removes an attacker's access before containing them), misjudges severity, or pads the answer with boilerplate ("enable a firewall") that does not engage the specific scenario.
Example character: jumps straight to "eradicate the malware" on an active intrusion without isolating the host first.

## 0 -- Unusable
Cites a fabricated CVE, CWE, or CVSS score as if verified, or recommends actively dangerous steps (disable logging, do not isolate an active breach) as sound practice. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Fabricated CVE, CWE, or CVSS identifiers presented as real.
- Eradication or patching recommended before containment on an active incident.
- Recommending disabling logging or otherwise destroying evidence.
- Ignoring implied breach-notification or regulatory timelines when sensitive data is involved.
- Treating every finding as equally critical with no severity differentiation.

## Unit-specific excellence markers
- Severity correctly triaged and prioritized against the described impact.
- Containment-before-eradication-before-recovery ordering respected.
- Real, correctly-applied CVE/CWE/ATT&CK references where relevant.
- Evidence-preservation explicitly called out.
- Notification or compliance timeline awareness when data exposure is implied.

### Prioritized Remediation Plan

**Priority 1: Secure Privileged Accounts (Global Admin MFA)**
*   **Finding:** 7 of 9 Global Administrator accounts do not have MFA enrolled.
*   **Risk:** Critical. Global Admins have unrestricted access to the tenant. Without MFA, these accounts are prime targets for credential stuffing, password spraying, and phishing. Compromise of a single unsecured Global Admin results in total tenant takeover.
*   **Action:** Immediately enforce Multi-Factor Authentication (MFA) on all Global Administrator accounts. Review the necessity of all 9 accounts; decommission or downgrade privileges where possible to adhere to the principle of least privilege. Enable "Secure Defaults" or equivalent baseline policies only after CA is verified, or ensure a CA policy targeting Global Admins is active.

**Priority 2: Implement Conditional Access & Block Legacy Authentication**
*   **Findings:** Security Defaults OFF; No Conditional Access policies; Legacy authentication (POP3, IMAP, EAS) enabled tenant-wide.
*   **Risk:** Critical/High. The absence of Conditional Access (CA) and Security Defaults leaves the tenant without baseline protections. Enabling legacy authentication allows clients to bypass MFA entirely, facilitating password spraying and credential theft. This directly enables the exploitation of unsecured admin accounts (Priority 1).
*   **Action:** Deploy a **Conditional Access policy** to block legacy authentication for all users (or specific groups if business-critical legacy apps require testing). This closes the gap for both the lack of CA and the legacy auth exposure. Review the "Sign-in logs" and "Legacy auth reports" prior to enforcement to assess potential impact, then set the policy to "Block" for production.

**Priority 3: Remediate CVE-2023-23397 (Outlook Zero-Click Vulnerability)**
*   **Finding:** Outlook patch level unverified; CVE-2023-23397 patched March 2023.
*   **Risk:** High. CVE-2023-23397 is a zero-click vulnerability triggered via malicious calendar reminder sounds (often delivered via EWS). Successful exploitation allows an attacker to relay NTLM credentials to gain unauthorized access. While identity controls (P1/P2) mitigate impact, the zero-click nature allows immediate foothold acquisition.
*   **Action:** Immediately deploy the March 2023 Patch Tuesday updates (or later) to all Outlook endpoints. Verify deployment via endpoint management tools. Prioritize devices with exposure to untrusted email or calendar invites.

**Priority 4: Publish DMARC Record**
*   **Finding:** SPF exists; DMARC not published.
*   **Risk:** Medium. While SPF validates the sender domain, the absence of DMARC means the domain cannot reject or quarantine spoofed emails, and the organization receives no forensic reporting on phishing attempts.
*   **Action:** Publish a DMARC TXT record for the domain. Begin with a `p=none` policy to monitor alignment and identify legitimate senders, then progress to `p=quarantine` and `p=reject` once legitimate traffic is verified.

### 1. Control to Close the Conditional Access / Legacy‑Auth Gap
**Enable a Conditional Access policy that *blocks all legacy authentication* and *requires modern authentication (MA) for all admin roles*.**  

**Policy definition (example):**

| **Name** | **Grant** | **Session Controls** | **Targeted Users / Roles** |
|----------|-----------|----------------------|----------------------------|
| **Block Legacy Auth – Global Admins & All Users** | **Block** (or **Require** modern auth) | **Require MFA** for all sign‑ins; **Require compliant device** for admin roles; **Enable “Client app type = Exchange ActiveSync, IMAP, POP, MAPI”** to **Block** | **All users** (for legacy‑auth block) and **Global Administrators, Exchange Administrators, Privileged Role Administrators** (for MFA & device). |

*Implementation steps:*

1. In **Azure AD > Conditional Access**, create a new policy.  
2. **Assignments → Users and groups** – select *All Users* (or a security group that contains all mail‑enabled users).  
3. **Cloud apps or actions → Select apps** – choose **Exchange Online**.  
4. **Conditions → Client apps** – select **“Browser”**, **“Mobile apps and desktop clients”**, and **“Other clients”** → **Block** the following **client app types**:  
   - `Exchange ActiveSync (EAS)` – **Legacy**  
   - `IMAP`  
   - `POP`  
   - `Other (Other)` – this catches Basic Auth.  
5. **Access controls → Grant** – **Block access** (or **Require** *Modern authentication only*).  
6. **Enable** the policy and monitor the **“Report-only”** mode for 48 h before enforcement.  

When the policy is enforced, any attempt to authenticate via POP3, IMAP, or EAS Basic Auth will be denied, forcing clients to upgrade to **OAuth‑2.0 / Modern Authentication** (which is covered by MFA and device compliance).

**Typical DMARC record:**

```
_dmarc.yourdomain.com.  IN TXT  "v=DMARC1; p=reject; rua=mailto:dmarc-rua@yourdomain.com; ruf=mailto:dmarc-ruf@yourdomain.com; fo=1; adkim=s; aspf=s; pct=100"
```

*Why it works:*  
- **`p=reject`** tells receivers to **reject** any mail that fails SPF and DKIM alignment, eliminating spoofed messages from reaching inboxes.  
- **`adkim=s; aspf=s`** enforces *strict* alignment for both DKIM and SPF, ensuring the "From" domain exactly matches the signing domain.  
- **Reporting URLs** (`rua`, `ruf`) give you visibility into any spoofing attempts.

*Implementation steps:*

1. Add the TXT record to the DNS zone for **yourdomain.com**.  
2. Verify publication with an online DMARC checker (e.g., MXToolbox, DMARCian).  
3. Monitor the initial reports for 1‑2 weeks; once you’re confident legitimate mail passes, tighten the policy to **`p=reject`** (if not already).

**Risk:** Critical. 7 of 9 admins lack MFA, and no Conditional Access policies exist. This is the highest-severity finding. If an attacker phishes or brute-forces an admin account, they gain total tenant control (RDP to servers, access to all data, ability to delete tenants).

**Remediation Steps:**
1.  **Enroll MFA immediately** for all 9 Global Administrator accounts. Do not enable MFA tenant-wide yet, as this may block legitimate users with legacy devices (a common issue in AEC firms with field crews using older phones).
2.  **Enable Azure AD Conditional Access Policies.** Turn off Microsoft Security Defaults (which are a simplified subset of CA) and build granular CA policies.
    *   Create a policy titled "Block Legacy Auth & Require MFA."
    *   Scope: All Users / All Applications.
    *   Conditions: **Block Legacy Authentication methods** (POP3, IMAP, EAS basic auth) and **Require MFA** or Password.
    *   Grant: Deny access if legacy auth is detected.
3.  **Verify:** Run a test login from a legacy client (e.g., Outlook mobile) to ensure it is denied or challenged, while ensuring CA is not blocking legitimate users due to strict configuration.

### Priority 2: Disable Legacy Authentication Protocols
**Risk:** High. Legacy protocols (POP3, IMAP, EAS) bypass modern security controls like MFA and Conditional Access. Even after Priority 1, if legacy auth remains enabled at the tenant level, attackers can potentially bypass the CA policy (depending on specific policy configuration) or simply use it to access mailboxes if a password is compromised.

**Remediation Steps:**
1.  **Microsoft 365 Defender:** Enable "Block legacy authentication protocols" in the *Attack Surface Reduction* settings or via the *Azure AD Authentication Methods* blade.
2.  **Conditional Access:** Ensure the policy created in Priority 1 explicitly has the "Block legacy authentication methods" condition enabled.
3.  **Exception Handling:** Configure an "Allow access" for specific scenarios (e.g., if field crews rely heavily on mobile email without MFA-capable devices), but default to block.
4.  **Verify:** Check the "Sign-in logs" in the Microsoft Purview Compliance Portal for any successful legacy authentication events to identify users who need to switch to modern authentication methods.

### Priority 3: Publish DMARC Record to Close Email Spoofing
**Risk:** High. Without DMARC, an attacker can spoof the AEC firm's email address (e.g., `claims@yourdomain.com`) to send phishing emails to employees or partners, bypassing SPF checks. This is a primary vector for credential theft.

**Remediation Steps:**
1.  **Publish a DMARC TXT record** at the `_dmarc.<yourdomain.com>` DNS entry.
2.  **Adopt a phased approach:**
    *   **Phase 1 (Week 1):** Set `p=none` to monitor reports. This ensures the record exists without blocking legitimate mail.
    *   **Phase 2 (Month 2):** Review DMARC aggregate reports (`rua=<report-uri>`) to identify sources of spoofing attempts.
    *   **Phase 3 (Month 3):** Move to `p=quarantine` to send suspected spoofed mail to spam.
    *   **Phase 4 (Month 6):** Move to `p=reject` to strictly block spoofed mail.
3.  **Verify:** Use a tool like MXToolbox or Dmarcian to confirm the record is published and check the domain's authentication status (SPF + DKIM + DMARC).

### Priority 4: Verify and Enforce Outlook Patching for CVE-2023-23397
**Risk:** High. CVE-2023-23397 is a zero-click NTLM-relay exploit. An attacker can trigger this via a malicious calendar reminder sound, hijacking the user's session without them clicking anything. If unpatched, field engineers or remote staff are vulnerable to session hijacking during any M365 activity.

**Remediation Steps:**
1.  **Microsoft Intune / SCCM:** If the firm uses Intune (recommended for M365), create a **Software Update Compliance Policy**.
    *   Target: All Windows devices enrolled in Intune.
    *   Settings: Require the March 2023 Cumulative Update (KB5001396 / KB5001395 depending on OS build).
    *   Action: Reboot required to complete the update.
2.  **Report:** Generate a compliance report to identify devices that failed to install the patch.
3.  **Out-of-Band Verification:** For devices not enrolled in MDM (e.g., older field laptops), run an on-premises scan (via SCCM or PowerShell `Get-Product | Where-Object {$_.Name -like '*Office*'}`) to verify the patch is installed.
4.  **Verify:** Check the Windows Update history on a sample of devices (`Get-Date` / `wmic qfe list` / `winver`) to confirm the specific KB number is present.

## Specific Control & Verification Answers

**1. Which control closes the Conditional Access / legacy-auth gap?**
You would enable **Azure AD Conditional Access Policies** (specifically a policy with the condition **"Block legacy authentication methods"** and the requirement **"Require MFA"**). You would then run a **compliance report** to verify that 100% of managed endpoints report the patch as installed and up to date, and for unmanaged devices, perform a manual **KB check** via PowerShell or Windows Update History.
