# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.

**Patch-Window Runbook – Remote Drilling Rig (VSAT 2 Mbps ↑ / 10 Mbps ↓)**  
**Objective:** Deploy the current Windows Server 2022 cumulative security update to all 14 domain‑joined endpoints (including the domain controller) without degrading SCADA/drilling‑telemetry performance.  

**Key Constraints**  
| Constraint | Impact |
|------------|--------|
| VSAT link shared with SCADA telemetry (2 Mbps ↑ / 10 Mbps ↓) | Any large concurrent download will saturate the link and cause telemetry latency or loss. |
| Only 4‑hour maintenance window per 14‑day hitch (crew changeover) | All patch activities must be completed inside this window; no “spill‑over” into drilling hours. |
| Domain Controller (DC) is critical for SCADA operator authentication | DC must be patched last (or first with a graceful restart) to avoid authentication outages. |
| 14 endpoints (13 workstations + 1 DC) | Need a sequenced, bandwidth‑aware rollout. |

---

## 1. Pre‑Patch Preparation (performed **outside** the 4‑hour window)

### 1.1. Inventory & Baseline
1. **Verify endpoint list** – Confirm the exact hostname/IP of each of the 14 servers/workstations.  
2. **Check current patch level** – Run `systeminfo` / `Get-HotFix` on each host to ensure no older cumulative updates are pending.  
3. **Capture performance baseline** – Record current VSAT utilization (e.g., via the satellite modem web UI or a simple `ping`/`iperf` test) to prove that the planned download rate stays well below the 2 Mbps upload / 10 Mbps download ceiling.

### 1.2. Backup & Rollback Planning
| Action | Details |
|--------|---------|
| **Domain Controller** | • Take an **authoritative system state backup** (e.g., using Windows Server Backup or a supported image backup). <br>• Document the backup location (local high‑capacity HDD + off‑site copy if possible). |
| **Workstations** | • Ensure each workstation has a **recent disk image** or at least a restore point. <br>• Verify that critical local data (e.g., drilling logs) are backed up to the rig’s NAS or cloud‑sync (outside the VSAT). |
| **Rollback Procedure** | • Scripted steps to revert to the pre‑patch backup (including DNS/AD service restart if needed). <br>• Test the rollback on a non‑production VM that mirrors the rig’s OS version. |

### 1.3. Staging the Update Package
1. **Download the update once** from a high‑bandwidth site (e.g., corporate HQ or a satellite‑friendly download portal) **before the hitch**.  
2. **Transfer the package** to the rig using one of the following low‑impact methods:  
   - **Physical media** (USB‑3.0 drive) – fastest, no VSAT usage.  
   - **Off‑hours WAN transfer** – if the rig has a secondary low‑speed link (e.g., cellular) that can be used overnight, schedule the download during the night when drilling is idle.  
3. **Place the package** on a **central file share** that all endpoints can reach (e.g., `\\DC\RigPatches\Win2022_Cumulative_2024-08-xx.cab`).  
4. **Verify checksum** (`Get-FileHash`) on each host to ensure integrity.

### 1.4. Communication & Coordination
- **Notify SCADA/Drilling Ops** at least 48 h before the hitch changeover that a maintenance window will occur.  
- **Confirm** that no scheduled rig‑wide tests or critical telemetry uploads are planned during the 4‑hour window.  
- **Assign a “Patch Lead”** on‑site (usually the IT field tech) and a **remote backup contact** (MSP engineer) for real‑time support.

## 2. In‑Window Execution – Bandwidth‑Constrained Sequencing

### 2.1. Assumptions for Bandwidth Calculation
| Parameter | Value |
|-----------|-------|
| Cumulative update size (typical) | **≈ 350 MB** (compressed) |
| Effective download speed per host (to stay < 10 Mbps) | **≈ 1.2 Mbps** (≈ 150 KB/s) – gives a comfortable 20 % headroom for telemetry. |
| Time to download 350 MB at 1.2 Mbps | **≈ 40 minutes** |
| Additional install + restart overhead | **≈ 15 minutes** per host (including OS apply, possible reboot). |
| **Total per host** | **≈ 55 minutes** |

### 2.2. Sequencing Strategy
Because 14 hosts × 55 min ≈ 14 h exceeds the 4‑hour window, we **pipeline** the workflow while **limiting concurrent downloads** to keep VSAT utilization ≤ 10 Mbps.

#### Step‑by‑step Pipeline (see timeline below)

1. **Start with the Domain Controller (DC)** – it must be patched **first** (or last) but **with zero impact on authentication**.  
   - **Why first?** Patching the DC early allows all workstations to authenticate against an already‑updated DC after their own patch/reboot.  
   - **Procedure:**  
     a. Trigger download **manually** from DC (no other host downloading).  
     b. Install update, **restart** the DC.  
     c. Verify AD services (DNS, Kerberos) before moving to workstations.  
   - **Time:** ~55 min (download + install + reboot + validation).

2. **Parallel “Download‑Only” Stage for 3 Workstations**  
   - **Select 3 workstations** that are **least critical** for immediate SCADA access (e.g., non‑operator consoles).  
   - **Initiate download** **simultaneously** on these three hosts **only**, each capped at 1.2 Mbps (≈ 3.6 Mbps total). This stays well under the 10 Mbps downlink ceiling, leaving ~6.4 Mbps for telemetry.  
   - **While they download**, the DC is already patched and online, so authentication for any workstation that later reboots will work.

3. **Install & Reboot on the First 3 Workstations** (sequentially or in small batches)  
   - As soon as a workstation finishes its download, **trigger the install** locally.  
   - Allow ~15 min for install + reboot.  
   - **Total for these three:** ≈ 3 × 55 min = **165 min**, but because downloads overlap, the **wall‑clock** time is roughly **115 min** (download 40 min + staggered installs).  

4. **Repeat the 3‑host pipeline** for the remaining 10 workstations, **grouped into four batches** of 3 + 1 final batch of 1.  
   - **Batch 2 (Workstations 4‑6)** – start downloads while Batch 1 is installing.  
   - **Batch 3 (Workstations 7‑9)** – start while Batches 1‑2 are installing.  
   - **Batch 4 (Workstations 10‑12)** – start while Batches 1‑3 are installing.  
   - **Final host (Workstation 13)** – downloaded last; its install finishes near the end of the window.

| 0‑55 | **DC**: Download → Install → Reboot → Verify AD |
| 20‑85 | **Batch 1 (WS 1‑3)**: Download (overlap) |

| 55‑110 | **Batch 1**: Install & Reboot WS 2 |

| 110‑155 | **Batch 2**: Install & Reboot WS 5 |
| 125‑170 | **Batch 2**: Install & Reboot WS 6 |

| 140‑185 | **Batch 3**: Install & Reboot WS 7 |

| 285‑300 | **Final verification** (AD, WSUS/Intune status, SCADA health check) |

- **Total elapsed time ≈ 300 minutes = 5 hours** – exceeds the 4‑hour window.  
- **Mitigation:**  
  1. **Pre‑stage the update on a local repository** *before* the hitch (Step 1.3). This removes the **download** portion from the critical path.  
  2. **Use the central share** to **push the install** via a remote command (e.g., `Invoke-Command` with `Start-Process` or SCCM/Intune “Install‑Only” mode). The **install** itself is only a few MB of transaction logs, well within the 2 Mbps upload limit.  
  3. **Resulting timeline** with pre‑staged package:  
     - DC patch: 55 min (including reboot).  
     - 13 workstations: ~13 × 15 min = **195 min** for install + reboot (can be overlapped 2‑3 at a time).  
     - **Overall ≈ 250 min (≈ 4 h 10 min)** – still slightly over.  
     - **Final tweak:** Run **two workstations concurrently** (max 2 × 1.2 Mbps ≈ 2.4 Mbps) while the DC is already up; this shaves ~30 min, bringing the total to **≈ 220 min (3 h 40 min)**, comfortably inside the 4‑hour slot.

### 2.3. Detailed Command Flow (example using PowerShell Remoting)

```powershell
# 1. On the Patch Lead workstation (connected to the rig LAN)
$dc = "DC01"
$workstations = @("WS01","WS02",...,"WS13")

# a) Patch Domain Controller first
Invoke-Command -ComputerName $dc -ScriptBlock {
    # Ensure update package is already present on C:\RigPatches\update.cab
    $pkg = "C:\RigPatches\Win2022_Cumulative_2024-08-xx.cab"
    dism /online /apply-unattend:$pkg
    # Reboot with forced flag (will auto‑return to caller)
    Restart-Computer -Force
} -AsJob -JobName "PatchDC"

# Wait for DC to come back and AD services to be healthy
Wait-Job -Name "PatchDC" -Timeout 1800   # 30 min safety
# Verify DNS/Kerberos (simple LDAP query)
Get-ADUser -Identity "SCADA_Operator" -ErrorAction SilentlyContinue

# b) Parallel patch of workstations (max 2 concurrent)
$scriptBlock = {
    param($pkg)
    # Apply the update (quiet mode)
    Start-Process -FilePath "dism.exe" -ArgumentList @("/online","/apply-unattend:$pkg","/quiet") -Wait
    # Reboot after install
    Restart-Computer -Force
}
$jobs = @()
foreach ($ws in $workstations) {
    $jobs += Invoke-Command -ComputerName $ws -ScriptBlock $scriptBlock -ArgumentList $pkg -AsJob
    # Throttle: if we already have 2 running, wait a bit
    if ($jobs.Count -ge 2) {
        Get-Job -Name ($jobs[0].Name) | Wait-Job -Timeout 1200   # wait ~20 min
        Remove-Job $jobs[0]
        $jobs = $jobs | Where-Object {$_.State -ne "Completed"}
    }
}
# Wait for any remaining jobs
Get-Job | Wait-Job
```

- **All `dism` operations read the *already‑local* CAB file**, so **no VSAT traffic** occurs during the 4‑hour window.  
- The only network activity is **management traffic** (PowerShell remoting, ~few KB per command) – negligible on a 2 Mbps uplink.

   - Ping the **SCADA gateway** from each workstation to ensure telemetry paths are intact.

2. **SCADA/Drilling Telemetry Monitoring**

3. **Patch Reporting**  
   - Run `Get-WindowsUpdateLog` or query WSUS/Intune for **installation status** on all 14 endpoints.  
   - Export a CSV report and email it to the rig manager and MSP ticketing system.

4. **Documentation**  
   - Log the exact **start/end timestamps** for each host’s patch cycle.  
   - Note any **exceptions** (e.g., a workstation that required a manual retry).

# Patch‑Window Runbook  
**Deploying the Windows Server 2022 cumulative security update (KB‑xxxxx) to a 14‑node remote drilling‑rig site**  

**Scope** – 14 domain‑joined endpoints (13 workstations + 1 Domain Controller) that must receive the patch **without** impacting the SCADA/drilling‑telemetry link (VSAT 2 Mbps ↑ / 10 Mbps ↓).  

**Operational constraint** – Only a **4‑hour** maintenance window is available each hitch (the day‑to‑night crew‑changeover). The rig runs on a **14‑day hitch schedule**, so the window recurs every 14 days.  

**Goal of this runbook** – Provide a repeatable, low‑bandwidth patch‑deployment plan that:  

1. Guarantees continuous SCADA telemetry.  
2. Keeps the DC online for authentication throughout the hitch.  
3. Completes the patch for **all 14 nodes** within a single 4‑hour window **each hitch**.  
4. Fits cleanly into the 14‑day hitch cadence.

## 1.  High‑Level Strategy  

| Phase | What | Why | Bandwidth Impact |
|-------|------|-----|------------------|
| **A – Pre‑patch preparation** | Build & test a local cache, create throttling policies, verify backup & rollback media. | All heavy traffic is done **offline** or at a throttled rate **outside** the maintenance window. | Minimal/no impact on VSAT. |
| **B – Patch‑rollout sequencing** | Deploy in 3 staggered waves (DC → “non‑critical” workstations → “critical” workstations) using a **peer‑to‑peer/BranchCache** distribution model. | DC must stay up for authentication; critical workstations are kept to a minimum during the window; peer traffic reduces upstream saturation. | Peaks ≤ 300 kbps upstream (well under 2 Mbps). |
| **C – Validation & cut‑over** | Run health‑checks, confirm SCADA telemetry, verify DC replication, then promote the patched DC as the sole authentication source. | Guarantees that any problem is caught before the next production shift. | No additional bandwidth; only small status packets. |
| **D – Documentation & hand‑off** | Record results, update the “Patch‑Ready” status for the next hitch. | Enables repeatability on the next 14‑day cycle. | None. |

## 3.  Patch‑Deployment Sequencing (Phase B)  

### 3.1  General Rules  

| Rule | Rationale |
|------|-----------|
| **Never patch the DC first** – the DC must stay online to authenticate all other hosts. | If the DC goes down, the whole site loses AD authentication and SCADA loses its security token source. |
| **Patch non‑critical workstations in batches of 3–4** – each batch is staggered by **5 minutes** to keep the upstream aggregate < 300 kbps. | The VSAT upstream is limited; 3–4 simultaneous downloads ≈ 150 kbps each → total ≈ 450 kbps, but with throttling we keep it under 300 kbps. |
| **Patch “critical” workstations (SCADA operator consoles) last** – they are the most sensitive to any network latency. | Their patch can be deferred to the next hitch if any anomaly occurs. |
| **All reboots are forced to occur **after** the 4‑hour window ends** – use the “Schedule Restart” option in WSUS/SCCM to reboot at **+5 minutes** after the window closes, ensuring the patch install finishes before the next production shift starts. | Guarantees the rig never runs a half‑patched OS while drilling. |
| **Peer‑cache warm‑up** – after each batch finishes, the newly patched machines become cache seeds for the next batch. | Reduces upstream traffic further. |

### 3.2  Detailed Rollout Timeline (4‑Hour Window)

| Time (hh:mm) | Action | Affected Nodes | Bandwidth Used (approx.) |
|--------------|--------|----------------|--------------------------|
| **00:00 – 00:05** | **Kick‑off** – Verify that the maintenance window is authorized, that the SCADA link is at its baseline utilization, and that the DC is healthy (`dcdiag`). | All | Negligible (status packets). |
| **00:05 – 00:12** | **Patch the Domain Controller** (DC01) – Deploy the cumulative update from the local depot, enable **“Install but do not restart”** option, set a **scheduled restart for +5 min** (i.e., 00:17). | 1 (DC) | ≤ 150 kbps (single stream, throttled). |
| **00:12 – 00:17** | **Monitor DC patch** – Ensure the DC finishes install, reboots, and comes back online (check `dcdiag /test:replications`). | DC | Same as above. |
| **00:17 – 00:22** | **Patch Batch 1 – Non‑critical workstations** (IDs 001‑003). | 3 workstations | ≤ 200 kbps total (3 × ~70 kbps). |

## 4.  Bandwidth‑Management Details  

| Technique | Implementation | Expected Impact |
|-----------|----------------|-----------------|
| **WSUS/SCCM bandwidth throttling** | Set **Maximum Download Bandwidth = 250 kbps** per client; enable **“Only download during maintenance window”**. | Guarantees the upstream never exceeds ~300 kbps even when several clients are active. |
| **BranchCache (Cache mode)** | Enable on the LAN NICs; set **Cache size = 2 GB** per client; configure **“Allow client-to-client communication”**. | Patched machines become local distribution points, cutting the need for repeated downstream copies. |
| **Peer‑to‑Peer “Delivery Optimization”** (Windows 10/Server 2022) | Use Group Policy `Delivery Optimization → Group Policy Path: Computer Configuration → Administrative Templates → Windows Components → Delivery Optimization → “Enable peer‑to‑peer distribution”`. Set **Maximum download bandwidth = 200 kbps** per client. | Further reduces simultaneous upstream usage; the first patched host caches the MSU and supplies it to peers. |
| **Scheduled restarts** | Use WSUS/SCCM “Restart computer after 5 minutes” option, *after* the maintenance window ends. | Guarantees that the host does not reboot while still handling SCADA traffic. |
| **Local depot replication** | Store the MSU on a gigabit‑connected NAS; replicate the depot to a second NAS in the field (optional) for redundancy. | Eliminates any need to pull the patch over VSAT after Day ‑ 2. |

1. **Post‑patch health script** (`Validate-Patch.ps1`) runs on each machine:

   - Verifies that the **SCADA client process** (`SCADA_Client.exe`) starts and can ping the remote rig’s data‑acquisition server.

2. **If any host fails**:  
   - Isolate it on the LAN (disable its switch port).  
   - Use the **offline USB backup** to roll back the OS to the pre‑patch snapshot (via `wbadmin` or Windows Recovery).

   - Re‑join the repaired DC to the domain and re‑establish replication before proceeding with workstation patches.

## 3.  BANDWIDTH‑CONSCIOUS PATCH SEQUENCE  

### 3.1  Rationale  

* **DC first** – If the DC becomes unavailable, all workstations lose authentication, causing SCADA operator login failures.  
* **Batch size** – With a 200 Kbps limit per client, **3 simultaneous clients** = 0.6 Mbps upstream, staying under the 30 % headroom.  
* **Staggered start** – Start each batch 5 minutes apart to allow the previous batch to finish downloading before the next begins, smoothing the traffic curve.  
* **Verification pause** – After each batch, pause 2 minutes to confirm SCADA telemetry health (via ping/latency to the SCADA gateway).

## 5.  ROLLBACK PROCEDURE  

1. **Identify failed node** (via verification script exit code).  
2. **Disconnect** the node from the VSAT (physically unplug Ethernet or disable Wi‑Fi) to prevent further traffic.  
3. **Boot from USB rollback media** (Windows PE).  
4. **Restore** the latest good image (the one taken in step 2 of Pre‑Patch).

6. **Re‑apply** the BITS throttling GPO (ensures the node does not re‑download the update automatically).  
7. **Validate** authentication and telemetry again.  
8. **Document** the failure cause (e.g., insufficient disk space) and schedule a repeat patch in the next hitch window.
