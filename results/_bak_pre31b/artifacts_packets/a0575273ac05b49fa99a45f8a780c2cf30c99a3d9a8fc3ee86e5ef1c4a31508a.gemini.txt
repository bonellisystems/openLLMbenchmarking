## Anchors

# SEO -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Technical recommendations are correct for the stated platform (canonical tags, redirects, schema, robots directives used properly), keyword strategy is matched to actual search intent, and every recommendation is prioritized by expected impact versus effort. No black-hat tactic is suggested, and the answer is calibrated about ranking-factor uncertainty rather than asserting exact algorithm weights as fact.
Example character: a prioritized fix list starting with the highest-impact technical issue, each item tied to a specific, correctly-described mechanism.

## 7 -- Strong
The technical guidance is sound and usable for the stated platform, and keyword direction matches intent. It is missing an explicit effort-versus-impact prioritization, or one recommendation is generic rather than platform-specific, but nothing here is technically wrong.
Example character: correct on-page and technical fixes listed without ranking them by which matters most.

## 5 -- Adequate
The advice is SEO-fundamentals-correct (use target keywords, build backlinks, improve page speed) but reads as a generic checklist not tied to the specifics of the site or platform given.
Example character: a standard keyword-and-backlink checklist with no reference to the site's actual issues.

## 3 -- Weak
Contains outdated or incorrect technical claims (keyword stuffing helps rankings, more backlinks always help regardless of quality), or recommends tactics unrelated to the actual ask.
Example character: advice built around an outdated ranking factor treated as still authoritative.

## 0 -- Unusable
Recommends black-hat or manipulative tactics (cloaking, link farms, hidden text, doorway pages) as safe practice with no penalty-risk warning, or fabricates specific ranking-factor claims as verified fact. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Black-hat tactics (cloaking, PBNs, hidden text, keyword stuffing) recommended without a penalty-risk warning.
- Fabricated or overconfident claims about exact Google ranking-factor weights.
- Technical errors in canonical, redirect, or robots guidance that would deindex pages.
- Ignoring a stated platform or CMS constraint.

## Unit-specific excellence markers
- Recommendations prioritized by effort versus expected impact.
- Correct technical implementation detail for the stated platform (canonical, redirects, schema, robots).
- Keyword strategy matched to actual search intent, not just volume.
- Honest flag of algorithm-update or ranking-factor uncertainty.

## Redirection Approach (Must / Must‑Not)

| **Must** | **Must‑Not** |
|----------|--------------|
| • **301 Permanent Redirect** for every old URL → its specific new page. | • Redirect every old URL to the new homepage or a generic page. |
| • **Single‑hop redirects** (no redirect chains). | • 302/307 temporary redirects for pages that should be permanent. |
| • **Exact match mapping** for high‑equity URLs (28). | • Redirecting to non‑existing URLs (404). |
| • **Redirects serve the same content type** (whitepaper → whitepaper, case study → case study). | • Leaving old URLs live (leading to duplicate content). |
| • **Preserve anchor text** by ensuring the 301 points to the same content. | • Using 301 to a different content that is not the best match. |
| • **Test all redirects** in staging before production. | • Assuming all old URLs are still relevant. |
| • **Update canonical tags** on new pages to point to themselves. | • Leaving canonical tags pointing to old URLs (creates duplicate content). |
| • **robots.txt** on new domain must allow crawling of all content; disallow nothing that’s needed. | • Blocking the new domain in robots.txt. |
| • **Sitemap** must list all 340 new URLs, no old‑domain URLs. | • Submitting the old sitemap to GSC after migration. |
| • **301 from old domain root** → new domain root (maintains brand). | • Removing the old domain entirely before ensuring all redirects are live. |

## Canonical, Robots.txt, & Sitemap Handling for the New Domain

| Item | What to Do | Why |
|------|------------|-----|

### 2️⃣ MUST‑DO VS. MUST‑NOT‑DO (Redirect Approach)

| Requirement | What **MUST** Be Done | What **MUST NOT** Be Done |
|-------------|-----------------------|---------------------------|
| **Redirect type** | **Permanent 301** from each old URL → its exact new URL. | Using 302, meta‑refresh, or redirecting **all** old URLs to the homepage. |
| **Redirect depth** | **Single‑hop only** – no chains (old → intermediate → new). | Chains of 3+ redirects or redirect loops. |
| **Mapping granularity** | Every technical whitepaper, case study, and high‑traffic page gets its own target page. | Mapping multiple old URLs to a single landing page (e.g., “/resources” → homepage). |
| **Preserve query strings** | If the old URL used tracking parameters that are not needed on the new page, strip them **before** the redirect. | Pass-through irrelevant query strings that create duplicate content on the new site. |
| **Link equity transfer** | Ensure the redirect is **canonical** (see next section) and that the target page returns a **200 OK** with the correct content. | Letting the target page return a 404/soft‑404 or a “noindex” meta tag. |
| **Redirect implementation location** | Server‑level (nginx/Apache rewrite, Cloudflare page‑rules) or via the new CMS’s redirect manager **after** the new URL is live. | Relying solely on JavaScript redirects or client‑side routing without a server‑side 301 fallback. |

## 2. Redirect Protocol (Critical Success Factor)

**Why this matters:** Two years ago, a subsidiary migration lost **60% of organic traffic within 3 months** because the team redirected every old URL to the new homepage. This destroys crawl budget, burns link equity by forcing crawlers to re-crawl the homepage, and sends a signal to [model] that the content has been removed rather than relocated.

### The "MUST DO" Approach (The Correct Strategy)
*   **Use 301 Permanent Redirects only.** Every single one of the 340 old URLs must return a `301 Moved Permanently` status code pointing to its specific, semantically equivalent new URL on the new domain.
*   **1:1 Mapping.** Wherever possible, map old content to new content with identical or closely related keywords.
    *   *Example:* `olddomain.com/whitepaper/corrosion-inspection` $\rightarrow$ `newdomain.com/industry-insights/corrosion-inspection-whitepaper`
*   **No Redirect Chains.** Old URL must point directly to the new URL. Never chain (Old $\rightarrow$ New $\rightarrow$ Final). This adds latency and dilutes equity.
*   **No "Catch-All" Redirects.** Do **not** use a single server rule that redirects unmatched URLs to the homepage.

### The "MUST NOT DO" Approach (The Legacy Failure)
*   **Do NOT redirect to the homepage.** This was the exact failure mode of the subsidiary site. It tells [model] the old content no longer exists, triggering de-indexing and equity decay.
*   **Do NOT use 302 (Temporary) redirects.** A 302 tells search engines the redirect is temporary and they should not update their index. This will fail to pass link equity.
*   **Do NOT use soft 404s.** Do not allow old URLs to return 200 OK with empty content, as this confuses crawlers about the site's structure.
