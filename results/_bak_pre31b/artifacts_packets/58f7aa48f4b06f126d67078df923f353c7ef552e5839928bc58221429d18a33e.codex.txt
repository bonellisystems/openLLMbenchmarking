concrete pipeline fix for each of the four issues.

## 4.  Why NULL `rate_type` rows are **silently excluded** (Issue 3)

The reporting query (or downstream materialised view) contains a predicate such as:

```sql
WHERE rate_type = 'standard'
```

* In SQL, `NULL` is **unknown**, not equal to any literal, including `'standard'`.  
* The expression `rate_type = 'standard'` evaluates to **UNKNOWN** for rows where `rate_type` is NULL.  
* The `WHERE` clause only keeps rows where the predicate evaluates to **TRUE**.  
* Rows that evaluate to UNKNOWN are **filtered out** automatically – they do not raise an error, they simply disappear from the result set.

Therefore the 460 rows with `rate_type = NULL` are omitted from any aggregation that relies on that filter, without any warning or exception.

    entry_sk          BIGINT AUTOINCREMENT PRIMARY KEY,
    source_entry_id   STRING,
    matter_id         STRING,
    attorney_id       STRING,
    entry_dt_local    TIMESTAMP,
    hours             NUMERIC,
    rate_type         STRING,
    billing_utc_dt    TIMESTAMP,
    -- … other columns …
    CONSTRAINT uq_source_entry UNIQUE (source_entry_id)
);

MERGE INTO dim.time_entries_fact tgt
USING staging.time_entries_raw src
ON tgt.source_entry_id = src.source_entry_id
WHEN NOT MATCHED THEN INSERT (
    source_entry_id, matter_id, attorney_id,
    entry_dt_local, hours, rate_type,
    billing_utc_dt

    src.source_entry_id, src.matter_id, src.attorney_id,

    src.billing_utc_dt
);

### 🧠 Why NULL `rate_type` Rows Are Silently Excluded (SQL Semantics)
SQL uses **three-valued logic**: `TRUE`, `FALSE`, and `UNKNOWN`. When a column contains `NULL`, any comparison (e.g., `rate_type = 'standard'`) evaluates to `UNKNOWN`, not `FALSE`. The `WHERE` clause is defined by the SQL standard to retain **only rows where the predicate evaluates to `TRUE`**. Rows evaluating to `FALSE` or `UNKNOWN` are filtered out. This is intentional design, not a bug: `NULL` represents "missing/unknown," and SQL deliberately avoids assuming equality or inequality with unknown values. Hence, `WHERE rate_type = 'standard'` silently drops `NULL`s without erroring, because no constraint or type mismatch is violated—only a logical filter is applied.

The `WHERE` clause is strictly a **boolean filter**: it retains rows where the condition evaluates to `TRUE`, and discards rows where it evaluates to `FALSE` or `UNKNOWN`. Because SQL treats `UNKNOWN` as non-TRUE, the row is filtered out. 

**Why no error is thrown:** SQL treats `NULL` as a valid relational state (missing/unknown data), not a type mismatch or syntax violation. The engine gracefully evaluates the predicate, resolves it to `UNKNOWN`, and applies the standard filter behavior. Errors only occur with invalid data types, unsupported operators, or explicit `IS NULL`/`COALESCE` misuse. To capture these rows, you must explicitly use `IS NULL`, `COALESCE(rate_type, 'standard')`, or `IS DISTINCT FROM`.

**3. Why NULL `rate_type` rows are silently excluded**

In SQL, a predicate such as  

```sql
WHERE rate_type = 'standard'
```  

is evaluated using **three‑valued logic**:

1. **TRUE** – the row matches the condition.  
2. **FALSE** – the row does **not** match the condition.  
3. **UNKNOWN** – the comparison yields `NULL` because one (or both) operands are `NULL`.

The rule is: *only rows for which the WHERE clause evaluates to TRUE are returned.*  
When `rate_type` is `NULL`, the expression `rate_type = 'standard'` evaluates to **UNKNOWN**, which SQL treats as **FALSE** for filtering purposes. Consequently, the row is filtered out **without any error or warning**. This behavior is by design: SQL does not raise an exception for a comparison involving `NULL`; it simply discards the row from the result set. To surface the problem you would need an explicit check, e.g.:

```sql
WHERE rate_type = 'standard' OR rate_type IS NULL
```

or a separate diagnostic query that counts `NULL` values.

### 3. SQL Semantics: Why NULL `rate_type` Rows Are Silently Excluded

The NULL rows are not excluded by an `IF` statement or a business rule; they are excluded by the **Three-Valued Logic (3VL)** semantics of the SQL standard `WHERE` clause.

In SQL, boolean expressions evaluate to one of three states: **TRUE**, **FALSE**, or **UNKNOWN** (not "NULL").

1.  **The Comparison:** When the query engine evaluates `rate_type = 'standard'`, it compares the column value to the literal.
2.  **The NULL State:** For the 460 rows where `rate_type` is `NULL`, the comparison `NULL = 'standard'` does not evaluate to FALSE. Instead, per the SQL standard, any comparison with `NULL` evaluates to **UNKNOWN**.
3.  **The Filter:** The `WHERE` clause is defined to return only rows where the predicate evaluates to **TRUE**. **UNKNOWN is treated as FALSE** in a `WHERE` filter context.
4.  **The Result:** The 460 rows are silently filtered out. SQL does not raise an error or warning because the standard defines the behavior as deterministic logic, not a runtime exception.

*Corrective Logic:* To catch these, the report must use `IS NULL` logic explicitly, e.g., `WHERE (rate_type = 'standard' OR rate_type IS NULL)`, or the ETL should populate `rate_type` with a default value (`COALESCE`) at ingestion.

### 3. Why `NULL rate_type` Rows Are Silently Excluded (SQL Semantics)
This behavior is not a bug; it is a direct consequence of **SQL's Three-Valued Logic (3VL)** and the `WHERE` clause's retention semantics:

- In SQL, `NULL` is not a value; it represents **missing/unknown information**.
- When the engine evaluates `rate_type = 'standard'` on a `NULL` row, it does **not** return `FALSE`. It returns `UNKNOWN`.

- SQL deliberately avoids raising errors on `NULL` comparisons because treating missing data as "invalid" would break queries on sparse/optional columns, force `IS NOT NULL` guards on every filter, and contradict the relational model's design for representing real-world incomplete data.

**The danger:** Because `UNKNOWN` is silently filtered out without error, warning, or row count change, business users see a report that appears fully populated but is actually missing an unknown fraction of rows. This is why `WHERE col = X` and `WHERE col != X` both exclude `NULL`s, and why `COUNT(rate_type)` differs from `COUNT(*)`.
