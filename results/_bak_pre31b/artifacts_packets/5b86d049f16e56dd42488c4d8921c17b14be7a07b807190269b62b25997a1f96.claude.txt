# Phased Microsoft 365 Migration Plan: Community Bank to Regional Bank Acquisition

## Executive Summary
This plan migrates 340 mailboxes from an unsupported Exchange Server 2016 environment to the acquiring bank’s Microsoft 365 tenant in **≤40 days**, leaving a **3–5 day stabilization buffer** before the core-banking cutover (Day 41+). The approach uses **batched Remote Move requests** staggered by branch/timezone, enforces **regulatory-grade chain of custody**, and maintains **zero mailbox interruption during any branch’s 9 AM–5 PM window**. Exchange 2016 is kept isolated but functional until full migration validation, after which it is decommissioned.

## 🔧 Cutover Approach (Given Unsupported Exchange 2016)

### 1. Migration Method: Remote Move (Idempotent & Metadata-Preserving)
- **Why not Cutover/Staged?** Deprecated for unsupported versions; lacks granular control.
- **Remote Move** syncs incrementally, preserves all MAPI properties (timestamps, senders, recipients, attachments, flags), and supports scheduled final delta syncs.
- **PowerShell scheduling**: `New-MoveRequest -TargetDeliveryDomain ... -StartAfter <Local 17:00> -EndBefore <Local 08:30>`
- Initial sync runs anytime; **final delta sync + MX switch** occurs during each branch’s local after-hours.

### 2. Handling Unsupported Exchange 2016
- **Network isolation**: Place Exchange in a restricted VLAN. Block all inbound internet traffic. Allow only outbound to Microsoft 365 migration endpoints (IPs documented in Microsoft KB).
- **Transport security**: Enforce TLS 1.2, modern authentication, and certificate pinning for migration endpoints.
- **No EUS reliance**: Plan assumes migration completes within 40 days. If Extended Security Updates are purchased, apply immediately but do not delay migration.
- **Rapid decommission**: Once all 340 mailboxes validate, disable on-prem provisioning, export audit logs, and power down. Do not extend runtime past Day 40.

### 3. Mail Flow & Client Cutover
- **DNS TTL**: Reduce MX/TXT/SPF DKIM/DMARC records to 300 seconds 72 hours before first batch cutover.
- **MX switching**: Per-batch, not global. Once a batch’s move request shows `CompletedSuccessfully`, update MX records to point to M365.
- **AutoDiscover & Client Config**: Redirect via DNS. Outlook uses MFA/Conditional Access. Mobile/OWA auto-configure via M365.
- **Training/Comms**: Branch-specific rollout notices 48h before local cutover. IT helpdesk on standby during each local transition window.

## 🔄 Rollback Plan (If a Batch Fails Mid-Migration)

Remote Move is **resumable and non-destructive**. True “rollback” means reverting to pre-move state without data loss.

| Failure Scenario | Action |
|------------------|--------|
| **Move request stuck/fails >50%** | `Suspend-MoveRequest` → verify on-prem mailbox integrity → `Resume-MoveRequest` or `Remove-MoveRequest` + requeue with adjusted schedule. |
| **Metadata/timestamp corruption suspected** | Pause batch. Compare pre/post checksums. If mismatch, restore affected mailbox from pre-migration backup (VSS or third-party). Re-validate, requeue. |
| **Mail flow disruption** | MX records remain pointing to on-prem until batch shows `CompletedSuccessfully`. No global MX change until final batch. |
| **Client connectivity break** | Redirect AutoDiscover back to on-prem DNS. Users continue working. IT troubleshoots M365 side offline. |
| **Chain of custody breach risk** | All rollback actions logged, timestamped, and signed by migration lead + compliance officer. No data is overwritten or deleted during rollback. |

**Rollback Success Criteria**: On-prem mailbox accessible, hold active, move request requeued, chain of custody logs updated, no regulatory exposure.

## 4.  Migration Execution Details

### 4.1 Migration Endpoint

```powershell
# Create an endpoint for Exchange 2016 source
New-MigrationEndpoint -Name "EX2016-Endpoint" `
  -ExchangeServer "EXCH01" `
  -UserName "admin@communitybank.com" `
  -Password (ConvertTo-SecureString "Pa$$w0rd" -AsPlainText -Force) `
  -SourceEndpointType "Exchange" `
  -ServerVersion "Exchange2016"
```

### 4.2 Batch Creation

```powershell
# CSV format: UserPrincipalName,DisplayName,EmailAddress
Get-Content "C:\Migrate\Batch1.csv" | ForEach-Object {
    $mailbox = $_
    New-MigrationBatch -Identity "Batch1-$(Get-Date -Format 'yyyyMMddHHmm')" `
        -SourceEndpoint "EX2016-Endpoint" `
        -CSVData $mailbox `
        -AutoStart:$true `
        -AutoComplete:$true
}
```

### 4.3 Monitoring & Reporting

```powershell
# Batch status
Get-MigrationBatch -Identity "Batch1-..." | Format-Table Identity,Status,PercentComplete,FailedItems

# Detailed per‑user report
Get-MigrationUserReport -Identity "Batch1-..." | Export-Csv "C:\Migrate\Reports\Batch1-Report.csv" -NoTypeInformation
```

### 4.4 Rollback (Batch Level)

```powershell
# Undo a failed batch
Undo-MigrationBatch -Identity "Batch1-..." -Confirm:$true
```

> **Tip:** Always keep an on‑prem backup of each mailbox **before** you start the batch. If `Undo-MigrationBatch` fails to restore corrupted mail, you can re‑import from backup with `New-MailboxRestoreRequest`.

### Microsoft 365 Migration Plan for Exchange 2016 to Microsoft 365

---

#### **1. Phased Migration Approach (Cutover Method)**
Given the **unsupported Exchange 2016** environment and regulatory/operational constraints, a **phased cutover migration** is optimal. This minimizes downtime per batch while preserving metadata and timestamps.

##### **Key Phases:**
- **Phase 1: Pre-Migration Setup (Days 1–7)**
  - **Assessment & Validation:**
    - Inventory all 340 mailboxes, sizes, and dependencies.
    - Validate Exchange 2016 health (e.g., ESEUTIL checks) and ensure no corruption.
    - Document chain of custody procedures (backup logs, migration logs, timestamps).
  - **Microsoft 365 Preparation:**
    - Configure tenant licenses (Exchange Online, compliance tools).
    - Set up mail-enabled groups, permissions, and security policies.
    - Enable audit logging for compliance tracking.
  - **Tooling:**
    - Use **Exchange Online PowerShell** with `New-MigrationBatch` for native cutover.
    - **Third-party tools** (e.g., Quest Migration Manager) for granular metadata preservation if native tools lack fidelity.
  - **Pilot Test:**
    - Migrate 5–10 mailboxes during off-hours (9 PM–9 AM) to validate metadata/timestamps.
    - Document findings and refine rollback/monitoring protocols.

- **Phase 2: Batched Migration (Days 8–28)**
  - **Batch Strategy (Time Zone & Size-Based):**
    - **Group mailboxes by time zone** (e.g., Zone A: Eastern, Zone B: Central) and size (small/medium/large).
    - **Batch Size:** 10–15 mailboxes per batch (30–45 GB total) to ensure completion in 8–12 hours.
    - **Schedule:**
      - **Zone A:** Migrate during 5 PM–9 AM Eastern (4 PM–8 AM Central).
      - **Zone B:** Migrate during 5 PM–9 AM Central (6 PM–9 AM Eastern).
      - **Overlap Window:** 9 PM–8 AM (covers both time zones’ off-hours).
    - **Frequency:** 3–4 batches/night, 5 nights/week (avoid weekends).
  - **Migration Execution:**
    1. **Start Batch:** `New-MigrationBatch -Name "Batch1" -SourceEndpoint "EX2016Server" -BatchMigrationOptions Complete -TargetDeliveryDomain "microsoft365tenant.com"`
    2. **Monitor:** Use `Get-MigrationBatch` and `Get-MigrationUser` for real-time status.
    3. **Validation Post-Migration:**
       - Verify metadata/timestamps via `Get-Mailbox -Identity "User" | Format-List MessageTrackingLog`.
       - Check for duplicates using `Search-Mailbox -Identity "User" -SearchQuery "subject:" -EstimateResultOnly`.
    4. **Document:** Log completion times, errors, and compliance artifacts.

- **Phase 3: Post-Migration & Decommission (Days 29–35)**
  - **Validation & Final Checks:**

## Executive Summary

This plan outlines the migration of 340 mailboxes from an unsupported on-premises Exchange 2016 environment to the acquiring bank’s Microsoft 365 tenant. ## 1. Technical Approach: Incremental Cutover (Soft Cutover)

A traditional "Cutover Migration" requires a final synchronization window where the source is paused and all mailboxes are moved at once. This is impossible under the constraint that no branch can lose access during 9 AM–5 PM in either time zone.

**The Solution:** We will implement an **Incremental Cutover**.
*   **Mechanism:** Users are migrated one-by-one or in small batches (5–10 users/day).
*   **Downtime:** Zero. The tool performs a background sync. When a batch is complete, the user’s mailbox is "Cutover'd" (moved from E2016 to M365) during the local off-hours of that specific branch.
*   **Time Zone Staggering:**
    *   *Branch A (ET):* Off-hours = 5 PM ET (11 PM CT).
    *   *Branch B (CT):* Off-hours = 5 PM CT (9 PM ET).
    *   *Daily Window:* We migrate a subset of users from Branch A during the evening of Branch B's off-hours, and a subset of Branch B during the evening of Branch A's off-hours. This ensures **at least one branch always has a usable window daily** without interrupting the other.

### Phase 2 – Staged Migration (Days 15‑38)

#### 2.1 Batch Design  

| Batch Size | Rationale |
|------------|-----------|
| **10‑15 mailboxes per batch** (≈ 1 GB each) | Keeps the **move‑duration < 4 hours** per batch, allowing a short “cut‑over” window (5 minutes) without impacting 9‑5 operations. |
| **Geographic grouping** – Batch A = East‑Coast branches, Batch B = West‑Coast branches. | Allows us to schedule the 5‑minute cut‑over **simultaneously** across both time zones during the **12:00‑12:05 pm local lunch** slot (no customer‑facing activity). |
| **Retention‑Tag grouping** – Keep any mailbox with a Litigation Hold in its own “high‑priority” batch, to be migrated **first** (so hold stays intact). | Guarantees compliance‑critical mailboxes are secured early. |

#### 2.2 Daily Migration Window  

| Time (Local) | Activity |
|--------------|----------|
| 09:00‑09:30 | **Pre‑move health check** – Verify AAD sync, network latency, Exchange services. |
| 09:30‑12:00 | **Remote‑move execution** – Batch runs in background; mail flow continues on‑prem. |
| 12:00‑12:05 | **Cut‑over** – `Set-MoveRequest -Identity <batch> -Complete` (final sync). Users are automatically re‑directed to Exchange Online; DNS MX remains unchanged (mail flow already pointed to Office 365). |
| 12:05‑13:00 | **Post‑move validation** – Run automated scripts that compare **message counts, folder sizes, and delivery timestamps** between source and target. |
| 13:00‑17:00 | **Monitoring & Support** – Real‑time alerting (Azure Monitor) for any sync errors; Service Desk on‑call for branch users. |

> **Why lunch?**  It is the only 5‑minute window that is **common to both time zones** (12 pm CT = 11 am ET, 1 pm PT) and does not interfere with customer‑facing activities.

#### 2.3 Automated Validation Script (PowerShell)

```powershell
# Compare source vs target for a given mailbox
param($User)

$src = Get-MailboxFolderStatistics -Identity $User -Database "DB01"
$dst = Get-MailboxFolderStatistics -Identity $User -Mailbox $User

$diff = Compare-Object $src $dst -Property FolderPath, ItemsInFolder, Size, LastModifiedTime

if($diff){
    Write-Error "Metadata mismatch for $User"
    # Log to immutable blob
    $json = $diff | ConvertTo-Json -Depth 5
    $hash = (Get-FileHash -InputObject $json -Algorithm SHA256).Hash
    Set-AzStorageBlobContent -File $json -Container "migration‑audit" -Blob "$User‑$(Get-Date -Format o).json" -Properties @{'x-ms-blob-type'='BlockBlob';'x-ms-immutability-policy'='true'} -Context $ctx
}
else{
    Write-Host "PASS: $User"
}
```

All scripts are version‑controlled in a **Git repo** with **GPG‑signed commits**; each run is logged to Azure Log Analytics and archived.

## 3. Cut‑Over Technique (Given Exchange 2016 is Unsupported)

1. **Hybrid Migration with MRS** – Even though Exchange 2016 is out of support, the Hybrid Configuration Wizard still works for **migration‑only** purposes. MRS performs a **two‑phase copy**:  
   * **Initial full copy** (performed during the sync window).  
   * **Incremental delta copy** (runs continuously until cut‑over).  

2. **Final Cut‑Over Steps (per batch)**  
   * **Step 1 – Verify Sync Lag** – Ensure `LastSyncTime` < 5 minutes and `SyncStatus` = *Completed*.  
   * **Step 2 – Set `RemoteRoutingAddress`** – `Set-Mailbox -Identity user@domain.com -RemoteRoutingAddress user@remote.onmicrosoft.com`. This forces all inbound SMTP to be delivered to the Office 365 mailbox.  
   * **Step 3 – Disable On‑Prem Mailbox** – `Disable-Mailbox -Identity user@domain.com -JournalingAddress user@remote.onmicrosoft.com`. The mailbox is kept in “soft‑deleted” state for 30 days (required for hold).  
   * **Step 4 – Update DNS (MX) – *only after the last batch of the week*** – Change MX record TTL to 5 minutes a week ahead, then point to Office 365. Because the MX points to the same target for all batches, the cut‑over is atomic.  

3. **Why This Works Despite Unsupported Server**  
   * No **new features** are required from Exchange 2016; we only use **core MRS replication** and **Hybrid** features that were supported up to Exchange 2016.  
   * The unsupported status only impacts **security patches**; we mitigate risk by:  
     * Isolating the server on a **dedicated VLAN** with no internet exposure.  
     * Applying **last‑known‑good cumulative update** (CU 17) before migration.  
     * Running **offline antivirus scan** on exported PSTs (if any).

### Executive Summary & Strategic Approach

**Migration Method:** **Hybrid Migration with Exchange Online Move Requests.**
Given Exchange 2016 is End-of-Extended Support (EOS) and branches require **zero interruption** across two time zones with no company-wide downtime window, a Hybrid configuration is the only viable approach. A Hybrid setup allows mailbox data to move in the background while users remain connected to the on-prem server. Outlook profiles update automatically, and mail flow is seamlessly rerouted. There is no user-facing downtime, and the migration tool includes throttling to prevent performance degradation at branches.

**Key Risk Mitigations:**
*   **Exchange 2016 EOS:** Pre-migration full backup of the Exchange database is mandatory. Since Microsoft will not support a crash, the source must be restorable if the server fails during migration.
*   **Regulatory/Chain of Custody:** Legal Hold and Preservation are applied immediately. Pre- and Post-migration audits with cryptographic verification of item counts and metadata timestamps provide the required documented chain.
*   **Operational:** Throttling is configured to reserve bandwidth/CPU for branch operations. Batches run 24/7 server-side, but throttling ensures no branch performance impact regardless of time zone.
*   **Timeline:** Migration is scheduled to complete **14 days prior** to the core-banking cutover week, creating a safety buffer.

This plan addresses the migration of 340 Exchange Server 2016 mailboxes from an unsupported environment to Microsoft 365 while meeting regulatory, operational, and timeline constraints. The approach uses staged migration with careful sequencing to minimize business disruption.

## Migration Approach

### Primary Migration Method
**Staged Migration with Hybrid Configuration** - This approach provides:
- Minimal disruption during business hours
- Full compliance with retention requirements
- Rollback capability
- Regulatory chain of custody maintenance

### Hybrid Configuration Requirements
1. Configure hybrid between source Exchange 2016 and target Microsoft 365
2. Set up hybrid migration connectors
3. Implement proper authentication (ADFS or Azure AD Connect)
4. Configure mailbox move requests with proper tracking

## Phased Migration Timeline

### Phase 1: Preparation (Week 1-2)
**Day 1-5: Environment Setup**
- Configure hybrid configuration with Exchange 2016 and Microsoft 365
- Set up Azure AD Connect for authentication
- Configure hybrid migration connectors
- Verify connectivity between environments

**Day 6-10: Compliance & Testing**
- Document chain of custody procedures
- Test backup/restore procedures for source environment
- Validate retention policies in Microsoft 365
- Conduct dry-run migration of 10 test mailboxes

**Day 11-14: Planning & Communication**
- Finalize migration batch assignments
- Communicate with branch managers about migration windows
- Establish monitoring procedures
- Prepare rollback documentation

### Phase 2: Migration Execution (Week 3-8)
**Week 3-4: Initial Migration**
- Batch 1: 68 mailboxes (20% of total)
- Schedule during off-peak hours for each branch (typically 7-9 PM local time)
- Monitor migration progress and performance
- Validate retention requirements for migrated mailboxes

**Week 5-6: Continued Migration**
- Batch 2: 68 mailboxes (20% of total)
- Continue with same scheduling approach
- Perform health checks on both environments
- Document migration status and any issues

**Week 7-8: Final Migration**
- Batch 3: 68 mailboxes (20% of total)
- Batch 4: 68 mailboxes (20% of total)
- Batch 5: 68 mailboxes (20% of total)
- Complete initial migration of all mailboxes

### Phase 3: Validation & Cutover (Week 9)
- Final validation of all migrated mailboxes
- Verify metadata preservation
- Test all functionality including search, retention, and compliance
- Prepare for final cutover to Microsoft 365

## Rollback Plan for Failed Batch Migration

### Immediate Actions (Within 2 Hours)
1. **Pause Migration**: Stop all pending mailbox moves for the affected batch
2. **Notification**: Alert IT management, compliance team, and branch managers
3. **Documentation**: Record exact failure symptoms and error codes
4. **Isolation**: Isolate affected mailboxes to prevent further issues

### Recovery Procedures
**Option 1: Retry Migration**
1. Check connectivity between source and target environments
2. Verify user account status in source environment
3. Retry mailbox move with same parameters
4. Monitor for recurrence

**Option 2: Manual Recovery**
1. Export problematic mailboxes using Exportsniff or similar tools
2. Restore from backup of source Exchange 2016 environment
3. Re-import mailboxes to source environment
4. Re-attempt migration with updated parameters

### Communication Protocol
- Notify impacted users immediately
- Provide temporary email access via web interface
- Establish new migration timeline with stakeholders
- Document all actions taken for audit purposes

## 3. Cutover Approach (Exchange 2016 EOL Context)

### Why Not Native Cutover?
Microsoft's native cutover wizard locks each mailbox 1–2 hours for final sync/DNS update. With 340 mailboxes and 9–5 branch hours across two TZs, this violates the operational constraint and creates unacceptable customer/transaction risk.

### Selected Approach: Incremental Sync + Per-Branch Final Cutover
1. **Exchange 2016 Hardening (Day 1–3):**
   - Disable IMAP, POP3, OWA, EWS external endpoints
   - Retain only migration endpoint (EWS API) with IP-restricted access
   - Disable user-facing authentication; keep admin accounts for migration only
   - Run pre-migration vulnerability scan; document baseline
2. **Online Incremental Sync:**
   - Third-party tool performs full sync → daily incremental deltas during 9–5
   - Users remain fully productive on Exchange 2016 throughout sync
   - Network bandwidth throttled to preserve core banking/branch operations
3. **Final Cutover (Per Branch, Local Off-Hours):**
   - For each branch: pause user access → run final delta sync (≤5 min) → update MAPI/OAB/Autodiscover/MX → lock mailbox 15–30 min → verify hash parity → unlock
   - Schedule Zone A branches 5–9 PM local, Zone B branches 5–9 PM local. **No simultaneous cross-zone lockouts.**
4. **EOL Risk Mitigation:**
   - Exchange 2016 is intentionally decommissioned within 45 days, eliminating long-term patch exposure
   - Source databases retained in read-only, air-gapped state for 90 days post-migration for regulatory audit
   - Migration performed before any EOL-induced instability can compound with core-banking cutover

## 4. Rollback Plan (Batch Failure Mid-Migration)

### Trigger Conditions
- Sync error rate >5% in batch
- SHA-256 hash mismatch on `ReceivedDate`/`MessageClass`/item count
- User access failure post-cutover
- Regulatory/compliance flag
- Exchange 2016 endpoint instability

### Rollback Steps
| Step | Action | Chain-of-Custody Impact |
|------|--------|--------------------------|
| 1 | Pause batch; isolate affected mailboxes in migration tool | Tool locks batch; no further sync until resolved |
| 2 | Revert MX, Autodiscover, MAPI/OAB to point back to Exchange 2016 | Users instantly restored to source; mail flow resumes |
| 3 | If mailbox moved but corrupted/incomplete: use tool's `Rollback Mailbox` to move back with full content + metadata | Source copy remains intact; destination copy quarantined |
| 4 | If partial sync failed: tool resumes from last successful delta checkpoint | No re-download of already-synced items; audit log shows exact sync boundary |
| 5 | Root cause analysis (network, license, EWS auth, mailbox corruption) | Documented in incident log; retained for compliance |
| 6 | Re-validate with 3-test mailbox before resuming batch | Full hash parity required before proceeding |
| 7 | Notify compliance officer if metadata chain was broken | Immutable source + destination copies preserved until sign-off |

### Critical Rollback Principles
- **Source data never deleted** until regulatory audit package is signed off (90-day immutable hold)
- **Rollback preserves chain of custody** because both source and destination copies are retained with cryptographic hashes
- **No data loss guarantee** via delta-sync checkpointing and tool-built-in retry/resume

This migration requires a high-integrity, low-impact approach. Because the source is Exchange 2016 (unsupported) and the regulatory requirements are stringent regarding metadata preservation (specifically original delivery timestamps), an **Exchange Hybrid Migration** is the only viable method. 

Unlike IMAP or PST imports, the Hybrid approach uses Exchange Web Services (EWS) to move mailboxes, ensuring that all MAPI properties, folder structures, and metadata are preserved, providing the "chain of custody" required for compliance.

---

### I. The Migration Approach: Exchange Hybrid
To meet the constraints, we will implement a **Minimal Hybrid Configuration**.

1.  **Identity Synchronization:** Deploy Microsoft Entra Connect (formerly Azure AD Connect) on-premises to synchronize user identities from the community bank’s Active Directory to the acquiring bank's Microsoft 365 tenant. This ensures users have matching UPNs (User Principal Names) and prevents "identity mismatch" during the move.
2.  **The "Bulk-Sync" Strategy:** We will use the **Hybrid Incremental Sync** method.
    *   **The Bulk Phase:** Most data is synchronized in the background while users are working. This consumes minimal bandwidth and has zero impact on mailbox availability.
    *   **The Delta Phase:** Only the "delta" (new mail received since the initial sync) is moved during the actual cutover window.
3.  **Branch-Specific Cutover:** Because of the time zone/9-5 constraint, we will not perform a "company-wide" cutover. Instead, we will perform **Branch-by-Branch Cutover Windows**. We will execute the final "Delta Sync" and mailbox switch for Branch A during its specific late-afternoon window, then move to Branch B in its respective window.

---

### II. Phased Migration Plan

#### Phase 1: Preparation & Compliance Audit (Days 1–14)
*   **Infrastructure Setup:** Install Entra Connect and configure the Exchange Hybrid Configuration Wizard (HCW).
*   **Integrity Baseline:** Perform a pre-migration audit. Export a "Manifest Report" of all 340 mailboxes, including item counts and metadata checksums, to establish the **Chain of Custody** baseline.
*   **Network Optimization:** Ensure the on-prem Exchange 2016 has sufficient resources to handle EWS traffic during the background sync.

#### Phase 2: Pilot & Testing (Days 15–21)
*   **Pilot Group:** Migrate 10 non-critical mailboxes (IT staff) to test the end-to-end flow.
*   **Regulatory Validation:** Use a third-party forensic tool or detailed PowerShell logging to verify that metadata (Original Received Date/Time) in the M365 mailbox matches the on-prem source exactly.

#### Phase 3: The High-Volume Migration (Days 22–40)
*   **Batch Execution:** Group the 340 mailboxes into batches (e.g., 20 mailboxes per branch).
*   **Incremental Sync:** Start the background synchronization for all batches. This happens during business hours without interruption.
*   **The "Rolling Cutover":** At the end of each branch’s business day, the "Switch" is flipped for that specific branch. Users will experience a single logout/login event (or a profile update) the next morning.

#### Phase 4: The Blackout Period (Days 40–47)
*   **Change Freeze:** Total moratorium on all IT changes. No mailbox moves, no password resets, no configuration changes.
*   **Core-Banking Cutover:** The core-banking system transition occurs here.

#### Phase 5: Post-Migration & Decommissioning (Day 48+)
*   **Cleanup:** Decommission the on-prem Exchange 2016 environment once all mailboxes are verified.
*   **Final Compliance Report:** Generate the final "Migration Completion Report" to close the Chain of Custody documentation.

---

### III. Rollback Plan: The "Source-of-Truth" Reversion
If a batch migration fails (e.g., data corruption or sync error), the following protocol will be enacted:

1.  **Immediate Halt:** Stop the migration service for the specific batch to prevent "split-brain" (where some mail is in M365 and some is on-prem).
2.  **Redirect Mail Flow:** Ensure the MX records or the transport rules are still pointing to the on-prem Exchange server for the affected users.
3.  **Rollback via Mailbox Remount:** Since we are using Hybrid, the original mailbox remains on the on-prem Exchange server until the move is *fully* completed and verified. We simply "abort" the move command. The user’s mailbox remains the on-prem version.
4.  **Root Cause Analysis (RCA):** Before attempting a retry, the logs must be audited to ensure the failure wasn't caused by a regulatory/metadata conflict.

---

### IV. Sequencing & The "Blast Radius" Analysis

**The Critical Sequence:**
The email migration must be **largely completed (80-90% through the "Bulk Sync" phase) BEFORE the core-banking cutover begins.**

**The Blast Radius of Incorrect Sequencing:**
If the email migration and core-banking cutover overlap (i.e., if you attempt to migrate mailboxes during the core-banking transition week), the "Blast Radius" includes:

1.  **Support Paralysis (The "Dual-Incident" Trap):** If a branch manager cannot access email to report a core-banking error, the core-banking implementation team loses their primary communication channel. IT will be unable to distinguish between a "Core System" issue and an "Email/Identity" issue.
2.  **Operational Blindness:** During core cutovers, staff rely heavily on "Transaction Logs" or "Instructional Emails" sent by the implementation team. If their mailboxes are in a "re-profiling" state during this window, the core transition will likely fail due to communication lag.
3.  **Audit Failure:** If errors occur in both systems simultaneously, the "Chain of Custody" documentation required by regulators becomes muddied. It becomes impossible to prove whether a data anomaly occurred during the *email* migration or the *core* database migration.

**Conclusion:** By utilizing Hybrid Migration with a "Bulk-Sync/Late-Delta" approach, we satisfy the time-zone constraints and metadata requirements, while the "Blackout Period" protects the high-stakes core-banking conversion.

## 2. Cut‑Over Approach (Operational Constraints)

| Constraint | How We Address It |
|------------|-------------------|
| **No single “after‑hours” window** – branches operate 9 am‑5 pm across **two time‑zones** (EST & CST primarily, with a few Mountain & Pacific sites). | Migration is **time‑zone‑driven**. Each batch runs during the **local off‑peak window** of the *majority* of users in that batch (e.g., 07:00‑09:00 EST for NY, 12:00‑14:00 CST for Chicago). This respects branch business hours and gives staff a quiet window to receive migration‑completion emails. |
| **Mailbox access cannot be interrupted** – users must stay online for customer‑service during cut‑over. | We **pre‑stage** mailboxes (copy to M365) **without disabling the source**. Users continue to read/write to the on‑prem mailbox until the final cut‑over step, which is performed **outside of business hours** for that region (e.g., 23:00 PST). The final cut‑over is a **single‑pass “switch”** that takes < 30 seconds per mailbox and is performed **after** the branch has closed. |
| **Regulatory chain‑of‑custody** – every message must retain original metadata. | • All migration batches set **`TargetDeliveryTime` = OriginalReceivedTime** via the migration API; this is validated post‑migration. <br>• Every batch writes a **tamper‑evident log** (hashes, timestamps, user‑IDs) to an **immutable Azure Blob** with legal‑hold retention > 7 years. <br>• A **pre‑migration snapshot** of the on‑prem store (VSS backup) is stored in a **write‑once** repository and referenced in the audit log for any rollback. |
| **Bandwidth & WAN limits** – branch connections are limited. | Throttling is **per‑user** (`Set‑MigrationUser -ThrottleLimit`) and **per‑batch** (max 500 mailboxes, 5 Mbps per mailbox). The migration engine dynamically adjusts based on real‑time bandwidth telemetry. |
| **No overlap with core‑banking cut‑over** – email must be fully functional for cut‑over questions. | Migration batches **stop** 5 business days before the core‑banking cut‑over window; a **“no‑migration”** freeze is enforced during the core‑banking week. Final cut‑over (if any) occurs **after** the core‑banking go‑live, ensuring email is stable for the cut‑over support crew. |

## 3. Rollback Plan (If a Batch Fails Mid‑Migration)

1. **Detect Failure** – Migration monitoring alerts when > 5 % of mailboxes in a batch report “Failed” or when **timestamp drift** > 5 seconds.  
2. **Pause the Batch** – `Stop-MigrationBatch` is invoked automatically; the batch is placed in **“Paused – Awaiting Review”** state.  
3. **Activate Rollback Snapshot** –  
   * The **pre‑migration VSS snapshot** of each failed mailbox is already stored in the immutable backup store.  
   * A **PST export** (encrypted, hash‑verified) of the same mailbox exists in the **Secure Transfer Hub**.  
   * Using PowerShell, the admin runs `Restore-MigrationUser -Identity <source> -FromBackup <snapshot‑path>` – this restores the mailbox to its exact pre‑migration state, including original timestamps (the snapshot is application‑consistent).  
4. **Re‑apply Retention/Hold Flags** – A PowerShell script re‑applies the original retention tags, litigation holds, and compliance tags that were present before migration.  
5. **Communicate** – An automated email goes to the Branch Manager, Compliance Officer, and Migration Lead with: <br> - Batch ID, affected mailboxes, root cause, ETA for retry, and reassurance that **no data loss** occurred.  
6. **Retry or Escalate** – If the failure is transient (e.g., network glitch), the batch is re‑started after a 30‑minute back‑off. If the root cause is systemic (e.g., schema mismatch), the Migration Lead escalates to the Architecture team, and the batch may be **re‑designed** (different throttling, adjusted mailbox ordering).  
7. **Audit Log Update** – All rollback actions, timestamps, and restored hashes are appended to the immutable audit repository with a “ROLLBACK‑EVENT” flag for future audit.  

**RTO/RPO Targets** –  
* **RTO** (time to restore a failed mailbox) ≤ **15 minutes** (automation).  
* **RPO** (potential data loss) = **0** because we restore from a **point‑in‑time VSS snapshot** taken before migration began.

## 4. Sequencing Relative to the 45‑Day Core‑Banking Cut‑Over  

### 4.1 Timeline Overview  

| Calendar Week | Activity | Notes |
|---------------|----------|-------|
| **W‑6 → W‑4** | **Discovery & Design** (Phases 0‑1) | No migration activity; compliance sign‑off obtained. |
| **W‑3** | **Pilot** (Phase 2) | Pilot migration executed; validation completed; sign‑off obtained. |
| **W‑2 → W‑1** | **Staged Production Migration** (Phase 3) – **All batches except the final cut‑over batch** | Migration continues **until the end of Week ‑1** (i.e., 5 full business days **before** the core‑banking cut‑over week). |
| **W‑0** | **Core‑Banking Cut‑Over Freeze** (45‑day cut‑over week) | **No migration activity** – email service must remain fully operational for cut‑over related questions. |

### 4.2 Blast‑Radius Analysis  

| Failure Scenario | Potential Impact | Mitigation |
|------------------|------------------|------------|
| **Migrating a batch **during** the core‑banking cut‑over week** | • Email outage for *all* branches would cripple the cut‑over support team (they cannot answer customer questions). <br>• Regulatory breach (loss of original timestamps) → possible audit finding. <br>• Change‑freeze conflict with core‑banking team → extended schedule, cost overruns. | • Strict **freeze**: all migration scripts are disabled via Azure DevOps pipeline lock. <br>• Automated **calendar interlock** prevents any pipeline trigger within the cut‑over week. |
| **A batch fails and rollback is required** | • Temporary loss of access to migrated mailboxes (≤ 15 min). <br>• If rollback fails, data could be lost → compliance breach. | • **Rollback snapshot** taken *before* migration starts; immutable backup ensures 0 data loss. <br>• Redundant PST copy stored in write‑once vault. <br>• Pre‑approved **rollback run‑book** with step‑by‑step automation. |
| **Incorrect sequencing (e.g., moving a high‑priority branch after the cut‑over week)** | • That branch’s staff would be without email during the cut‑over, causing service degradation for customers and possible regulatory breach. <br>• Re‑scheduling would push the migration into the next month, jeopardizing the 45‑day core‑banking timeline. | • **Branch Criticality Matrix** ensures “high‑risk” branches (e.g., main‑office, compliance, senior execs) are migrated **earliest** in the staged schedule. <br>• Automatic **dependency check** in the migration orchestration tool prevents moving a branch that is flagged as “critical for cut‑over support”. |
| **Bandwidth saturation causing network latency across branches** | • Users may experience slow Outlook/OWA performance, leading to missed calls and SLA breaches. | • **Throttle per‑batch** and **bandwidth‑cap per branch**; real‑time monitoring with alerts to pause a batch if WAN utilization > 80 %. |
| **Retention tag mismatch after migration** | • Failure to meet statutory retention periods → legal exposure. | • Migration API automatically **re‑applies** source retention tags; a **post‑migration compliance search** validates that each tag exists in target. <br>• Any mismatch triggers an immediate rollback of that batch. |

**Bottom‑line:** The **only safe sequencing** is to **complete all staged migrations before the core‑banking cut‑over week**, execute a **minimal final cut‑over batch after** the core‑banking go‑live, and keep a **rollback‑ready snapshot** throughout. Any deviation expands blast radius dramatically—potentially causing service outage, compliance penalties, and project delays measured in **weeks** rather than days.

1. PRE‑CHECK (06:30 EST)
   • Verify Azure Migration Hub shows “Ready – No Errors”.

   • New‑MigrationBatch -Name "MIG‑BR‑001‑NY" -SourceServer ex2016‑ny –TargetTenant <M365‑Tenant> -AutoStage $true -BatchSize 500

3. MONITOR (real‑time dashboard)
   • % Completed, Errors, Avg. Latency, Timestamp Drift.

   • Run‑ComplianceSearch -SourceMailboxes "MIG‑BR‑001‑NY" -TargetMailboxes "MIG‑BR‑001‑NY‑M365"

   • Log entry in Change‑Management System (CMS‑12345).

ROLLBACK TRIGGER (if ANY of the following occurs):
   a) ErrorRate > 10 % for > 5 min.
   b) TimestampDrift > 10 seconds.
   c) ComplianceSearch fails to find > 99 % of messages.
   → Execute Stop‑MigrationBatch, then Run‑Restore‑FromSnapshot -Batch "MIG‑BR‑001‑NY".

## 7. Risks & Mitigations (Quick Reference)

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|------------|
| **Migration tool does not preserve OriginalReceivedTime** | Low (vendor supports it) | High (regulatory breach) | Run pilot with hash verification; enforce `TargetDeliveryTime` in API call; lock configuration via code‑review. |
| **Network saturation causing branch latency** | Medium | Medium | Throttle per‑mailbox; schedule batches during low‑traffic windows; monitor WAN utilization; automatic pause if >80 % utilization. |
| **Rollback fails due to corrupted snapshot** | Low | Critical | Take **dual backups** (VSS + PST); verify hash before migration; store snapshots in write‑once vault; test restore on a non‑production mailbox before go‑live. |
| **Change‑freeze conflict with core‑banking team** | Medium | High | Formal **Change‑Control Board (CCB)** gate; schedule migration freeze 5 days before core‑banking cut‑over; obtain written sign‑off from both teams. |
| **Branch manager refuses migration during business hours** | Low | Medium | Provide **pre‑notification** and schedule migration for the branch’s *local* off‑peak window; obtain written acknowledgment of the off‑peak slot. |
| **Retention tags get lost** | Low | High | Pre‑export retention tag list; use migration API’s `-RetentionTags` parameter; post‑migration compliance search validates 100 % presence. |

## 8. Final Recommendations  

1. **Lock the migration schedule** now: complete all staged batches **by the end of Week ‑1** before the core‑banking cut‑over week.  
2. **Freeze any further migration activity** during the core‑banking cut‑over week – enforce via pipeline lock and CCB sign‑off.  
3. **Execute the final cut‑over batch** (if any) **immediately after** the core‑banking go‑live, using the “cut‑over” migration mode with a 30‑second cut‑over window per mailbox.  
4. **Maintain the immutable audit repository** throughout the project; it is the single source of truth for the chain‑of‑custody required by regulators.  
5. **Conduct a “post‑mortem”** after migration completion to capture lessons learned and update the bank’s **Email Migration SOP** for future acquisitions.  

Following this phased, time‑zone‑aware, and audit‑driven approach will satisfy the regulatory retention and chain‑of‑custody obligations, keep branch email services continuously available, and ensure that the migration does not interfere with the critical 45‑day core‑banking cut‑over—thereby minimizing blast radius and preserving operational continuity.
