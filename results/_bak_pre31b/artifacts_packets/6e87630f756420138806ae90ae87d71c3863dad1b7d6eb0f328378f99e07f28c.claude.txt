## Task

The task given to every model in this cohort:

Your MSP monitors IT for a contract biotech lab that stores irreplaceable sponsor study
samples in 14 ultra-low-temperature (-80C) freezers, each with an IoT temperature sensor
feeding your RMM/monitoring platform. Current alert rule: any freezer reading warmer than
-75C fires a P1 page to the on-call engineer immediately. Problem: these freezers routinely
cycle up to about -70C during a normal defrost cycle, which happens roughly every 6 hours and
lasts about 12 minutes -- so each freezer generates several false P1 pages per day. On-call
engineers have started acknowledging and silencing pages without checking them, which is
dangerous, because the first few minutes of a genuine compressor failure look identical to a
defrost cycle on the temperature graph alone. Propose a retuned alerting strategy: what the
new threshold/timing logic should be so a normal defrost cycle no longer pages on-call, and
a compensating control (not just a wider static threshold) that still guarantees a genuine
compressor failure is caught given that on-call has started ignoring pages.

To solve this problem, we must move away from **"point-in-time"** alerting and move toward **"state-based"** alerting. The goal is to filter out the predictable "noise" of the defrost cycle while creating a fail-safe for the human element (the engineer's tendency to ignore pages).

### 1. The New Alerting Logic: "Threshold + Duration"

The current rule is a "Level Trigger" (If $X > Y$, then Alert). This is inappropriate for cyclical processes. We must switch to a **"Duration Trigger"** (If $X > Y$ for $Z$ minutes, then Alert).

**The Proposed Rule:**
*   **Condition:** Temperature $> -75^{\circ}\text{C}$
*   **Duration (Persistence):** Must be sustained for **20 minutes**.
*   **Logic:** Since the defrost cycle is known to last only 12 minutes, a 20-minute threshold ensures that the "spike" caused by the cycle never reaches the threshold required to trigger a page.

**Why this works for compressor failures:**
A compressor failure is a sustained event. Once the cooling mechanism fails, the temperature will not return to -80°C after 12 minutes; it will continue to climb linearly or exponentially. By setting the window to 20 minutes, we provide a 8-minute "buffer" beyond the defrost cycle, ensuring the engineer is only woken up when the temperature rise is non-cyclical.

New threshold/timing logic: don't just move the static threshold warmer (e.g., to -65C) --
that only delays detection of a real failure, since a genuine compressor failure also passes
through -70C on its way up and would now take even longer to page. Instead, add a duration
(dwell-time) condition on top of the existing -75C threshold: only fire the P1 if the reading
stays above -70C for longer than a normal defrost cycle -- defrost cycles run about 12 minutes,
so require the breach to be sustained for, say, 20 consecutive minutes before paging. That
filters out every routine ~12-minute defrost cycle while still catching a real failure within
about 20 minutes of onset, which is still fast enough to act on a -80C freezer.

Compensating control: given that on-call has already started silencing pages without checking
them, a wider/smarter threshold alone isn't enough -- add a secondary, independent signal that
doesn't depend on the same temperature-threshold logic being trusted, such as monitoring
compressor run-time or power draw (a failing compressor's duty cycle looks different from a
normal defrost well before the temperature climbs that far), or an automatic escalation rule
that re-pages a second on-call engineer if the first page isn't acknowledged within a set
window. That way, even if the primary temperature alert is ignored out of habit, a second,
differently-triggered signal still catches a genuine failure before sample loss.
