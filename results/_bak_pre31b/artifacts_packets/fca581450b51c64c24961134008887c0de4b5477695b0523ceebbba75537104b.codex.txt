# Cybersecurity -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Severity is triaged correctly against the actual impact described, response actions follow containment before eradication before recovery, and any CVE, CWE, or ATT&CK reference used is real and correctly applied (never invented). Evidence-preservation is called out before disruptive remediation, and breach-notification or compliance timelines are flagged when the scenario implies regulated or sensitive data. The answer is calibrated about what needs live forensics versus what can be assessed from the facts given.
Example character: a triaged action list that isolates the affected system first, preserves logs, then patches, with the real CVE cited only where it is genuinely relevant.

## 7 -- Strong
The response plan is sound and correctly ordered (containment before eradication), and is directly usable by a responder. References to standards or CVEs are generic rather than specific, or evidence-preservation/notification timing gets only a light mention. Severity is judged reasonably even if not formally scored.
Example character: a correct incident-response sequence that never names a specific CVE or ATT&CK technique even where the prompt supports one.

## 5 -- Adequate
The advice reads as a generic security checklist (patch systems, enable MFA, monitor logs) that is directionally correct but not prioritized by the actual severity or tailored to the specific incident described.
Example character: a list of general hardening steps with no sense of which one matters most given the described exposure.

## 3 -- Weak
The response gets the ordering wrong (patches or removes an attacker's access before containing them), misjudges severity, or pads the answer with boilerplate ("enable a firewall") that does not engage the specific scenario.
Example character: jumps straight to "eradicate the malware" on an active intrusion without isolating the host first.

## 0 -- Unusable
Cites a fabricated CVE, CWE, or CVSS score as if verified, or recommends actively dangerous steps (disable logging, do not isolate an active breach) as sound practice. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Fabricated CVE, CWE, or CVSS identifiers presented as real.
- Eradication or patching recommended before containment on an active incident.
- Recommending disabling logging or otherwise destroying evidence.
- Ignoring implied breach-notification or regulatory timelines when sensitive data is involved.
- Treating every finding as equally critical with no severity differentiation.

## Unit-specific excellence markers
- Severity correctly triaged and prioritized against the described impact.
- Containment-before-eradication-before-recovery ordering respected.
- Real, correctly-applied CVE/CWE/ATT&CK references where relevant.
- Evidence-preservation explicitly called out.
- Notification or compliance timeline awareness when data exposure is implied.

# PHISHING RESPONSE RUNBOOK: Follina Credential Harvesting Incident
**Audience:** Level-1 Helpdesk Technician (No Security Background)  
**Environment:** Microsoft 365, 60 employees, MSP-managed  
**Affected Users:** 6 (word document openers)  
**Confirmed Artifacts:** Credential harvester, foreign-ASN sign-ins without MFA, 2 inbox rules forwarding/deleting "invoice" emails

---

## ⚠️ CRITICAL CONTEXT: WHY A PASSWORD RESET ALONE IS NOT ENOUGH
Before you take any action, understand why simply forcing a password change will **not** stop the attacker:

1. **Sign-in logs show no MFA challenge** → Either MFA isn't enforced for these accounts, Conditional Access is misconfigured, or the attacker used **legacy authentication** or an **OAuth app** that bypasses MFA entirely. Changing the password does not block legacy auth or invalidate OAuth consent grants.
2. **Refresh tokens may already be compromised** → M365 issues session tokens that can be refreshed without re-entering credentials. A password reset does not automatically revoke existing refresh tokens or trusted device sessions.
3. **Persistence is already in place** → The attacker has already created inbox rules, may have set up mail forwarding, granted themselves mailbox access, or installed endpoint backdoors via Follina. None of these depend on the user's password.
4. **Follina (CVE-2022-30190) executes via MSDT** → The exploit drops payloads directly on the endpoint. If the machine isn't cleaned, the attacker can re-harvest credentials, modify mailbox settings, or maintain network access regardless of password changes.

**Bottom line:** Reset passwords, but **revoke sessions, block MFA bypass vectors, remove all persistence artifacts, and clean the endpoints** or the attacker will retain access.

## 🔴 PHASE 1: IMMEDIATE CONTAINMENT (0–2 HOURS)
*Goal: Lock the attacker out of active sessions and block new logins.*

| Step | Action | Exact UI Path |
|------|--------|---------------|
| 1 | **Revoke all active sessions** for the 6 affected accounts | M365 Admin Center → Users → Active Users → Select each user → Click **Revoke sessions** |
| 2 | **Force password reset** for all 6 accounts | Same page → Click **Reset password** → Check "Require user to change password at next sign-in" |
| 3 | **Restrict sign-in locations** to known countries | M365 Admin Center → Users → Active Users → Select each → **Manage sign-in restrictions** → Restrict to approved countries (block all others temporarily) |
| 4 | **Block legacy authentication** for affected accounts | Entra ID (Azure AD) → Users → Select each → **Authentication methods** → Disable "App passwords" and block legacy protocols (IMAP/POP/SMTP basic auth) |
| 5 | **Enable/enforce MFA** on all 6 accounts | Entra ID → Users → Select each → **Authentication methods** → **Enforce** Multi-Factor Authentication |
| 6 | **Document** start time, actions taken, and who performed them | Copy-paste into incident log (ticket #XYZ) |

> 🛑 **Stop & Escalate If:** You cannot find the "Revoke sessions" button, sign-in restrictions are greyed out, or MFA cannot be enforced. This indicates misconfigured Conditional Access or tenant-level restrictions. Escalate to your MSP Security/SOC team immediately.

## 🔵 PHASE 2: MAILBOX DEEP INSPECTION (4–8 HOURS)
*Goal: Remove all persistence artifacts in every affected mailbox. The 2 known "invoice" rules are just the tip of the iceberg.*

### What to Check (Beyond Inbox Rules)
Run through this checklist for **each of the 6 affected mailboxes**. Do not skip any step.

| Artifact to Check | Why It Matters | Exact UI Path | What to Do |
|-------------------|----------------|---------------|------------|
| **Inbox Rules** | Attackers hide forwarding, deletion, or reply rules | Exchange Admin Center → Mail flow → **Rules** | Delete any rule that forwards, copies, deletes, or redirects. Pay special attention to rules with misleading names like "Accounting", "Backup", or "AutoSort". |
| **Mail Forwarding (SMTP & Client)** | Allows silent exfiltration even without inbox rules | Exchange Admin Center → Mailboxes → Select user → **Mail flow** → **Mail forwarding** | Disable forwarding. If a forwarding address exists, remove it. |
| **Delegated Access (Full Access / Send As)** | Lets attacker log in as the user without their password | M365 Admin Center → Users → Select user → **Mail** → **Mailbox delegation** | Remove all "Full access", "Send As", and "Send on behalf" permissions. |
| **Shared Mailbox Access** | Often overlooked persistence vector | Same as above → Check **Shared mailbox access** tab | Remove any unfamiliar users/groups. |
| **Calendar Permissions** | Can be used to schedule meetings, send lures, or hide activity | Exchange Admin Center → Recipients → Mailboxes → Select user → **Calendar** | Remove all "Reviewer", "Editor", or "Owner" permissions for unknown users. |
| **Out-of-Office / Auto-Reply** | Can silently reply to internal/external senders to appear legit | Exchange Admin Center → Mailboxes → Select user → **Message** → **Automatic replies** | Disable auto-replies. |
| **Hidden Contacts / Groups** | Used to send phishing from trusted sender addresses | Outlook Web (OWA) → Contacts → Filter by **Hidden** | Delete any hidden contacts or groups. |
| **OAuth Applications / Consent Grants** | Apps that bypass MFA and access mailbox data | Entra ID → Enterprise Applications → **User consent** → **Apps configured for user consent** | Revoke consent for any unfamiliar app, especially those requesting `Mail.ReadWrite`, `Mail.Send`, or `User.Read`. |
| **Mailbox Auditing Logs** | Shows what the attacker actually did | Entra ID → Protection → **Mailbox auditing** → Enable & search logs for the 6 accounts | Look for `New-InboxRule`, `Set-Mailbox`, `Add-MailboxPermission`, `SendAs` from unusual IPs or app IDs. Document findings. |

> 🛠️ **Tip:** For each step, sort/filter by **Date Created** or **Modified** and look for changes within the 48 hours after the phishing email. Delete anything created during that window.

## 🟡 PHASE 3: ENDPOINT TRIAGE (FOLLINA-SPECIFIC) (8–12 HOURS)
*Goal: Clean the 6 endpoints that opened the Word file. Follina executes via MSDT and leaves predictable artifacts.*

| Step | Action | How to Do It |
|------|--------|--------------|
| 1 | **Check network connections** to the harvesting page | Open Command Prompt (Admin) → `netstat -ano | findstr ESTABLISHED` → Look for connections to unknown IPs/domains. Compare to sign-in logs. |
| 2 | **Scan for malicious scheduled tasks** | Task Scheduler → Task Scheduler Library → Sort by **Last Run Time**. Delete any task created in the last 48 hours that runs scripts, `msdt.exe`, `cmd.exe`, or `powershell.exe`. |
| 3 | **Check startup items & browser extensions** | Task Manager → Startup tab. Chrome/Edge → Extensions. Remove anything unfamiliar. |
| 4 | **Look for MSDT/Follina artifacts** | Open File Explorer → Navigate to `%ProgramData%\Microsoft\Diagnosis\ExternalData\` and `C:\Windows\System32\` → Look for recently modified `.dat`, `.xml`, or `.exe` files. |
| 5 | **Run Windows Defender Offline Scan** | Settings → Update & Security → Windows Security → Virus & threat protection → **Scan options** → Choose **Microsoft Defender Offline scan** → Restart & let it run. |
| 6 | **Patch CVE-2022-30190** | Windows Update → Check for updates → Install all pending patches. If Windows Update is blocked, manually download from Microsoft Update Catalog. |
| 7 | **Document** findings & endpoint status | Add to ticket. Note if machine appears clean or requires imaging/replacement. |

> 🛑 **Stop & Escalate If:** You find suspicious processes you can't terminate, the machine won't boot, or network connections persist after scan. Do not attempt to manually delete system files. Image the machine and escalate to your MSP SOC/endpoint team.

Phishing-response runbook (priority order):

1. Revoke, don't just reset. For all 6 compromised accounts: revoke all active refresh tokens /
sign out of all sessions (in Microsoft 365 this is the "Revoke Sessions" action, or via
Microsoft Graph's revokeSignInSessions) BEFORE or alongside the password reset. This is the
step a simple password reset misses: the sign-in logs show logins from an unfamiliar ASN that
never triggered MFA, which strongly suggests the attacker is using a stolen session/refresh
token captured by the credential-harvesting page, not just a password. A password reset alone
does not invalidate an already-issued token -- the attacker's session can keep working even
after the password changes, unless the token is explicitly revoked.

2. Remove the malicious inbox rules. Delete the auto-forward-and-delete rules already found on
accountspayable@ and controller@ (classic Business Email Compromise persistence and
invoice-fraud staging), and don't stop there -- check EVERY affected mailbox (all 6, not just
the 2 already flagged) for similar hidden rules, since attackers often plant rules on multiple
mailboxes.

3. Check for illicit OAuth app consent grants. Beyond inbox rules, review each of the 6
accounts' app permissions / enterprise application consents for anything unfamiliar the
attacker may have granted themselves during the compromise window -- an illicit consent grant
also survives a password reset and can give the attacker ongoing mailbox access via the Graph
API even after tokens are revoked and inbox rules are cleaned up, so this needs checking in the
same pass, not as an afterthought.

4. Contain the initial vector. Confirm the malicious Word attachment exploiting CVE-2022-30190
(Follina) is quarantined/blocked at the email gateway for all 60 mailboxes (not just the 6 that
opened it), and patch/mitigate the MSDT protocol handler issue per Microsoft's guidance on any
endpoint that hasn't applied the fix, since Follina requires no macros and can be re-triggered
by a similar attachment.

5. Communicate and monitor. Notify the 6 affected employees and the finance department
specifically about the invoice-fraud angle (the attacker may already have sent fraudulent
payment-redirect emails from the compromised mailboxes before detection), and monitor sign-in
logs for the next several days for any recurrence from the same ASN.

# Phishing Incident Response Runbook - Priority 1-5

## **PRIORITY 1: Immediate Containment & Isolation**

**Action:** Isolate affected accounts immediately
- Place all 6 affected accounts on **account lockout** (temporarily disable login capability)
- Contact IT to quarantine the compromised machines if possible
- Add all affected email addresses to **email blacklists** at network level
- **DO NOT** reset passwords yet - see explanation below

## **PRIORITY 2: Password Reset & MFA Enforcement**

**Action:** Reset credentials and enforce MFA for ALL accounts
- Reset passwords for ALL 6 affected accounts (including accountspayable@ and controller@)
- **Critical**: Enforce MFA for ALL accounts immediately
- **Why this alone is insufficient**: The sign-in logs show successful logins from an unfamiliar ASN in another country WITH NO MFA challenges. This indicates the attackers likely already had access to the **Microsoft 365 admin credentials** (likely from the same compromised accounts) and bypassed MFA through:
  - Admin consent delegation
  - App access tokens
  - Compromised service accounts
  - Or other Microsoft Graph API access methods

## **PRIORITY 3: Check Inbox Rules (Beyond What's Already Found)**

**Action:** Review ALL inbox rules for affected mailboxes
- **Check for additional forwarding rules** (not just "invoice" rules)
- **Look for rules that delete emails immediately after forwarding**
- **Search for rules that redirect to external email addresses**
- **Check for rules that automatically move emails to specific folders**
- **Verify no rules exist that forward emails to non-company addresses**
- **Look for rules that automatically send replies or forwards**

## **PRIORITY 4: Email Configuration Review**

**Action:** Check email permissions and configurations
- **Review mailbox permissions** - ensure no unauthorized users have access
- **Check for shared mailboxes** or delegate access that might have been compromised
- **Verify auto-forwarding settings** are properly configured
- **Review transport rules** that might have been modified
- **Check for suspicious email aliases** or forwarding addresses created

## **PRIORITY 5: Account & Access Review**

**Action:** Comprehensive account security audit
- **Review all admin roles** assigned to affected accounts
- **Check for suspicious app registrations** or service principals
- **Review Microsoft 365 audit logs** for any unauthorized changes
- **Check for new security groups** or permissions that were created
- **Verify no new Azure AD applications** were registered
- **Review Microsoft Defender for Office 365 alerts** for additional compromise indicators

## **IMPORTANT: Why Password Reset Alone Won't Work**

The incident shows a sophisticated attack pattern:
1. **Initial compromise** via Follina exploit (CVE-2022-30190) - users clicked on malicious document
2. **Credential harvesting** - captured M365 passwords through credential harvesting page
3. **Lateral movement** - attackers used those credentials to access M365 from unfamiliar IP ranges
4. **MFA bypass** - no MFA challenges were triggered, indicating either:
   - The attackers already had elevated admin credentials
   - MFA bypass was achieved through compromised admin consent
   - The accounts were compromised before MFA enforcement was applied

## **Additional Immediate Checks**

**For controller@ and accountspayable@ mailboxes specifically:**
- Check if any emails have been deleted or modified (audit logs)
- Review any recent email traffic for financial information exposure
- Check for any external sharing links or document permissions that were modified

**For all affected accounts:**
- Verify no new email aliases or forwarding addresses exist
- Check for suspicious calendar entries or meetings created
- Review any recent file sharing or OneDrive access logs

This approach ensures comprehensive containment and prevents further unauthorized access or data exfiltration.

## Phishing‑Response Runbook  
*(Level‑1 helpdesk – no security background required)*  

> **Goal:** Contain the incident, secure the compromised accounts, and eliminate the
> malicious rules that could keep the attackers in the system.  
> **Why a password reset alone is NOT enough:**  
> * The attackers logged in successfully with the stolen credentials.  
> * The sign‑ins **did not trigger MFA** – the attackers may have had a valid, un‑expired

> * Resetting the password only locks the *credential*; any *active session* or *cached
> token* remains valid until the user signs out or the session is revoked.  
> * The malicious inbox rules (and possibly other hidden rules or forwarding
> settings) can keep sending copies of every “invoice” email to the attacker even

# Phishing Incident Response Runbook
**Client:** Industrial Parts Distributor (60-employee MSP)
**Severity:** Critical
**Target Audience:** Level-1 Helpdesk Technician
**Prerequisites:** Microsoft 365 Admin Center access, Defender for Endpoint access (or client admin contact), access to the 6 affected user accounts.

---

## ⚠️ CRITICAL: Why a Password Reset Alone Fails
**Do not rely on a password reset to resolve this incident.** Based on the facts, a password reset is insufficient for three specific reasons:

1.  **The Endpoints Are Compromised (Follina):** The email opened a Word attachment that executed code directly on the computer (CVE-2022-30190). This is not just a stolen password; it means **malware is installed on the hard drive**. Changing the account password does not remove the malware from the computer. The attacker can re-enter the account using the malware or a previously stolen token.
2.  **Active Sessions Exist:** Sign-in logs show the attacker logged in from a foreign country *within 48 hours*. If the attacker registered a device (like their own phone) as a trusted login source, Microsoft may not ask for MFA again even if the password changes. The attacker may still hold an **active, valid session** on the account right now.
3.  **Ongoing Theft via Inbox Rules:** The `accountspayable@` and `controller@` accounts have rules that silently delete emails. If the attacker can still access the mailbox (via the active session mentioned above), they will continue to forward invoice data until the rules and the session are removed.

---

## Phase 1: Containment (Do Immediately)
*Goal: Stop the attacker from accessing accounts or data further.*

**1. Block the Threat Source**
*   Open **Microsoft Defender Portal** (security.microsoft.com).
*   Go to **Threat intelligence** > **Incidents**. Find the phishing email.
*   Click **Block** > **Block all senders**. Add the sender address and the malicious URL to the block list.
*   *Why:* Prevents other employees from receiving or opening the same phishing email.

**2. Disable the 6 Compromised Accounts**
*   Open **Microsoft 365 Admin Center** (admin.microsoft.com).
*   Go to **Users** > **Active users**.
*   Select the 6 affected users. Click **Disable account**.
*   *Why:* The attacker is currently logged in. Disabling the account cuts their current session immediately.
*   *Note:* Do not permanently delete the account. You will need to re-enable them after verification.

**3. Block the Malicious ASN**
*   If your firewall or DNS provider allows it, block the ASN (Autonomous System Number) identified in the sign-in logs.
*   *Why:* Prevents the attacker from maintaining access from their country.

---

## Phase 2: Investigation & Evidence
*Goal: Confirm the scope of damage before re-enabling accounts.*

**4. Check Endpoint Security on the 6 Affected Computers**
*   **Action:** Log into the 6 affected computers. Run a **Full Scan** in Microsoft Defender (Windows Security > Virus & threat protection > Scan options > Full scan > Start Scan).
*   **Decision:**
    *   If malware is found: Quarantine the files.
    *   **If no malware is found:** Do not trust the scan. Contact the client's IT admin to **re-image (wipe)** these computers. Follina payloads are designed to hide. A clean scan does not guarantee a clean machine.
*   **Why:** Passwords are useless if the malware on the PC is re-uploading credentials.

**5. Check the 6 Accounts for Active Sessions (Conditional Access)**
*   **Action:** Go to **Azure AD Admin Center** (portal.azure.com) > **Protection** > **Sign-in logs**.
*   **Filter:** Select the 6 users and the last 7 days.
*   **Look for:** Any "Active Sessions" that are not from the user's office IP.
*   **Check Conditional Access:** In **Azure AD** > **Policies** > **Conditional Access**, verify that "Require MFA" is set to **On** for all users.
*   **Why:** If MFA is not enforced, the attacker can log back in with the old password (or a reset password) without being challenged.

---

## Phase 3: Mailbox Remediation
*Goal: Remove the attacker's backdoors in the email system.*
*Note: You must check every affected mailbox (`accountspayable@`, `controller@`, and any other 4 compromised accounts).*

**6. Check Inbox Rules (Priority: High)**
*   **Action:** Go to **Microsoft 365 Admin Center** > **Exchange** > **Mail flow** > **Mail rules**.
*   **OR:** Have the user open Outlook Web App (OWA) > **Settings** (gear icon) > **Mail** > **Mail rules**.
*   **Check:** Look for any rule that:
    *   Forwards emails to an external address.
    *   Deletes emails matching a subject (e.g., "invoice").
    *   Moves emails to a hidden folder.
*   **Action:** **Delete all suspicious rules immediately.**

**7. Check Sent Items (Priority: High)**
*   **Action:** Log into OWA for the affected users.
*   **Navigate to:** **Sent Items**.
*   **Check for:** Any emails sent to an external address (especially to bank accounts or unrelated domains). Look for emails with "invoice," "payment," or "wire transfer" in the subject or body.
*   **Action:** Report any fraudulent invoices found to the client's finance team.

**8. Check Deleted Items (Priority: High)**
*   **Action:** Log into OWA.
*   **Navigate to:** **Deleted Items**.
*   **Check for:** Emails that were deleted recently.
*   **Why:** The inbox rules in this case **delete** the original emails after forwarding them. The attacker is hiding the evidence. If you only check the Inbox, you will miss the theft.

**9. Check ActiveSync / IMAP Connections (Priority: Medium)**
*   **Action:** Go to **Microsoft 365 Admin Center** > **Exchange** > **Teams & Voice** > **Mailbox** > **Mail flow** > **Mail flow rules** (if unavailable, check **Azure AD** > **Devices**).
*   **Alternative:** Contact the client's IT admin to run **Defender for Office 365** > **Threats** > **Email** > **Threats** to see if any emails were blocked.
*   **Why:** The attacker may be connecting to the mailbox via a mobile device (ActiveSync) or desktop app (IMAP) that is not covered by the inbox rules. You must ensure the attacker has not installed a hidden profile on a phone or laptop.

**10. Check "People" / Contacts (Priority: Low)**
*   **Action:** Log into OWA.
*   **Navigate to:** **People** (Contacts).
*   **Check for:** New contacts added recently.
*   **Why:** The attacker may have added themselves as a contact to communicate with the user or set up a backdoor.

## Phase 4: Recovery & Verification
*Goal: Safely return the accounts to service with security hardened.*

**11. Force Password Reset + MFA Re-enrollment**
*   **Action:** Even after disabling and re-enabling, force a password change for all 6 users.
*   **Action:** Require the user to **re-register their MFA method** (e.g., phone number, authenticator app).
*   **Action:** **Remove all registered devices** from the account (Azure AD > Users > [Name] > **Sign-in** > **Require password** > **Remove all devices**).
*   **Why:** The attacker may have a registered device (like their own phone) that auto-approves MFA challenges. Re-enrolling ensures the attacker does not have a shortcut.

**12. Enable Conditional Access Policy (Tenant-Wide)**
*   **Action:** Go to **Azure AD** > **Policies** > **Conditional Access**.
*   **Create a new policy:**
    *   **Users:** All users.
    *   **Cloud apps:** All Microsoft 365 apps.
    *   **Conditions:**
        *   **Locations:** Block all locations (or only allow your office country).
        *   **Devices:** Only compliant devices.
    *   **Grant controls:** **Require MFA**.
*   **Why:** This prevents the attacker from logging in from any other country without being challenged. This is the single most important step to prevent recurrence.

**13. Monitor Sign-In Logs (7 Days)**
*   **Action:** Set a reminder to check sign-in logs daily for 7 days.
*   **Look for:** Any new logins from unfamiliar IP addresses or countries.
*   **Why:** If the attacker can still access the account, they will try again after the password reset.
