## Role

You are one of three independent judges (Claude, Codex, Gemini) scoring a set
of blinded answers to a single MSP-realistic business task. You do not know
which model produced which answer -- every answer below is labeled only by a
letter. Do not try to guess model identity from writing style. Score only
what is on the page against the anchors below.

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

**Update** – Windows Server 2022 cumulative security update (Cumulative Update 2023‑03, ~550 MB).

**Goal** – Deploy the update without saturating the VSAT link or degrading SCADA telemetry.

> **Key constraint** – All patch traffic must stay on the local rig LAN. The VSAT uplink is only used for the *initial* download of the update package, which is done **outside** the 4‑hr window.

Pre-patch step (before touching anything): take a VM-level snapshot (or equivalent backup) of
the domain controller and, where the hypervisor supports it, of each endpoint before applying
any update. This is the rollback point -- if the cumulative update causes an authentication or
driver issue on this specific rig hardware, you revert to the snapshot rather than
troubleshooting live against SCADA-adjacent systems.

Sequencing given the 2 Mbps up / 10 Mbps down VSAT link shared with SCADA telemetry: do NOT
push the update to all 14 endpoints simultaneously -- that saturates the link and disrupts
drilling telemetry. Instead, pre-stage the update package to a local cache/WSUS-like
distribution point on-site during a low-telemetry period earlier in the hitch if possible, so
the actual patch-window activity is local installation, not 14 simultaneous downloads over
VSAT. Within the 4-hour changeover window, patch endpoints in small batches (e.g., 3-4 at a
time), starting with non-DC workstations and patching the domain controller last, once you've
confirmed no batch caused an issue -- so a bad patch doesn't take down authentication for the
whole site before you've had a chance to catch it on lower-risk machines first.

Cadence: this 4-hour window only exists once per 14-day hitch, at the day-to-night crew
changeover, so the entire patch cycle (pre-stage, batch install, DC patch, verification) has
to fit inside that single window -- if it doesn't complete, don't leave it half-applied; roll
back the in-progress batch and resume at the next hitch's window rather than attempting an
ad-hoc patch outside the approved window while drilling is active.

# Patch‑Window Runbook  
**Subject:** Deploying the Windows Server 2022 cumulative security update (KB‑XXXXX) to the 14 domain‑joined endpoints on the offshore drilling rig  
**Version:** 1.0 – 02 Nov 2025  
**Author:** [Your Name], Sr. Systems Engineer – Remote Site Operations  

---  

## 1.  Purpose & Scope  

- **Purpose** – Provide a controlled, bandwidth‑friendly method to install the Windows Server 2022 cumulative security update on all 14 rig endpoints (including the Domain Controller – DC) without compromising the real‑time SCADA/telemetry link (VSAT 2 Mbps ↑/10 Mbps ↓).  
- **Scope** – Applies to every server/workstation that is a member of the rig’s Active Directory (AD) forest and that must remain functional for SCADA operator authentication and data collection.  
- **Exclusions** – Non‑critical test rigs, third‑party PLC controllers, and any device that does **not** participate in AD authentication.

---  

## 2.  Key Constraints  

| Constraint | Detail |
|------------|--------|
| **Back‑haul bandwidth** | 2 Mbps uplink / 10 Mbps downlink shared with SCADA telemetry. |
| **Maintenance window** | One 4‑hour block per *hitch* (crew‑changeover day). No patching during active drilling. |
| **Hitch cadence** | 14‑day rotation of crews; each hitch provides **one** approved 4‑hour window. |
| **Critical services** | Domain Controller must stay online to authenticate SCADA workstations; any authentication outage stops telemetry collection. |
| **Rollback requirement** | Ability to uninstall the patch within the same maintenance window if telemetry degrades or authentication fails. |
| **Patch size** | Approx. 1.8 GB per endpoint (compressed source). |

---  

## 3.  Assumptions  

1. **WSUS / Configuration Manager (SCCM) distribution point** is already installed on the rig’s internal file server (≈ 200 GB free space).  
2. **BranchCache / Peer‑Cache** can be enabled on the DC to serve updates locally to other endpoints.  
3. **Power‑over‑Ethernet (PoE) UPS** guarantees uninterrupted power during the 4‑hour window.  
4. **Network‑policy enforcement** allows only **10 %** of the link capacity to be used for OS update traffic (to protect SCADA).  
5. **Backup** of the DC (System State) and of critical SCADA operator workstations has been verified within the last 7 days.

## 4.  Pre‑Patch Preparation  

| Step | Owner | Description | Success Criteria |
|------|-------|-------------|------------------|
| **4.1** | Site IT Lead | Verify patch metadata (KB‑XXXXX) against vendor security bulletin – confirm no known regressions for SCADA services. | Patch‑KB listed as “Safe for production”. |
| **4.2** | Patch Owner | Download the cumulative update ISO to the internal WSUS server **offline** (using a separate satellite link or USB‑3.0). | ISO checksum verified; stored on WSUS content library. |
| **4.3** | DC Admin | Take a **System State** backup of the DC to the onsite NAS (incremental, retained 30 days). | Backup completed, checksum verified. |
| **4.4** | SCADA Ops Lead | Confirm telemetry status – ensure all SCADA data streams are **green** before patching. | Telemetry health = **OK**. |

| **4.6** | Bandwidth Planner | Pre‑configure **BITS** (or SCCM) throttling policy: max 1 Mbps downstream / 200 kbps upstream per endpoint, with a global cap of **10 %** of total link bandwidth. | Policy applied and tested with a dummy 100 MB file. |

## 5.  Sequencing Strategy (Bandwidth‑Aware Roll‑out)

The 14 endpoints are split into **four logical groups** based on criticality and the order they can be safely taken offline without breaking authentication or SCADA telemetry.

| Group | Endpoints (example hostnames) | Reason for Placement | Approx. Update Time* |
|-------|------------------------------|----------------------|----------------------|
| **A – Core Infrastructure** | *DC01* (Domain Controller) | Must stay online; will be patched **last** to avoid loss of authentication. | 30 min (offline install) |
| **B – SCADA Operator Workstations** | *OP‑ST01* – *OP‑ST06* (6 workstations) | These are the *only* machines that SCADA operators use to view real‑time data. Must keep at least **one** functional during each window. | 20 min each |
| **C – Supporting Servers** | *LOG‑S01*, *DB‑S01* (SQL/Log servers) | Provide backend for SCADA; can be offline briefly. | 20 min each |
| **D – General Endpoints** | *ENG‑PC01* – *ENG‑PC07* (7 generic PCs) | No direct impact on SCADA; can be taken offline in bulk. | 15 min each |

\*Times are **net install time** after the download has been staged locally on the WSUS server. They include OS verification, reboot, health‑check.

### 5.1  Bandwidth Management  

| Technique | Settings |
|-----------|----------|
| **BITS** (Background Intelligent Transfer Service) | `bcdedit /set {xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx} RecoveryConsole yes` <br> `bitsadmin /settransportparameters` → limit to **1 Mbps** per transfer. |
| **SCCM/WSUS** | Set *Maximum Bandwidth* = **10 %** of link (≈ 1 Mbps downstream, 100 kbps upstream). |
| **Peer‑Cache** | Enable **Cache mode** on the DC; configure *Cache Size* = 20 GB per endpoint; set *Cache Duration* = 7 days. |
| **Schedule** | All update transfers start **30 min before** the maintenance window to allow pre‑download; actual installation occurs **during** the 4‑hour block. |

### 5.2  Rolling Update Flow  

| Phase | Action | Endpoints Updated | Timing (per 4‑hr window) |
|-------|--------|-------------------|--------------------------|
| **Phase 1 – Pre‑download** | Push the update package to WSUS & cache on DC (no client impact). | All 14 endpoints (metadata only). | 30 min before window. |
| **Phase 2 – Pilot** | Update **one** non‑critical endpoint (e.g., *ENG‑PC01*) to verify telemetry impact. | 1 (Group D) | 00:00‑00:20 (first 20 min of window). |
| **Phase 3 – Core Group B** | Update **two** SCADA operator workstations simultaneously (ensuring at least one remains online). | 2 (Group B) | 00:30‑01:10 (40 min). |
| **Phase 4 – Supporting Servers** | Patch *LOG‑S01* and *DB‑S01* (offline for 10 min each). | 2 (Group C) | 01:20‑01:40 (20 min). |
| **Phase 5 – Remaining Workstations** | Update the remaining **four** SCADA operator workstations (2 per sub‑batch). | 4 (Group B) | 01:50‑02:30 (40 min). |
| **Phase 6 – Domain Controller** | Finally patch the DC (offline for 30 min). | 1 (Group A) | 02:40‑03:10 (30 min). |
| **Phase 7 – General Endpoints** | Update the final **7** generic PCs (in two sub‑batches of 3‑4). | 7 (Group D) | 03:20‑04:00 (40 min). |

**Total per 4‑hour window:** Up to **13 endpoints** can be patched (the DC is left for the *final* window if needed). The schedule deliberately caps simultaneous traffic to **≤10 %** of the link, guaranteeing SCADA telemetry remains uninterrupted.

> **Why the DC is patched last** – If the DC loses connectivity, authentication for all SCADA workstations fails, instantly halting telemetry collection. By deferring DC patching to the **final** window of a given hitch (or to a subsequent hitch), we keep authentication intact for the entire maintenance period.

## 7.  Rollback / Recovery Procedure  

1. **Identify failure** – Telemetry drop > 30 % or authentication errors > 5 % during the window.  
2. **Abort further installs** – Stop BITS jobs via `bitsadmin /reset`.  
3. **Rollback individual endpoint** –  
   ```powershell
   wmic product where "name like 'KB%'" call uninstall /confirm
   ```  
   or use **Windows Update Standalone Installer (wusa.exe /uninstall /kb:<KBNumber> /quiet /norestart**.  
4. **Restore DC** – If DC itself fails, restore the System State backup taken in step 4.3.  
5. **Notify crew** – Immediately broadcast “Patch abort – return to pre‑maintenance state”.  
6. **Post‑mortem** – Log root cause, adjust bandwidth throttling or batch size, and re‑schedule for the next approved window.

# Patch Window Runbook: Remote Drilling Rig VSAT Environment

## Pre-Patch Preparation (24-48 hours prior)

### 1. Environment Assessment
- Verify all 14 endpoints are domain-joined and reachable
- Confirm domain controller is functioning properly
- Check current Windows Update status and installed KB numbers
- Validate that SCADA systems are operating normally
- Document baseline network performance metrics

### 2. Test Deployment
- Deploy update to 2 test machines (non-critical)
- Monitor for 24 hours to ensure no adverse effects
- Verify SCADA telemetry unaffected during test deployment

### 3. Communication
- Notify rig crew and SCADA operators of scheduled maintenance
- Confirm crew changeover timing for the maintenance window
- Prepare rollback procedures for critical failures

## Patch Deployment Sequence

### Phase 1: Critical Infrastructure (Hours 1-2)
**Target:** Domain Controller, SCADA operator workstations
- Deploy updates to domain controller first
- Verify authentication system stability
- Deploy to 3 SCADA operator workstations
- Monitor SCADA telemetry for 30 minutes post-deployment

### Phase 2: Critical Operations (Hours 2-3)
**Target:** 2-3 remaining SCADA workstations, 2-3 core operational workstations
- Deploy to remaining SCADA operator workstations
- Deploy to 2-3 core operational workstations
- Monitor network utilization (target <80% of bandwidth)

### Phase 3: Remaining Endpoints (Hours 3-4)
**Target:** 7-8 remaining workstations
- Deploy to remaining endpoints in batches of 2-3
- Monitor network performance continuously
- Verify system stability

## Bandwidth Management Strategy

### Network Usage Optimization
- Schedule updates during 4-hour window only
- Prioritize critical systems first
- Monitor real-time bandwidth usage
- If bandwidth exceeds 80% utilization, pause deployment
- Resume after 30-minute cooldown period
- Implement Windows Update bandwidth throttling

## 14-Day Hitch Cadence Integration

### Deployment Schedule
- **Week 1:** Deploy to 1st batch (critical infrastructure)
- **Week 2:** Deploy to 2nd batch (critical operations)
- **Week 3:** Deploy to 3rd batch (remaining endpoints)
- **Week 4:** Full system verification and rollback preparation

### Maintenance Window Timing
- **Day 1:** Deploy to critical infrastructure (2 hours)
- **Day 2:** Deploy to critical operations (2 hours)
- **Day 3:** Deploy to remaining endpoints (2 hours)
- **Day 4:** Verification and rollback preparation (2 hours)

## Rollback Procedures

### Immediate Rollback (if required)
1. If critical authentication issues arise:
   - Revert domain controller update immediately
   - Revert SCADA operator workstations
   - Notify SCADA operations and operations management
2. If network performance degrades:
   - Pause all remaining deployments
   - Revert failed updates in reverse sequence
   - Restore network bandwidth before resuming

### Long-term Rollback
1. Document all failed updates and system states
2. Prepare full system restore points
3. Maintain backup copies of all critical system images
4. Plan for re-deployment within 30 days

## Post-Deployment Verification

### Critical Checks
- Verify all 14 endpoints are patched and online
- Confirm domain controller authentication stability
- Verify SCADA telemetry performance
- Validate network utilization remains below 80%
- Document any issues encountered

### Monitoring Requirements
- Continuous network performance monitoring

## 2. Sequencing Logic – Staggered 14‑Endpoint Deployment

### 2.1 Bandwidth Math
- **Available safe bandwidth:** 2 Mbps (≈ 0.25 MB/s).  
- **Update size per endpoint:** ~1.2 GB ≈ 1228 MB.  
- **Time to transfer one endpoint (if downloaded from the internet):** 1228 MB ÷ 0.25 MB/s ≈ **4910 s ≈ 82 min** (far exceeds our window).  
- **Solution:** **Pre‑stage** the package locally (no VSAT traffic) and only trigger **install** which is < 5 MB of metadata traffic.  

Thus the real network load during the window is **metadata + WSUS reporting**, well under 2 Mbps.

### 2.2 Staggered Install Plan (4‑hour window = 14,400 s)
