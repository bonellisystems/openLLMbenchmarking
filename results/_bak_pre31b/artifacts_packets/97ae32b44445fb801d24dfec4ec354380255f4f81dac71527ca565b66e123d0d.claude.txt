## Role

You are one of three independent judges (Claude, Codex, Gemini) scoring a set
of blinded answers to a single MSP-realistic business task. You do not know
which model produced which answer -- every answer below is labeled only by a

## Anchors

The following anchors define what a 0, 3, 5, 7, and 10 look like for this
business unit. Use them as the scoring scale for every answer.

# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

### M365/AD Tenant Consolidation Change Plan: Firm A Absorbing Firm B

**Objective:** Consolidate Firm B (45 users) into Firm A's Microsoft 365/AD tenant while guaranteeing zero disruption to Active AutoCAD Xref links and ensuring uninterrupted workflow for two critical permit-submission deadlines occurring within 10 business days.

**Core Risk Principle:** AutoCAD external references (Xrefs) using absolute UNC paths are brittle. Any change to the NetBIOS name, DNS resolution of the file server, share name, or user session stability (via UPN change) risks breaking Xrefs or causing file corruption. **The Golden Rule for this plan:** *Preserve `\\FIRMB-FS01\...` paths and `@firmB.com` UPNs until all permit submissions are complete.*

---

### 1. Pre-Migration Preparation (Days 1–2)
*Goal: Establish environment readiness without touching production data paths or user identities.*

1.  **Domain Verification:** Add `firmB.com` as a verified **Standard Domain** in Firm A's M365 Tenant. This allows users to be migrated while retaining their `@firmB.com` UPN.
2.  **AD Sync/Trust:**
    *   If Firm B has on-prem AD, configure a **One-Way Trust** (Firm B trusts Firm A) or configure Azure AD Connect to sync Firm B's identities to Tenant A while preserving the `@firmB.com` UPN suffix.
    *   Ensure `\\FIRMB-FS01` DNS records remain static and authoritative. Do not modify DNS TTLs aggressively yet.
3.  **Backups:**
    *   Full backup of Firm B's File Share (`\\FIRMB-FS01`) and Exchange Database.
    *   Snapshot of Firm B's AD Domain Controller.
4.  **Staging:** Create a dedicated OU in Firm A's AD for "Firm B Migrated Users" to apply GPOs that preserve legacy session behaviors if needed.

---

### 2. Migration Phase 1: Mailbox & Identity Migration (Days 3–4)
*Goal: Move users and mail to Tenant A without changing their login identity or file paths.*

**Sequence:**
1.  **Batch Mailbox Migration:**
    *   Execute **Batch Migration** to move Firm B mailboxes to Firm A's Exchange Online.
    *   **Critical Configuration:** Set **Target Primary SMTP/UPN to match Source**.
        *   *Result:* Users migrate to Tenant A but continue to log in with `user@firmB.com`.
        *   *Benefit:* No UPN change occurs. Cached credentials remain valid; Outlook profiles do not break; user sessions are not forcibly dropped. Xref stability is maintained.
2.  **Validation:** Verify all 45 mailboxes are active in Tenant A, accessible via OWA/Outlook, and calendar sharing works.
3.  **MX Record Cutover:**
    *   *Only after* all batches show "Completed" in the migration batch report, update the MX record for `firmB.com` to point to Firm A's M365.
    *   *Risk Mitigation:* If MX is moved before all batches complete, mail for un-migrated users may queue or bounce. Waiting ensures a clean cutover.

**State at End of Day 4:**
*   Users are in Tenant A.
*   Users log in as `user@firmB.com`.
*   Mail flows to Tenant A.
*   **File Share remains `\\FIRMB-FS01`.**
*   **Xrefs are untouched and functional.**

---

### 3. Permit Deadline Window (Days 5–10)
*Goal: Hypercare support and absolute freeze on infrastructure changes.*

1.  **Change Freeze:**
    *   **NO** file share moves.
    *   **NO** share name changes.
    *   **NO** UPN suffix changes.
    *   **NO** DNS changes affecting `FIRMB-FS01`.
2.  **Support Model:**
    *   Establish "Permit War Room" support for Firm B drafters.
    *   Monitor AutoCAD session stability and file lock contention.
3.  **Contingency:** If `\\FIRMB-FS01` hardware fails during this window, restore from backup to a server with the **identical NetBIOS name and IP address** (or update DNS to point to new IP but retain CNAME/NetBIOS name exactly). Do not rename the server.

---

### 4. Post-Deadline Migration (Day 11+)
*Goal: Complete consolidation only after permits are submitted and risk of Xref breakage is acceptable.*

**Changes permitted ONLY AFTER both permit deadlines pass:**

1.  **File Share Migration & Xref Remediation:**
    *   **Action:** Migrate file data to Firm A's storage.
    *   **Risk:** Moving files will break absolute UNC Xrefs.
    *   **Mitigation:**
        *   Perform migration after hours.
        *   Use a **CNAME/DFS Redirection** strategy *if* AutoCAD supports it, testing rigorously. However, given the prompt's risk warning, the safest approach is:
        *   Move files to new path (e.g., `\\FIRMA-FS01\Projects`).
        *   Deploy a **batch Xref re-linking tool** (e.g., AutoCAD batch utility, `xreflinker.lsp`, or third-party tool like XRef Manager) to update drawings in the new path.
        *   Communicate to users to "Reload Xrefs" or use the re-linked versions.
2.  **UPN Suffix Standardization:**
    *   **Action:** Update all Firm B user UPNs from `@firmB.com` to `@firmA.com`.
    *   **Method:** Update UPN in AD/M365. Force users to log off and log back in.
    *   **Timing:** Execute during a scheduled maintenance window post-deadline.
3.  **Decommissioning:**
    *   Retire Firm B's on-prem Exchange.
    *   Decommission `FIRMB-FS01` and AD infrastructure once data migration and UPN changes are verified.

### 5. Rollback Plan: Mailbox Migration Batch Failure
*Scenario: A migration batch fails partway (e.g., corruption, quota error, or service outage), and the failure impacts mail flow or data integrity.*

**Prerequisite:** MX Record has **not** been moved until all batches are complete. Therefore, rollback does not require reverting DNS.

1.  **Immediate Action:**
    *   Stop the migration batch in the M365 Admin Center.
    *   Assess error logs. Determine if the failure is transient (retryable) or permanent (corruption/quota).
2.  **Rollback Execution:**
    *   **If Source is Intact:** Since Batch Migration is copy-based, the source mailboxes on Firm B's Exchange remain untouched.
        *   Delete the failed mailbox objects in Tenant A.
        *   Restart the batch from the source.
    *   **If Mail Flow is Impacted (e.g., MX was moved prematurely due to error):**
        *   Revert MX record for `firmB.com` to point to Firm B's on-prem Exchange.
        *   Ensure Firm B's Exchange is accepting mail and replicating.
        *   Notify users to log in to the legacy Exchange environment temporarily.
        *   Restore any incremental changes made during the failed window from source backup if necessary.
3.  **Communication:**
    *   Notify affected users: "Mailbox migration paused. Please continue using email as normal. We are resolving a technical issue."
    *   If MX rollback occurred: "Email has been temporarily reverted to the previous system. Please restart Outlook."

| Change Item | Risk to Xrefs/Workflows | Timing |
| :--- | :--- | :--- |
| **File Share Path/Name** | **Critical.** Breaks absolute UNC Xrefs immediately. | **DEFERRED.** Move only after permit deadlines. Use batch re-link tool post-move. |

| **DNS/NetBIOS for FS** | **Critical.** `FIRMB-FS01` must resolve consistently. | **FREEZE.** No DNS changes to file server name during permit window. |

**Final Recommendation:** Proceed with **Identity-First Migration**. Move users and mail to Tenant A while strictly preserving the `@firmB.com` UPN and `\\FIRMB-FS01` path. This achieves tenant consolidation goals while isolating the fragile AutoCAD workflows from infrastructure changes until the permit deadlines are safely cleared.

    Get-Mailbox -ResultSize Unlimited | Where-Object {$_.PrimarySmtpAddress -like "*@firmB-users*" -and $_.RecipientTypeDetails -eq "UserMailbox"} | Remove-Mailbox -Confirm:$false

## 4. Rollback Plan: Mailbox Migration Batch Failure

### Trigger Conditions
- Move request status = `Failed`, `Retry`, or `FailedMailbox`
- >15% of batch fails within 2 hours
- User reports critical Outlook/Exchange functionality loss

### Rollback Procedure
```powershell
# 1. Pause all ongoing moves
Get-MoveRequest -MoveStatus InProgress | Remove-MoveRequest -Confirm:$false

# 2. Identify failure root cause
Get-MoveRequest -ResultStatsOnly | Where-Object {$_.Status -in @("Failed","Retry")} |
    Get-MoveRequestStatistics -IncludeReport | Out-File C:\Rollback\MoveReport.html

# 3. Check AD Connect state (must be paused during rollback)
Get-ADSyncScheduler | Select-Object Enabled, NextSyncCycle

# 4. Re-queue with corrected parameters
# Option A: Skip bad items, increase limits
New-MoveRequest -Identity <User> -TargetMoveRequest <TenantID> -BadItemLimit 50 -LargeItemLimit 100 -IgnoreSizesLimits

# Option B: Move failed-only users back to source
New-MoveRequest -Identity <User> -TargetMoveRequest <SourceTenant> -BadItemLimit 25

# 5. Validate rollback
Get-MoveRequestStatistics -IncludeReport | Where-Object {$_.Status -eq "Completed"}
Test-Mailbox -Identity <User>

# 6. Resume AD Connect only after all mailboxes confirmed accessible
Start-ADSyncScheduler
```

### Rollback Safeguards
- **Source mailbox remains online** during entire migration window; no deletion or offline flags
- **AD Connect stays paused** until rollback is validated; prevents UPN propagation that would compound the issue
- **File share access unchanged** throughout rollback; DFS namespace remains pointing to live server
- **Communication:** “Migration paused; your mailbox is accessible via [web/legacy]. Engineering work unaffected.”
- **Decision gate:** If >30% of batch fails after one retry, halt migration entirely and engage Microsoft Support before attempting Phase 2C (UPN change) or Phase 2B (file share move)

## 4. Rollback Strategy for Mailbox Migration  

Because mailbox moves are **asynchronous** and can be partially completed, a clear rollback path is essential.

### 4.1 Pre‑Migration Safeguards  

1. **Full backup** of each source mailbox (export to PST or use native Exchange **Mailbox Export/Import**). Store PSTs in a secure location (e.g., Azure Blob with immutable storage).  
2. **Snapshot** of the on‑prem Exchange database (if using Exchange Server) taken **just before** the first move request.  
3. **Document** every `New-MoveRequest` command with its **RequestGuid** and the **batch number** (e.g., Batch‑01‑A, Batch‑01‑B …).  

### 4.2 Detection of a Failed Batch  

- **Monitoring**: Use **Exchange Admin Center** alerts + **PowerShell** `Get-MoveRequestStatistics` filtered by `Status -eq "Failed"` or `Status -eq "InTrouble"`.  
- **Threshold**: If **any** user in a batch reports failure (e.g., missing items, size mismatch, or error code `ErrorPermanentFailure`), treat the whole batch as **failed**.  

### 4.3 Immediate Rollback Steps  

| Step | Action | Command / Tool |
|------|--------|----------------|
| **4.3.1** | **Cancel** the pending move requests for the failing batch. | `Get-MoveRequest -BatchId <BatchGUID> | Remove-MoveRequest` |
| **4.3.2** | **Re‑enable** the original on‑prem mailbox (if it was placed in **RetentionHold** or **Disabled** state). | `Set-Mailbox -Identity <user>@firmB.local -IsArchive $false -ArchiveStatus None` |
| **4.3.3** | **Restore** from the PST backup (if any data was partially migrated). | `New-MailboxImportRequest -Mailbox <user>@firmB.local -FilePath \\BackupShare\pst\<user>.pst` |
| **4.3.4** | **Notify** the user and the project lead that the mailbox is back to the original state and that mail will continue to flow from the on‑prem server. | Email template (pre‑written). |
| **4.3.5** | **Investigate** root cause (e.g., corrupt PST, network latency, permission issue) and **fix** before re‑attempting. | Review Exchange logs, run `Get-MessageTrackingLog`. |

### 4.4 Post‑Rollback Validation  

1. **Send/Receive test** from the user’s workstation.  
2. **Run** `Get-MailboxStatistics -Identity <user>` to confirm **ItemCount** matches the pre‑migration snapshot.  
3. **Confirm** that the user’s **UPN** is still the old one (`@firmB.com`) – **do not** change it until after the permit deadlines.  

### 4.5 Re‑Attempt Strategy  

- After fixing the identified issue, **re‑run** the move request for the *same* batch (or split into smaller sub‑batches of 5 users).  
- Keep the **same monitoring** window; if the second attempt succeeds, proceed to the next batch.  

### 4.6 Full‑Project Rollback (worst‑case)  

If **multiple batches** fail and a decision is made to **abort the entire mailbox migration**, execute:

1. **Cancel all pending move requests** (`Get-MoveRequest | Remove-MoveRequest`).  
2. **Re‑enable** every on‑prem mailbox that was placed in a hold.  
3. **Re‑apply** the original DNS MX records to point back to Firm B’s mail servers (if they were switched).  
4. **Communicate** to all stakeholders that the migration is paused; schedule a new window after the permit deadlines.
