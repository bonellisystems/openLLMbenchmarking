# Network Segmentation Review & Remediation Plan
**Client:** Multi-Provider Outpatient Clinic
**Scope:** EHR Server, Workstations, Medical IoT, Guest WiFi, Back-Office
**Constraint:** Zero EHR downtime between 8:00 AM and 6:00 PM
**Compliance Driver:** HIPAA Security Rule §164.312(a)(1) – Access Control

---

## 1. Risk Assessment
The current flat network topology (10.10.0.0/22) violates the HIPAA Security Rule. Because Guest WiFi and EHR infrastructure share a Layer 2 broadcast domain with no inter-VLAN ACLs, a compromised or misconfigured guest device has direct lateral movement to the EHR application server via RDP (TCP/3389). This constitutes a violation of the **Access Control** requirement to ensure that only authorized persons access ePHI.

**Immediate Gap:** Guest WiFi (Source) → Flat Network (Path) → EHR Server (Destination: Port 3389).
**Risk:** Unauthorized ePHI access, potential ransomware pivot from guest devices to clinical systems.

---

## 2. Proposed VLAN Architecture

We will segment the existing 10.10.0.0/22 address space into four logical VLANs. This preserves the existing IP address scheme for the EHR server and workstations while creating hard Layer 2 boundaries for Guest and Admin traffic.

| VLAN ID | Name | IP Range | Subnet Mask | Role |
|:---|:---|:---|:---|:---|
| **10** | `CLINICAL_PROD` | 10.10.0.0 – 10.10.0.255 | /24 | EHR Servers, Provider Workstations, Medical IoT (Infusion Pumps, Monitors) |
| **20** | `BACK_OFFICE` | 10.10.1.0 – 10.10.1.255 | /24 | Payroll, Billing, HR, General Admin Systems |
| **30** | `GUEST_WLAN` | 10.10.2.0 – 10.10.2.255 | /24 | Guest WiFi APs (Internet-only access) |
| **40** | `MGMT` | 10.10.3.0 – 10.10.3.255 | /24 | Switches, APs, Firewalls (Out-of-Band Management) |

**Rationale for Guest VLAN (30):**
*   **Layer 2 Isolation:** VLAN 30 is logically separated from VLAN 10. By default, traffic cannot traverse Layer 2 boundaries between VLANs without a Layer 3 device (router/firewall).
*   **DHCP Relay:** The existing DHCP server (or a new relay agent) will assign 10.10.2.0/24 addresses to the Guest VLAN.

---

## 3. Closing the Guest-to-EHR RDP Gap

The specific fix is the implementation of an **Inter-VLAN Access Control List (ACL)** on the core Layer 3 device (Firewall or Multilayer Switch) that routes between VLANs.

### The Configuration
We will apply a "Default Deny" policy at the inter-VLAN boundary, with explicit deny rules for high-risk ports.

**Action:** Deny all traffic from Guest VLAN (10.10.2.0/24) to Clinical VLAN (10.10.0.0/24).

**Cisco IOS / Firewall ACL Example:**
```bash
! Applied inbound on the interface connecting VLAN 30 to the L3 device
access-list 101 deny tcp 10.10.2.0 0.0.0.255 10.10.0.0 0.0.0.255 eq 3389
access-list 101 deny ip 10.10.2.0 0.0.0.255 10.10.0.0 0.0.0.255
! Allow Guest to Internet (assuming default gateway is on VLAN 30's L3 interface)
access-list 101 permit ip any any
interface GigabitEthernet0/1
 ip access-group 101 in
```

**Why this closes the gap:**
1.  **RDP Block:** The explicit deny on TCP/3389 removes the direct path from the Guest WiFi to the EHR server. Even if the EHR port 3389 remains open on the server, the firewall rejects the packet.
2.  **Lateral Movement Block:** The broad `deny ip` prevents the guest device from scanning or pinging the EHR subnet, eliminating pivot points.
3.  **HIPAA Compliance:** This satisfies the Access Control requirement by technically enforcing that Guest VLAN traffic cannot reach systems touching ePHI.

## 5. Rollback Plan

If the change fails or EHR performance degrades, the following steps will restore the network to its pre-change state.

**Rollback Trigger:** Any EHR downtime detected, ACL causing false positives, or patient care disruption.

### Immediate Rollback Steps (During 8 AM – 6 PM)
1.  **Remove ACL:** On the L3 device, remove the `access-list 101` configuration and re-enable the interface. This restores flat-layer-3 routing, re-establishing connectivity between VLANs (though not ideal security-wise, it restores service).
2.  **Revert VLAN Configs:** On all managed switches, revert port configurations to "Access VLAN 1" (Native). This collapses the VLANs back to the flat 10.10.0.0/22 topology.
3.  **Verify EHR:** Confirm EHR connectivity is restored via the original flat network path.
4.  **Document:** Record the rollback in the change log and notify the clinic's compliance officer.

### Full Revert (After 6:00 PM)
1.  **Restore DHCP:** Revert DHCP scopes to the original single scope (10.10.0.0/22).
2.  **Restore APs:** Revert APs to broadcast Guest SSID on the original VLAN 1.
3.  **Restore Configs:** Reload the original backup configurations on all switches, APs, and L3 devices.
4.  **Notify:** Inform the clinic that the segmentation change is suspended pending further analysis.

### Network Segmentation Review & Remediation Plan
**Client:** Multi-Provider Outpatient Clinic

#### 1. Risk Assessment & HIPAA Alignment
**Current State:** The network operates as a flat Layer 2 domain (`10.10.0.0/22`). Guest Wi-Fi traffic shares the same broadcast domain as EHR servers, clinical workstations, and medical IoT devices.
**Vulnerability:** A device on Guest Wi-Fi can establish RDP sessions (TCP 3389) directly to the EHR Application Server. There are no ACLs to prevent this lateral movement.
**Compliance Impact:** This violates **HIPAA Security Rule §164.312(a)(1) [Access Control]**, which requires technical policies and procedures that allow only authorized persons to access ePHI systems. Guest users have no need-to-know and must be logically isolated from all systems containing ePHI.

---

#### 2. Proposed VLAN Structure
To remediate this gap while supporting distinct security postures for clinical, IoT, administrative, and guest traffic, the following VLAN structure is proposed. 

*Note: The current `/22` block limits the number of large subnets. We will utilize Variable Length Subnet Masking (VLSM) to fit five security zones within the existing `10.10.0.0/22` range. This structure may require re-IPing static devices or updating DHCP scopes during the change.*

| VLAN ID | Name | Subnet | CIDR | Purpose | Access Control Summary |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **100** | **MGT** | 10.10.0.0 | /25 | Network Management | Mgmt access to all VLANs; No client traffic. |
| **200** | **EHR** | 10.10.0.128 | /25 | EHR Servers, Clinical Workstations | Allow EHR↔EHR; Allow Admin→EHR (specific ports); Allow IoT→EHR (if required); **Block Guest→EHR.** |
| **300** | **MED-IoT** | 10.10.1.0 | /24 | Infusion Pumps, Monitors | Allow IoT→EHR (data ingestion); Block IoT→Admin/Guest; Block IoT↔IoT. |
| **400** | **ADMIN** | 10.10.2.0 | /24 | Back-office, Billing, HR | Allow Admin→EHR; Block Admin→IoT/Guest; Block Guest→Admin. |
| **500** | **GUEST** | 10.10.3.0 | /24 | Guest Wi-Fi | **Allow Guest→Internet only.** Block Guest→All Internal VLANs. |

---

#### 3. Mechanism Closing the Guest-to-EHR RDP Gap
The vulnerability is closed through a combination of **Layer 2 Segmentation** and **Layer 3 Policy Enforcement**:

1.  **VLAN Isolation:** Guest Wi-Fi APs are configured to assign the Guest SSID to **VLAN 500**. EHR servers and workstations are assigned to **VLAN 200**. This removes Layer 2 adjacency; a guest laptop is no longer in the same broadcast domain as the EHR server.
2.  **Inter-VLAN Firewall Rule:** The core firewall enforces an explicit deny rule on the trust boundary:
    *   *Rule:* `DENY` Source=`VLAN 500` Destination=`VLAN 200` Protocol=`Any` Port=`Any`.
    *   *Result:* Even if routing is enabled, the firewall drops all packets from the Guest subnet to the EHR subnet. RDP traffic (TCP 3389) is blocked along with all other protocols.
3.  **Default Deny:** All inter-VLAN traffic defaults to `DENY`. Only explicitly permitted flows (e.g., EHR workstation to EHR server) are allowed. This ensures that even if RDP is closed, other attack vectors (SMB, DNS tunneling, ARP spoofing) are also blocked.

## 3. What Specifically Closes the Guest‑to‑EHR RDP Path

1. **ACL on the L3 Switch (or firewall) –**  
   ```  
   access-list 100 deny tcp   10.10.3.0 0.0.0.255   10.10.1.0 0.0.0.255   eq 3389
   access-list 100 deny ip    10.10.3.0 0.0.0.255   10.10.1.0 0.0.0.255
   access-list 100 permit ip    any any
   ```  
   *Explanation:*  
   - The first rule blocks any TCP traffic from the Guest VLAN (10.10.3.0/24) to the EHR VLAN (10.10.1.0/24) on port 3389.  
   - The second rule blocks all other IP traffic from Guest to EHR.  
   - The final rule permits all other inter‑VLAN traffic (e.g., workstations to EHR, IoT to EHR).  

   **Result:** Guest laptops can *never* reach the EHR servers, not even via other ports.  

2. **Optional firewall rule** (if an NGFW is deployed between Guest and Core):  
   ```
   deny from 10.10.3.0/24 to any port 3389
   deny from 10.10.3.0/24 to 10.10.1.0/24
   ```

3. **No changes to the EHR application server** – the server stays up, but it is now on a different subnet and can only be reached by devices that belong to VLAN 10 (workstations, admin).

The gap is closed by **three layered controls**, with the first being the authoritative control:

### Primary Control: Inter-VLAN ACL on L3 Boundary
Applied **inbound** on the core router/L3 switch interface for VLAN 40 (Guest) and **outbound** on VLAN 10 (EHR):

```
access-list ACL_GUEST_INBOUND deny   ip 10.10.3.0/24 10.10.0.0/24
access-list ACL_GUEST_INBOUND deny   ip 10.10.3.0/24 10.10.1.0/26
access-list ACL_GUEST_INBOUND deny   ip 10.10.3.0/24 10.10.2.0/24
access-list ACL_GUEST_INBOUND deny   ip 10.10.3.0/24 10.10.4.0/24
access-list ACL_GUEST_INBOUND permit ip 10.10.3.0/24 any   (Internet only)
interface Vlan40
 ip access-group ACL_GUEST_INBOUND in
```

**Defense-in-depth explicit rule:**
```
access-list ACL_EHR_INBOUND deny   tcp any any eq 3389
access-list ACL_EHR_INBOUND permit tcp 10.10.4.0/24 any eq 3389   (IT jump hosts only)
access-list ACL_EHR_INBOUND permit tcp 10.10.2.0/24 10.10.0.0/24 eq 8080   (EHR app traffic)
interface Vlan10
 ip access-group ACL_EHR_INBOUND in
```

### Secondary Control: EHR Server Host Firewall
Windows Firewall (or equivalent) on the EHR application server blocks TCP/3389 for all sources except the `10.10.4.0/24` jump host range.

### Tertiary Control: RDP Disable for Non-Admin Sources
Group Policy applied to EHR workstations/servers disables RDP inbound for all non-IT-Mgmt source IPs.

**Result:** A laptop on Guest WiFi cannot ARP, route, or establish TCP/3389 to any EHR host. The path is structurally impossible.

### Network Segmentation Review and Change Plan

#### **Proposed VLAN Structure**
To address the HIPAA Security Rule gap while ensuring zero EHR downtime during clinic hours (8:00 AM–6:00 PM), we propose a **segmented VLAN architecture**. The flat VLAN (10.10.0.0/22) will be replaced with the following VLANs:

| **VLAN ID** | **Name**          | **Purpose**                                                                 | **IP Subnet**   | **Key Systems**                                  |
|-------------|-------------------|-----------------------------------------------------------------------------|-----------------|--------------------------------------------------|
| 10          | **GUEST**         | Guest WiFi devices (isolated from all internal networks).                   | 10.10.0.0/24    | Guest laptops, phones, tablets.                  |
| 20          | **IoT**           | Medical IoT devices (infusion pumps, patient monitors).                     | 10.10.1.0/24    | Medical devices, IoT gateways.                   |
| 30          | **EHR**           | EHR workstations and application servers (HIPAA-protected).                 | 10.10.2.0/24    | EHR servers, provider workstations.             |
| 40          | **ADMIN**         | Back-office systems (finance, HR, billing).                                 | 10.10.3.0/24    | Admin workstations, file servers.                |
| 50          | **INFRA**         | Network infrastructure (routers, firewalls, switches).                      | 10.10.4.0/24    | Core network devices.                            |

**Key Segmentation Rules:**
- **Guest VLAN (10)**: No access to any other VLAN. Only outbound internet access via a dedicated firewall/NAT rule.
- **IoT VLAN (20)**: Restricted access to Admin VLAN (40) for updates only. No access to EHR (30).
- **EHR VLAN (30)**: Accessible only from Admin VLAN (40) for maintenance. No access from Guest (10) or IoT (20).
- **Admin VLAN (40)**: Access to EHR (30) via specific ports (e.g., HTTPS for reporting, not RDP). No direct access from Guest (10) or IoT (20).
- **INFRA VLAN (50)**: Management-only access for IT staff.

---

#### **What Closes the Guest-to-EHR RDP Path**
The **Guest-to-EHR RDP path is closed by**:
1. **VLAN Isolation**: Guest devices are in VLAN 10, while EHR systems are in VLAN 30. By default, traffic between different VLANs is blocked at Layer 2.
2. **Inter-VLAN ACLs**: A firewall or layer-3 switch ACL explicitly denies:
   ```bash
   access-list 100 deny tcp any 10.10.2.0 0.0.0.255 eq 3389  // Blocks RDP from ALL to EHR VLAN
   access-list 100 permit ip any any                          // Allow other necessary traffic (e.g., Admin→EHR)
   ```
   - This ACL is applied to the router/firewall interface between VLANs. The `deny` rule specifically targets RDP traffic from any source to the EHR subnet (10.10.2.0/24).
3. **EHR Firewall Rules**: EHR servers are hardened to only accept RDP from Admin VLAN (10.10.3.0/24), not Guest (10.10.0.0/24).

**Result**: A guest device (VLAN 10) cannot reach the EHR server (VLAN 30) via RDP (port 3389), as traffic is blocked at both Layer 2 (VLAN separation) and Layer 3 (ACL/firewall rules).

### 1. Executive Summary  

A flat‑VLAN design (10.10.0.0/22) allows any device on the network—including guest‑WiFi clients—to reach the EHR application server (RDP 3389). This violates the **HIPAA Security Rule** requirement to “implement policies and procedures to prevent unauthorized access to ePHI.”  

The remediation is a **network‑segmentation redesign** that isolates the Guest Wi‑Fi, the Medical‑IoT, the Clinical (EHR) workstations, and the Back‑Office/Admin systems into separate Layer‑2 broadcast domains, with a stateful firewall (or Layer‑3 switch) enforcing a **zero‑trust “need‑to‑know”** policy.  

The change can be performed **outside of the 08:00 – 18:00 clinic‑hours window**, guaranteeing zero EHR downtime during patient‑care hours. A detailed rollout and rollback plan is provided below.

---

## 2. Current Topology (as‑is)

| VLAN | Subnet | Primary Devices | Observations |
|------|--------|-----------------|--------------|
| **VLAN 10** | 10.10.0.0/22 | All EHR workstations, infusion pumps, patient monitors, admin servers, guest Wi‑Fi APs | **Flat broadcast domain – no ACLs** |
| **IP‑range** | 10.10.0.0 – 10.10.3.255 | – | RDP (3389) on EHR server reachable from any host |

**Key Gap** – Guest Wi‑Fi clients obtain an IP address from the same subnet, and because there is no inter‑VLAN firewall or ACL, they can open a TCP 3389 session directly to the EHR server (10.10.0.50, for example).

### 3.1 What *exactly* closes the Guest‑to‑EHR RDP path?

1. **Layer‑3 firewall ACL (or router ACL) rule** on the **inter‑VLAN interface** for VLAN‑40:  

   ```text
   # Deny any traffic from Guest (10.10.3.0/24) to Clinical (10.10.0.0/24) on TCP 3389
   access-list GUEST-TO-CLINICAL deny tcp 10.10.3.0 0.0.0.255 10.10.0.0 0.0.0.255 eq 3389
   # Optional: deny all traffic from Guest to Clinical (defense‑in‑depth)
   access-list GUEST-TO-CLINICAL deny ip 10.10.3.0 0.0.0.255 10.10.0.0 0.0.0.255
   # Permit everything else (Internet, DHCP, DNS) as required
   access-list GUEST-TO-CLINICAL permit ip 10.10.3.0 0.0.0.255 any
   ```

2. **Switch port‑based VLAN assignment** – All Guest AP uplinks are statically placed in VLAN‑40; no trunk ports carry VLAN‑10 traffic to the APs.  

3. **No ACL on the EHR server itself** is required once the network boundary blocks the traffic, but a host‑based firewall (Windows Defender Firewall) can keep a “deny inbound RDP from any IP except 10.10.0.0/24 and 10.10.2.0/24” as a safety net.

**Result:** A laptop on Guest Wi‑Fi cannot even *see* the EHR server’s IP on its ARP table, and any attempt to open TCP 3389 is dropped at the first hop (Layer‑3 firewall), satisfying the HIPAA “access‑control” requirement.

permit ip any any                  # (Optional) Allow intra-VLAN / local routing as needed

### 2. Current Architecture – What’s Wrong  

| Component | Current Logical Placement | Security Observation |
|-----------|---------------------------|----------------------|
| **Guest Wi‑Fi** | VLAN 10 (untagged) – 10.10.0.0/22 | Shares the same broadcast domain as all production systems. |
| **EHR Application Server** | Same VLAN 10, IP 10.10.0.45 | Open RDP (TCP 3389) inbound from any address in the VLAN (including Guest). |

*Result:* A single compromised guest device can directly initiate an RDP session to the EHR server, potentially exfiltrating or altering ePHI – a clear breach of the HIPAA Security Rule’s “access‑authentication” and “transmission security” expectations.

### 3. Target VLAN Architecture  

| VLAN | ID | Name | IP Subnet (example) | Primary Purpose | Recommended Devices |
|------|----|------|---------------------|-----------------|----------------------|
| **Management** | 10 | **MGMT** | 10.10.10.0/24 | Switches, routers, firewall, NTP, syslog, out‑of‑band mgmt | L3 Switch / Firewall (e.g., Palo Alto, Cisco ASA) |

| **EHR Services** | 30 | **EHR** | 10.10.30.0/24 | EHR application servers, DB servers, print services | Application server(s), DB server(s) |
| **Clinical Devices** | 40 | **CLINICAL** | 10.10.40.0/24 | Infusion pumps, patient monitors, imaging workstations | Vendor‑specific VLAN tagging |

| **DMZ / VPN** | 60 | **DMZ** | 10.10.60.0/24 | Remote access VPN concentrator, web portal, audit logs | VPN gateway, log collector |

> **Key Design Decisions**  
> 1. **Physical Separation** – All VLANs are defined on the existing L3‑capable core switch (or on a dedicated firewall) and **tagged** accordingly.  
> 2. **Inter‑VLAN Routing** – Only the **Management VLAN (10)** hosts a **Layer‑3 interface** that performs routing between VLANs. This device also terminates the **guest‑internet** uplink and hosts the **ACL enforcement point**.  
> 3. **ACLs (Firewall Rules)** – All traffic is **explicitly permitted**; everything else is denied. The rule set is the single source of truth for segmentation.  
> 4. **No Direct Guest‑to‑EHR Path** – The Guest VLAN **cannot** reach the EHR VLAN on TCP 3389 (or any other EHR‑specific ports).  

---

### 4. What Specifically Closes the Guest‑to‑EHR RDP Path?  

| Layer | Mechanism | Exact Configuration |
|-------|-----------|----------------------|
| **VLAN Assignment** | Guest laptops are placed in **VLAN 20 (10.10.20.0/24)**; the EHR server lives in **VLAN 30 (10.10.30.0/24)**. | Guest DHCP scope → VLAN 20 tag; EHR DHCP/static IP → VLAN 30 tag. |
| **Layer‑3 Routing** | The firewall/L3‑switch **does not advertise a route** from VLAN 20 to VLAN 30 for **TCP 3389**. | ACL (see below) denies `src 10.10.20.0/24 dst 10.10.30.45 eq 3389`. |
| **Firewall ACL** | Explicit deny rule placed **before** any permit rule for guest traffic. | `deny tcp 10.10.20.0/24 host 10.10.30.45 eq 3389` <br>`allow ip any any` (remaining traffic allowed as needed). |
| **Stateful Inspection** | The firewall tracks connection state; the deny rule blocks **both new and returning** RDP packets, preventing “session‑hopping”. | No extra configuration needed beyond the deny rule; stateful inspection is default. |
| **Network‑Level Segmentation** | Even if a guest device somehow obtains a static IP in VLAN 30 (mis‑configuration), the firewall still enforces the ACL, so the port remains closed. | ACL is applied on the **inbound** interface facing VLAN 30 (or on the outbound interface toward VLAN 20, whichever is more convenient). |

**Result:** The *only* way for a guest device to reach the EHR server is via a **dedicated, authenticated administrative VLAN** (e.g., VLAN 50) that is **not** used by the Guest SSID. This satisfies HIPAA “access‑control” and eliminates the direct RDP vector.

### 5. Detailed Change Plan (Zero‑Downtime During Clinic Hours)

The plan is divided into **four phases**. All production changes are performed **outside of the 08:00‑18:00 window**; the final verification step is performed **after 18:00** to ensure the EHR remains available for the next day’s patient care.

| Phase | Activity | Timing | Impact | Verification |

#### Rollback Procedure (≤ 5 min)

1. **Re‑apply the original firewall rule set** (permit all traffic from VLAN 20 to VLAN 30).  
   - Command example on a Cisco ASA: `no access-list GUEST-TO-EHR-DENY`.  
2. **Re‑enable the default “allow any any”** rule (or the pre‑change permit rule) on the **Guest‑to‑EHR** path.  
3. **Verify** connectivity from a guest laptop to the EHR server on TCP 3389 using `telnet <EHR_IP> 3389`.  
4. **Confirm** that all clinical devices still register and that admin workstations can RDP to the EHR.  
5. **Notify** the change‑control board that the rollback succeeded and open a post‑incident review.  

Because the rollback only touches a **single ACL line** and **does not modify VLAN assignments**, it can be executed instantly from the firewall management console, ensuring that the EHR remains reachable for the next day’s patient charting.

## Closing Statement  

By **re‑architecting the flat 10.10.0.0/22 network into a set of purpose‑segmented VLANs** and **enforcing a stateful ACL that explicitly denies TCP 3389 traffic from the Guest VLAN to the EHR server**, the clinic eliminates the HIPAA‑critical gap without jeopardizing the 08:00‑18:00 availability of the EHR. The change plan respects the “no‑downtime” mandate by confining all configuration work to the after‑hours window, and the **rollback step**—a single ACL removal—restores the pre‑change state in under five minutes should any unexpected condition arise.

Adopting this design not only fulfills the clinic’s **HIPAA Security Rule access‑control obligations**, it also hardens the environment against future lateral‑movement attacks from compromised guest devices, thereby protecting patient privacy and the clinic’s operational continuity.
