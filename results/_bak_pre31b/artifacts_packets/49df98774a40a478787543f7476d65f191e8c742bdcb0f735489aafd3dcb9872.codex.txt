## 🔹 PART 1: Retuned Alerting Logic

### Core Insight
Defrost and early compressor failure are **distinguishable by trajectory, not absolute temperature**. 
- **Defrost:** rises to ~-70°C, holds briefly, then *returns to ≤ -75°C* within 12–15 min.
- **Failure:** rises past -70°C and *continues monotonically upward* (toward -50°C, -40°C, etc.) with no natural reversal.

### New State Machine + Trajectory Logic

| State | Condition | Action |
|-------|-----------|--------|
| `NOMINAL` | Temp ≤ -75°C | No alert |
| `WARM-UP DETECTED` | Temp > -75°C | Open **15-min staging window**. Log event. **No page.** |
| `DEFROST CONFIRMED` | Temp returns ≤ -75°C within 15 min | Close as informational defrost event. Log with timestamp & duration. |
| `STAGING EXTENDED` | Temp between -75°C & -70°C at 15 min, still rising | Extend window to 25 min (12-min defrost + 13-min margin). Continue logging. |
| `P1 FIRE` | Temp > -70°C at 25 min, **OR** rate of change > -1°C/min sustained for >10 min | Page on-call. Auto-attach trajectory graph + freezer diagnostics snapshot. |
| `P1 OVERRIDE` | Within defrost window, but trajectory *diverges* (no peak/recovery after 15 min) | Bypass defrost suppression. Fire P1. |

### Key Logic Additions
1. **Rate-of-Change Filter:** Sustained rise >1°C/min for >10 min = failure signature, even if temp hasn't hit -70°C yet.
2. **Defrost Schedule Integration:** Suppress `WARM-UP DETECTED` during known defrost windows, **but only if the trajectory matches the expected defrost profile**. Divergence auto-triggers P1.
3. **Cross-Freezer Correlation:** If ≥2 freezers enter `WARM-UP DETECTED` within 10 min of each other → escalate to facility power/HVAC event (likely UPS, breaker, or refrigerant loop issue).
4. **Sensor Drift Guard:** Cross-validate IoT sensor against manufacturer controller readout. If drift >±1°C, tag alert as `SENSOR_DISPUTED` and escalate to calibration.

### 1. New Alerting Logic: "Sustained Breach" Detection

## 3. Revised Alert Logic – Step‑by‑Step  

### 3.1  Stage‑0 – “Defrost‑Gate” (instantaneous suppression)

```
IF  ( compressor_power == 0   AND   defrost_heater_active == true )
    THEN  suspend_all_temperature_alerts_for_this_freezer  (for up to 20 min)
```

*The suppression window is intentionally a little longer than the typical 12‑minute defrost so that any temperature excursion that *starts* during defrost but *continues* after the heater shuts off can still be caught.*

### 3.2  Stage‑1 – “Warm‑Check” (first‑level trigger)

Only evaluate when Stage‑0 is **inactive**.

| Condition | Threshold | Minimum Duration | Additional Requirement |
|-----------|-----------|------------------|------------------------|
| **Temperature > T1** | `T1 = -73 °C` (2 °C *above* the old ‑75 °C trigger) | **≥ 5 min** of *continuous* exceedance | Must be **rising** (`dT/dt ≥ 0.25 °C/min`) **or** already at a high plateau (`T ≥ -70 °C`) |
| **AND** | *Either* (a) `dT/dt ≥ 0.25 °C/min` **OR** (b) `T ≥ -70 °C` | – | Guarantees that a brief “spike” caused by a door opening or a brief power surge does **not** fire. |

*Why these numbers?*  

- `-73 °C` is high enough that a normal defrost ramp (which typically peaks around `-70 °C` for ~12 min) will **not** stay above it for longer than 5 min *unless* it is a genuine failure.  
- The 5‑minute minimum prevents a short‑lived transient from causing a page.  
- The “rising” clause forces the system to see a *trend* consistent with a failing compressor (temperature is climbing, not just hovering).  

If **both** temperature and trend requirements are satisfied for the full 5 min, a **P1‑Level‑1** alert is generated (same page as before) **but** it is *tagged* as “Warm‑Check‑Triggered”.

### 3.3  Stage‑2 – “Critical‑Hold” (second‑level escalation)

If a **P1‑Level‑1** alert is **not acknowledged within 3 minutes**, the system automatically:

1. **Re‑evaluates** the same freezer using a stricter rule (Stage‑2).  
2. Stage‑2 condition: `Temperature ≥ -68 °C` **and** `duration ≥ 10 min` **and** `dT/dt ≥ 0.35 °C/min`.  

If the condition still holds, the system **escalates** to **P1‑Level‑2**, which is **non‑suppressible**:

- Sends a **SMS/voice call** to the on‑call engineer (cannot be silenced from the web UI).  
- Triggers the **local audible alarm** on the freezer (a 95 dB horn that cannot be muted without physical access).  
- Opens a **high‑priority ticket** in the lab’s LIMS that must be acknowledged before any other work can continue.

### 3.4  Stage‑3 – “Compressor‑Failure Confirmation” (optional safety net)

If a **Stage‑2** alert fires, the system also checks two ancillary signals:

| Check | Requirement |
|-------|-------------|
| **Compressor power** | Must be **OFF** for > 2 min *and* show **no power‑draw** (i.e., a true loss of compressor). |
| **Door‑open sensor** | Must be **closed** for the entire excursion (so an open door cannot masquerade as a failure). |

If **either** of these checks fails, the alert is downgraded to “investigate but not P1”. This prevents a false positive caused by a technician inadvertently leaving the door ajar while the unit is being serviced.
