# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)

- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.

**Patch-Window Runbook: Windows Server 2022 Cumulative Update Deployment on Remote Drilling Rig**  
*Environment: VSAT (2 Mbps up / 10 Mbps down), shared with SCADA, 14 domain-joined endpoints, 14-day crew hitch, 4-hour maintenance window per hitch*

---

### **Objective**  
Safely and reliably deploy the monthly Windows Server 2022 cumulative security update to 14 domain-joined endpoints, including the domain controller (DC), without saturating the VSAT link or impacting SCADA/drilling operations.

---

## **Phase 0: Pre-Patch Preparation (Before Any Maintenance Window)**

**Objective:** Minimize risk, ensure readiness, and prepare for controlled deployment.

### **Pre-Patch Steps (To Be Completed Remotely Before First Maintenance Window)**

1. **Download & Validate Update Package**
   - Download the latest Windows Server 2022 cumulative update CAB/MSU file from Microsoft Update Catalog.
   - Verify SHA-256 hash and digital signature.
   - Test installation on an isolated lab environment matching the rig’s OS and patch level.

2. **Staging the Update Locally at the Rig**
   - Transfer the update package via BITS or background download during off-peak telemetry hours (e.g., overnight), using throttling:
     - Limit bandwidth to **≤1 Mbps down** to avoid interfering with SCADA.
   - Store the update file on a secure shared network location accessible to all endpoints (e.g., `\\RIG-DC\Software\Updates\YYYY-MM\`).
   - Confirm accessibility and permissions on each target system.

3. **Update Readiness Checks**
   - Use PowerShell remoting (WinRM over HTTPS) to verify:
     - OS version and build number.
     - Available disk space (≥10 GB free per endpoint).
     - Pending reboots.
     - Antivirus compatibility (confirm no known issues with update).
   - Run `DISM /Online /Cleanup-Image /CheckHealth` and `sfc /scannow` remotely if possible.

4. **Backup Critical Systems**
   - Perform full system state backup of the **domain controller** using Windows Server Backup (stored locally and replicated to AWS S3 via VSAT overnight with QoS prioritization).
   - Confirm SCADA operator workstation configurations are version-controlled and recoverable.

5. **Coordinate with Operations Team**
   - Notify drilling supervisors and SCADA engineers of upcoming patch activities.
   - Confirm next 4-hour maintenance window (crew changeover) date/time.

6. **Prepare Rollback Plan**
   - Document uninstall command: `wusa.exe /uninstall /kb:XXXXXXX /quiet /norestart`
   - Prepare bootable recovery media (stored on-site).
   - Confirm DC can be restored from backup within 2 hours if needed.

## **Phase 1: Patch Deployment Strategy**

### **Constraints**
- VSAT: **2 Mbps up / 10 Mbps down** – shared with SCADA.
- SCADA telemetry requires **≥3 Mbps sustained down, ≤1 Mbps up** for real-time monitoring.
- **No network disruption** during drilling operations.
- **Only 4-hour window** every 14 days.
- Domain controller must be updated **last** to avoid authentication outage.

---

### **Bandwidth Management Plan**
- Max update file size: ~1.2 GB (typical for Win2022 Cumulative Update).
- Available bandwidth during patch window: **Use ≤1.5 Mbps down per transfer** to leave ≥8.5 Mbps for SCADA.
- Estimated download time per endpoint:  
  `1.2 GB × 8 bits/byte = 9.6 Gb ÷ 1.5 Mbps ≈ 6,400 seconds ≈ 1.78 hours`  
  Allow **2 hours per endpoint** including install/reboot.

> ⚠️ **Cannot patch more than 2 endpoints per 4-hour window** at this rate.

---

### **Sequencing Strategy (Staggered Over 3 Hitches)**

| **Hitch** | **Maintenance Window** | **Endpoints Patched** | **Rationale** |
|----------|------------------------|------------------------|-------------|
| **Hitch 1** | Window 1 (Day 0–14) | 1x Domain Controller (Staged Pre-Copy Only – **NO INSTALL**) + 2 non-SCADA servers (e.g., file server, print server) | Pre-stage update on DC. Patch least-critical systems first. Confirm process. |
| **Hitch 2** | Window 2 (Day 14–28) | 6 SCADA operator workstations (3 in first 2 hrs, 3 in next 2 hrs) | Spread load. Validate SCADA client stability post-reboot. Monitor telemetry. |
| **Hitch 3** | Window 3 (Day 28–42) | Remaining 4 workstations + **Domain Controller (FINAL STEP)** | Finalize deployment. DC updated last to preserve authentication. |

> ✅ Total: 2 + 6 + 6 = 14 endpoints (DC included)

### **Detailed Execution Per Window**

#### **Each 4-Hour Maintenance Window: Standard Runbook**

**Prerequisites:**
- Confirm drilling operations are paused.
- SCADA team acknowledges system is in maintenance mode.
- All users logged off.
- Backup of DC completed before any change.

---

**Step-by-Step Procedure (Example: Hitch 2 – SCADA Workstations)**

1. **[T+0:00 – T+0:15]** Pre-Window Checks
   - Validate network link health (ping, traceroute to DC).
   - Confirm update file exists and is accessible on `\\RIG-DC\Software\Updates\`.
   - Run pre-check script:
     ```powershell
     # Check disk space, pending reboot, update file access
     Get-WmiObject -Class Win32_OperatingSystem | Select FreePhysicalMemory
     Get-ChildItem "\\RIG-DC\Software\Updates\*.msu" -ErrorAction Stop
     ```

2. **[T+0:15 – T+2:15]** Patch First Group (3 Workstations)
   - Use Group Policy Scheduled Task or PDQ Deploy (agentless) to:
     - Copy update file locally (if not already present).
     - Install silently:  
       `wusa.exe "\\RIG-DC\Software\Updates\windows10.0-kbXXXXXX-x64.msu" /quiet /norestart`
     - Reboot automatically after 5 minutes.
   - Monitor bandwidth via `iftop` or `PRTG Mini-Server` on local network.
   - Limit BITS/transfer rate to **≤1.5 Mbps down per machine**.

3. **[T+2:15 – T+3:45]** Patch Second Group (3 Workstations)
   - Repeat for next set.
   - SCADA engineer verifies telemetry resumes on patched machines.

4. **[T+3:45 – T+4:00]** Post-Window Validation
   - Confirm all patched machines:
     - Rebooted successfully.
     - Rejoined domain.
     - Show update in `Get-HotFix` or `wmic qfe list`.
     - Have stable network and authentication.
   - Log results in central patch tracking sheet (AWS-hosted, synced post-window).
   - Notify operations team: “Patch window complete. Systems operational.”

---

### **Domain Controller Patching (Final Window Only)**

- **Timing:** Final 2-hour block of Hitch 3 window.
- **Preconditions:**
  - All other endpoints patched and stable.
  - Full system state backup completed 24h prior.
  - Secondary time source (e.g., local NTP) available in case of DC reboot delay.
- **Procedure:**
  1. Pause all non-essential services.
  2. Install update:  
     `wusa.exe "C:\Updates\update.msu" /quiet /norestart`
  3. Manually reboot.
  4. Monitor:
     - AD services (Netlogon, DNS, Kerberos).
     - Replication status (if multi-DC, though assumed single DC here).
     - Event logs for errors.
  5. Confirm SCADA workstations can authenticate.

## **Post-Patch Monitoring (After Each Window)**

- Remote monitoring via Zabbix/Nagios for:
  - Uptime.
  - Authentication success rate.
  - VSAT latency and packet loss.
- SCADA team confirms telemetry stability within 1 hour post-window.
- Schedule follow-up health check 24h after DC update.

## **Rollback Plan (Trigger: Critical Failure)**

If DC fails to boot or authentication breaks:
1. Power down DC.
2. Restore system state backup from external drive.
3. Reboot and validate AD services.
4. Delay next patch cycle; investigate root cause.

For workstation failure:
- Reimage from golden image (stored locally).
- Rejoin to domain.

## **Long-Term Recommendations**
1. **Implement Windows Server Update Services (WSUS) on-prem** at the rig (even with small footprint) to eliminate repeated downloads.

## 2. Patch Sequencing & Bandwidth Management (During the 4‑hour Window)

### 2.1 General Rules
1. **Patch in Parallel Groups** – 2 endpoints at a time (including the Domain Controller only in the final round).  
2. **Throttle Each Endpoint** to **1 Mbps** (WSUS setting) → combined 2 Mbps, just below link capacity, leaving ~0.5 Mbps for SCADA telemetry.  
3. **Round‑Based Timeline** – 7 rounds (14 endpoints ÷ 2).  
4. **Reboot Handling** – Each endpoint reboots automatically; the next round starts **after** the previous round’s reboots have completed and all services (including SCADA) are verified.  
5. **Monitoring** – Real‑time bandwidth monitor (VSAT console + `netstat -e` on endpoints). If telemetry dips below 600 kbps, pause the next round.

### 2.2 Detailed Round Schedule

| Round | Time | Endpoints | Notes |
|-------|------|-----------|-------|
| 1 | 00:00 – 00:30 | **Workstation‑01**, **Workstation‑02** | Download & install. |
| 2 | 00:30 – 01:00 | **Workstation‑03**, **Workstation‑04** | |
| 3 | 01:00 – 01:30 | **Workstation‑05**, **Workstation‑06** | |
| 4 | 01:30 – 02:00 | **Workstation‑07**, **Workstation‑08** | |
| 5 | 02:00 – 02:30 | **Workstation‑09**, **Workstation‑10** | |
| 6 | 02:30 – 03:00 | **Workstation‑11**, **Workstation‑12** | |
| 7 | 03:00 – 04:00 | **Domain‑Controller**, **Management‑Workstation** | Final patch; reboot DC last. |

> **Why 7 rounds?**  
> - Each endpoint ~20 min (download 13 min, install 7 min).  
> - 2 endpoints in parallel → 20 min per round.  
> - 7 rounds × 20 min = 140 min.  
> - 140 min < 240 min, leaving ample buffer for reboots, verification, and any unforeseen delays.

### 2.3 Execution Flow

1. **Round 1**  
   - Command on Workstation‑01: `wuauclt /detectnow /updatenow`  
   - Same on Workstation‑02.  
   - Monitor bandwidth; wait for both to finish.  
   - Verify that SCADA telemetry remains ≥ 600 kbps.  

2. **Rounds 2–6**  
   - Repeat step 1 for the next pair of endpoints.  
   - After each round, run a quick connectivity test:  
     `Test-Connection -ComputerName <Target> -Count 10`  
   - Log any failures; if > 2 failures in a round, pause and investigate.

3. **Round 7 – Domain Controller**  
   - Patch DC last to avoid authentication interruptions.  
   - After DC reboot, run:  
     `dsquery * -limit 0 | find /c /i "DC"`  
     to confirm replication is healthy.  
   - Verify that SCADA operator workstations can still authenticate.

| **C – Domain Controller** | 1 DC (primary) | Highest priority to keep authentication alive; patched **last** after all others are stable. |

### 3.2. Bandwidth Estimate per Endpoint  

- Cumulative update size ≈ **1.2 GB** per machine (compressed .cab).  
- VSAT downlink: **10 Mbps** ≈ **1.25 MB/s**.  
- Time to download 1.2 GB = 1.2 GB ÷ 1.25 MB/s ≈ **1024 s** ≈ **17 min** (ideal, no contention).  

Because we will **stage** the update locally (step 2.5), the actual *install* step only reads the cached file, which is negligible network‑wise. The real bandwidth consumption occurs **only once** when the update package is initially pulled onto the local WSUS share (pre‑hitch). Therefore, during the 4‑hour window we are **not** limited by download speed; the limiting factor is **CPU/IO on each endpoint** and **reboot time**.

## 2. Bandwidth & Traffic Engineering Strategy
The VSAT link is shared. SCADA telemetry is latency-sensitive and must not be disrupted.

- **QoS Enforcement:** VSAT router applies DSCP marking: SCADA/telemetry → `EF` (strict priority queue), Patch traffic → `AF11` (best-effort, rate-limited).
- **Download Phase (Pre-Window):** Throttled BITS background download over D-3 to D-1. Consumes ≤1.5 Mbps DL. SCADA queue remains untouched.
- **Window Phase:** Only **installation, reboot, and verification** traffic occurs. No large payloads flow. Estimated peak per wave: ~200–400 Kbps DL + ~100 Kbps UL (telemetry/metadata). Well under 10/2 Mbps cap with SCADA headroom.
- **Traffic Shaper:** Configured to hard-cap patch traffic at 2 Mbps DL / 500 Kbps UL during the window. Any SCADA queue contention automatically throttles patch traffic.

## 3. Endpoint Sequencing Logic (14 Devices)
Sequence prioritizes **authentication continuity** and **bandwidth smoothing**. The DC is patched **last** to preserve live authentication for all prior reboots.

| Wave | Devices | Rationale |
|------|---------|-----------|
| 1 | 3 non-critical office PCs (e.g., admin, comms, medical) | Low blast radius; validates update install/reboot cycle on site |
| 2 | 3 SCADA operator workstations | Confirms cached credentials survive reboot; telemetry agents remain functional |
| 3 | 3 non-critical endpoints (drilling logs, environmental monitors) | Bandwidth breathing room; verifies no SCADA impact from prior wave reboots |
| 4 | 2 SCADA workstations + 1 non-critical | Final client patching before DC; ensures all auth-dependent endpoints are updated |
| 5 | **Domain Controller** | Patched last. SCADA uses cached logon; brief reboot impact is bounded to final window phase |

**Wave Size Constraint:** Maximum 3 concurrent installs to keep DL traffic ≤1.8 Mbps. Each wave includes install + reboot + post-reboot verification.

### 2.  Deployment Sequencing – “Bandwidth‑Friendly Rollout”  

#### 2.1 Bandwidth Calculations  

| Parameter | Value |
|-----------|-------|
| VSAT downstream capacity | 10 Mbps = **1,250 KB/s** (practical sustained ≈ 900 KB/s after protocol overhead) |
| Target patch size (cumulative update) | ≈ 150 MB per endpoint (average for Windows Server 2022) |
| Time to transfer 150 MB at 900 KB/s | **≈ 2 h 45 min** if sent in one burst |
| Desired per‑slot transfer time | **≤ 30 min** (to keep the link under 30 % of capacity and leave headroom for telemetry) |
| Required per‑slot throughput | 150 MB / 30 min ≈ **85 KB/s** → well below the 900 KB/s ceiling |

> **Conclusion:** We can safely push one endpoint at a time, using a 30‑minute slot, while reserving **≈ 850 KB/s** for SCADA telemetry and other critical traffic.

#### 2.2 Slot Allocation & Order  

| Slot # | Endpoint (Role) | Reason for Order | Estimated Start Time (hh:mm) | Estimated End Time (hh:mm) |
|--------|----------------|------------------|------------------------------|----------------------------|
| 1 | **DC (Domain Controller)** | Must be patched **first** – it authenticates all other machines; patching it early avoids a later “re‑boot‑and‑re‑join” cascade. | 00:00 | 00:30 |
| 2‑8 | Workstations **1‑7** (SCADA operator PCs) | These keep the drilling‑telemetry UI alive. They are patched **in parallel** with the rig’s control loops; patching them early guarantees they stay up during the crew‑changeover. | 00:30‑02:30 (30 min each) | 00:30‑02:30 |
| 9‑13 | Remaining workstations **8‑12** (support, admin, monitoring) | Lower priority; can tolerate a short reboot window after the high‑impact machines. | 02:30‑04:30 (30 min each) | 02:30‑04:30 |
| 14 | **Backup/Recovery VM** (optional sanity check) | If the DC rebooted cleanly, run a quick health‑check script; otherwise keep as fallback. | 04:30‑05:00 | 04:30‑05:00 |

*Why 30‑minute slots?*  
- 30 min × 14 endpoints ≈ **7 h** total.  
- The 4‑hour maintenance window is **shared** with the crew‑changeover; however, **only one slot runs at a time** because the crew is present on‑site only during the overlap.  
- By staggering the deployments we keep the VSAT usage **≤ 150 KB/s per slot**, leaving **≈ 850 KB/s** for SCADA telemetry, which must stay ≥ 99 % reliable.

#### 2.3 Deployment Mechanics per Slot  

1. **Pre‑stage** the update on the local WSUS/SCCM server (already cached).  
2. **Target** the endpoint via its **computer object name** (e.g., `RIG01-DC01`).  
3. **Set** the deployment to **“Install but do not reboot automatically”** – we will manually reboot after the download completes (to verify success).  
4. **Monitor** bandwidth on the VSAT interface (via `nload`/`iftop`). If utilization exceeds 750 KB/s, abort and resume after a 5‑minute cool‑down.  
5. **Reboot** the machine **only after** the update installs successfully.  
6. **Validate** service health (AD DS, DNS, SCADA agents) via a quick PowerShell health check script (`Test-ComputerSecureChannel`, `Get-Service -Name WinRM`).  
7. **Log** slot outcome in the Runbook spreadsheet (timestamp, endpoint, status, bandwidth used).

## Patch‑Window Run‑book  
**Target:** 14 domain‑joined Windows Server 2022 endpoints (1 DC, 13 workstations) on a remote drilling rig  
**Update:** Monthly cumulative security roll‑up (KB‑xxxxxx)  
**Network:** VSAT back‑haul – 2 Mbps ↑ / 10 Mbps ↓ (shared with SCADA/telemetry)

**Goal:** Install the update on all 14 endpoints **without saturating the VSAT link** or degrading SCADA authentication/telemetry.

### 1.  High‑Level Strategy  

| Phase | What | Why |
|-------|------|-----|
| **A – Preparation** | Verify backups, health, and create a local content cache. | Guarantees a safe rollback and removes most of the 2 Mbps‑up traffic from the VSAT. |
| **B – Bandwidth‑Managed Staggered Deploy** | Push the update in **four batches** (3‑4 endpoints per batch) using **BITS throttling** (≈ 400 kbps per host). | Total upstream ≤ 1.6 Mbps → well under the 2 Mbps ceiling; SCADA traffic (telemetry) stays unaffected. |
| **C – Domain‑Controller (DC) last** | Update the DC **after** all workstations have successfully rebooted. | Prevents authentication outages during the critical crew‑change window. |
| **D – Verification & Roll‑back** | Validate patch success, telemetry health, and be ready to revert within 30 min per batch. | Keeps the rig operational if anything goes wrong. |
| **E – Hitch‑Cycled Timing** | Run the whole sequence **once per 14‑day hitch** (i.e., during the upcoming crew‑change). | Aligns with the only approved maintenance window. |

### 3.  Bandwidth‑Management & Sequencing Plan  

#### 3.1  Why 4‑batch approach?  

* **VSAT upstream limit:** 2 Mbps = 2 000 kbps.  
* **Target per host:** 400 kbps (≈ 20 % of the link).  
* **Maximum concurrent hosts:** 4 × 400 kbps = **1.6 Mbps** → leaves ~400 kbps for SCADA telemetry and protocol overhead.  

#### 3.2  Batch composition  

| Batch | Hosts (order) | Approx. download time per host* | Estimated total batch time |
|-------|---------------|--------------------------------|----------------------------|
| 1 | **Workstation 01‑04** (lowest telemetry priority) | 1 GB / 0.4 Mbps ≈ **35 min** | 45 min (incl. reboot & health check) |
| 2 | **Workstation 05‑08** | 35 min | 45 min |
| 3 | **Workstation 09‑12** | 35 min | 45 min |
| 4 | **Workstation 13‑14** + **Domain Controller** (DC last) | 35 min (WS 13‑14) + 35 min (DC) – staggered start | 1 h (DC reboot takes longer) |

\*Assumes the MSU is ~1 GB (typical cumulative roll‑up). BITS will **pull from the local cache**, so the only upstream traffic is the **ACK/handshake** (~10 kbps per host). The real upstream load is the **SCADA telemetry** that continues unabated.

### 4.  Detailed Execution Steps  

#### 4.1  Core PowerShell helper (run on the **Patch Server**)

```powershell
# -------------------------------------------------
# Invoke-PatchBatch.ps1
# -------------------------------------------------
param(
    [ValidateSet('1','2','3','4','DC')]
    [string]$Group,
    [string]$CachePath = '\\rigfiles\PatchCache\KBxxxxxx.msu',
    [int]$BitsRateKbps = 400
)

# Mapping of groups to hostnames (adjust per rig)
$Groups = @{
    '1'  = 'WS01','WS02','WS03','WS04'
    '2'  = 'WS05','WS06','WS07','WS08'
    '3'  = 'WS09','WS10','WS11','WS12'
    '4'  = 'WS13','WS14'
    'DC' = 'DC01'
}

$Targets = $Groups[$Group]

foreach ($host in $Targets) {
    Write-Host "=== Starting patch on $host ==="

    # 1. Create remote session
    $sess = New-PSSession -ComputerName $host -ErrorAction Stop

    # 2. Copy MSU locally (from cache) – no VSAT upstream traffic
    Invoke-Command -Session $sess -ScriptBlock {
        param($src,$dst)
        Copy-Item -Path $src -Destination $dst -Force
    } -ArgumentList $CachePath, "C:\Temp\KBxxxxxx.msu"

    # 3. Install via BITS with throttling
    Invoke-Command -Session $sess -ScriptBlock {
        param($msu,$rate)
        # Register BITS job
        $job = Start-BitsTransfer -Source $msu -Destination "C:\Temp\KBxxxxxx.msu" `
                -TransferType Download -Priority Normal -DisplayName "PatchKB" `
                -MaxDownloadRate $rate

        # Wait for completion
        $job | Wait-BitsTransfer -Timeout 3600

        # Run the update silently, force reboot
        Start-Process -FilePath "wusa.exe" -ArgumentList "`"$using:msu`" /quiet /norestart" -Wait
    } -ArgumentList "C:\Temp\KBxxxxxx.msu",$BitsRateKbps

    # 4. Reboot
    Invoke-Command -Session $sess -ScriptBlock { Restart-Computer -Force }

    # 5. Wait for host to come back
    $null = Wait-Job -Timeout 600 -ErrorAction SilentlyContinue
    Write-Host "=== $host rebooted, proceeding to health check ==="

    # 6. Health check
    $ok = Invoke-Command -Session $sess -ScriptBlock {
        $kb = Get-HotFix -Id 'KBxxxxxx' -ErrorAction SilentlyContinue
        $svc = Get-Service -Name 'SCADA*' | Where-Object {$_.Status -eq 'Running'}
        return ($kb -and $svc)
    }

    if ($ok) {
        Write-Host "$host PATCH SUCCESS"
        # Log to central file
        "$host,$Group,Success,$((Get-Date).ToString('u'))" | Out-File -Append '\\rigfiles\PatchLogs\YYYYMMDD_PatchResults.csv'
    } else {
        Write-Error "$host PATCH FAILED – flag for rollback"
        "$host,$Group,Failed,$((Get-Date).ToString('u'))" | Out-File -Append '\\rigfiles\PatchLogs\YYYYMMDD_PatchResults.csv'
    }

    Remove-PSSession $sess
}
```

*Save the script as `Invoke-PatchBatch.ps1` on the patch server and call it from the run‑book (e.g., `powershell -File Invoke-PatchBatch.ps1 -Group 1`).*

#### 4.2  Manual fallback (if PowerShell fails)

| Step | Command (run locally on the endpoint) |
|------|----------------------------------------|
| a. Copy MSU from cache | `copy \\rigfiles\PatchCache\KBxxxxxx.msu C:\Temp\` |
| b. Install (quiet) | `wusa C:\Temp\KBxxxxxx.msu /quiet /norestart` |
| c. Reboot | `shutdown /r /t 0` |
| d. Verify | `Get-HotFix -Id KBxxxxxx` and `sc query scada*` |

#### 4.3  Roll‑back procedure (per host)

1. **Restore System State** from VSS backup (or revert the VM snapshot if the endpoint is virtualized).  
   ```powershell
   wbadmin start systemstaterecover -version:<timestamp> -backupTarget:<backupshare> -quiet
   ```  
2. **Re‑boot** and confirm the previous OS build (use `winver`).  
3. **Re‑enable** any services disabled in step 10 of the pre‑patch checklist.  
4. **Notify** Operations Lead and reopen the maintenance window if needed.

# Patch Management Runbook: Remote Drilling Rig
**Target:** 14 Endpoints (1x Domain Controller, 13x Workstations/Servers)
**Update Type:** Windows Server 2022 Cumulative Security Update
**Constraint Profile:** High Latency/Low Bandwidth (VSAT); 4-hour Maintenance Window; Critical SCADA uptime requirements.

---

## 1. Pre-Patch Phase: "Zero-Bandwidth" Preparation
**Timing:** To be performed 48–72 hours *prior* to the scheduled maintenance window.
**Objective:** Eliminate the need for VSAT usage during the 4-hour maintenance window.

*   **Step 1: Local Repository Staging:** Do **not** trigger the update via Windows Update/WSUS directly from the endpoints during the window. Instead, use a single "Staging Machine" (an administrative laptop or a non-critical workstation) to download the cumulative update packages via the VSAT link well in advance.
*   **Step 2: Payload Verification:** Once downloaded, calculate the SHA-256 hash of the update files on the Staging Machine to ensure no corruption occurred during the high-latency satellite transmission.
*   **Step 3: Local Distribution Setup:** Copy the verified update files to a local file share accessible by all 14 endpoints on the local LAN. This ensures that when the update is triggered, the 10 Mbps VSAT link is not used; the traffic remains entirely on the local rig network.
*   **Step 4: Snapshot/Backup:** Perform a full system state backup or VM snapshot of the Domain Controller and the primary SCADA operator workstations.

---

## 2. The Deployment Sequence (The 4-Hour Window)
**Timing:** During the crew changeover (Maintenance Window).
**Strategy:** "Outside-In" deployment. We patch the periphery first and the "anchor" (Domain Controller) last to ensure that if a machine fails to reboot, the authentication services remain online for the rest of the fleet.

| Sequence | Target Group | Rationale |
| :--- | :--- | :--- |
| **Phase 1** | **Non-Critical Endpoints (6 units)** | These are standard office/admin machines. Testing them first ensures the local update files are compatible with the rig's specific software environment. |
| **Phase 2** | **SCADA Operator Workstations (7 units)** | Once Phase 1 is verified, patch the SCADA workstations. This ensures the human-machine interface (HMI) is updated and ready for the incoming crew. |
| **Phase 3** | **The Domain Controller (1 unit)** | **The Final Step.** The DC is patched last. This ensures that even if the DC requires multiple reboots or experiences a delay, the workstations are already patched and the environment is stable. |

**Execution Logic:**
*   **No Parallelism:** Do not trigger updates on more than two machines at a time. Even though files are local, the simultaneous disk I/O and CPU spikes on the local network switch should be minimized to prevent micro-bursts that could impact SCADA packet timing.
*   **The "Go/No-Go" Check:** After Phase 1, a technician must verify that the patched machines can still reach the DC and authenticate. If Phase 1 fails, **abort** and roll back to prevent a rig-wide lockout.

---

## 3. Hitch Cadence Integration
**Timing Alignment:** The maintenance window occurs once per 14-day hitch during the crew changeover.

*   **Scheduled Frequency:** Patching will be scheduled for the **first maintenance window of a new hitch**. 
*   **Reasoning:** 
    *   **Risk Mitigation:** By patching during the first window of the new hitch, we ensure that the "Incoming Crew" inherits a secure, updated environment. 
    *   **Stability Buffer:** If a patch causes an unforeseen issue (e.g., a driver conflict with a specific SCADA peripheral), the MSP has the remainder of the 14-day hitch to troubleshoot via a scheduled window or a remote session, rather than being "stuck" in the middle of a high-activity drilling period.
    *   **Crew Transition:** The crew changeover is the only time the rig has "human redundancy"—if an operator finds a login issue post-patch, there is a handover period where both old and new crews can assist in troubleshooting the interface.
