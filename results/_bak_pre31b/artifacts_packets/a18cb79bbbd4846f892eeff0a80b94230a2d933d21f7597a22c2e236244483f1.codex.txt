## 10 -- Frontier
The runbook or document is testable: a newcomer could follow it step by step and reach the stated outcome without needing undocumented tribal knowledge. Prerequisites are listed up front, failure or rollback branches are included for steps that can go wrong, and a currency or ownership signal (last verified, owned by) is present when the prompt supports it.
Example character: numbered steps with prerequisites stated first, a rollback note on the one risky step, and a last-verified date.

## 7 -- Strong
The document is mostly step-by-step and usable as a runbook, but is missing one prerequisite check or a failure-branch note for a step that could plausibly fail. Nothing here requires guesswork to follow.
Example character: a clear numbered procedure that omits what to do if the third step fails.

## 5 -- Adequate
The content is a correct-gist prose description of the process rather than an executable, testable runbook -- a new reader would need to reverse-engineer the actual steps.
Example character: a paragraph explaining how the process generally works, without numbered, followable steps.

## 3 -- Weak
The document skips steps a newcomer would need, silently assumes undocumented tribal knowledge, and gives no ownership or currency signal at all.
Example character: a procedure that jumps from step one to step four with an unstated step in between.

## 0 -- Unusable
References fabricated tools, systems, or menu paths that do not exist, or gives a dangerously wrong sequence for a risky operation. Empty or off-task.

### Proposal: Lot-Tracking Taxonomy and File Naming Strategy

**Objective:** Eliminate filename overwrites, resolve lot-number collisions, and establish a self-describing, audit-compliant file/folder taxonomy that satisfies USDA traceability requirements.

---

#### 1. Proposed Taxonomy

We recommend a two-tier taxonomy: a **Lot-ID structure** that enforces uniqueness across lines, and a **File/Folder naming convention** that captures context without requiring file access.

**A. Lot-ID Format (Scanner Software Configuration)**
The current 4-digit counter creates collisions because it is not scoped to the production line. We must incorporate the Line ID and Quarter into the Lot ID to guarantee global uniqueness while preserving the plant's quarterly reset workflow.

*   **New Format:** `LOT-{LinePrefix}-{QuarterCode}-{Sequence}`
*   **Examples:**
    *   Line 1, Q3, 5th Lot: `LOT-L1-Q3-0005`
    *   Line 2, Q3, 5th Lot: `LOT-L2-Q3-0005`
*   **Benefits:**
    *   **Collision-Free:** `L1` and `L2` prefixes ensure physical lots with the same sequence number never share an ID.
    *   **Auditability:** The ID reveals the line, quarter, and sequence immediately.
    *   **Business Logic Preserved:** The counter still resets to `0001` every quarter per line.

**B. Filename Convention**
Scanners must be reconfigured to write logs using the unique Lot-ID and timestamp. The filename must be deterministic and unique.

*   **Format:** `{LinePrefix}_lot_log_{LotID}_{YYYYMMDDHHmmss}.csv`
*   **Example:** `L1_lot_log LOT-L1-Q3-0005_20241015143022.csv`
*   **Benefits:**
    *   **Uniqueness:** The combination of Line, Lot-ID, and timestamp ensures no two files ever have the same name, even if scans occur simultaneously on different lines.
    *   **Self-Describing:** An auditor can identify the line, lot, and exact scan time by inspecting the filename alone.
    *   **No Overwrites:** The timestamp and Lot-ID prevent the "overwrite" behavior caused by generic filenames.

**C. Folder Structure**
Instead of a single shared folder, implement a hierarchical structure to group logs logically and simplify retrieval.

*   **Structure:** `C:\USDA\LotLogs\{Year}\{Quarter}\`
*   **Workflow:**
    *   Scanners write files into the current quarter's folder.
    *   Example: `C:\USDA\LotLogs\2024\Q3\`
    *   This ensures files are naturally sorted and prevents "folder noise," further supporting audit reviews.

**Root Path:** `\\MSP_Server\USDA_Traceability\`

**Directory Structure:**
```text
\USDA_Traceability\
  \2023\
    \04\
      \Line01\
      \Line02\
      \Line03\
```

*   **Level 1:** `{Year}` (e.g., `2023`)
*   **Level 2:** `{Month}` (e.g., `04` for April)

`{YYYYMMDD}_{HHMMSS}_{FacilityCode}_{LotID}_{Source}.csv`

**Example:**
`20230415_143000_USDA_P01_2023L10045_Scanner01.csv`

*   **Uniqueness:** The timestamp ensures no two files are ever identical, even if the Lot ID is the same.

    *   **Date/Time:** April 15, 2023 at 14:30.
    *   **Facility:** USDA Plant P01.
    *   **Lot ID:** 2023L10045.
    *   **Source:** Scanner 01.
*   **No Overwrite:** Files are written into the specific Line folder for that month, preserving history.

The current 4-digit counter resets quarterly, causing the collision. This must be replaced with a schema that guarantees global uniqueness across all lines and time.

*   **LineCode:** `L1`, `L2`, `L3`.

**Why this works:** Even if Line 1 and Line 2 produce a batch at the exact same minute, their IDs are mathematically distinct. The ID itself tells the auditor exactly *when* and *where* the product originated without needing to open a database.

### Proposed Solution for File/Folder Naming and Lot-ID Taxonomy

To resolve the issues of ambiguous lot numbers, overwritten logs, and non-self-describing filenames, implement the following structured approach:

---

#### **1. New File/Folder Naming Convention**
Create a hierarchical directory structure and filenames that **uniquely identify** each log file without requiring file content inspection. The format incorporates **production line**, **lot number**, **timestamp**, and **file type**:

**Directory Structure:**
```
/file_server
  ├── [YEAR]
  │   ├── [QUARTER]
  │   │   ├── [LINE]_Q[QUARTER]_LOT[LOT]_START[DATE]_END[DATE].csv
  │   │   ├── [LINE]_Q[QUARTER]_LOT[LOT]_START[DATE]_END[DATE].csv
  │   │   └── ... (additional files per lot)
  │   └── ... (future quarters)
  └── ... (future years)
```

**Filename Format:**
`[LINE]_Q[QUARTER]_LOT[LOT]_START[DATE]_END[DATE].csv`

- **`[LINE]`**: Unique identifier for the production line (e.g., `L1`, `L2`, `L3`).  
- **`[QUARTER]`**: Quarter number (1-4).  
- **`[LOT]`**: Lot number (4-digit, **now unique per line**).  
- **`START[DATE]` & `END[DATE]`**: Dates in `YYYYMMDD` format (e.g., `START20231001` for October 1, 2023).  

**Example:**  
A log for Line 2, Quarter 4, Lot 1234 (started Oct 15, 2023, ended Oct 16, 2023) would be:  
`L2_Q4_LOT01234_START20231015_END20231016.csv`

---

#### **2. Lot-ID Taxonomy to Eliminate Collisions**
Modify the lot numbering scheme to **include the line identifier**, ensuring uniqueness across all lines in a quarter:

- **New Lot Number Format:** `[LINE]_[LOT]`  
  - Example: `L1_0001` (Line 1, Lot 1), `L2_0001` (Line 2, Lot 1).  
- **Behavior:**  
  - Each line maintains its own 4-digit counter (`0001`–`9999`).  
  - Counters reset quarterly (e.g., `L1_0001` starts each quarter for Line 1).  
  - Guarantees global uniqueness (e.g., `L1_0001` ≠ `L2_0001`).  

**Why This Works:**  
- Line-specific counters prevent cross-line duplicates.  
- Filenames retain the legacy 4-digit lot number for backward compatibility but disambiguate via the `[LINE]` prefix.

## 3.  Lot‑Number Taxonomy – Preventing Collisions  

### 3.1  From “local 4‑digit counter” to a **plant‑wide unique lot sequence**  

| Old approach | New approach |
|--------------|--------------|
| Each line increments a 4‑digit counter that resets every quarter (`0001 → 9999`). | A **single plant‑wide monotonic counter** (5‑digit, zero‑padded) is allocated by the MES when a new lot is started on *any* line. The counter is stored in a central database and never resets within the quarter (or ever). |
| Result: two lines could generate `0042` in the same quarter → same lot number. | Result: lot numbers look like `S00001`, `S00002`, … globally; they are unique across all lines and all quarters. |

**How it works in practice**

1. **Lot‑creation request** – When a line’s operator scans the first barcode for a new lot, the scanner sends a *lot‑initiation* message to the MES.  
2. **MES assigns a global sequence** – The MES looks up the next unused 5‑digit counter (e.g., `S00001`) and writes it into the lot header.  
3. **Filename generation** – The scanner immediately creates the filename using that sequence (`_S00001`).  
4. **Persistence** – The same sequence is embedded in the CSV header (mandatory field) so that downstream systems can trace back to the same lot even if the file is moved.

Because the counter is monotonic **across the whole plant**, the chance of two lines ever receiving the same sequence number is **zero**, eliminating the audit‑failure scenario.

### 3.2  Quarter‑level reporting  

The quarter (`Q1`‑`Q4`) is encoded in the folder name (`LotQ1`, `LotQ2`, …). This enables:

* **Automatic quarterly roll‑up** – a simple directory scan returns all lot folders for `LotQ1`.  
* **Retention policies** – the plant can archive an entire quarter by deleting the top‑level `YYYY/MM/DD/L{L}` trees older than X months, knowing that each folder name already contains the quarter token.

### 3.3  Optional checksum for integrity  

To satisfy USDA audit requirements for data integrity, the filename can optionally end with a **32‑bit CRC** derived from the filename contents (excluding the checksum token). Example:

```
lot_log_20250918_143210Z_L02_LotQ1_S00001_6F2A.csv
```

The checksum token is not required for uniqueness but can be added automatically by the scanner if the plant wishes.

## 1.  Naming taxonomy – “what the file name tells you”

| Element | Format | Example | Why it matters |
|---------|--------|---------|----------------|
| **Plant code** | 2‑letter (or 3‑digit) code – e.g., **US** for “USDA‑checked plant” or **001** if you already have a numeric plant ID | `US` | Guarantees uniqueness if the same naming rules are ever reused at another site. |
| **Line identifier** | `L01`, `L02`, `L03` (fixed, never changes) | `L02` | Distinguishes the three parallel lines. |
| **Quarter** | `YYQn` – 2‑digit year + Q1‑Q4 | `24Q3` | The current lot‑counter reset is still quarter‑based, so we keep that reference. |
| **Line‑local sequence** | 4‑digit zero‑padded counter **reset each quarter per line** | `0015` | The “running 4‑digit counter” you already use, but now it is **line‑scoped** – no cross‑line collisions. |
| **Date** | `YYYYMMDD` (ISO‑8601) | `20240718` | Human‑readable production day. |
| **Start‑time (UTC)** | `HHMMSS` (24‑hour) | `081732` | Gives second‑level precision; together with the line‑local sequence it is already unique. |
| **Optional millisecond** | `sss` (0‑999) – only needed if you ever have two lots start in the same second on the same line (unlikely but safe). | `047` | Guarantees absolute uniqueness. |
| **File type suffix** | Fixed string `lotlog` (or whatever you like) | `lotlog` | Makes the purpose obvious. |
| **Extension** | `.csv` | `.csv` | Standard file type. |

### Full filename pattern  

```
<Plant>_<Line>_<YYQn>-<Seq>_<YYYYMMDD>_<HHMMSS>[sss]_<filetype>.csv
```

**Example (real‑world):**

```
US_L02_24Q3-0015_20240718_081732_lotlog.csv
```

If you need millisecond granularity:

```
US_L02_24Q3-0015_20240718_081732047_lotlog.csv
```

**Why this is self‑describing**

* **Plant** – tells you which site the data belong to.
* **Line** – tells you which production line generated it.
* **Quarter + sequence** – maps directly to the existing lot‑numbering practice, but now the sequence is scoped to a line, so “0015” on L01 and “0015” on L02 are different lots.
* **Date & time** – you can instantly see *when* the lot started without opening the file.
* **Filetype** – makes it obvious that the file is a scan‑log (you could have other file types in the same folder).

## 3.  New lot‑ID taxonomy (the *human‑readable* lot number)

You will still need a **lot identifier that people can read and quote** (e.g., on labels, shipping paperwork, and USDA reports). Use a **compact “Lot ID”** that is printed on the product and stored in the CSV header, but that is **derived directly from the filename**.

```
<Line>-<YYQn>-<Seq>
```

* **Line** – L01 / L02 / L03
* **YYQn** – 24Q3
* **Seq** – 4‑digit counter (reset each quarter per line)

**Examples**

* `L01-24Q3-0015`
* `L02-24Q3-0015`

Because the sequence is **line‑scoped**, the same 4‑digit number can safely appear on different lines without any ambiguity. The full filename already carries the date and time, so if ever a dispute arises you can always go back to the exact file.

**Implementation tip:**  
When the scanner finishes a lot, the software should:

1. **Read the current line‑local counter** (stored in a tiny “lot‑counter” file in the line’s folder, e.g., `L02_counter_2024Q3.txt`).  
2. **Increment it**, write the new value back, and embed it in the Lot ID and filename.  
3. **Create the CSV** using the full filename pattern shown above.  
4. **Write the Lot ID** (`L02-24Q3-0015`) into the first line of the CSV (or as a column header).  

This guarantees that the Lot ID printed on the label will **always match** the filename that holds the scan log.

## 2. Lot‑ID Taxonomy

### Problem with the current scheme

* 4‑digit counter that resets every quarter → **Same number on two different lines in the same quarter**.

### Proposed new format

| Element | Description | Example |
|---------|-------------|---------|
| **Plant ID** | Two‑letter code (or longer) | `PL01` |
| **Line ID** | Two‑digit code | `L02` |
| **Date** | YYYYMMDD (or YYYYMM for quarter) | `20240718` |
| **Local Counter** | 4‑digit, *never* reset for the plant (or per‑day if you prefer) | `0001` |
| **Optional suffix** | e.g., `-A` for audit trail, `-B` for batch, etc. | `-A` |

### Why it eliminates collisions

* The *combination* of plant, line, date (or quarter), and counter is unique.  
* Even if two lines produce the same 4‑digit counter on the same day, the line ID makes the lot‑ID distinct.

## 3. Handling Existing Ambiguous Lots

### 3.1. Keep the original logs

* `InternalLotID` is the *new* unique ID that you will use for all future logs and audit reports.

### 3.3. Update the audit workflow

1. **During an audit** the USDA inspector asks for “Lot 0010”.  
2. The auditor consults the *disambiguation table* and sees that there are two entries, one for each line.  
3. The auditor requests the *InternalLotID* (e.g., `PL01-L02-20240718-0001`) to resolve the ambiguity.  
4. The plant’s internal systems automatically map the original lot number to the new, unique ID for all downstream processes (inventory, traceability, recalls, etc.).

### 3.4. Automation

* Add a tiny service or script that runs each time a new lot starts:  
  * It generates the `InternalLotID`.

  * It writes the new log file to the uniquely named folder.

* The script also checks whether an `OriginalLotID` already exists for the plant+quarter+line. If it does, it appends a suffix (e.g., `-A`, `-B`) to keep the internal ID unique.
