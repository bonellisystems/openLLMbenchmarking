## 🔍 Bug 1: **Incorrect use of default mutable argument**

### 📍 Line 14:
```python
def flag_overpressure_events(readings, alerts=[]):
```

### ❌ Issue:
The parameter `alerts=[]` is a **mutable default argument**, which is a common Python gotcha. Default arguments are evaluated **once at function definition time**, not each time the function is called. This means that all calls to the function share the same list instance.

### 🧠 Effect:
If `flag_overpressure_events` is called multiple times without explicitly passing `alerts`, it will accumulate values from previous calls, leading to incorrect behavior in multi-well scenarios where the function is used repeatedly.

### ✅ Fix:
Change it to:
```python
def flag_overpressure_events(readings, alerts=None):
    if alerts is None:
        alerts = []
    for psi in readings:
        if psi > ALERT_THRESHOLD_PSI:
            alerts.append(psi)
    return alerts
```

---

## 🔍 Bug 2: **Silent output corruption due to shared state (via mutable list)**

### 📍 Line 10:
```python
readings_by_well.setdefault(well_id, []).append(psi)
```

### ❌ Issue:
This line is actually **correctly written** and does not cause any bug per se. However, the **real silent bug** lies in how `flag_overpressure_events` handles `alerts` — and more importantly, in the logic around how `events` are collected and returned.

But let’s trace back more carefully.

In `summarize_well`, this is called:
```python
events = flag_overpressure_events(readings)
```

Because `flag_overpressure_events` uses a mutable default list, and we **reuse** `alerts` across different wells if not explicitly reinitialized, it can lead to `events` from one well bleeding into another — even though `flag_overpressure_events` is called per well.

But again, that's due to the **default mutable argument bug** already addressed above.

However, if you look at how `alerts` is used:

We call:
```python
events = flag_overpressure_events(readings)
```
And then:
```python
avg = statistics.mean(readings)
```

But if the `alerts` list is shared between calls (due to default argument), and the same list object is mutated, then the list of events may contain entries from prior wells — which can corrupt the output silently.

### 🧠 So the **real silent corruption bug** is:

Even if `flag_overpressure_events` were rewritten correctly (as fixed above), we’d still have a **logical error** in `summarize_well()` in how we handle the returned list.

In fact, we **should not be reusing or mutating shared lists**, but the issue is subtle.

But if we interpret it strictly as what **causes silent data corruption** in multi-well reports, we see it's actually caused by **not properly isolating the `alerts` list per call**, which is addressed by **fixing the default argument**.

So the **primary silent corruption** is due to shared state in the mutable default argument.

### **Bug 2 — Mutable default argument (line 14)**

**Where:** Line 14 inside `flag_overpressure_events`

**Problem:** The default mutable argument `alerts=[]` is a classic Python anti-pattern. Because lists are mutable, the same list object is reused across calls. After the first well, `alerts` retains the previous well's overpressure values, so the second well's `flag_overpressure_events` call starts with stale data and silently appends to it — corrupting the count and list for every subsequent well.


**Fix:** Use `None` as the default and create a fresh list inside the function:

