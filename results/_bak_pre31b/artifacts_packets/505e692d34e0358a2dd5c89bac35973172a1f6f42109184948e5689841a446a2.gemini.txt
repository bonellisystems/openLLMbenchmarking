## General Rule

**When two or more one-to-many child tables must be aggregated before being joined together:**

**Rule:** Aggregate each child table separately by parent key, then join the pre-aggregated results. This prevents the Cartesian product problem that occurs when joining multiple one-to-many relationships directly.

**When to apply this rule:**
1. You have multiple one-to-many relationships from the same parent table
2. You're aggregating amounts or counts from these child tables
3. The child tables don't have a direct relationship to each other
4. You need accurate totals that sum independently for each parent

**Alternative syntax using subqueries:**
```sql
SELECT 
    p.project_id,
    p.project_name,
    COALESCE(
        (SELECT SUM(co_amount) FROM change_orders WHERE project_id = p.project_id), 
        0
    ) as total_co_amount,
    COALESCE(
        (SELECT SUM(invoice_amount) FROM invoices WHERE project_id = p.project_id), 
        0
    ) as total_invoice_amount
FROM projects p
ORDER BY p.project_id;
```

The first approach with CTEs is generally preferred as it's more readable and performs better in most cases.

### 1. Analysis of the Trap (The Cartesian Product)

If you were to join `projects` to `change_orders` and `invoices` directly in a single query, you would create a **Cartesian Product** (fan-out). The database joins every row from one child table to every row of the other child table for the same project.

For **Project 101 ("Riverside Office Park")**, the data is:
*   **Change Orders:** 3 rows ($50k, $30k, $20k). Sum = **$100,000**.
*   **Invoices:** 4 rows ($500k, $500k, $500k, $300k). Sum = **$1,800,000**.

If you join these directly (e.g., `FROM change_orders JOIN invoices ON projects.project_id = ...`), you get **12 rows** (3 COs × 4 Invoices).

**What goes wrong numerically:**
1.  **Change Order Total:** Each CO amount is repeated 4 times (once for each Invoice).
    *   Calculation: True Total ($100,000) × Invoice Count (4) = **$400,000**.
    *   *Result:* The CO total is inflated by a factor of 4.
2.  **Invoice Total:** Each Invoice amount is repeated 3 times (once for each CO).
    *   Calculation: True Total ($1,800,000) × CO Count (3) = **$5,400,000**.
    *   *Result:* The Invoice total is inflated by a factor of 3.

### 2. The Correct Query

To prevent this multiplication, you must aggregate the child tables into single rows **before** joining them to the parent table.

```sql
SELECT 
    p.project_id,
    p.project_name,
    COALESCE(co_agg.total_co_amount, 0) AS total_change_order_amount,
    COALESCE(inv_agg.total_invoice_amount, 0) AS total_invoiced_amount
FROM 
    projects p
LEFT JOIN (
    -- Pre-aggregate Change Orders
    SELECT project_id, SUM(co_amount) AS total_co_amount
    FROM change_orders
    GROUP BY project_id
) co_agg ON p.project_id = co_agg.project_id
LEFT JOIN (
    -- Pre-aggregate Invoices
    SELECT project_id, SUM(invoice_amount) AS total_invoice_amount
    FROM invoices
    GROUP BY project_id
) inv_agg ON p.project_id = inv_agg.project_id;
```

**Why this works:**
*   The subquery `co_agg` reduces the 3 rows for Project 101 to 1 row with the value $100,000.
*   The subquery `inv_agg` reduces the 4 rows for Project 101 to 1 row with the value $1,800,000.
*   Joining these pre-aggregated results to `projects` preserves the 1:1 relationship per project, yielding the correct totals.

### 3. The General Rule

**The Rule of Aggregation:**
When joining a parent table to multiple child tables where both relationships are One-to-Many (1:M), you must **aggregate (GROUP BY) each child table individually before performing the JOIN**.

If you join two 1:M relationships directly, the row counts multiply (fan-out), causing `SUM` calculations for any column from either child table to be multiplied by the row count of the *other* table. Always use derived tables (subqueries) or `LATERAL` joins to isolate and aggregate the child data first.

## The Trap: Why You Cannot Aggregate After Joining

**Do not** write a query like this:

```sql
SELECT
    p.project_id,
    SUM(co.co_amount) AS total_change_orders,
    SUM(i.invoice_amount) AS total_invoiced
FROM projects p
JOIN change_orders co ON co.project_id = p.project_id
JOIN invoices i     ON i.project_id = p.project_id
GROUP BY p.project_id;
```

### What Goes Wrong Numerically for Project 101

When you join `change_orders` and `invoices` directly, SQL produces a **Cartesian product** (cross-join) between the two child tables.

*   Project 101 has **3** change order rows.
*   Project 101 has **4** invoice rows.
*   The result set contains $3 \times 4 = \mathbf{12}$ rows per project, instead of the 7 individual source rows.

Because `SUM()` aggregates over these 12 duplicated rows, the totals are inflated by the multiplication factor of the *other* table:

| Metric | True Total | Naive Join Total | Multiplier |
| :--- | :--- | :--- | :--- |
| **Change Orders** | **$100,000** | **$400,000** | Inflated by 4 (row count of invoices) |
| **Invoiced** | **$1,800,000** | **$5,400,000** | Inflated by 3 (row count of change orders) |

**Calculation:**
*   **Wrong CO Total:** $(50k + 30k + 20k) \times 4 \text{ invoice rows} = 400,000$
*   **Wrong INV Total:** $(500k \times 3 + 300k) \times 3 \text{ CO rows} = 5,400,000$

In a construction context, this means you would report the project is "invoiced" at $5.4M instead of $1.8M, and the change order exposure at $400k instead of $100k. This leads to massive billing errors and cash flow forecasting failures.

## The Correct Query

To fix this, we must **aggregate the child tables independently in subqueries first**, then join the pre-aggregated totals to the `projects` table.

```sql
SELECT
    p.project_id,
    p.project_name,
    COALESCE(co.total_co_amount, 0)  AS total_change_orders,
    COALESCE(inv.total_invoice_amount, 0) AS total_invoiced
FROM projects p
LEFT JOIN (
    SELECT
        project_id,
        SUM(co_amount) AS total_co_amount
    FROM change_orders
    GROUP BY project_id
) co ON co.project_id = p.project_id
LEFT JOIN (
    SELECT
        project_id,
        SUM(invoice_amount) AS total_invoice_amount
    FROM invoices
    GROUP BY project_id
) inv ON inv.project_id = p.project_id
ORDER BY p.project_id;
```

### Why this works
1.  **Independent Aggregation:** The subqueries `co` and `inv` each perform their own `SUM()` on their respective tables before any joining happens.
2.  **No Multiplication:** Each project appears only once in the `co` subquery and once in the `inv` subquery. Joining them results in exactly **1 row per project**, not a cross-product.
3.  **LEFT JOIN Safety:** We use `LEFT JOIN` to ensure projects with zero change orders or zero invoices still appear in the report with a total of `0` (handled by `COALESCE`).

---

## General Rule: The "Subquery First" Pattern

> **If you have two one-to-many child tables joined to a parent, and you need to aggregate (SUM, AVG, COUNT) columns from *both* children independently, you must aggregate each child table separately in a subquery (or CTE) before joining them back to the parent.**

### Rule of Thumb

| Scenario | Method |
| :--- | :--- |
| You need the sum of Col A from Table X **and** Col B from Table Y in one result set | **Aggregate first**, then join. |
| You need to filter rows from Table X to find the row where Col A > Threshold | Join first, then filter. |
| You need to count distinct values across a single table | Aggregate in a single subquery. |

**Why?** `SUM(col)` is a *reduction* operation. It requires a fixed number of input rows to produce a single output row. If a `JOIN` creates $N$ rows from $M$ and $K$ rows (where $N = M \times K$), the aggregation treats the cross-product rows as distinct data points rather than duplicates, artificially inflating the result by a factor of $N$. Aggregating before joining preserves the cardinality of each independent dataset.

### Analysis of the Cartesian Product Trap

If you join the `change_orders` and `invoices` tables directly to the `projects` table and attempt to sum the amounts in a single `GROUP BY` query, you will encounter the **Fan-out (Cartesian Product) Problem**.

Because both `change_orders` and `invoices` have a one-to-many relationship with `projects`, the database engine creates a row for every combination of change orders and invoices. For **Project 101**, the logic proceeds as follows:

1.  **The Join:** The engine joins the 3 change-order rows with the 4 invoice rows ($3 \times 4$), resulting in **12 rows** for Project 101.
2.  **The Multiplication:**
    *   Each specific `co_amount` is duplicated 4 times (once for each invoice match).
    *   Each specific `invoice_amount` is duplicated 3 times (once for each change-order match).
3.  **The Incorrect Totals:**
    *   **Change Orders:** The true total ($100,000) is inflated by the number of invoice rows.
        $$100,000 \times 4 = \mathbf{\$400,000}$$
    *   **Invoices:** The true total ($1,800,000) is inflated by the number of change-order rows.
        $$1,800,000 \times 3 = \mathbf{\$5,400,000}$$

### The Correct Query

To prevent this inflation, you must aggregate the child tables individually before joining them. This query uses Common Table Expressions (CTEs) to calculate the sums independently, then joins them back to the parent table.

```sql
WITH co_totals AS (
    -- Aggregate Change Orders first
    SELECT 
        project_id, 
        SUM(co_amount) AS total_co_amount
    FROM change_orders
    GROUP BY project_id
),
inv_totals AS (
    -- Aggregate Invoices first
    SELECT 
        project_id, 
        SUM(invoice_amount) AS total_inv_amount
    FROM invoices
    GROUP BY project_id
)
SELECT 
    p.project_id,
    p.project_name,
    p.contract_value,
    COALESCE(c.total_co_amount, 0) AS total_change_orders,
    COALESCE(i.total_inv_amount, 0) AS total_invoiced
FROM projects p
LEFT JOIN co_totals c ON p.project_id = c.project_id
LEFT JOIN inv_totals i ON p.project_id = i.project_id
ORDER BY p.project_id;
```

### The General Rule

**"Aggregate child tables before joining."**

When two or more one-to-many child tables link to the same parent table (or to each other), you must perform the aggregation (using `SUM`, `COUNT`, `AVG`, etc.) **before** the join. By collapsing the child data into a single row per parent first, you establish a 1:1 relationship, ensuring that the parent’s metrics are not multiplied by the row counts of the child tables.

**1. What goes wrong if you “join‑then‑sum” the two child tables**

|---------------|-----------|

| co_amount | invoice_amount |
|-----------|----------------|

| 50 000    | 300 000 |

That is the numeric error caused by joining before aggregation.

**2. General rule**

> **When two child tables are each *one‑to‑many* relative to the same parent, you must aggregate each child table **before** you join the results to the parent (or to each other).**  
> Aggregating first guarantees that each parent’s child rows are reduced to a single scalar value (e.g., total amount) that can be safely combined without duplication.

**3. Correct query – one result set with both totals per project**

The safest way is to aggregate each child table in its own sub‑query (or CTE) and then join those aggregated results to the `projects` table.

```sql
/* 1️⃣ Aggregate change_orders per project */
WITH co_per_project AS (
    SELECT
        project_id,
        SUM(co_amount) AS total_change_order_amount
    FROM change_orders
    GROUP BY project_id
),

/* 2️⃣ Aggregate invoices per project */
inv_per_project AS (
    SELECT
        project_id,
        SUM(invoice_amount) AS total_invoiced_amount
    FROM invoices
    GROUP BY project_id
)

/* 3️⃣ Join the aggregated totals back to the projects table */
SELECT
    p.project_id,
    p.project_name,
    COALESCE(co.total_change_order_amount, 0) AS total_change_order_amount,
    COALESCE(inv.total_invoiced_amount, 0)   AS total_invoiced_amount
FROM projects p
LEFT JOIN co_per_project co ON p.project_id = co.project_id
LEFT JOIN inv_per_project   inv ON p.project_id = inv.project_id
ORDER BY p.project_id;
```

**What goes wrong if you join the three tables in one step**

If you write a naïve query that joins `projects` to `change_orders` **and** `invoices` in a single `FROM` clause and then sum the two amount columns, the join creates a **Cartesian product** of the two child tables for every project that has rows in *both* tables.

```sql
SELECT p.project_id,
       SUM(co.co_amount) + SUM(i.invoice_amount) AS total_amount
FROM   projects      p
JOIN   change_orders co ON co.project_id = p.project_id
JOIN   invoices      i  ON i.project_id  = p.project_id
GROUP BY p.project_id;
```

For **project 101** (`Riverside Office Park`) we have  

* 3 change‑order rows (CO‑1 $50 000, CO‑2 $30 000, CO‑3 $20 000) → true change‑order total **$100 000**  
* 4 invoice rows (INV‑1 $500 000, INV‑2 $500 000, INV‑3 $500 000, INV‑4 $300 000) → true invoice total **$1 800 000**

Because the join pairs **every** change‑order with **every** invoice for the same project, the intermediate result set contains  

```
3 (change‑orders) × 4 (invoices) = 12 rows
```

Each change‑order amount appears 4 times (once for each invoice) and each invoice amount appears 3 times (once for each change‑order). Consequently:

* Sum of `co.co_amount` across the 12 rows = 3 × 4 × (50 000 + 30 000 + 20 000) / 3  
  = **$400 000** (the true $100 000 multiplied by 4 invoices)  

* Sum of `i.invoice_amount` across the 12 rows = 4 × 3 × (500 000 + 500 000 + 500 000 + 300 000) / 4  
  = **$5 400 000** (the true $1 800 000 multiplied by 3 change‑orders)  

The combined total would be **$5 800 000**, which is far larger than the correct $1 900 000 ( $100 000 + $1 800 000 ).  
The over‑counting happens because the join multiplies the cardinalities of the two one‑to‑many relationships.

**Correct approach**

The remedy is to **aggregate each child table separately first**, turning the one‑to‑many sets into single‑row summaries, and **then join those aggregates** to the parent table. This eliminates the Cartesian‑product effect.

```sql
/* ANSI‑SQL, PostgreSQL‑compatible */
SELECT  p.project_id,
        COALESCE(co.total_co_amount, 0)      AS total_change_order_amount,
        COALESCE(i.total_invoice_amount, 0)  AS total_invoice_amount
FROM    projects p
LEFT JOIN (
        SELECT project_id,
               SUM(co_amount) AS total_co_amount
        FROM   change_orders
        GROUP BY project_id
) co ON co.project_id = p.project_id
LEFT JOIN (
        SELECT project_id,
               SUM(invoice_amount) AS total_invoice_amount
        FROM   invoices
        GROUP BY project_id
) i ON i.project_id = p.project_id;
```

* The sub‑queries `co` and `i` each collapse the many‑to‑one child rows into a **single** summed value per `project_id`.  
* The outer `LEFT JOIN`s attach those single‑row results to the `projects` table, preserving projects that have no change‑orders or no invoices (the `COALESCE` turns `NULL` into 0).  

For **project 101** the query returns:

| project_id | total_change_order_amount | total_invoice_amount |
|------------|---------------------------|----------------------|
| 101        | 100 000                   | 1 800 000            |

which matches the true totals.

**General rule**

> **When two (or more) child tables are related to the same parent by one‑to‑many relationships, you must aggregate (e.g., `SUM`, `COUNT`, `AVG`, …) each child table **before** joining them to the parent (or to each other).**  
> Otherwise the join will duplicate rows according to the product of the child cardinalities, leading to inflated (or otherwise incorrect) aggregate results.

In SQL terms:  

```sql
SELECT …
FROM   parent
LEFT JOIN ( SELECT child_key, SUM(metric) … FROM child1 GROUP BY child_key ) c1
       ON c1.child_key = parent.key
LEFT JOIN ( SELECT child_key, SUM(metric) … FROM child2 GROUP BY child_key ) c2
       ON c2.child_key = parent.key;
```

This pattern guarantees correct totals even when one or both child tables contain multiple rows per parent.

### The Problem: Join Multiplication

If you write a single `JOIN` query that connects `projects` to both `change_orders` and `invoices` simultaneously, you trigger a **Cartesian product** (row multiplication).

**The Naive Query (Incorrect):**
```sql
SELECT 
    p.project_id,

    SUM(inv.invoice_amount) AS total_invoiced
FROM projects p
JOIN change_orders co ON p.project_id = co.project_id
JOIN invoices inv ON p.project_id = inv.project_id
GROUP BY p.project_id;
```

**Why this fails for Project 101:**
1.  **Row Cardinality:** Project 101 has **3** Change Order rows and **4** Invoice rows.
2.  **The Join:** When the database joins these two tables directly, it does not merge rows; it combines every row from the left with every row from the right.
3.  **Resulting Rows:** $3 \times 4 = 12$ rows are generated for Project 101.
4.  **The Math:**
    *   **Change Orders:** Each of the 3 original rows is repeated 4 times (once per invoice).
        *   *Wrong Total:* $\$100,000 \text{ (true sum)} \times 4 = \mathbf{\$400,000}$
    *   **Invoices:** Each of the 4 original rows is repeated 3 times (once per change order).
        *   *Wrong Total:* $\$1,800,000 \text{ (true sum)} \times 3 = \mathbf{\$5,400,000}$

---

### The Solution: Aggregation Before Joining

To fix this, we must aggregate the child tables (`change_orders` and `invoices`) **individually** first. This reduces them to one row per project, preventing the multiplication effect. We then join these summarized results to the `projects` table.

**The Correct Query (PostgreSQL-Compatible, ANSI-Standard):**

```sql
WITH 
-- 1. Aggregate change orders per project first
project_co_totals AS (
    SELECT 
        project_id, 
        SUM(co_amount) AS total_co_amount
    FROM change_orders
    GROUP BY project_id
),

-- 2. Aggregate invoices per project first
project_inv_totals AS (
    SELECT 
        project_id, 
        SUM(invoice_amount) AS total_invoice_amount
    FROM invoices
    GROUP BY project_id
)

-- 3. Join the pre-aggregated results to projects
SELECT 
    p.project_id,
    p.project_name,
    COALESCE(co.total_co_amount, 0) AS total_change_orders,
    COALESCE(inv.total_invoice_amount, 0) AS total_invoiced
FROM projects p
LEFT JOIN project_co_totals co ON p.project_id = co.project_id
LEFT JOIN project_inv_totals inv ON p.project_id = inv.project_id;
```

**Rule:** When a parent table has **multiple** one-to-many relationships with different child tables, you must **aggregate the child tables individually** (using `GROUP BY`) **before** joining them together in a single query.

**Why:** If you join the child tables to the parent in the same step, the database combines the row counts of the children (Cardinality Multiplication). Since `SUM()` is applied after the join, the sum is calculated over the multiplied row set, resulting in inflated totals. By aggregating first, you reduce each child to a single row per parent, ensuring the join remains 1-to-1.
