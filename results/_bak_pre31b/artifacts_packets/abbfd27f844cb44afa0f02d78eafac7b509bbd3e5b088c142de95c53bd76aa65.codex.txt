## 10 -- Frontier
The runbook or document is testable: a newcomer could follow it step by step and reach the stated outcome without needing undocumented tribal knowledge. Prerequisites are listed up front, failure or rollback branches are included for steps that can go wrong, and a currency or ownership signal (last verified, owned by) is present when the prompt supports it.
Example character: numbered steps with prerequisites stated first, a rollback note on the one risky step, and a last-verified date.

## 7 -- Strong
The document is mostly step-by-step and usable as a runbook, but is missing one prerequisite check or a failure-branch note for a step that could plausibly fail. Nothing here requires guesswork to follow.
Example character: a clear numbered procedure that omits what to do if the third step fails.

## 5 -- Adequate
The content is a correct-gist prose description of the process rather than an executable, testable runbook -- a new reader would need to reverse-engineer the actual steps.
Example character: a paragraph explaining how the process generally works, without numbered, followable steps.

## 3 -- Weak
The document skips steps a newcomer would need, silently assumes undocumented tribal knowledge, and gives no ownership or currency signal at all.
Example character: a procedure that jumps from step one to step four with an unstated step in between.

## 0 -- Unusable
References fabricated tools, systems, or menu paths that do not exist, or gives a dangerously wrong sequence for a risky operation. Empty or off-task.

Here is a proposal for a file/folder taxonomy and lot-ID scheme that satisfies USDA traceability requirements, eliminates collisions, ensures filename uniqueness, and handles the legacy ambiguity without altering retained records.

## 1. Lot-ID Taxonomy (Prevents Collision, Self-Describing)

**Schema:**
```
{PlantCode}-{LineCode}-{Quarter}-{Counter}
```

**Example:** `USDA-PL01-L2-2024Q3-0042`

**Rules:**
1.  **Line-Prefix:** The Lot ID is anchored by the production line code (`L1`, `L2`, `L3`). This mathematically eliminates collision. If Line 2 and Line 3 both reach counter `0042`, the Lot IDs are `L2-...` and `L3-...`. They are distinct.
2.  **Quarter in ID:** Including the quarter (`2024Q3`) prevents confusion as counters reset; the quarter is part of the identity, not just a folder context.
3.  **Counter Scope:** The counter may reset per-line per-quarter (e.g., `0001` on Line 2 at the start of Q4 is valid) because the Line/Quarter prefix makes the ID globally unique.
4.  **Scanner Action:** The barcode scanner writes the **full** Lot ID to the log. This ensures the log is self-describing.

**Why this works for USDA:**
*   **Uniqueness:** No two physical lots can share the same string.
*   **Traceability:** A USDA auditor reading the Lot ID can immediately identify the line and quarter without opening the file.
*   **Operator Friendly:** The format is short enough for labels but structured enough for automated systems.

---

## 2. Folder Structure (Partitioned by Line and Time)

**Root:** `/MSP-USDA-Scans/Plant01/`

**Hierarchy:**
```
/Plant01/
├── /Scans/
│   ├── /2024/
│   │   ├── /2024-09/
│   │   │   ├── /L1/
│   │   │   │   ├── ScanLog_20240915T143022_L1_USDA-PL01-L1-2024Q3-0042_Scr01_001.csv
│   │   │   │   └── ...
│   │   │   ├── /L2/
│   │   │   └── /L3/
```

**Rationale:**
*   **Parallel Safety:** Each line writes to its own folder. Even if the naming scheme fails, files cannot overwrite each other because the destination path is unique per line.
*   **Retention:** Quarterly/annual retention policies can be enforced on the date folders.
*   **Audit Navigation:** Auditors can navigate directly to the relevant line and date range.

## 3. Filename Convention (Unique, Self-Describing, Append-Only)

**Pattern:**
```
ScanLog_{ISODateTime}_{LineID}_{LotID}_{ScannerID}_{SeqNum}.csv
```

**Example:**
```
ScanLog_20240915T143022_L2_USDA-PL01-L2-2024Q3-0042_Scr01_001.csv
```

**Components:**
*   `ISODateTime`: Truncated ISO 8601 (e.g., `20240915T143022`). Guarantees uniqueness per scan event.
*   `LineID`: `L1`, `L2`, `L3`. Self-describing context.
*   `LotID`: The full lot ID from Section 1.
*   `ScannerID`: Hardware identifier of the scanner (`Scr01`, `Scr02`). Disambiguates device swaps and aids root-cause analysis.
*   `SeqNum`: Zero-padded sequence within the lot session.

**File Server Policy:**
*   **No Overwrites:** The MSP must enforce an **append-only** policy on this share. If the scanner attempts to write a file that exists, the write must fail or the system must abort. This prevents the "generic filename" overwriting risk from recurring.
*   **Immutable:** Files should be marked read-only after write to preserve evidence integrity for audit.

## 4. Handling Legacy Ambiguous Lot Numbers

**Constraint:** Records from this quarter contain ambiguous Lot IDs (e.g., both Line 2 and Line 3 used `0001` in the CSV content). These records cannot be renamed or altered because product has shipped under those numbers. The label on the product matches the ambiguous ID in the file.

**Strategy:** Do not alter the records. Instead, create a **Disambiguation Registry** and augment the file references to allow the auditor to resolve the ambiguity using the preserved context.

### 4.1. MSP-Level File Renaming (Safe)
The MSP can rename the **files** to append the unique context, provided the internal CSV content (and thus the shipped Lot ID) remains untouched. This makes the retained files unique and self-describing without changing the data.

*   **Before:** `lot_log.csv` (Overwritten/Lost or Ambiguous)
*   **After:** `Legacy_0001_L2_2024Q3_20240915T1430.csv`

The MSP should recover all retained files from this quarter and apply this naming convention, capturing the Line ID and the timestamp of the first scan (which defines the lot start) in the filename. If files were overwritten and lost, they must be flagged as **MISSING** in the registry, not silently discarded.

### 4.2. Disambiguation Registry (`LotID_Disambig_2024Q3.csv`)
The MSP creates a metadata sidecar file in the root audit folder. This registry bridges the gap for any audit of this quarter.

**Format:**
```csv
LegacyLotID,Quarter,ResolvedLineID,FirstScanTimestamp,RetainedFileName,FileHash
0001,2024Q3,L2,2024-09-15T14:30:22,Legacy_0001_L2_2024Q3_20240915T1430.csv,a3f2b...
0001,2024Q3,L3,2024-09-15T16:10:05,Legacy_0001_L3_2024Q3_20240915T1610.csv,b8c1d...
```

**Rules:**
*   **Authoritative:** Any query for `0001` in Q3 must consult this registry. The registry proves that `0001` is not a single lot but two distinct lots resolved by Line and Time.
*   **Product Alignment:** Since product shipped under `0001`, the registry confirms that for any specific shipment, the auditor can determine which line's record applies based on the production timestamp. If Line 2 produced at 14:30 and Line 3 produced at 16:10, a shipment shipped at 15:00 corresponds to Line 2.
*   **Integrity:** The `FileHash` column ensures the retained file has not been tampered with since the registry was created.

### 4.3. Operational Warning
A prominent notice must be placed on the lot-numbering documentation:
> *"For Q3 2024, Lot IDs `0001` through `N` are ambiguous across lines. All lot identification queries must reference the `LotID_Disambig` registry. Future lots use the new `Line-Prefix` schema which does not require disambiguation."*

### 1. Lot-ID Taxonomy (Going Forward)

To eliminate collisions and satisfy USDA traceability requirements, the lot identifier must be **globally unique**, **self-describing**, and **independent of arbitrary quarterly resets**.

**Proposed Format:**
```text
USDA[PlantCode]-[LineCode]-[YYYYMMDD]-[4DigitSequence]
```

*   **`[PlantCode]`**: The USDA Establishment Number (e.g., `12345`). This anchors the ID to the physical facility.
*   **`[LineCode]`**: A fixed 1-2 character code per line (e.g., `L1`, `L2`, `L3`). This immediately differentiates parallel production streams.
*   **`[YYYYMMDD]`**: The production date. This replaces the ambiguous quarterly counter with a time-bound sequence. It allows auditors to verify lot freshness and prevents cross-quarter ambiguity.
*   **`[4DigitSequence]`**: A daily counter per line (e.g., `0001` to `9999`). This retains the operator's familiarity with a 4-digit counter while ensuring uniqueness because the date and line differentiate any two lots.

**Examples:**
*   Line 1, Oct 25, 42nd lot of the day: `USDA12345-L1-20231025-0042`
*   Line 2, Oct 25, 42nd lot of the day: `USDA12345-L2-20231025-0042`
*   **Result**: No collisions across lines or time. The ID is unique by construction.

### 2. File & Folder Naming Scheme

Files must be **unique**, **self-describing**, and **isolated** to prevent overwrites. The naming convention embeds all critical metadata in the path and filename so no file needs to be opened to verify its content.

**Folder Structure:**
```text
/LotTracking/[YYYY]/[MM]/[DD]/[LineCode]/
```
*   *Example*: `/LotTracking/2023/10/25/L1/`
*   **Benefit**: Folder isolation prevents race conditions where scanners on different lines attempt to write to the same file. It also organizes data chronologically for easy audit retrieval.

**Filename Format:**
```text
[LOTID]_scans_[YYYYMMDD_HHMMSS].csv
```
*   **`[LOTID]`**: The full Lot-ID from the taxonomy.
*   **`_scans_`**: Static descriptor indicating file type.
*   **`[YYYYMMDD_HHMMSS]`**: Timestamp of the final write/completion. This guarantees uniqueness even if multiple logs exist for the same lot (e.g., re-scans) and allows recovery of the exact generation time.

*   *Example*: `USDA12345-L1-20231025-0042_scans_20231025_143205.csv`

**Self-Describing Check:**
Without opening the file, an auditor or MSP can see:
1.  **Plant**: USDA12345
2.  **Line**: L1
3.  **Date**: Oct 25, 2023
4.  **Lot**: 0042
5.  **Type**: Scans
6.  **Time**: Completed at 14:32:05

## 1. New File Naming Convention

**Format:** `[PlantCode]_[YYYYMMDD]_[LineID]_[LotNumber]_[HHMMSS].csv`

**Example:** `PoultryPlant_20231001_L1_0001_143000.csv`

*   **`LineID`:** Three-character code (e.g., `L1`, `L2`, `L3`). This is the critical disambiguation field that separates production lines.
*   **`LotNumber`:** The internal lot counter (e.g., `0001`).
*   **`HHMMSS`:** Timestamp of the scan initiation. Provides a unique tie-breaker if two lines produce the same lot on the same day.

## 2. New Lot-ID Taxonomy

**Current Scheme (Broken):** `NNNN` (4-digit counter, resets quarterly, independent per line).
*   **Collision Risk:** `L1-0001` and `L2-0001` share the same short code.

**New Scheme (Resolved):** `[YYYYMMDD]-L{LineID}-NNNN`

*   **Definition:** The "Lot ID" is no longer just the 4-digit counter. It is the composite string: **Date + Line + Counter**.

*   **Line Independence:** Lines can still run at different speeds (the counter resets per line per quarter), but the system-level identifier prevents ambiguity.

Below is a complete, step‑by‑step taxonomy that solves the three problems you highlighted:

1. **Every retained scan‑log file gets a name that is *guaranteed* to be unique** – even if two lines generate a lot at the same instant.  
2. **The name tells you, without opening the file, exactly what it contains** – plant, line, date, quarter, lot‑counter, shift, etc.

4. **Existing, ambiguous lot numbers from the current quarter are left untouched** (they cannot be renamed after product has shipped), but they are *de‑conflicted* in the retained audit trail by adding an immutable “collision‑resolution suffix” that will never be reused for a different physical lot.

## 1. High‑level naming philosophy  

| Element | What it tells you | How it is generated | Example value |
|--------|-------------------|---------------------|---------------|
| **Plant‑ID** | The USDA establishment number or internal plant code | Fixed 3‑digit code | `001` |
| **Line‑ID** | Production line identifier (1‑3 digits) | Fixed per line | `L01` |
| **Year** | Calendar year of the lot | 4‑digit year | `2025` |
| **Quarter** | USDA quarter (Q1‑Q4) | `Q01`‑`Q04` | `Q02` |
| **Lot‑Seq** | *Line‑local* sequential counter that **never resets within a quarter** (starts at 0001 each quarter and increments monotonically) | Incremented each time a new lot is started on that line | `L001` |
| **Date‑Stamp** | ISO‑8601 date the lot started (YYYYMMDD) | Extracted from the first scan record | `20250415` |
| **Shift‑ID** | Optional – “D” (day), “N” (night), “M” (mid) | Fixed per shift schedule | `D` |
| **Collision‑Suffix** | A 2‑character hash derived from the *global* unique lot identifier (see §4) – used only when the same lot‑number would otherwise repeat on a *different* line within the same quarter | Computed from a deterministic hash of Plant‑ID+Line‑ID+Lot‑Seq+Date‑Stamp | `H7` |

The final filename is built as:

```
<PlantID>_<LineID>_<Year>_<Quarter>_<LotSeq>_<DateStamp>_<Shift>_<CollisionSuffix>.csv
```

**Full concrete example**

```
001_L01_2025_Q02_001_20250415_D_H7.csv
```

*If the same lot‑number were generated on another line during the same quarter, the Collision‑Suffix would be different, guaranteeing a unique filename.*

## 2. Why this naming scheme eliminates collisions

* **Lot‑Seq is *line‑local*.** Each line starts its own counter at `001` each quarter and never re‑uses a number that has already been used on that line.  
* **The quarter is part of the filename.** Because the quarter string (`Q01`‑`Q04`) is baked into the name, a lot‑number that was `001` in Q1 can be reused as `001` in Q2 without any conflict.  
* **The Collision‑Suffix ties the filename to the *global* lot identifier.** Even if two lines accidentally start a lot with the same `LotSeq` on the same day, the suffix will differ because it incorporates the line identifier and the hash of the unique lot sequence number (see §4).  
* **The filename is self‑describing.** Anyone glancing at `001_L01_2025_Q02_001_20250415_D_H7.csv` knows:  
  * Plant 001  
  * Line 01  
  * Year 2025, Quarter 2  
  * This is the first lot on that line in the quarter (`001`)  
  * It started on 2025‑04‑15  
  * It was generated during the Day shift (`D`)  
  * The suffix `H7` guarantees uniqueness.

No need to open the file to know what it contains.

## 4. Generating a **globally‑unique lot identifier** (the source of the Collision‑Suffix)

1. **Create a “Lot‑UID”** that is unique across the *entire plant* for the duration of the quarter.  
   *Method:*  
   ```
   LotUID = PlantID + "_" + LineID + "_" + Quarter + "_" + LotSeq + "_" + DateStamp
   ```
   Example: `001_L01_Q02_001_20250415`

2. **Hash the Lot‑UID** with a short, deterministic algorithm (e.g., CRC‑16 or first two characters of an SHA‑256 digest).  
   ```
   CollisionSuffix = Substring( SHA256(LotUID), 0, 2 )   // yields e.g., "H7"
   ```

3. **Store the mapping** `LotUID → CollisionSuffix` in a *read‑only* reference file (e.g., `LotIndex.csv`) that is retained for audit purposes. The mapping never changes, so the suffix can be regenerated at any time and will always point back to the original lot.

Because the hash incorporates **PlantID**, **LineID**, **Quarter**, **LotSeq**, and **DateStamp**, two different physical lots will *never* produce the same suffix on the same line, and two different lines can never generate the same suffix for the same Lot‑UID.
