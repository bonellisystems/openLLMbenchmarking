# Helpdesk -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
Triage priority matches the actual business impact described, and the response tone is consistent with the urgency that priority implies. Troubleshooting steps are ordered from least to most disruptive, a clear escalation path is given for when the fix is out of the agent's scope, and the answer is calibrated about what genuinely needs remote hands or an on-site visit.
Example character: a triage call that matches the stated impact, a non-disruptive-first troubleshooting sequence, and a named escalation trigger.

## 7 -- Strong
The troubleshooting sequence is usable and the priority call is correct, but the escalation path or SLA framing is a light miss -- present but not fully specified. Nothing here jumps to a disruptive step too early.
Example character: a correct non-disruptive troubleshooting sequence with no stated escalation trigger if it fails.

## 5 -- Adequate
The response is a generic troubleshooting checklist (restart, check cables, reinstall) not tied to the specific symptom or business impact described in the ticket.
Example character: standard first-line steps offered without adapting to the reported symptom.

## 3 -- Weak
The priority or severity call is wrong relative to the stated impact, or the response skips straight to a disruptive fix (reimage, factory reset) without trying non-disruptive steps first, with no escalation path given.
Example character: recommends reimaging a device as the first step for a minor, non-blocking symptom.

## 0 -- Unusable
Recommends a data-destructive action (wipe, reformat, delete profile) with no backup step or warning, or fabricates vendor or product behavior presented as known fact. Empty or off-task.

## Unit-specific red flags (deduct hard)
- Destructive troubleshooting step (reimage, factory reset, delete profile) recommended before non-disruptive steps, or with no backup warning.
- Priority/SLA call that does not match the stated business impact.
- No escalation path given when the issue is clearly out of scope.
- Fabricated product or vendor behavior presented as known fact.

## Unit-specific excellence markers
- Triage priority matches the stated business impact.
- Troubleshooting steps ordered least-to-most disruptive.
- Explicit escalation trigger and path given.
- SLA/urgency framing consistent with the ticket's actual severity.


## Task

An architecture firm's senior architect reports that the shared Revit central model (the

## Detailed justification

### 1. Verify the 10 : 00 PM backup
* **Why?** A backup that is itself corrupted will not help. Since the last successful backup was made at 10 : 00 PM, it is the only “known good” data we have that predates the reboot.  
* **How to check:**  
  * Use a backup‑utility feature (many enterprise backup products allow a “restore‑to‑different‑folder” or “quick‑restore”).  
  * Compute a checksum (MD5/SHA‑1) of the backup file and compare it to the checksum of the file on the backup media (if the backup software exposes it).  
  * Check the backup log for any errors during that backup window.  
* **Result:**  
  * **Pass:** proceed to the next step.  
  * **Fail:** either the backup is bad or the backup process failed. In that case the only safe path is to get the file from an earlier, verified backup or to contact Autodesk/BIM‑support for a deeper forensic recovery.  

### 2. Attempt “Open as Read‑Only → Repair” in Revit
* **Why?** Revit’s repair routine is designed to fix corruption that results from abrupt server restarts or power failures. It reads the corrupted file, attempts to rebuild the internal database, and writes a new “clean” copy.  
* **What to look for:**  
  * Does the file open in “Read‑Only” mode? If it does not open at all, the corruption is likely beyond simple repair.  
  * If it opens, does the “Repair” button enable? If it succeeds, you’ll see a progress bar and a “Repair successful” message.  
* **Result:**  
  * **Success:** you now have a clean central file. Sync all local files immediately; the unsynced changes will still be present in the local models and can be merged back.  
  * **Failure or no read‑only option:** proceed to restore from backup.  

### 3. Restore from the 10 : 00 PM backup
* **Why?** A clean restore gives us a known, stable state. The only risk is losing the unsynced changes (the 1 h 40 m window).  
* **What to do:**  
  1. **Notify architects** that the central file will be replaced. Ask them to close Revit, commit any pending local changes, and back up their local files just in case.  
  2. **Stop all Revit worksharing sessions** on the server.  
  3. **Run the restore** (either via the backup software or a manual copy).  
  4. **Verify the file** after restore (open it, check file size, confirm the timestamp).  
  5. **Restart the server services** (if needed).  
  6. **Ask architects** to sync their local files again.  
* **Cost to each architect:**  
  * 1 h 40 m of work lost (the unsynced changes).  
  * Estimated 2–3 h of effort to re‑enter those changes, sync, and re‑validate.  
  * In the worst case, if the unsynced changes were large (e.g., model geometry, families), the effort could be higher.  
* **When it’s acceptable:**  
  * If the unsynced changes are modest or if the architects can re‑enter them quickly (they’re familiar with the model).  
  * If the deadline (26 h) allows for a quick re‑sync and re‑validation.  

### 4. Escalate to Autodesk/BIM‑specialist
* **When to do it:**  
  * **Helpdesk lacks Revit recovery knowledge**: The helpdesk team has not been trained in Revit central‑file internals. Even with a simple “repair” command, they may inadvertently corrupt the file further or lose data.  
  * **Corruption is severe**: The file does not open at all, or repair fails.  
  * **Time pressure and data‑loss risk**: The client presentation is in 26 h. Any delay or additional data loss could jeopardize the deliverable.  
  * **Restore from backup fails**: Either the backup is corrupted or the restore process is too complex for the helpdesk.  
* **What the specialist brings:**  
  * Deep knowledge of Revit’s internal database layout.  
  * Access to Autodesk’s proprietary recovery tools (e.g., Revit Central Model Recovery).  
  * Ability to recover unsynced changes from the corrupted file or from the backup.  
  * Proven methodology to minimize data loss.  
* **If helpdesk can handle**:  
  * They should have a clear procedure (verify backup, attempt repair, restore if needed).  
  * They must keep the architects informed and coordinate the sync process.
