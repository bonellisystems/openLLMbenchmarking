# IT Infrastructure -- scoring anchors (0-10)

Scale: integers 0-10. Anchors define 0/3/5/7/10; use 1-2/4/6/8-9 for answers between anchors.

## 10 -- Frontier
The diagnosis or design is correct and tied to the specific systems, symptoms, and constraints given, with exact commands or configuration for the stated platform rather than generic advice. It includes a rollback or backup step before any risky change, quantifies blast radius and expected downtime, and is calibrated about what still needs on-site or live verification. A maintenance-window or change-freeze constraint mentioned in the prompt is respected, not ignored.
Example character: a targeted fix with the exact command sequence, a stated rollback step, and a note on which part of the environment is affected.

## 7 -- Strong
The technical recommendation is sound and directly usable, with correct commands or configuration for the stated platform. It is missing one of: an explicit rollback plan, a quantified blast-radius/downtime estimate, or a post-change verification step. Nothing here would misdiagnose the problem.
Example character: a correct fix for the stated symptom that does not spell out how to undo it if it goes wrong.

## 5 -- Adequate
The direction is correct but the advice reads as a generic troubleshooting checklist rather than being tailored to the specific hardware, software, or symptoms given. An engineer would need to fill in the exact commands and confirm the environment before acting.
Example character: "check logs, restart the service, verify connectivity" offered without adapting to the platform named in the prompt.

## 3 -- Weak
The answer misdiagnoses the stated problem, ignores an explicit constraint (no maintenance window, no downtime allowed, specific hardware), or jumps to a disruptive fix without trying safer steps first.
Example character: recommends a reboot or reinstall as the first step on a production system the prompt flagged as always-on.

## 0 -- Unusable
Recommends a destructive action (wipe, factory reset, force-delete) with no backup or rollback warning, or invents command syntax or vendor behavior that does not exist. Empty or off-task response.

## Unit-specific red flags (deduct hard)
- Destructive commands (rm -rf, drop database, factory reset, force reformat) with no backup or rollback step.
- Fabricated CLI flags, config keys, or vendor documentation presented as real.
- Ignoring a stated production, change-freeze, or maintenance-window constraint.
- No mention of testing a risky change in non-production first.
- Treating a symptom fix as a root-cause fix without saying so.

## Unit-specific excellence markers
- Explicit rollback or backup step before any risky change.
- Blast radius and expected downtime called out in concrete terms.
- Exact commands or configuration syntax for the stated platform.
- Maintenance-window and change-freeze awareness.
- Post-change verification or monitoring step included.

   Get-MoveRequest -Identity "user@firmb.com" | Remove-MoveRequest -Confirm:$false

## 2. Changes That Must Happen ONLY AFTER Both Permit Deadlines

The following changes carry the highest risk of breaking Xref links or forcing user logoff mid-work. **None of these may occur until both permit submissions are complete.**

1.  **Changing the File Share Path or Name:** Any modification to `\\FIRMB-FS01\Projects\...` (e.g., renaming to `\\FIRMA-FS01\...`) breaks absolute Xref paths immediately. Open drawings will fail to load Xrefs.
2.  **Changing User Mailbox / UPN:** Per the consolidation risk profile, changing the UPN triggers credential refresh loops or forced logoffs that can corrupt active AutoCAD sessions and break Xref references tied to mapped drives or session state.
3.  **Forcing Password Resets / Logoff Scripts:** Any AD Group Policy or migration step that forces a password change or logs users off breaks active work.
4.  **Removing the Source File Server:** The source `\\FIRMB-FS01` must remain online and accessible until Day +2 post-deadline to allow safe cutover.
5.  **Updating Xref Bindings:** External references must not be re-linked or bound until the new path is live and permits are closed.

## 3. Rollback Approach: Mailbox Migration Batch Failure

If a migration batch fails partway through, the following rollback procedure prevents data loss and stops the cascade to subsequent batches.

### Immediate Response
1.  **Pause:** Stop all pending migration batches immediately via the Exchange Admin Center or PowerShell:
    ```powershell
    Get-MigrationBatch | Where-Object {$_.Status -eq 'Queued' -or $_.Status -eq 'InProgress'} | Stop-MigrationBatch
    ```
2.  **Assess:** Check the failed batch status and error details:
    ```powershell
    Get-MigrationBatch -Identity "FirmB_MailboxBatch_03" | Get-MigrationBatchSummary
    ```
3.  **Preserve State:** If the batch is `InProgress`, the source mailboxes are in a partial move state. Do not restart the batch immediately.

### Rollback Execution
If the failure cannot be resolved within the maintenance window, or if data consistency is at risk, rollback the affected mailboxes to the source:

1.  **Remove Failed Batch:**
    ```powershell
    Remove-MigrationBatch -Identity "FirmB_MailboxBatch_03" -Confirm:$false
    ```
2.  **Move Mailboxes Back to Source:**
    Initiate reverse move requests to restore Firm B's tenant (or local mailbox database if on-prem source remains).
    ```powershell
    $Users = Get-MigrationUser -BatchId "FirmB_MailboxBatch_03"
    foreach ($User in $Users) {
        New-MoveRequest -Identity $User.Identity -TargetDeliveryDomain "firmB-source.onmicrosoft.com" -MoveToOfflineDatabase:$false
    }
    ```
    *Note: Adjust `TargetDeliveryDomain` or `TargetDatabase` to match the actual Firm B source configuration.*
3.  **Monitor Rollback:**
    ```powershell
    Get-MoveRequest -MoveStatus InProgress | Get-MoveRequestStatistics
    ```
4.  **Verify:** Confirm all rolled-back mailboxes reach `Completed` status. Ensure users can log in and access data in the source state.

### Resume Strategy
*   Do not proceed with Batch 04 or subsequent batches until the failed batch is fully rolled back and root cause is identified.
*   Investigate failure (e.g., license conflicts, sync issues, size limits).
*   Apply fix and resume migration in smaller sub-batches (e.g., 5 users) rather than the original batch size.

### 4. Rollback Approach: Mailbox Migration Batch Failure

1.  **Stop the Batch:**

    *   Identify failure reason (e.g., throttling, large items, corruption).
4.  **Remediate & Resume:**
    *   Address the root cause (e.g., increase throttling limits, quarantine large items).
    *   Re-initialize the migration batch.
    *   **Crucial:** Ensure UPN preservation settings are re-confirmed in the new batch configuration.
5.  **Communication:**
    *   Notify the affected users that a migration error occurred and data is being restored. Reassure them that their UPN and file paths are unchanged, so their active drawings are safe.

    *   **NO** file migrations.

    *   **NO** UPN or mailbox changes for any user assigned to the two critical projects.
2.  **Monitoring:** IT staff monitors the file share for any unauthorized file moves or permission changes.

### **III. Phase 3: Post-Deadline Migration (Day 11+)**
*Goal: Complete the consolidation once the legal risk is cleared.*

1.  **Step 1: Engineer Mailbox Migration:** Migrate the engineers working on the permits. (Note: Perform this on a Friday evening to minimize mid-drawing disruption).
2.  **Step 2: File Share Migration:**
    *   Perform a final data sync (using Robocopy or a migration tool) from `\\FIRMB-FS01\Projects` to the new Firm A storage.
    *   **Crucial Step (The Xref Fix):** Instead of telling engineers to change their AutoCAD settings, create a **DFS Namespace** or a **Symlink** on the old server. 
    *   Configure `\\FIRMB-FS01\Projects` to point to the new physical location `\\FIRMA-STORAGE\Projects`. 
    *   *Result:* AutoCAD still looks at the "old" path, but the data is physically residing on the new Firm A hardware.

## 4. **Rollback Approach for Mailbox Migration (Batch‑Level)**  

### 4.1 Preconditions for a Rollback

| Condition | How to Verify |
|-----------|----------------|
| **MoveRequest status** is *Completed* or *Failed* for the batch in question. | `Get-MoveRequestStatistics -Identity <batch‑guid>` |
| **Backup of source mailboxes** exists (native Exchange Online retention + on‑prem backup if applicable). | Confirm **mailbox export** logs or **Veeam/Azure Backup** snapshots taken pre‑migration. |
| **No critical email has been sent/received** from the migrated mailboxes after the batch completed (or a “hold” period of 2 h has passed). | Check **Message Trace** in Exchange Admin Center for the batch window. |

### 4.2 Step‑by‑Step Rollback Procedure

1. **Identify the Failed Batch**  
   - Retrieve the **batch GUID** from the migration log created in Phase B‑4. Example: `BatchA-20230831-01`.  

2. **Place Source Mailboxes on **Mailbox **Hold** (if not already)**  
   - Run:  
     ```powershell
     New-MailboxSearch -Name "Hold-<BatchID>" -SourceMailboxes <list-of‑source‑mailboxes> -ResultSize Unlimited -InPlaceHoldEnabled $true
     ```  
   - This prevents any deletions or modifications while we revert.  

3. **Cancel the Move Requests** (if still in *InProgress* state)  
   - For each mailbox in the batch:  
     ```powershell
     Remove-MoveRequest -Identity <User@firmB.com> -Confirm:$false
     ```  
   - Verify status returns to **Queued** (i.e., not migrating).  

4. **Re‑enable the Original Mailboxes**  
   - If the source mailboxes were **soft‑deleted** (common in a remote move), restore them:  
     ```powershell
     Connect-ExchangeOnline -UserPrincipalName admin@firmB.com
     Get-Mailbox -SoftDeletedMailbox -ResultSize Unlimited | Where-Object {$_.DisplayName -in <list>} | Restore-Mailbox -SourceStoreMailbox <OriginalGUID>
     ```  
   - Alternatively, if the source mailbox still exists in Firm B’s on‑prem AD, simply **reactivate** the AD account and ensure **Directory Synchronization** re‑creates the link.  

5. **Update Azure AD / UPN** (if UPN change already applied)  
   - Revert the UPN to the original value (`user@firmB.com`). Use:  
     ```powershell
     Set-AzureADUser -ObjectId <userObjectId> -UserPrincipalName user@firmB.com
     ```  
   - Notify the user to re‑login; the password remains unchanged.  

6. **Notify Affected Users**  
   - Send an automated email (template) informing them that the mailbox migration was rolled back, instructing them to continue using their original address, and providing a **support ticket** link for any issues.  

7. **Post‑Rollback Validation**  
   - Run a **mail flow test** for each mailbox (send a test message from an external address, verify receipt).  
   - Check **calendar/appointment** continuity (no loss of appointments that were in‑flight during the move).  

8. **Document the Incident**  
   - Record **root cause** (e.g., network timeout, corrupt PST, permission error) in the **Change Management System** (e.g., ServiceNow).  
   - Append the **rollback log** to the project repository for audit purposes.  

### 4.3 Rollback Success Criteria

- **All mailboxes** in the failed batch are back in their **original source tenant** with the **original UPN**.  
- **No data loss**: mail items, calendars, contacts, and rules are identical to pre‑migration state (validated via mail‑item counts and sample content checks).  
- **User experience**: users can send/receive email immediately after the rollback without additional configuration.

## 5. Rollback Plan: Mailbox Migration Batch Failure
*Scenario:* During Batch 3 of the mailbox migration, 5 out of 9 users fail to migrate (e.g., due to duplicate object errors, license conflicts, or sync failures).

### Immediate Action
1.  **Stop the Batch:** Abort the remaining users in Batch 3 immediately. Do not attempt to force-complete the failed users.
2.  **Hold Remaining Batches:** Do **not** proceed to Batch 4 or Batch 5 until Batch 3 is fully resolved.

### Isolation Strategy
1.  **Preserve Legacy State:** The 5 failed users remain on their original mailboxes (Firm B's original tenant or legacy accounts). Their email and Outlook profiles remain untouched.
2.  **No Xref Risk:** Since these users have not had their UPN changed or mailbox moved, their Xref links remain intact on `FIRMB-FS01`.
3.  **Diagnostic:** IT Admins review the migration logs to identify the specific failure reason (e.g., password hash mismatch, mailbox full, object not found).

### Recovery
1.  **Re-Attempt Failed Users:** Once the root cause is identified and fixed, re-run the migration for **only the 5 failed users**.
2.  **Validation:** Verify the 5 users can send/receive and that their Outlook profiles load without error.
3.  **Re-Attempt Remaining Batch:** Once Batch 3 is clean, proceed to Batch 4.

### Full Rollback (Worst Case)
If the mailbox migration fails entirely and cannot be recovered:
1.  **Revert UPNs:** Revert all migrated users' UPNs back to their original `@firmb.com` identity (if cross-tenant migration was used).
2.  **Decommission M365 Changes:** Remove the temporary accounts from Firm A's tenant.
3.  **File Share:** Since the file share migration (Step 1) was completed in a separate phase, the UNC paths on the file share remain valid regardless of mailbox status.
4.  **Status:** Firm B users retain full email and file access via their original accounts. The consolidation is paused for a future window.

| Change | Reason it Must Wait |
|--------|---------------------|
| **Rename or decommission `\\FIRMB‑FS01`** (share name or server name) | Changing the UNC path breaks every AutoCAD Xref that was written to that share. |
| **Alter DNS / NetBIOS name resolution for `FIRMB‑FS01`** | Same as above – resolves to a new IP/host would invalidate all open drawings. |
| **Remove the temporary read‑only protection** on the original share before the deadlines | If a user accidentally saves while the share is still read‑only, the Xref would still be fine; removing protection early *does not* break links, but the *rename* does. |
| **Delete the old on‑prem file server from the domain** | The server holds the original security descriptors; removal would orphan permissions and break access for users who still rely on the old SID mapping. |
| **Migrate the last batch of mailboxes** while a user has an open drawing referencing the share **and** the share is still in “read‑only” mode? | Actually the migration of mailboxes can proceed anytime **as long as the share path is unchanged**; however, the *final cut‑over* of the share cannot. |
| **Apply any post‑migration GPO changes that reference the old server** | Same Xref‑risk applies. |

## 5.  Rollback Approach for a Failed Mailbox Migration Batch  

### 5.1  Failure Detection  

| Trigger | Action |
|--------|--------|
| SPMT reports **> 5 % failed items** in a batch (e.g., “Mailbox not mounted”) | Migration job aborts automatically; migration console shows **Failed** status. |
| Exchange Online **mail‑flow errors** (undeliverable messages) | Immediate rollback flag raised. |
| **User‑reported** missing items after activation | Ticket opened; rollback initiated. |

### 5.2  Rollback Steps  

1. **Pause further migration activity** – stop the batch scheduler.  
2. **Restore the source mailboxes** from the **pre‑migration PST backup** taken at the start of the migration (Veeam/Commvault snapshot).  
   * Command example (PowerShell):  

   ```powershell
   Import-Mailbox -PstFolderPath \\BackupServer\MailboxBackups\<User> -TargetMailbox <User> -IsStaged
   ```  

3. **Re‑apply mailbox permissions & mailbox policies** from the exported configuration (AD permissions, retention tags).  
4. **Update the migration dashboard** to reflect “Rollback completed – source state restored”.  
5. **Notify stakeholders** (IT, business leads) with a short incident report.  
6. **Resume migration** after root‑cause analysis and after any required **remediation** (e.g., adjust throttling, adjust target mailbox size).  

### 5.3  Time‑Line Goal  

| Step | Max Allowed Duration |
|------|----------------------|
| Detect failure & stop migration | < 5 min |
| Retrieve latest backup (VSS snapshot) | < 15 min (network‑attached storage) |
| Restore mailboxes to original state | < 45 min (average 10 GB per mailbox) |
| Validate restored mailboxes (item count, OOF) | < 15 min |
| Resume migration (new batch) | At discretion of migration lead |

**Rollback Success Criteria:**  
- All restored mailboxes contain **100 %** of original items (verified via `Get‑MailboxFolderStatistics`).  
- No duplicate messages or missing calendar events.  
- No increase in mail‑flow errors.  

If the rollback cannot be completed within **2 hours**, the incident escalates to the **Incident Management** team for a full service‑wide restore from the **full‑system backup** (which would involve a longer downtime but guarantee data integrity).

By **preserving the original UNC path** through a transparent front‑end share until **both permit deadlines have elapsed**, we guarantee that AutoCAD drawings stay linked and that engineers can continue to submit permits without interruption.
